Section 7

Virtual threads and structured concurrency

Every thread you have met so far in this module is a platform thread: a thin wrapper over an operating-system thread, with a stack reserved up front (half a megabyte or more), created and scheduled by the kernel. That is why §5 taught you to pool them: you can afford a few hundred, not a few hundred thousand, and the thread-per-request server that is the simplest thing to write runs out of threads long before it runs out of CPU. §6 was one response to that — stop blocking, describe the work as a pipeline of callbacks, let a small pool execute it. It works, and it is hard to read, debug, and cancel.

Java 21's answer (JEP 444) is to make the thread itself cheap. A virtual thread is a thread whose stack lives on the heap as an ordinary object and which is scheduled not by the kernel but by the JVM, onto a small pool of platform threads called carriers. When a virtual thread blocks — on a socket, a sleep, a lock from java.util.concurrent — the JVM copies its frames off the carrier (unmounts it), and the carrier picks up another virtual thread. When the I/O completes, the virtual thread is mounted again on whichever carrier is free. The cost of a blocked virtual thread is a few hundred bytes of heap. You can have a million of them. And the code you write is the sequential, blocking code from Fundamentals, with no callbacks at all.

Worked example

Ten thousand pickers each wait ten milliseconds for a scanner. On platform threads that is either a 100-second sequential run or ten thousand OS threads. On virtual threads it is neither.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.LongAdder;
import java.util.concurrent.locks.ReentrantLock;

public class VirtualThreads {
    public static void main(String[] args) throws Exception {
        LongAdder done = new LongAdder();
        LongAdder virtualInside = new LongAdder();

        long t0 = System.nanoTime();
        try (ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 10_000; i++) {
                ex.submit(() -> {
                    Thread.sleep(10);                               // a blocking call: the thread unmounts
                    if (Thread.currentThread().isVirtual()) virtualInside.increment();
                    done.increment();
                    return null;
                });
            }
        }                                                           // close() waits for every task
        long seconds = (System.nanoTime() - t0) / 1_000_000_000L;
        System.out.println("tasks completed       = " + done.sum());
        System.out.println("all ran virtual       = " + (virtualInside.sum() == 10_000));
        System.out.println("100 s of sleeps took under 30 s = " + (seconds < 30));

        Thread picker = Thread.ofVirtual().name("picker-", 0).unstarted(() -> { });
        System.out.println("isVirtual             = " + picker.isVirtual());
        System.out.println("isDaemon              = " + picker.isDaemon());
        System.out.println("name                  = " + picker.getName());
        System.out.println("priority              = " + picker.getPriority() + " (always NORM_PRIORITY)");
        System.out.println("platform isVirtual    = " + Thread.ofPlatform().unstarted(() -> { }).isVirtual());

        // ThreadLocal is per thread, virtual or not. That is what makes it expensive at a million threads.
        ThreadLocal tenant = ThreadLocal.withInitial(() -> "unset");
        Thread vt = Thread.startVirtualThread(() -> tenant.set("warehouse-A"));
        vt.join();
        System.out.println("main sees ThreadLocal = " + tenant.get());

        // A j.u.c. lock parks the virtual thread and frees its carrier for someone else.
        ReentrantLock lock = new ReentrantLock();
        LongAdder counter = new LongAdder();
        try (ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000; i++) {
                ex.submit(() -> { lock.lock(); try { counter.increment(); } finally { lock.unlock(); } });
            }
        }
        System.out.println("locked increments     = " + counter.sum());
    }
}

On the machine this page was built on, the ten thousand sleeps finished in well under a second; the output says "under 30 s" only because a verified output must be true on any machine. Read the rest of it:

  • newVirtualThreadPerTaskExecutor creates a thread per task and never reuses one. It is an ExecutorService, so the submit/shutdown API from §5 is unchanged, and it is AutoCloseable: the try-with-resources block ends only when every task has finished. That is the simplest form of structured concurrency — the tasks cannot outlive the block that started them.
  • Virtual threads are always daemon threads with normal priority, and setDaemon(false) or setPriority on one is ignored or rejected. The JVM does not wait for them at exit; your executor's close does.
  • ThreadLocal works exactly as before, which is the problem: a value cached per thread is now cached per task, a million times over. Prefer passing context as parameters, and watch for scoped values (ScopedValue, preview in 21, final in a later release) which were designed for this.
  • A ReentrantLock unmounts cleanly. A thousand virtual threads contended for one lock; each one that had to wait was parked off its carrier, so the carriers kept serving others. The same program with a synchronized block behaves differently in 21, as the next part shows.

Mounting, parking and pinning

The scheduler is a ForkJoinPool whose size defaults to the number of cores. Those are the carriers. Watch what happens to them under three kinds of task, with a handful of carriers and many virtual threads.

Virtual threads on carriers Simulated

The three cases are the whole story of when virtual threads help:

  • Blocking I/O is the design target. Each virtual thread needs a carrier only for its two ticks of CPU; while it waits, its carrier serves someone else. Throughput is bounded by the I/O, not by the thread count, and two carriers finish sixty-four tasks almost as fast as sixty-four would.
  • CPU-bound work gains nothing. A virtual thread that never blocks never unmounts, so at most carriers tasks progress at once — exactly the fixed pool of §5, with extra bookkeeping. Virtual threads do not create parallelism; they make waiting cheap.
  • Pinning is the trap in Java 21. A virtual thread that blocks while holding a monitor (synchronized) or inside a native frame cannot be unmounted, so its carrier sits idle for the whole wait. With a handful of carriers, a few pinned threads collapse throughput to that of a tiny platform pool. The fix in 21 is to use ReentrantLock on blocking paths; JEP 491 (Java 24) removes the synchronized limitation. -Djdk.tracePinnedThreads=full prints a stack whenever it happens.

Underneath is a continuation: the JVM can freeze a running frame stack into an object and thaw it later on any carrier. That mechanism is internal, but it explains why a virtual thread's identity, stack trace and ThreadLocals survive a move from one carrier to another.

A pool exists to amortise the cost of creating a thread. A virtual thread costs about as much as a small object, so pooling it saves nothing and loses the one-task-per-thread model that makes stack traces and cancellation make sense. The rule is: never pool virtual threads; create one per task, and if you need to limit concurrency on a scarce resource — a database that allows 50 connections — limit that with a Semaphore, not by capping the threads.

// WRONG: a fixed pool of virtual threads caps concurrency for no benefit
ExecutorService wrong = Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());

// RIGHT: one virtual thread per task; bound the scarce resource instead
Semaphore dbSlots = new Semaphore(50);
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Order o : orders) {
        ex.submit(() -> {
            dbSlots.acquire();
            try { return reserve(o); } finally { dbSlots.release(); }
        });
    }
}

Cheap is not free. Each virtual thread still allocates its stack chunks on the heap and still carries its ThreadLocal map, so a million threads each caching a 1 MB buffer in a ThreadLocal is a terabyte. Audit what libraries stash per thread before you turn the dial up.

Cheap threads make a new discipline affordable: a task that forks sub-tasks waits for all of them before it returns, so the sub-tasks are scoped to a block like local variables. If one fails, the others are cancelled; if the parent is cancelled, so are the children; a thread dump shows the tree. StructuredTaskScope is a preview API in Java 21 (JEP 453; it needs --enable-preview, so this block is not compiled at build time) and the shape is:

// PREVIEW in Java 21 — requires --enable-preview; shape only
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask price = scope.fork(() -> priceService.lookup(sku));
    Subtask stock = scope.fork(() -> stockService.lookup(sku));

    scope.join()            // wait for both
         .throwIfFailed();  // rethrow the first failure, after cancelling the other

    return new Quote(sku, price.get(), stock.get());
}   // leaving the block guarantees no sub-task is still running

Compare this with the thenCombine of §6: same two lookups, but the code reads top to bottom, the failure propagates as a normal exception on the caller's thread, and cancelling the lost sibling is automatic. Until the API is final, newVirtualThreadPerTaskExecutor in a try-with-resources gives you the "cannot outlive the block" half of the guarantee today.

A classic jstack dump lists platform threads only, and a million virtual threads would not fit in it anyway. The JDK 21 tools:

# every thread, grouped by the executor / scope that owns it, as JSON
jcmd <pid> Thread.dump_to_file -format=json threads.json

# JFR records virtual-thread starts, ends and pinning events
java -XX:StartFlightRecording=filename=rec.jfr ... MyApp
jfr print --events jdk.VirtualThreadPinned rec.jfr

# print a stack trace whenever a virtual thread pins its carrier
java -Djdk.tracePinnedThreads=full MyApp

Two knobs you will meet: -Djdk.virtualThreadScheduler.parallelism sets the carrier count (default: cores), and -Djdk.virtualThreadScheduler.maxPoolSize caps the extra carriers the scheduler may add temporarily to compensate for pinned ones.

Where teams get burnt in the first month
  • synchronized on a blocking path. A JDBC driver or an old HTTP client that synchronises around socket reads pins every carrier it touches. Check the libraries before you check your own code; the pinned-threads trace will tell you.
  • Unbounded fan-out. "One thread per task" with no limit on tasks means one virtual thread per row of a ten-million-row table, all of them opening a connection. Virtual threads remove the thread limit, not the limits of the things the threads talk to.
  • Expecting speed-ups on CPU work. A parallel sort does not get faster on virtual threads; it may get slower. Keep the §5 fixed pool for compute.
  • Relying on daemon semantics. The JVM exits while virtual threads are still running. Always own them in an executor you close, or join them.
  • Thread-identity assumptions. Code that keyed caches or locks by thread, or counted "active threads" to size itself, now sees a different thread for every request. That is usually a sign the design was leaning on the pool.

Check yourself

1.A service does CPU-heavy price optimisation, no I/O. It moves from a fixed pool of 8 platform threads to one virtual thread per request on an 8-core box. What happens to throughput?

B. A virtual thread that never blocks never unmounts, so only as many run as there are carriers — eight, the core count. The CPU was the bottleneck before and still is. Virtual threads make waiting cheap; they do not add cores.

A describes an I/O-bound service, where the old pool spent most of its time blocked. C: they run any code; they just cannot be descheduled mid-computation. D is invented; the scheduler is an ordinary ForkJoinPool of platform threads.

2.In Java 21 a virtual thread calls socket.read() inside a synchronized method. Which is true while the read waits?

C. In 21 the monitor's ownership is tied to the carrier's native frame, so the virtual thread cannot be unmounted while it holds one. The scheduler may compensate by adding a temporary carrier, up to maxPoolSize, but under load the effect is a tiny platform pool. ReentrantLock avoids it; JEP 491 in Java 24 fixes it for synchronized too.

A is true for java.util.concurrent locks and for blocking calls outside a monitor. B: monitors work; they just pin. D: nothing converts thread kinds; a virtual thread stays virtual.

3.Which statements about Executors.newVirtualThreadPerTaskExecutor() are true? Select all that apply.

A and C. The name says it: a thread per task, unbounded, never reused. close() (which try-with-resources calls) shuts the executor down and waits for termination, which is what makes the worked example's counts reliable.

B is a fixed pool; there is no queue here because there is no reason to wait for a thread. D is backwards: virtual threads are daemon threads, so an un-closed executor's tasks die with the JVM — the opposite of a platform pool, which keeps the JVM alive until you shut it down.
