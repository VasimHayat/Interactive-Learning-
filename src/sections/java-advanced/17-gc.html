Section 8

Garbage collection: generations, G1 and ZGC

Fundamentals §1 said the JVM frees memory for you and left it there. The mechanism matters the day a service that was fine for a month starts pausing for two seconds, or dies with OutOfMemoryError at 3 a.m. with plenty of RAM on the box. Both are garbage-collection stories, and both are diagnosable once you know what the collector is doing.

The collector's job has one definition: an object is reachable if some chain of references leads to it from a root — a local variable or operand on any thread's stack, a static field, a JNI handle, a few JVM-internal structures. Everything else is garbage, and the collector may reclaim it at any time. It does not count references (cycles would leak), it does not run when you call System.gc() (that is a hint), and it does not know what your object "means"; it only knows whether anything can still get to it. The entire section follows from that definition plus one empirical fact: most objects die young.

Worked example

The four reference strengths, a root that keeps an object alive no matter what, a map whose entries vanish with their keys, and the modern replacement for finalize(). Every System.gc() here is a request in a bounded loop, and the program prints facts, never sizes.

import java.lang.ref.Cleaner;
import java.lang.ref.Reference;
import java.lang.ref.ReferenceQueue;
import java.lang.ref.SoftReference;
import java.lang.ref.WeakReference;
import java.util.Map;
import java.util.WeakHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.function.BooleanSupplier;

public class Reachability {

    static final class Pallet {
        final String sku;
        Pallet(String sku) { this.sku = sku; }
    }

    static Pallet pinned;                                   // a static field is a GC root

    // System.gc() is a request, not a command. Ask repeatedly, with a bound, and report the fact.
    static boolean gcUntil(BooleanSupplier condition) throws InterruptedException {
        for (int i = 0; i < 50 && !condition.getAsBoolean(); i++) {
            System.gc();
            Thread.sleep(20);
        }
        return condition.getAsBoolean();
    }

    public static void main(String[] args) throws Exception {
        // 1. Weak: cleared as soon as nothing strong reaches the object.
        ReferenceQueue queue = new ReferenceQueue<>();
        Pallet p = new Pallet("BOLT-7");
        WeakReference weak = new WeakReference<>(p, queue);
        System.out.println("weak while a strong ref exists = " + (weak.get() != null));
        p = null;                                           // the last strong reference is gone
        System.out.println("weak cleared after gc          = " + gcUntil(() -> weak.get() == null));
        Reference notified = queue.remove(5_000);
        System.out.println("reference enqueued             = " + (notified == weak));

        // 2. A root keeps it alive no matter how often you ask.
        pinned = new Pallet("GIRD-1");
        WeakReference weakPinned = new WeakReference<>(pinned);
        for (int i = 0; i < 3; i++) System.gc();
        System.out.println("rooted object still reachable  = " + (weakPinned.get() != null));

        // 3. Soft: cleared only under memory pressure, so an idle gc leaves it alone.
        SoftReference soft = new SoftReference<>(new Pallet("CAM-9"));
        for (int i = 0; i < 3; i++) System.gc();
        System.out.println("soft survives an idle gc       = " + (soft.get() != null));

        // 4. WeakHashMap: the entry goes when the key goes.
        Map onHand = new WeakHashMap<>();
        Pallet key = new Pallet("NUT-3");
        onHand.put(key, 1200);
        System.out.println("entries while key is held      = " + onHand.size());
        key = null;
        System.out.println("entries after key dropped + gc = " + (gcUntil(() -> onHand.isEmpty()) ? 0 : onHand.size()));

        // 5. Cleaner: the replacement for finalize(). The action must not capture the object.
        Cleaner cleaner = Cleaner.create();
        CountDownLatch ran = new CountDownLatch(1);
        Runnable release = ran::countDown;                  // captures the latch, not the Pallet
        Pallet handle = new Pallet("ROD-4");
        Cleaner.Cleanable cleanable = cleaner.register(handle, release);
        handle = null;
        gcUntil(() -> ran.getCount() == 0);
        System.out.println("cleaner ran after gc           = " + ran.await(5, TimeUnit.SECONDS));

        CountDownLatch ran2 = new CountDownLatch(1);
        Cleaner.Cleanable explicit = cleaner.register(new Pallet("PIN-2"), ran2::countDown);
        explicit.clean();                                   // deterministic release: call it yourself, from close()
        System.out.println("explicit clean() ran at once   = " + (ran2.getCount() == 0));
        explicit.clean();                                   // idempotent
        cleanable.clean();                                  // already run by the cleaner thread: also a no-op
        System.out.println("repeated clean() is a no-op    = " + (ran2.getCount() == 0));
    }
}

Why finalize() is gone. It ran on an unspecified thread at an unspecified time, could resurrect the object, delayed reclamation by at least one extra cycle, and a slow finalizer stalled every other one behind it. It has been deprecated for removal since Java 18 (JEP 421). Cleaner keeps the one legitimate use — releasing a native resource whose owner forgot to close() — and fixes the design: the cleanup action is a separate object that must not reference the thing being cleaned (or the thing is reachable and never cleaned), it runs at most once, and calling clean() yourself from close() makes release deterministic with the cleaner as a safety net.

Generations, and why copying is cheap

Mark-and-sweep over a whole heap costs time proportional to the heap. The generational hypothesis — most objects die almost immediately, and the ones that survive a while tend to survive a long while — turns that around. Allocate everything in a small young area (eden). When it fills, trace from the roots and copy only the live objects out into a survivor space; everything else is reclaimed by doing nothing at all. The cost is proportional to the survivors, which is a small fraction of what was allocated. Objects that survive enough young collections are promoted to the old generation, which is collected rarely and differently.

Ten seconds of young collections Simulated

Three readings to try. Keep the defaults and note that a collection copies a tenth of what was allocated. Push still alive to 40%: now each young collection is copying almost half of eden and the old generation fills within the run — the hypothesis is false for that workload and no amount of eden helps. Set alive to 20% with a tenuring threshold of 15: the survivor space (an eighth of eden, the JVM's default SurvivorRatio) overflows and objects are promoted early, where they will die in the old generation and cost a far more expensive collection to reclaim. The real flags are -Xmn (young size), -XX:SurvivorRatio and -XX:MaxTenuringThreshold, and the real signal is the GC log in §9.

Which collector, and what it is trading

A collector's two costs are pause time (the application stops while the collector moves things: "stop-the-world", STW) and throughput (CPU spent collecting rather than working). You cannot minimise both. Each collector in the JDK picks a point on that line:

A G1 cycle, region by region

G1 abandons the fixed young/old split of a contiguous heap. The heap is cut into a few thousand equal regions (1–32 MB each), and every region is, at any moment, eden, survivor, old, humongous (one object too large for half a region), or free. Collections pick a set of regions to evacuate, which is how G1 keeps a pause under its target: it evacuates as many as it predicts it can afford.

ZGC: moving objects without stopping

Even G1's pauses grow with the live set, because copying live objects happens while the world is stopped. ZGC copies them while the application runs. Two ideas make that possible. First, coloured pointers: a 64-bit reference has spare bits, and ZGC uses a few of them to record the object's GC state (marked, remapped, relocated). Second, a load barrier: every time the application reads a reference from the heap, a few instructions check those colour bits and, if the object has been moved, fix the reference up to the new address before the application sees it. The application therefore never observes a stale pointer, and the collector can relocate objects at its own pace. The pauses that remain only scan the thread roots, so they stay around a millisecond on a terabyte heap. The price is throughput — those barriers run on every load — and, before generational ZGC, no cheap young collections; -XX:+ZGenerational in Java 21 adds a young generation on top of the same machinery and is the default from Java 23.

Memory leaks in a garbage-collected language

A leak in Java is an object that is still reachable but will never be used. The collector is doing its job; the program is lying to it. The usual suspects:

  • A static or long-lived collection that only grows. A Map<OrderId, Order> "cache" with no eviction. Bound it (Caffeine, LinkedHashMap with removeEldestEntry from Intermediate §11) or key it weakly.
  • Listeners and callbacks never removed. The subject holds the listener, the listener holds its whole object graph. Unsubscribe in close(), or hold listeners through WeakReference.
  • ThreadLocal in a thread pool. The pool thread lives forever, so its thread-local map does too. Always remove() in a finally; §7 showed why this multiplies with virtual threads.
  • Unclosed resources. A stream, connection or socket holds buffers and native memory the heap collector cannot see. Try-with-resources, always (Fundamentals §11).
  • Inner-class and lambda captures. An anonymous listener inside an activity-sized object keeps the object alive (Intermediate §2). Static nested classes capture nothing by accident.

Check yourself

1.A young collection in a copying collector is cheap mainly because…

B. The collector traces from the roots and copies what it reaches; everything it does not reach is reclaimed by simply reusing the region. Under the generational hypothesis most of eden is dead, so most of eden is free. The sandbox shows this breaking down when the survival fraction climbs.

A: the collector does not "scan" eden at all — it never visits dead objects, whatever eden's size. C: young collections in Serial, Parallel and G1 are stop-the-world; only ZGC and Shenandoah collect concurrently. D: they do have references, and those into the old generation are tracked by card tables or remembered sets so the whole old space need not be scanned.

2.You register a native handle with a Cleaner: cleaner.register(this, () -> nativeFree(this.ptr)). What is wrong?

C. The cleaner keeps the action strongly reachable until it runs; the action references this; so this is reachable from a root for as long as the cleaner lives. The object becomes immortal and the handle leaks. The fix is a static nested Runnable holding only the long ptr — exactly why the worked example captures a latch, not the Pallet.

A is the trap the Javadoc warns about in its first paragraph. B: freeing native memory is the main use case. D: there is no finalizer here, and Cleanable.clean() is guaranteed to run the action at most once.

3.A service on a 48 GB heap sees 1.5-second pauses logged as Pause Young (Mixed) under G1. Which responses are sound? Select all that apply.

A and D. A G1 pause is a copy of live objects, so the two levers are "copy them concurrently instead" (ZGC) and "have fewer of them" (a smaller live set, less premature promotion, fewer humongous allocations). Both address the cause.

B: an explicit System.gc() under G1 is a full, stop-the-world collection by default — the longest pause there is, now on a schedule. C: Parallel GC maximises throughput and its old-generation pauses are longer still, since it compacts the entire old space in one stop.
