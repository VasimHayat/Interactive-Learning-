Section 10

Class loading, linking and initialization

Fundamentals §1 said the JVM "loads" a class the first time it is needed. That one word hides three phases with different timing, different failure modes and different rules, and the gaps between them are where some of Java's most confusing errors live: a class that is found but not usable, a static field that reads as zero, a NoClassDefFoundError for a class that is plainly on the class path.

The three phases are loading (find the bytes, parse them, create a Class object), linking (verify the bytecode is well-formed and safe, prepare static fields with their default values, optionally resolve symbolic references), and initialization (run the static initializers, in order). Loading and linking happen when a class is first referenced; initialization is deferred until the class is first actively used — and the JLS lists exactly what counts as active use.

Worked example: when static initializers run

Every static block here prints when it runs. Read the output against the triggers above; the ordering is specified, not accidental.

public class ClassInit {

    static int trace(String what, int value) {
        System.out.println("  init: " + what);
        return value;
    }

    static class Base {
        static int counter = trace("Base.counter", 1);
        static { trace("Base static block", 0); }
    }

    static class Derived extends Base {
        static int level = trace("Derived.level", 2);
        static { trace("Derived static block", 0); }
    }

    static class Lazy {
        static { trace("Lazy static block", 0); }
        static final int SIZE = 8;                 // compile-time constant: inlined by javac
        static int size = 8;                       // a real static field
    }

    static class ViaName {
        static { trace("ViaName static block", 0); }
    }

    static class Holder {
        static { trace("Holder static block", 0); }
        static final Object INSTANCE = new Object();
    }

    interface Config {
        int LIMIT = trace("Config.LIMIT", 10);     // not a constant: initialised on first use
    }

    static class Trap {
        static int first = Trap.second + 1;        // qualified name: legal, reads the DEFAULT 0
        static int second = 5;
    }

    static class Broken {
        static int value = 1 / zero();
        static int zero() { return 0; }
    }

    public static void main(String[] args) throws Exception {
        System.out.println("-- a compile-time constant does not initialise its class --");
        System.out.println("Lazy.SIZE = " + Lazy.SIZE);
        System.out.println("Lazy.size = " + Lazy.size);

        System.out.println("-- superclass first, then subclass, textual order within each --");
        System.out.println("Derived.level = " + Derived.level);

        System.out.println("-- loadClass loads but does not initialise; Class.forName does --");
        ClassLoader app = ClassInit.class.getClassLoader();
        Class loaded = app.loadClass("ClassInit$ViaName");
        System.out.println("loaded " + loaded.getSimpleName() + ", nothing printed yet");
        Class.forName("ClassInit$ViaName", false, app);
        System.out.println("forName(init=false): still nothing");
        Class.forName("ClassInit$ViaName");
        System.out.println("forName(): initialised");

        System.out.println("-- the holder idiom: lazy, thread-safe, no locks --");
        System.out.println("about to touch Holder.INSTANCE");
        Object o = Holder.INSTANCE;
        System.out.println("got instance: " + (o != null));

        System.out.println("-- an interface initialises when a non-constant field is read --");
        System.out.println("Config.LIMIT = " + Config.LIMIT);

        System.out.println("-- forward reference: a static reads a later static's default --");
        System.out.println("Trap.first = " + Trap.first + ", Trap.second = " + Trap.second);

        System.out.println("-- a failing initialiser: two different errors --");
        try {
            System.out.println(Broken.value);
        } catch (ExceptionInInitializerError e) {
            System.out.println("first use : " + e.getClass().getSimpleName()
                    + " caused by " + e.getCause().getClass().getSimpleName());
        }
        try {
            System.out.println(Broken.value);
        } catch (NoClassDefFoundError e) {
            System.out.println("second use: " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }
}

Six facts, one per block of output:

  • Lazy.SIZE printed without initializing Lazy. static final int SIZE = 8 is a compile-time constant, so javac copied the literal 8 into main's bytecode; at runtime Lazy is never consulted. This is also why changing a constant in a library and not recompiling its users leaves them with the old value.
  • Superclass before subclass, and textual order within a class. Field initializers and static blocks are one sequence, executed top to bottom.
  • loadClass and forName(…, false, …) produce a Class object but run no code. Only the one-argument Class.forName initializes — which is why JDBC drivers historically registered themselves from a static block triggered by Class.forName("com.vendor.Driver").
  • The holder idiom is lazy initialization for free. Holder is not initialized until INSTANCE is read, the JVM guarantees initialization happens exactly once even under contention, and no lock is ever visible to you. It beats double-checked locking on every axis.
  • The forward-reference trap. first = second + 1 is a compile error, but first = Trap.second + 1 is legal — and reads the default value 0 that linking's prepare step gave second before any initializer ran. The result is 1, silently.
  • A static initializer that throws poisons the class. The first use gets ExceptionInInitializerError wrapping the real cause. Every later use gets a bare NoClassDefFoundError: Could not initialize class with no cause attached — the class is marked erroneous forever in this JVM. When you see that message in a log, scroll up: the real exception was logged once, earlier, often at start-up.

Who loads what: the loader hierarchy

A class loader is an object that turns a name into a Class. Since JDK 9 there are three built-in ones, arranged parent-first, and each is responsible for a set of modules:

The built-in class loaders
LoadergetName()LoadsParent
Bootstrap— (appears as null)java.base and the core modules: String, Object, collectionsnone
PlatformplatformThe rest of the JDK: java.sql, java.net.http, java.xml…bootstrap
Application (system)appYour class path and module pathplatform

The rule connecting them is parent delegation: a loader asked for a class first asks its parent, and only searches its own sources if every ancestor came back empty. The consequence is that java.lang.String is always the bootstrap loader's String, no matter what jar someone puts on the class path — you cannot replace core classes by shadowing them, which is a security property, not an inconvenience.

import java.io.IOException;
import java.io.InputStream;

public class Loaders {

    /* Follows standard delegation and, once every parent has given up,
       refuses — so the fall-through is visible. */
    static class Strict extends ClassLoader {
        Strict(ClassLoader parent) { super(parent); }
        @Override protected Class findClass(String name) throws ClassNotFoundException {
            System.out.println("  Strict.findClass(" + name + "): parents had no answer");
            throw new ClassNotFoundException(name);
        }
    }

    public static class Twin { public Twin() { } }   // public: the copy lives in a different runtime package

    /* Child-first for one class: defines its own copy from the bytes on the
       class path instead of asking its parent. */
    static class ChildFirst extends ClassLoader {
        ChildFirst(ClassLoader parent) { super(parent); }
        @Override protected Class loadClass(String name, boolean resolve) throws ClassNotFoundException {
            if (name.equals("Loaders$Twin")) {
                try (InputStream in = Loaders.class.getResourceAsStream("Loaders$Twin.class")) {
                    byte[] bytes = in.readAllBytes();
                    return defineClass(name, bytes, 0, bytes.length);
                } catch (IOException e) {
                    throw new ClassNotFoundException(name, e);
                }
            }
            return super.loadClass(name, resolve);
        }
    }

    public static void main(String[] args) throws Exception {
        ClassLoader app = Loaders.class.getClassLoader();
        System.out.println("-- the built-in hierarchy --");
        System.out.println("String's loader is bootstrap (null) : " + (String.class.getClassLoader() == null));
        System.out.println("java.sql.Driver's loader           : " + java.sql.Driver.class.getClassLoader().getName());
        System.out.println("Loaders' loader                    : " + app.getName());
        System.out.println("its parent                         : " + app.getParent().getName());
        System.out.println("the platform loader's parent       : " + app.getParent().getParent());

        System.out.println("-- delegation: parents are asked first --");
        Strict strict = new Strict(app);
        Class s = strict.loadClass("java.lang.String");
        System.out.println("String via Strict is the same Class : " + (s == String.class));
        Class me = strict.loadClass("Loaders");
        System.out.println("Loaders via Strict is the same Class: " + (me == Loaders.class)
                + " (defined by " + me.getClassLoader().getName() + ")");
        try {
            strict.loadClass("com.acme.Missing");
        } catch (ClassNotFoundException e) {
            System.out.println("ClassNotFoundException: " + e.getMessage());
        }

        System.out.println("-- identity is (loader, name): the same bytes loaded twice --");
        Class twin2 = new ChildFirst(app).loadClass("Loaders$Twin");
        System.out.println("same name      : " + twin2.getName().equals(Twin.class.getName()));
        System.out.println("same Class     : " + (twin2 == Twin.class));
        Object copy = twin2.getDeclaredConstructor().newInstance();
        System.out.println("instanceof Twin: " + (copy instanceof Twin));
        System.out.println("named module   : " + Loaders.class.getModule().isNamed()
                + "; String lives in " + String.class.getModule().getName());
    }
}

The last block is the one to remember. ChildFirst read the same .class bytes the application loader had already used and defined them again. The result is a second, unrelated Class object with the same name: a Twin from one loader is not instanceof the Twin from the other, and a cast between them throws ClassCastException with the baffling message "Loaders$Twin cannot be cast to Loaders$Twin". A class's identity is the pair (defining loader, binary name), not the name alone. Application servers and plugin systems exploit this deliberately — a child-first loader per deployment lets two web apps ship different versions of the same library — and it is also why they leak: a loader stays alive as long as any of its classes is reachable, and with it every class it defined and all of their statics.

Two errors that look alike

Both say a class could not be used. They mean opposite things about when it went wrong.

Exception in thread "main" java.lang.ClassNotFoundException: com.acme.Picker
        at java.base/jdk.internal.loader.BuiltinClassLoader.loadClass(BuiltinClassLoader.java:641)
        at java.base/java.lang.Class.forName0(Native Method)
        at java.base/java.lang.Class.forName(Class.java:534)
        at com.acme.Boot.main(Boot.java:12)

Exception in thread "main" java.lang.NoClassDefFoundError: com/acme/Picker
        at com.acme.Boot.main(Boot.java:12)
Caused by: java.lang.ClassNotFoundException: com.acme.Picker
        ... 1 more
  • ClassNotFoundException is a checked exception thrown by an explicit lookup by name — Class.forName, loadClass. The loader searched and found nothing. The fix is a class path or spelling fix.
  • NoClassDefFoundError is an error thrown by the JVM itself when bytecode that compiled against a class cannot resolve it at runtime. Two causes, told apart by the message: with a Caused by: ClassNotFoundException, the class existed at compile time and is missing now — a dependency not shipped, a jar with the wrong version. With "Could not initialize class" and no cause, the class was found but its static initializer failed earlier; look for the ExceptionInInitializerError that preceded it.
Class-loading gotchas
  • Classloader leaks eat Metaspace. A ThreadLocal set from a web app and never removed, a JDBC driver registered in the DriverManager (which lives in the platform loader), a shutdown hook, a static cache in a shared library keyed by an app's class — each pins the app's loader after undeployment. Redeploy ten times and the Metaspace OOM arrives. §9's table has the diagnostics.
  • Static state is per loader, not per JVM. A "singleton" in a library loaded by two child-first loaders is two singletons. Logging frameworks and DriverManager have had decades of bugs from this.
  • Initialization can deadlock. Two classes whose static initializers touch each other, initialized concurrently by two threads, each hold their own initialization lock while waiting for the other's. The JVM does not detect it; a thread dump shows both threads "in <clinit>". Keep static initializers free of cross-class calls.
  • The verifier is not optional. -Xverify:none and -noverify are deprecated for removal because skipping verification lets malformed bytecode corrupt the JVM; the start-up time they saved is now negligible.
  • Resolution is lazy too. A method call to a class that does not exist fails only when that line executes, not when the calling class loads — which is why a missing optional dependency can lurk until a rarely used feature is hit. javap -v shows the constant pool entries that will be resolved.

Check yourself

1.Class Prices has a static block that prints "loaded". Which of these lines prints it?

B. Reading a static field that is not a compile-time constant is active use, and the class is initialized first — even though count is zero and the read looks trivial.

A loads the class (the literal needs a Class object) but does not initialize it. C never touches Prices at runtime: javac inlined 100. D creates an array object whose element type is Prices; the array class is loaded, Prices is not initialized until an element is constructed.

2.A plugin system loads each plugin with its own child-first URLClassLoader. Plugin A returns an Order object to the host, and the host's (Order) result cast throws ClassCastException: com.acme.Order cannot be cast to com.acme.Order. Why?

C. Child-first means the plugin loader defined Order itself instead of delegating to the host's loader. Identity is (loader, name), so the plugin's Order and the host's are two types. The fix is the standard one: shared API classes must live only in the parent, and the child loader must delegate for them.

A is about serialization, which is not involved in a cast. B confuses initialization with type checking; casts never trigger or need initialization. D is false — delegation is the default for every package, and the problem here is that the plugin loader deliberately broke it.

3.A service logs NoClassDefFoundError: Could not initialize class com.acme.RateTable on every request, with no "Caused by". Which statements are true? Select all that apply.

A and D. "Could not initialize class" is the second-and-later failure of a class whose <clinit> threw. The first failure carried the cause as ExceptionInInitializerError; later ones do not. Find the first one.

B would produce a NoClassDefFoundError with a Caused by: ClassNotFoundException. C is false within one JVM: an erroneous class stays erroneous; the only retry is a restart (or a fresh class loader).
