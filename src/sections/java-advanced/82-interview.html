Rehearsal

Interview questions

Twelve questions that actually get asked about this material, with the answer a strong candidate gives. Say your answer out loud before opening the reveal — recognising an answer and being able to produce one are different skills.

Easy  1. Why does count++ from two threads lose updates, and what are the two fixes?

Because it is three operations, not one: load the field into a register, add one, store it back. If two threads both load 41, both add, both store 42, one increment has vanished — and nothing throws, so the bug surfaces as a slightly wrong total weeks later. The two fixes are mutual exclusion or an atomic. synchronized (or a ReentrantLock) makes the three steps one critical section that only one thread enters at a time. AtomicInteger.incrementAndGet() uses a compare-and-swap instruction that succeeds only if the value is still what was read, and retries otherwise — no blocking, no lock. The one thing that is not a fix is volatile: it makes every read see the latest store, but the gap between load and store is still there.

Easy  2. What does volatile guarantee, and what does it not?

It guarantees visibility and ordering: a write to a volatile field happens-before every subsequent read of that field, so a reader cannot see a stale cached value, and everything the writer did before the volatile write is visible to the reader after the volatile read — which is why a volatile flag can safely publish a whole object built before the flag was set. It does not guarantee atomicity of compound actions: volatile int i; i++ still races, and a check-then-act on a volatile field is still a race. The rule of thumb: volatile is right for a status flag written by one thread and read by others, and for the double-checked-locking instance field. For a counter use an atomic; for an invariant across several fields use a lock.

Easy  3. When would you use ReentrantLock instead of synchronized?

Only when I need something synchronized cannot give me. Four things: a timed or interruptible acquire (tryLock(10, MILLISECONDS), lockInterruptibly()) so a thread can give up rather than block forever; more than one condition queue on the same lock (notFull and notEmpty in a bounded buffer, instead of notifyAll waking everyone); fairness, rarely; or a lock whose acquire and release are in different methods, which a block cannot express. Otherwise synchronized wins: it cannot be forgotten in a finally, the JIT can elide it, thread dumps show the monitor, and both are reentrant with equivalent performance on modern JVMs. Mention that a read-mostly structure wants a ReadWriteLock or StampedLock, and that a counter wants no lock at all.

Easy  4. How do you prevent deadlock?

Deadlock needs four conditions at once — mutual exclusion, hold-and-wait, no preemption, and a circular wait — so I remove one. The practical cure is to break the cycle with a global lock order: every thread that needs two locks acquires them in the same order, by a stable key such as an account id, never by identity hash code. The second cure breaks hold-and-wait: tryLock with a timeout, releasing everything and backing off randomly on failure, which also needs a bound so it does not livelock. The third is to not need two locks: one coarser lock, or a lock-free structure. Then I detect what is left: jstack prints "Found one Java-level deadlock" with the cycle, and a ThreadMXBean.findDeadlockedThreads() health check catches it in production.

Medium  5. How do you size a thread pool, and why can Executors.newFixedThreadPool run out of memory?

By what the threads wait for. CPU-bound work wants about one thread per core — more just adds context switches. I/O-bound work wants cores × (1 + wait time ÷ compute time): if a request spends 9 ms waiting on a database for every 1 ms of CPU, eight cores can keep eighty threads busy. Past a few hundred threads the right answer is virtual threads, not a bigger pool. newFixedThreadPool bounds the threads but not the queue — it uses an unbounded LinkedBlockingQueue, so when producers outrun the pool, tasks accumulate until the heap is gone, and the OOM surfaces in a thread that had nothing to do with it. A real pool is a ThreadPoolExecutor with a bounded queue and a rejection policy, usually CallerRunsPolicy for back-pressure, and a named ThreadFactory so dumps are readable.

Medium  6. thenApply versus thenCompose, and which thread runs a stage?

thenApply is map: the function returns a plain value. thenCompose is flatMap: the function returns another CompletableFuture, and compose unwraps it so the chain continues with its value rather than with a CompletableFuture<CompletableFuture<T>>. Which thread runs a stage depends on the method variant. A non-async stage such as thenApply runs on whichever thread completes the previous stage — the pool thread that finished the supplier, or, if the future was already complete when you attached the stage, the caller's own thread, which is how a "quick" callback ends up doing heavy work on a request thread. The thenApplyAsync variants always hand the stage to an executor: the common ForkJoinPool by default, which is shared with parallel streams and sized to cores, so I pass my own executor for anything that blocks.

Medium  7. What is a virtual thread, and when does it not help?

A thread whose stack lives on the heap and is scheduled by the JVM rather than the operating system. When it blocks — on a socket, a sleep, a j.u.c lock — the JVM unmounts it from its carrier platform thread and mounts another, so a handful of carriers can serve millions of virtual threads. That makes thread-per-request scale without async code. It does not help CPU-bound work: the carriers are still about one per core, so throughput is unchanged. It does not help in Java 21 when the blocking happens inside a synchronized block or a native frame, because the virtual thread is pinned to its carrier; JEP 491 fixes the monitor case in Java 24, and ReentrantLock avoids it today. And it is not a reason to pool: virtual threads are meant to be created per task and thrown away; bound the scarce resource with a Semaphore instead.

Medium  8. How does G1 differ from ZGC, and what is a GC pause actually doing?

Both are generational, region-based collectors; the difference is what they do while the application is stopped. A pause is the time when every mutator thread is at a safepoint so the collector can see a consistent graph: G1 uses that time to copy live objects out of the regions it is evacuating — young collections and mixed collections are all evacuation pauses, and the pause scales with the amount of live data, with marking done concurrently in between. ZGC moves objects concurrently: coloured pointers carry metadata bits, and a load barrier on every reference read fixes up a pointer to an object that has moved, so the pauses are only the tiny start and end of a phase, well under a millisecond, regardless of heap size. The cost is throughput — barriers on every load — and memory. G1 is the balanced default; ZGC is for large heaps with strict latency targets.

Medium  9. From a GC log, how do you tell a memory leak from an undersized heap?

Watch the after number of each Full GC. A Full collection reclaims everything unreachable, so what remains is the live set. If the post-GC occupancy climbs steadily across hours — 200M, then 260M, then 330M — something is holding references it should have dropped: a static cache, listeners never removed, a ThreadLocal in a pool, an unclosed resource. That is a leak and no heap size fixes it, only a heap dump and the dominator tree. If the post-GC occupancy is stable but close to the ceiling and Full GCs are frequent, the live set simply does not fit with room for allocation: that is an undersized heap, and -Xmx fixes it. A third pattern: the JVM reports nothing and the container is killed with exit code 137 — the heap fit, but heap plus metaspace, thread stacks and native memory exceeded the cgroup limit.

Hard  10. Walk through what happens when a class is first used, and why loaders delegate to their parent.

Three phases. Loading: the loader finds the bytes and defines a Class object. Linking: the verifier checks the bytecode, preparation allocates statics with default values, and resolution of symbolic references happens lazily. Initialization: the superclass initializes first, then <clinit> runs static initializers in textual order, exactly once, under a lock. Loading can happen early; initialization is deferred until the first active use — new, a static method call, a non-constant static field access, Class.forName — and reading a compile-time constant is not a use because the compiler inlined it. Delegation: before a loader looks for a class itself it asks its parent, up to bootstrap. That is how java.lang.String is always the JDK's, and why class identity is the pair (loader, name): the same bytes loaded by two loaders are two unrelated classes, which is the ClassCastException you get from plugin systems.

Hard  11. What is strong encapsulation, and what does --add-opens do?

Since Java 9 a package is accessible from another module only if its module exports it, and reflectively accessible to private members only if it opens it; setAccessible(true) on a member of a package that is not opened to you throws InaccessibleObjectException. Java 16 made this the default for the JDK's own internals, which is why a library that reached into java.lang.String's private value field worked on 11 and fails on 17. --add-opens java.base/java.lang=ALL-UNNAMED is the escape hatch: it opens that one package of that one module to class-path code at run time. It is a workaround, not a fix — the fix is a library version that uses supported APIs — and I would make it explicit in the launch script rather than hidden in a manifest. The companion flags are --add-exports for compile-time access to non-exported public types and --add-modules to resolve a module that nothing requires.

Hard  12. Why is Java serialization dangerous, and what do records change?

Because deserialization instantiates whatever classes the byte stream names and runs their readObject methods, without calling a constructor and before your code sees the object. Attackers chain classes that are already on the class path — a gadget chain — so that the act of reading the stream ends in Runtime.exec. That is why "deserialization of untrusted data" is its own CVE category. The defences: do not accept serialized objects across a trust boundary at all (JSON or Protobuf); if you must, install an ObjectInputFilter allow-list, per stream or globally via jdk.serialFilter, with depth and size limits. Records change one thing substantially: a record is always reconstructed through its canonical constructor, so a compact constructor's validation runs on deserialization too, and the no-constructor path that makes classic classes unsafe does not exist for them. They are still subject to gadget chains in the rest of the stream, so the filter stays.
