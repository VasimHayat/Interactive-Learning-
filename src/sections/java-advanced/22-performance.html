Section 13

Measuring: JIT tiers, JMH, JFR and profilers

Java performance intuitions imported from C are mostly wrong, and intuitions from Python are wrong in the other direction, because the code that runs is not the code you wrote. The JVM starts by interpreting bytecode, watches what is hot, compiles that with a fast compiler, keeps watching, then recompiles the hottest parts with an aggressive optimiser that inlines calls, removes allocations and deletes branches the profile says never happen. A method's speed therefore depends on how long it has been running, what types it has seen, and what the code around it looks like. Measuring it well means respecting all three.

This section has no verified program. Every number here is machine-dependent by definition, and the build of this page would prove nothing by printing one. Instead it shows you the tools that produce trustworthy numbers and the mistakes that produce confident wrong ones.

Tiered compilation

HotSpot's compilation tiers
TierWhoWhatEntered when
0InterpreterExecutes bytecode directly; counts invocations and loop back-edgesEvery method starts here
1C1, no profilingFinal tier for trivial methods (getters) that C2 could not improveC1 decides the method is trivial
2C1, light profilingUsed when C2's queue is long, so the method is not stuck at tier 3Compiler back-pressure
3C1, full profilingFast compile; instruments branches, receiver types, counters for C2~200 invocations or ~2,000 back-edges (defaults)
4C2The optimising compiler: inlining, escape analysis, loop unrolling, vectorisation, profile-guided layout~5,000 invocations or ~15,000 back-edges, with a profile

A loop that is hot inside a method called once (a main that loops a million times) is handled by on-stack replacement (OSR): the compiled version is entered mid-loop, at a back-edge. Compiled code can also be thrown away. If a branch the profile called "never taken" is taken, C2's uncommon trap deoptimises the method back to the interpreter, re-profiles, and recompiles. Loading a new subclass can do the same thing to every compiled call site that assumed the old hierarchy. Steady state is a moving target, which is the first reason benchmarks need warm-up.

Why microbenchmarks lie, and how JMH tells the truth

A loop with System.nanoTime() around it measures, in roughly this order: the interpreter, C1, a C2 compile, JIT compiler threads competing for the CPU, a GC pause, and then, if you are unlucky, nothing at all because C2 noticed the result was never used and deleted the code. The Java Microbenchmark Harness exists to remove each of those, one option at a time.

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.infra.Blackhole;
import java.util.concurrent.TimeUnit;

@BenchmarkMode(Mode.AverageTime)            // ns per operation, not ops per second
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)           // let tiered compilation finish BEFORE measuring
@Measurement(iterations = 5, time = 1)
@Fork(2)                                    // fresh JVMs: run-to-run variance becomes visible
@State(Scope.Thread)
public class PricingBench {

    Product[] products;

    @Setup(Level.Trial)
    public void setUp() {
        products = new Product[1_000];
        for (int i = 0; i < products.length; i++)
            products[i] = new Product("SKU-" + i, 80 + (i % 7) * 25);   // data the JIT cannot fold
    }

    @Benchmark
    public void subtotal(Blackhole bh) {
        for (Product p : products) bh.consume(p.price() * 3);   // consumed: cannot be dead-code eliminated
    }

    @Benchmark
    public long subtotalReturned() {
        long sum = 0;
        for (Product p : products) sum += p.price() * 3;
        return sum;                                            // returning is the other way to keep it alive
    }
}
  
Benchmark                        Mode  Cnt    Score    Error  Units
PricingBench.subtotal            avgt   10  512.431 ±  6.209  ns/op
PricingBench.subtotalReturned    avgt   10  341.877 ±  4.113  ns/op

Two benchmarks of "the same" loop and a 50% difference: Blackhole.consume per element costs a few nanoseconds itself, which the returned-sum version avoids. Neither number is wrong; they measure different things. Reading a benchmark means knowing exactly what the measured code was allowed to become.

@Benchmark
public void wrong() {
    long x = products[0].price() * 3;      // never read → C2 deletes the multiply AND the call
}

@Benchmark
public long right() {
    return products[0].price() * 3;        // the result escapes, so the work must be done
}

The wrong version reports an impossibly small number (often under 1 ns), which is the time of an empty method. C2 is not being clever; removing unobservable work is its job. Return the value or feed it to a Blackhole.

private static final int QTY = 3;          // a compile-time constant

@Benchmark
public long wrong() {
    return 80L * QTY;                      // folded to 240 at JIT time: you measure a constant load
}

@State(Scope.Thread)
public static class Input { int qty = 3; long price = 80; }   // non-final fields: real loads

@Benchmark
public long right(Input in) {
    return in.price * in.qty;
}

Anything derivable from final or literal values is computed once by the compiler. Benchmark inputs belong in non-final fields of a @State object so the JIT has to read them every time, the way production code would.

public static void main(String[] a) {
    long t0 = System.nanoTime();
    for (int i = 0; i < 1_000_000; i++) work();
    System.out.println((System.nanoTime() - t0) / 1_000_000 + " ns/op");
    // measures: interpreter + C1 + C2 compile time + JIT threads + first GC. Not work().
}

The first few hundred thousand iterations run at interpreter speed and include the compilers' own CPU time. JMH's @Warmup runs the method until the tiers settle, then measures; @Fork repeats in fresh JVMs because the order in which classes happened to load changes what gets inlined, and a single JVM's number is one sample of that distribution. Also: disable CPU frequency scaling, close the browser, and never benchmark on battery.

Measuring the real thing: JFR and profilers

Microbenchmarks answer "is A faster than B?" for code you have already decided to look at. The prior question, "what is slow?", is answered by looking at the running application, and the JDK ships the tool for that: JDK Flight Recorder. It is built into the JVM, costs about 1–2% overhead, and records allocation, GC, lock contention, I/O, exceptions and sampled stacks into a file you analyse offline with JDK Mission Control or the jfr command.

# record one minute, starting now, from a running process
jcmd 12345 JFR.start duration=60s filename=/tmp/inventory.jfr settings=profile

# or from launch
java -XX:StartFlightRecording=duration=60s,filename=inventory.jfr,settings=profile -jar inventory.jar

# what allocated the most?
jfr print --events jdk.ObjectAllocationSample inventory.jfr | grep -A3 "objectClass" | sort | uniq -c | sort -rn | head

# summary of everything recorded
jfr summary inventory.jfr

# where are threads waiting on monitors longer than 10 ms?
jfr print --events jdk.JavaMonitorEnter inventory.jfr

# a thread dump, when "it is slow right now" and you have thirty seconds
jcmd 12345 Thread.print

Sampling profilers (JFR's method sampler, async-profiler, YourKit) interrupt threads periodically and record the stack. JFR samples only at safepoints by default, points where the JVM can safely pause a thread, which biases the samples toward method exits and loop back-edges and away from the middle of tight compiled code. async-profiler uses the kernel's perf events and AsyncGetCallTrace to avoid that bias, which is why its flame graphs are the usual choice for CPU work, while JFR is unmatched for allocation, lock and I/O events. Use both; they disagree in instructive ways.

The first three things to look at when a service is slow
  1. GC log (-Xlog:gc*, §8–9). Long or frequent pauses explain latency spikes immediately, and a sawtooth that never returns to baseline is a leak.
  2. A thread dump under load (jcmd PID Thread.print, three of them ten seconds apart). Dozens of threads BLOCKED on one monitor, or WAITING in a connection pool, is a contention problem, not a CPU problem, and no profiler flame graph will show it.
  3. Hot methods (JFR or async-profiler). Only now. The hottest frame is usually a surprise — a toString in a log statement, a regex compiled per call, String.format in a loop.

Startup and the alternatives to JIT

JIT optimises for throughput after warm-up, which is the wrong trade for a CLI tool or a serverless function that lives for 200 ms. Class Data Sharing (CDS) maps a pre-parsed archive of classes instead of loading them from JARs; the JDK ships one for its own classes, and -XX:ArchiveClassesAtExit=app.jsa then -XX:SharedArchiveFile=app.jsa extends it to yours, typically cutting startup by a third. GraalVM native image goes further: it compiles the whole program ahead of time into a native executable with no JIT, no bytecode and no class loading, starting in milliseconds and using a fraction of the memory, at the cost of a closed-world assumption (reflection, proxies and resources must be declared up front), a long build, and peak throughput that only recently caught up with C2 on some workloads. Project Leyden is bringing parts of that idea into the standard JDK.

Performance gotchas
  • A benchmark of a method measures the method in isolation, which production never runs. Inlining context changes the generated code. If the question is "which Map is faster in my service?", measure the service.
  • "Optimising" by making methods bigger can make them slower. Past FreqInlineSize a hot callee stops being inlined; past about 8,000 bytecodes (HugeMethodLimit) it is never compiled at all. The generated code for a giant switch or a 2,000-line method runs in the interpreter forever.
  • Interface calls on one implementation are free; on three they are not. A monomorphic List site inlines ArrayList.get. Mix in LinkedList and Arrays.asList at the same site and it becomes a megamorphic itable dispatch. This is also why Stream pipelines in hot paths can be slower than a loop: the lambda call sites inside the stream implementation are shared by every stream in the process.
  • Median, not mean. GC pauses and deoptimisations give latency a long tail. Report p50/p99/p999; a mean hides the pauses that pages your on-call.
  • The profiler changes the program. Instrumenting profilers (the kind that rewrite bytecode) disable inlining in instrumented methods and can slow code 10×, attributing time to the wrong place. Prefer sampling for CPU; use instrumentation only for counting.

Check yourself

1.A JMH benchmark of products[0].price() * 3 reports 0.3 ns/op, faster than a single CPU cycle on the machine. The most likely cause?

B. Sub-cycle times mean no work happened. A value that is neither returned nor passed to a Blackhole has no observable effect, and C2 removes it along with the call that produced it.

A cannot make one multiply take less than a cycle. C is backwards: JMH measures many operations per timer read precisely so granularity does not matter. D describes something that does happen but still leaves a field load and a multiply, which take time; inlining removes the call, not the work.

2.A service's p99 latency jumps from 20 ms to 400 ms a few times an hour, while CPU is at 30%. Where do you look first?

C. Intermittent tail latency with idle CPU is the signature of waiting: GC pauses or lock/pool contention. The GC log shows the former in seconds; thread dumps during a spike show the latter as many threads BLOCKED or WAITING on one thing.

A finds where CPU time goes, and CPU is not the problem. B measures the handler alone in a warm JVM, which is exactly the condition under which it is fine. D can explain a one-off spike after deployment (recompilation), but not a recurring one at steady state.

3.Which changes could make a hot method slower after C2 compiles it? Select all that apply.

A and C. A megamorphic site loses inlining and becomes a real dispatch, and a method past FreqInlineSize is no longer inlined into its callers; both remove optimisations the small, monomorphic version enjoyed.

B usually helps or is neutral: small methods inline back together. D changes nothing for the JIT; final on locals and parameters is a compile-time check with no bytecode footprint.
