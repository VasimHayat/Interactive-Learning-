Section 6

CompletableFuture: composing asynchronous work

§5 ended with a Future, and a Future can do exactly two things: block until the value arrives, or tell you whether it has arrived yet. There is no way to say "and when it does, do this with it". A quote that needs a price and a stock level and then a supplier lookup becomes a thread that blocks three times in a row, which is the thread-per-wait design that pools were meant to avoid.

CompletableFuture is a Future that is also a completion stage: a cell that will hold either a value or a failure, to which you attach the next step before the value exists. When the cell completes, the attached steps run, each producing a new cell. A pipeline of lookups becomes a description of what to do, written once on the calling thread, and executed by whichever threads happen to finish the work. The two questions that explain everything in this section are which thread runs a stage and what happens to a failure.

Worked example

Every lookup here is a stand-in for a remote call. The pool is explicit, every future is joined before anything is printed, and the fan-out results are sorted, so the output is the same on every machine even though the work is genuinely parallel.

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Composing {

    record Quote(String sku, int priceInCents, int onHand) {
        String line() { return sku + " @ " + priceInCents + "c, " + onHand + " on hand"; }
    }

    static final Map PRICES = Map.of(
            "BOLT-7", 80, "NUT-3", 25, "CAM-9", 2300, "GIRD-1", 120_000, "ROD-4", 4500);
    static final Map STOCK = Map.of(
            "BOLT-7", 400, "NUT-3", 1200, "CAM-9", 2, "GIRD-1", 3, "ROD-4", 40);
    static final Map SUPPLIER = Map.of("BOLT-7", "ACME", "NUT-3", "ACME", "CAM-9", "KINETIC");

    // Each "lookup" stands in for a remote call: slow, independent, may fail.
    static int price(String sku) {
        Integer p = PRICES.get(sku);
        if (p == null) throw new IllegalArgumentException("unknown sku " + sku);
        return p;
    }
    static int stock(String sku) { return STOCK.getOrDefault(sku, 0); }
    static String supplier(String sku) { return SUPPLIER.getOrDefault(sku, "none"); }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4);

        // 1. Two independent lookups, combined when BOTH are done.
        CompletableFuture price = CompletableFuture.supplyAsync(() -> price("BOLT-7"), pool);
        CompletableFuture stock = CompletableFuture.supplyAsync(() -> stock("BOLT-7"), pool);
        CompletableFuture quote = price.thenCombine(stock, (p, s) -> new Quote("BOLT-7", p, s));
        System.out.println("thenCombine  = " + quote.join().line());

        // 2. A dependent lookup: thenCompose flattens a stage that itself returns a future.
        CompletableFuture supplier = quote.thenCompose(q ->
                CompletableFuture.supplyAsync(() -> supplier(q.sku()), pool));
        System.out.println("thenCompose  = " + supplier.thenApply(s -> "supplied by " + s).join());

        // 3. A failing lookup. Nothing is thrown here: the failure is stored in the future.
        CompletableFuture bad = CompletableFuture.supplyAsync(() -> price("NOPE"), pool);
        System.out.println("recovered    = " + bad.exceptionally(ex -> -1).join());
        System.out.println("handle       = " + bad.handle((v, ex) ->
                ex == null ? "value " + v : "failed: " + ex.getCause().getMessage()).join());
        String wrapping = bad.handle((v, ex) ->
                ex.getClass().getSimpleName() + " wrapping " + ex.getCause().getClass().getSimpleName()).join();
        System.out.println("stage saw    = " + wrapping);
        try { bad.join(); }
        catch (CompletionException e) { System.out.println("join threw   = CompletionException -> " + e.getCause().getMessage()); }
        try { bad.get(); }
        catch (ExecutionException e) { System.out.println("get threw    = ExecutionException -> " + e.getCause().getMessage()); }

        // 4. Fan out five quotes, wait for all, read them back in a stable order.
        List skus = List.of("ROD-4", "BOLT-7", "GIRD-1", "NUT-3", "CAM-9");
        List> quotes = new ArrayList<>();
        for (String sku : skus) {
            quotes.add(CompletableFuture.supplyAsync(() -> price(sku), pool)
                    .thenCombine(CompletableFuture.supplyAsync(() -> stock(sku), pool),
                                 (p, s) -> new Quote(sku, p, s)));
        }
        CompletableFuture all = CompletableFuture.allOf(quotes.toArray(new CompletableFuture[0]));
        all.join();                                              // Void: it only says "every one is done"
        List lines = quotes.stream().map(CompletableFuture::join).map(Quote::line).sorted().toList();
        System.out.println("allOf        = done " + all.isDone() + ", " + lines.size() + " quotes");
        lines.forEach(l -> System.out.println("    " + l));

        // 5. A stage that never completes, bounded by a timeout (Java 9+).
        CompletableFuture never = new CompletableFuture<>();
        System.out.println("onTimeout    = " + never.completeOnTimeout("cached quote", 50, TimeUnit.MILLISECONDS).join());
        CompletableFuture never2 = new CompletableFuture<>();
        try { never2.orTimeout(50, TimeUnit.MILLISECONDS).join(); }
        catch (CompletionException e) { System.out.println("orTimeout    = " + e.getCause().getClass().getSimpleName()); }

        // 6. A value already in hand enters the same pipeline without touching a thread.
        System.out.println("completed    = " + CompletableFuture.completedFuture(21).thenApply(x -> x * 2).join());

        pool.shutdown();
        System.out.println("pool stopped = " + pool.awaitTermination(5, TimeUnit.SECONDS));
    }
}

Six things to take from it, in order:

  • thenCombine joins two independent stages. Price and stock were submitted together and ran in parallel; the combining function ran once, after the later of the two finished, on whichever thread finished it.
  • thenCompose is for a step that returns a future. With thenApply you would have got a CompletableFuture<CompletableFuture<String>>. thenCompose unwraps it, exactly as flatMap does for Optional and streams (Intermediate §5, §7).
  • A failure is a value in the cell, not a thrown exception. price("NOPE") threw on a pool thread and nobody saw a stack trace. The future completed exceptionally, and every dependent stage sees that state wrapped in a CompletionException. exceptionally substitutes a value; handle sees both outcomes; join rethrows the wrapper and get rethrows an ExecutionException instead. Either way the real cause is one getCause() away.
  • allOf gives you Void. It signals that every input is done and nothing else; you read the values back from the inputs you kept. Sorting them is what makes the printed order stable.
  • Timeouts are a property of the stage. completeOnTimeout supplies a fallback, orTimeout fails the stage with a TimeoutException. Both exist since Java 9; before that, every timeout meant a blocking get(n, unit).
  • completedFuture is the unit. A value you already hold joins the pipeline without a thread, which is how caches and fast paths plug into the same code as the slow path.

The rule the stepper shows: a non-async stage (thenApply, thenCompose, thenAccept…) runs on the thread that completes its input, or on the calling thread if the input was already complete when you attached it. An *Async stage is always handed to an executor: the one you pass, or ForkJoinPool.commonPool() if you pass none. Two consequences: a cheap stage should stay non-async to avoid a hand-off, and a stage that does real work after a fast input may run on your caller's thread unless you say Async.

Five ways this goes wrong in production
  • Blocking inside a stage. thenApply(x -> other.join()) ties up a pool thread doing nothing. With the common pool, which has cores − 1 threads, a handful of these deadlocks the whole JVM's async work. Compose instead of joining.
  • Forgetting the executor. supplyAsync(s) without an executor uses the common pool. Put I/O there and every parallel stream in the process slows down with you. Give I/O its own bounded pool (§5) or, in Java 21, a virtual-thread executor (§7).
  • A dropped failure. A future nobody joins or attaches a handler to fails silently. If you fire and forget, at least whenComplete a log line.
  • cancel() does not interrupt. It completes the cell with a CancellationException; the supplier keeps running to its end on the pool thread. If the work must stop, the task has to check a flag of its own.
  • Wrapping, twice. A failure inside exceptionally's own function, or a CompletionException rethrown from a stage, gets wrapped again. When unwrapping, loop on getCause() while the throwable is a CompletionException rather than calling it once.

One last thing. A pipeline of a dozen stages across three pools is powerful and very hard to read six months later: the structure of the computation is spread across callbacks, a failure in the middle produces a stack trace that names none of your methods, and cancelling a sub-task means nothing. §7 shows the other direction Java 21 is taking: give each concurrent task a cheap thread of its own and write the waiting as ordinary, sequential code.

Check yourself

1.CompletableFuture<Integer> a = CompletableFuture.completedFuture(1); a.thenApply(x -> heavyWork(x)); — which thread runs heavyWork?

C. thenApply is a non-async stage. Its input is already complete, so there is no completing thread to inherit; the stage runs immediately on the thread that attached it. If heavyWork takes a second, the caller is stuck for a second.

A is what thenApplyAsync would do. B: nothing in CompletableFuture creates threads; it only submits to executors. D: stages are eager, not lazy — a future is not a stream, and join only waits.

2.A stage's function is q -> fetchSupplierAsync(q), where fetchSupplierAsync returns CompletableFuture<Supplier>. You attach it with thenApply. What is the type of the result, and what should you have used?

B. thenApply wraps whatever the function returns, and the function returns a future, so you get a future of a future. thenCompose expects a function that returns a CompletionStage and flattens it: the outer stage completes when the inner one does.

A and C: it compiles, and the type is nested — the compiler is perfectly happy to infer CompletableFuture<CompletableFuture<Supplier>>, which is why this bug survives until someone tries to join() and gets a future back. D: thenCombine joins two independent futures with a two-argument function; here the second lookup depends on the first.

3.cf = supplyAsync(() -> { throw new IllegalStateException("offline"); }, pool).thenApply(v -> v + 1); Which statements are true? Select all that apply.

A and D. The failure is stored in the first cell, skips the thenApply stage (which completes exceptionally with the same wrapped cause), and surfaces from join as a CompletionException. Attaching exceptionally anywhere downstream substitutes a value, and the chain continues normally from there.

B: a normal-path stage is never run on a failed input; it is bypassed. C: nothing is printed anywhere — the whole point, and the whole danger, of a stored failure is that it is silent until someone looks. An uncaught exception in a plain Thread would print; inside a CompletableFuture it is captured.
