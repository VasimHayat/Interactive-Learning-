Section 12

The module system

Everything before this section ran on the class path: a flat list of directories and JARs in which every public class is visible to every other class, duplicate packages silently shadow each other, and a missing dependency is discovered the first time a class is touched, as a NoClassDefFoundError in production. The Java Platform Module System (JPMS, Java 9) exists because the JDK itself suffered from exactly those problems. It adds a second mechanism, the module path, in which each JAR declares what it needs and what it exposes, and the JVM checks both at startup.

Two guarantees follow. Reliable configuration: if a module you require is missing, the JVM refuses to start, with a message naming the module, rather than failing later at an arbitrary call site. Strong encapsulation: a package that a module does not export is invisible to other modules at compile time and at run time, even to reflection. That second guarantee is why, since Java 16, code that pokes at sun.misc or java.lang internals fails with InaccessibleObjectException unless the JVM was started with an explicit --add-opens.

Worked example: what the running JVM knows

This program is not itself a module — it is compiled and run on the class path, like every other program in this course — yet it still runs inside a module graph. Every class belongs to some module, and the facts below are the ones worth knowing by heart.

import java.lang.module.ModuleDescriptor;

public class ModuleFacts {
    public static void main(String[] args) throws Exception {
        Module base = Object.class.getModule();
        Module mine = ModuleFacts.class.getModule();

        System.out.println("java.lang.Object lives in     = " + base.getName());
        System.out.println("this class's module is named  = " + mine.isNamed());
        System.out.println("java.sql.Driver lives in      = " + Class.forName("java.sql.Driver").getModule().getName());
        System.out.println("boot layer has java.base      = " + ModuleLayer.boot().findModule("java.base").isPresent());
        System.out.println("java.base exports java.lang   = " + base.isExported("java.lang"));
        System.out.println("java.base exports jdk.internal.misc = " + base.isExported("jdk.internal.misc"));
        System.out.println("unnamed module reads java.base = " + mine.canRead(base));

        ModuleDescriptor d = base.getDescriptor();
        System.out.println("java.base requires anything   = " + !d.requires().isEmpty());
        System.out.println("java.base is open             = " + d.isOpen());
    }
}

  • Code on the class path lives in the unnamed module, which is why isNamed() is false. The unnamed module reads every other module and exports everything, so class-path code keeps working exactly as before Java 9.
  • java.base is the one module every other module implicitly requires, and the only one that requires nothing. jdk.internal.misc is in it but not exported: that is strong encapsulation, observable from your own code.
  • The JDK is itself about seventy modules (java.sql, java.net.http, java.desktop…). jlink, below, builds a runtime containing only the ones you need.

A two-module application

A module is a JAR, or a directory, with a module-info.java at its root. Here the warehouse is split into an API module that other teams compile against and an application module that depends on it. The example is complete; it is not compiled during the build of this page because a module-info.java would turn every other program on this page into part of the same module.

inventory/
├── com.acme.inventory.api/
│   ├── module-info.java
│   └── com/acme/inventory/api/
│       ├── Product.java
│       └── StockSource.java          # a service interface
└── com.acme.inventory.app/
    ├── module-info.java
    └── com/acme/inventory/app/
        ├── Main.java
        └── internal/MemoryStock.java # implements StockSource; NOT exported
  
module com.acme.inventory.api {
    exports com.acme.inventory.api;          // the public surface: Product, StockSource
    // nothing else — no "internal" package is visible outside this module
}
  
module com.acme.inventory.app {
    requires com.acme.inventory.api;         // compile error if missing; JVM refuses to start if absent
    requires java.net.http;                  // a JDK module beyond java.base must be named
    requires static java.compiler;           // needed at compile time only, optional at run time

    provides com.acme.inventory.api.StockSource
        with com.acme.inventory.app.internal.MemoryStock;   // a service implementation, found via ServiceLoader

    opens com.acme.inventory.app.config to com.fasterxml.jackson.databind;  // reflection for ONE consumer
}
  
# compile both modules in one go; --module-source-path maps module names to directories
javac -d out --module-source-path . $(find . -name "*.java")

# run: -m names the module and its main class
java --module-path out -m com.acme.inventory.app/com.acme.inventory.app.Main

# package each module as a modular JAR (the module-info.class goes in the root)
jar --create --file mods/api.jar -C out/com.acme.inventory.api .
jar --create --file mods/app.jar --main-class com.acme.inventory.app.Main -C out/com.acme.inventory.app .

# what does this JAR actually depend on?
jdeps --module-path mods -s mods/app.jar

# a trimmed runtime image: only the modules reachable from the app, ~40 MB instead of ~300 MB
jlink --module-path mods:$JAVA_HOME/jmods --add-modules com.acme.inventory.app \
      --launcher inventory=com.acme.inventory.app --output inventory-runtime
./inventory-runtime/bin/inventory

Readability, accessibility, and what breaks

Two separate checks gate every cross-module reference. Readability is a relation between modules: A reads B if A requires B (or B is required transitively, or A is the unnamed module). Accessibility is a relation between a class and a package: a type in B is accessible to A only if A reads B, B exports the package, and the type is public. Reflection adds a third level: deep reflection into non-public members needs the package to be open to A as well. Try the combinations:

The class path did not go away

Everything on the class path is lumped into one unnamed module. It reads every named module, exports all its packages, and opens them all. That is why a 2015 application runs on Java 21 unchanged. The price: a named module cannot requires the unnamed module, so modular code cannot depend on class-path code. Migration therefore proceeds bottom-up, from the leaves of the dependency graph.

Most applications still run this way, deliberately. A module graph pays off for libraries (a clear API surface, no accidental dependency on internals), for the JDK itself, and for anything shipped with jlink. For a service deployed in a container with a fixed dependency list, the gains are smaller and the migration cost of every reflective framework is real.

A plain JAR placed on the module path becomes an automatic module: its name is derived from the file name (jackson-databind-2.17.0.jar → jackson.databind) unless the manifest sets Automatic-Module-Name, it exports every package, and it reads every other module including the unnamed one. That last point is the bridge that lets a modular application use a not-yet-modular library.

Split packages are the migration bug you will hit: two JARs containing classes in the same package (common with javax.* and old API-plus-implementation pairs) are legal on the class path and forbidden on the module path, because a package must belong to exactly one module. jdeps reports them before the JVM does.

# make an unexported package accessible at compile/run time
--add-exports java.base/jdk.internal.misc=ALL-UNNAMED

# allow deep reflection into a package (what most framework warnings ask for)
--add-opens java.base/java.lang=ALL-UNNAMED

# resolve a module that nothing requires (e.g. a JDK tool module, or jdk.incubator.vector)
--add-modules jdk.incubator.vector

# resolve a module and pretend module M reads it
--add-reads com.acme.inventory.app=ALL-UNNAMED

These flags go on the java command line or into a JDK_JAVA_OPTIONS environment variable; they cannot be set from inside the program, by design. Treat each one as technical debt with a name: it records precisely which encapsulation boundary you are crossing and for whom.

// in the api module
public interface StockSource { int onHand(String sku); }

// in the app module's module-info: provides StockSource with MemoryStock;
// in any consumer's module-info:   uses StockSource;

ServiceLoader<StockSource> sources = ServiceLoader.load(StockSource.class);
StockSource first = sources.findFirst()
        .orElseThrow(() -> new IllegalStateException("no StockSource on the module path"));

Services are how a module uses an implementation it cannot see: MemoryStock sits in a non-exported package, the consumer names only the interface, and the module system wires them together. It predates JPMS (the file META-INF/services/… does the same on the class path) but provides … with makes it checked and explicit. JDBC drivers, charsets and HttpClient implementations are all found this way.

Module gotchas
  • exports is not opens. An exported package lets other modules call public members. It does not let a JSON library set a private field. Frameworks need opens; give them a qualified one.
  • requires is not transitive by default. If your API returns a type from module M, callers cannot even name that type unless you write requires transitive M. The symptom is a baffling "cannot access class" error in their build.
  • The module name is not the package name. They usually coincide by convention (com.acme.inventory.api contains package com.acme.inventory.api), but the module declaration lists packages explicitly; a new package added to the API module is private until you export it. That is the point.
  • Reflection across modules fails late. setAccessible(true) on a member in a non-open package throws InaccessibleObjectException at run time, not at compile time, typically the first time a framework touches the class. Test the modular build, not just the class-path one.
  • Class.forName still works, access does not. You can load any class by name; you cannot instantiate or call it unless its package is exported to you. Loading and accessing are different checks.

Check yourself

1.Module app requires api, and api exports com.acme.inventory.api. Jackson, running in its own module, tries to set the private field sku of Product via reflection. What happens?

C. exports grants access to public members at compile and run time. Deep reflection into a private member additionally requires the package to be open to the caller, and the failure is a run-time exception at the setAccessible call.

A confuses exporting with opening. B is wrong because nothing in app references the private field; the compiler has no reason to complain. D gets the direction wrong: an automatic module reads everything, but reading api does not make api's private members accessible; accessibility is decided by the target module's declaration.

2.api has a public method JsonNode toJson() where JsonNode comes from module json, and api declares requires json;. Module app declares only requires api; and calls product.toJson().size(). Result?

B. Readability is not transitive unless declared so. app does not read json, so it cannot use JsonNode even though a method it can call returns one. The API module should say requires transitive json, which is the rule of thumb: anything in your public signatures must be transitive.

A describes what transitive would give you. C is impossible here because javac catches it first. D is wrong because json is resolved (api requires it); resolution and readability are different things.

3.Which statements about the unnamed module are true? Select all that apply.

A and D. Class-path code is one unnamed module that reads all resolved modules and exports and opens all of its packages, which is what keeps old applications working.

B is the migration constraint: named modules cannot depend on the unnamed module, so you modularise from the bottom of the dependency graph up (automatic modules are the bridge). C is false for java.sql, which is in the default root set for the class path; --add-modules is needed only for modules outside that set, such as incubator modules.
