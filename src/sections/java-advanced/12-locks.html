Section 3

synchronized, ReentrantLock and deadlock

§1 showed that count++ is three operations and that two threads interleaving them lose updates. §2 showed that even a correctly ordered write may never become visible to another core. A lock solves both at once: while one thread holds it, no other thread can enter the guarded code (mutual exclusion), and releasing it publishes everything that thread wrote to whoever acquires it next (happens-before). That second guarantee is the one people forget. A lock is not only a turnstile; it is also a memory barrier.

Every Java object carries an intrinsic lock, also called its monitor. synchronized (obj) { … } acquires obj's monitor on entry and releases it on exit, by any path — a return, an exception, a break. A synchronized instance method locks this; a synchronized static method locks the Class object. The monitor is reentrant: a thread that already owns it can acquire it again, which is why a synchronized method may call another synchronized method on the same object without deadlocking against itself.

Worked example: one lock, one invariant

Eight picker threads leave a CountDownLatch gate together and hammer one InventoryService holding 500 units. The invariant — reserved + on hand = 500, and every attempt is either applied or refused — must survive 800 racing calls. Then a synchronized method re-enters another, and a bounded buffer hands 1,000 items between two threads using nothing but wait and notifyAll.

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.CountDownLatch;

public class Synchronized {

    /* One lock, one invariant: onHand never goes negative and every
       reservation is either fully applied or refused. */
    static final class InventoryService {
        private int onHand;
        private int reserved;
        private int refused;

        InventoryService(int onHand) { this.onHand = onHand; }

        synchronized boolean reserve(int qty) {
            if (qty > onHand) { refused++; return false; }
            onHand -= qty;
            reserved += qty;
            return true;
        }

        synchronized void release(int qty) { onHand += qty; }

        // a synchronized method calling another synchronized method on the
        // same object: the thread already owns the monitor, so it re-enters
        synchronized boolean reserveTwice(int qty) {
            return reserve(qty) && reserve(qty);
        }

        synchronized int onHand() { return onHand; }
        synchronized int reserved() { return reserved; }
        synchronized int refused() { return refused; }
    }

    /* A bounded buffer built on wait/notifyAll: the textbook shape every
       BlockingQueue implements for you. */
    static final class BoundedBuffer {
        private final Deque items = new ArrayDeque<>();
        private final int capacity;
        BoundedBuffer(int capacity) { this.capacity = capacity; }

        synchronized void put(int item) throws InterruptedException {
            while (items.size() == capacity) wait();   // loop, never if: spurious wakeups
            items.addLast(item);
            notifyAll();
        }

        synchronized int take() throws InterruptedException {
            while (items.isEmpty()) wait();
            int item = items.removeFirst();
            notifyAll();
            return item;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        // ── 8 pickers hammer one service ────────────────────────────────────
        InventoryService inv = new InventoryService(500);
        int threads = 8, perThread = 100, qty = 1;
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);
        for (int t = 0; t < threads; t++) {
            Thread picker = new Thread(() -> {
                try { start.await(); } catch (InterruptedException e) { return; }
                for (int i = 0; i < perThread; i++) inv.reserve(qty);
                done.countDown();
            }, "picker-" + t);
            picker.start();
        }
        start.countDown();                          // everyone leaves the gate together
        done.await();

        int attempts = threads * perThread;         // 800 attempts against 500 units
        System.out.println("attempts        = " + attempts);
        System.out.println("reserved        = " + inv.reserved());
        System.out.println("refused         = " + inv.refused());
        System.out.println("on hand         = " + inv.onHand());
        System.out.println("invariant holds = " + (inv.reserved() + inv.onHand() == 500
                                                   && inv.reserved() + inv.refused() == attempts));

        // ── reentrancy ──────────────────────────────────────────────────────
        InventoryService small = new InventoryService(10);
        System.out.println("reentered       = " + small.reserveTwice(3) + " (on hand " + small.onHand() + ")");

        // ── wait / notifyAll producer-consumer ──────────────────────────────
        BoundedBuffer buffer = new BoundedBuffer(4);
        int n = 1000;
        long[] consumedSum = new long[1];
        Thread producer = new Thread(() -> {
            try { for (int i = 1; i <= n; i++) buffer.put(i); buffer.put(-1); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "producer");
        Thread consumer = new Thread(() -> {
            try { for (int v; (v = buffer.take()) != -1; ) consumedSum[0] += v; }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "consumer");
        producer.start(); consumer.start();
        producer.join(10_000); consumer.join(10_000);
        System.out.println("consumed sum    = " + consumedSum[0] + " (expected " + ((long) n * (n + 1) / 2) + ")");
    }
}

Three things to notice. The reserve check-then-act — is there enough? then subtract — is exactly the compound operation §1 broke, and the only reason it survives 800 racing calls is that both halves sit inside the same monitor. The accessors are synchronized too: without that, a reader could see a stale onHand even after every writer has finished (§2). And every wait() sits inside a while, because the JVM is permitted to wake a waiting thread for no reason at all — a spurious wakeup — and because notifyAll wakes every waiter, most of whom will find the condition still false.

What to lock on

synchronized methods lock this, which means any code holding a reference to your object can lock it too — and can therefore block your methods or, worse, deadlock against them. A private lock object keeps the lock inside the class:

private final Object lock = new Object();          // nobody outside can synchronize on it

void reserve(int qty) {
    synchronized (lock) { /* … */ }
}

Lock on a final field, never on a value that can be reassigned, and never on a boxed primitive or a String — Integer.valueOf(7) and "lock" are shared instances, so two unrelated classes can end up contending for the same monitor without knowing it.

synchronized or a Lock object?

  • Cannot be forgotten. Release is structural: the block ends, the lock is released. There is no unlock() to miss on an exception path.
  • Cannot be interrupted, timed, or tried. A thread blocked on a monitor waits until it gets it. If the owner never releases, the waiter is stuck for the life of the process.
  • One condition per lock. wait/notifyAll is a single wait set, so "not full" and "not empty" waiters are woken together and most go straight back to sleep.
  • The default. Correct, well optimised by the JIT (lock elision, biased-then-lightweight locking), and readable. Reach for ReentrantLock only when you need something from the next tab.
private final ReentrantLock lock = new ReentrantLock();          // new ReentrantLock(true) = fair
private final Condition notEmpty = lock.newCondition();
private final Condition notFull  = lock.newCondition();

void put(int item) throws InterruptedException {
    lock.lockInterruptibly();                                      // or lock(), or tryLock(2, SECONDS)
    try {
        while (items.size() == capacity) notFull.await();
        items.addLast(item);
        notEmpty.signal();                                         // wake ONE consumer, not everyone
    } finally {
        lock.unlock();                                             // the one line you must never forget
    }
}
  • tryLock() returns immediately; tryLock(timeout) gives up after a while; lockInterruptibly() lets a blocked thread be cancelled. These are the deadlock escape hatches a monitor lacks.
  • Multiple Conditions let producers and consumers wait on different queues, so a signal() wakes the right kind of thread.
  • Fairness (new ReentrantLock(true)) hands the lock to the longest waiter. It prevents starvation at a real throughput cost; the default is unfair and usually right.
  • Always unlock() in finally, and acquire outside the try — if lock() itself throws, there is nothing to release.
private final ReadWriteLock rw = new ReentrantReadWriteLock();

int onHand(String sku) {
    rw.readLock().lock();                      // many readers at once …
    try { return stock.getOrDefault(sku, 0); } finally { rw.readLock().unlock(); }
}
void restock(String sku, int qty) {
    rw.writeLock().lock();                     // … but a writer waits for all of them, and excludes everyone
    try { stock.merge(sku, qty, Integer::sum); } finally { rw.writeLock().unlock(); }
}

// StampedLock: optimistic reads that pay nothing when no write intervened
private final StampedLock sl = new StampedLock();
int onHandOptimistic(String sku) {
    long stamp = sl.tryOptimisticRead();       // no lock taken at all
    int v = stock.getOrDefault(sku, 0);
    if (!sl.validate(stamp)) {                 // a write happened meanwhile: fall back to a real read lock
        stamp = sl.readLock();
        try { v = stock.getOrDefault(sku, 0); } finally { sl.unlockRead(stamp); }
    }
    return v;
}
  • A read-write lock pays off only when reads vastly outnumber writes and the critical sections are long enough to amortise its heavier bookkeeping. For a short map lookup, a plain lock or a ConcurrentHashMap (§4) is faster.
  • StampedLock is not reentrant and has no conditions. Its optimistic mode is the fastest read path in the JDK when writes are rare, and the easiest to misuse: read every field you need before validate, and never dereference something you read optimistically until it validates.

Deadlock

Two threads, two locks, opposite order. Thread A holds BOLT-7's lock and wants NUT-3's; thread B holds NUT-3's and wants BOLT-7's. Neither can proceed, neither will release, and because monitors cannot be interrupted or timed out, the JVM will sit there until someone kills it. Four conditions must all hold for this to happen — mutual exclusion, hold-and-wait, no preemption, and a circular wait — and the cures each break one of them. Worked example: two cures that cannot deadlock

Two mover threads shift one unit at a time between BOLT-7 and NUT-3, 5,000 times each, in opposite directions — exactly the shape above. The naive version is deliberately absent: it would hang this page's build. Both versions here complete, and the latch's timed await is the proof: a deadlock would return false.

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class LockOrdering {

    static final class Stock {
        final String sku;
        final ReentrantLock lock = new ReentrantLock();
        int units;
        Stock(String sku, int units) { this.sku = sku; this.units = units; }
    }

    /* Cure 1: every thread acquires in the same global order, here by SKU.
       Two threads moving stock in opposite directions still lock BOLT-7
       first and NUT-3 second, so neither can hold what the other needs. */
    static void transferOrdered(Stock from, Stock to, int qty) {
        Stock first = from.sku.compareTo(to.sku) < 0 ? from : to;
        Stock second = first == from ? to : from;
        first.lock.lock();
        try {
            second.lock.lock();
            try {
                if (from.units >= qty) { from.units -= qty; to.units += qty; }
            } finally { second.lock.unlock(); }
        } finally { first.lock.unlock(); }
    }

    /* Cure 2: no fixed order, but never wait forever. A thread that cannot
       get the second lock within the timeout releases the first and retries,
       so a would-be deadlock resolves itself. */
    static boolean transferTimed(Stock from, Stock to, int qty) throws InterruptedException {
        for (int attempt = 0; attempt < 1000; attempt++) {
            if (from.lock.tryLock(10, TimeUnit.MILLISECONDS)) {
                try {
                    if (to.lock.tryLock(10, TimeUnit.MILLISECONDS)) {
                        try {
                            if (from.units >= qty) { from.units -= qty; to.units += qty; }
                            return true;
                        } finally { to.lock.unlock(); }
                    }
                } finally { from.lock.unlock(); }
            }
            Thread.onSpinWait();            // back off, then try again
        }
        return false;
    }

    interface Transfer { void run(Stock from, Stock to, int qty) throws InterruptedException; }

    static void race(String label, Transfer transfer) throws InterruptedException {
        Stock bolt = new Stock("BOLT-7", 10_000), nut = new Stock("NUT-3", 10_000);
        int moves = 5_000;
        CountDownLatch start = new CountDownLatch(1), done = new CountDownLatch(2);
        Runnable ab = () -> { try { start.await(); for (int i = 0; i < moves; i++) transfer.run(bolt, nut, 1); } catch (InterruptedException e) { } done.countDown(); };
        Runnable ba = () -> { try { start.await(); for (int i = 0; i < moves; i++) transfer.run(nut, bolt, 1); } catch (InterruptedException e) { } done.countDown(); };
        new Thread(ab, "mover-A").start();
        new Thread(ba, "mover-B").start();
        start.countDown();
        boolean finished = done.await(30, TimeUnit.SECONDS);   // a real deadlock would time out here
        System.out.println(label);
        System.out.println("  transfers completed = " + finished);
        System.out.println("  total units         = " + (bolt.units + nut.units) + " (expected 20000)");
    }

    public static void main(String[] args) throws InterruptedException {
        race("ordered locks", LockOrdering::transferOrdered);
        race("tryLock with timeout", (f, t, q) -> transferTimed(f, t, q));
    }
}

The ordering cure breaks circular wait: with one global order there can be no cycle. The order must be something stable and total — a SKU string, a database id, a sequence number assigned at construction. System.identityHashCode is a popular choice that is almost right: two objects can share an identity hash, and then you need a tie-breaker lock. The timeout cure breaks hold-and-wait: a thread that cannot get everything it needs gives back what it has. It costs a retry loop and the possibility of livelock — both threads backing off and retrying in lockstep forever — which a small random delay before retrying removes. The third cure is the simplest and often the best: use one lock for both accounts, and accept the lost parallelism.

Will it deadlock?

Two threads, two locks

Starvation, livelock and granularity

Starvation is a thread that is runnable but never scheduled onto the lock — unfair locks under heavy contention can do this to a slow waiter; a fair ReentrantLock is the fix, at a cost. Livelock is the opposite of deadlock in appearance and identical in effect: every thread is busy, nothing progresses, because each keeps responding to the others. Granularity is the trade-off you make in choosing what a lock covers. One lock for the whole inventory is simple and serialises every picker; one lock per SKU is parallel and invites deadlock the moment an operation touches two. Lock striping — N locks, each covering a slice of the keys chosen by hash — is the middle path, and it is how ConcurrentHashMap was built before it moved to per-bin locking (§4).

Lock gotchas
  • if (cond) wait(); is a bug. Spurious wakeups are permitted by the specification, and notifyAll wakes threads whose condition is still false. Always while.
  • notify() can lose a wakeup. With two kinds of waiter on one monitor, waking "one thread" may wake the wrong kind, which goes back to sleep, and the right one never hears. Use notifyAll, or a ReentrantLock with two Conditions.
  • Calling out while holding a lock. Invoking a listener, a callback or an unknown object's method inside synchronized means its code runs under your lock. If it takes another lock, you have just created a lock-order dependency you cannot see. Copy what you need, release, then call.
  • Locking on this in a public class publishes your lock. Any caller can synchronized (yourObject) and block you. Prefer a private lock object.
  • synchronized on a static method and on an instance method are different locks. One guards the Class, the other the instance. Code that assumes they exclude each other is wrong.
  • A ReentrantLock without finally is a lock that leaks on the first exception. Every thread that arrives afterwards blocks forever, and the dump shows them all waiting on a lock whose owner has long since died.

Check yourself

1.A thread calls wait() inside a synchronized method. What happens to the monitor?

C. wait() atomically releases the monitor and parks the thread in the wait set. After a notify, the thread moves to the entry set and competes for the monitor like any other; wait() returns only once it owns it again — which is why the code after wait() may safely touch shared state, and why it must re-check its condition.

A would make producer-consumer impossible: the producer could never enter. B describes a thread running shared-state code without the lock, which Java never permits here. D is backwards — that exception is thrown when you call wait() without owning the monitor.

2.Which of these remove the possibility of deadlock between two threads that each need locks L1 and L2? Select all that apply.

B and D. A global acquisition order makes a circular wait impossible; a timed acquisition that gives back what it holds removes hold-and-wait. Each breaks one of the four necessary conditions.

A changes who gets a lock first, not whether two threads can each hold one and want the other. C is a different API with the same blocking semantics: lock() waits forever exactly as a monitor does. The escape hatches are tryLock and lockInterruptibly, and only if you use them.

3.Integer stock = 500; … synchronized (stock) { stock--; } — eight threads run this. What is wrong?

A. Integer is immutable: stock-- unboxes, decrements and boxes a new object into the variable. The next thread to arrive synchronizes on that new object, not the one the current holder owns, so there is no mutual exclusion at all. Lock on a final field that is never reassigned, and keep the counter separate from the lock.

B is wishful: boxing adds allocation, not atomicity. C — it compiles; any object reference is a legal monitor. D — cached Integers in −128…127 are shared instances, which is a different hazard (unrelated code contending on the same lock), but sharing a monitor causes contention, not deadlock.
