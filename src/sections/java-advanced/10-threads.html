Section 1

Threads, stacks and the shared heap

A thread is the unit the operating system schedules: a program counter that says which instruction runs next, a set of registers, and a stack holding the frames of the methods it is currently inside — their parameters and local variables. Each thread has its own. What threads do not have their own copy of is the heap: every object, every field, every array element lives in one shared space that all threads of the process see. That split is the whole subject of this module. Locals are private and therefore safe; fields are shared and therefore need rules.

Picture the warehouse. Three pickers walking the aisles each carry their own clipboard — that is a stack. The stock board on the wall is the heap. Two pickers can write on their own clipboards all day without conflict; the moment both update the same line on the board, the number can be wrong, and nobody is told.

What each thread owns versus what all threads share
Per thread (private)Per process (shared)
Program counter — where this thread is in the codeThe heap — every object and array, including Strings and boxed values

One consequence is worth stating plainly: a reference held in a local variable is private, but the object it points to is not. Two threads holding references to the same ArrayList are sharing it, however private the variables look.

Worked example

Three ways to create a thread, a daemon, an interruption, and a demonstration that recursion on one thread cannot disturb another. Note what the program prints: nothing until every thread has been joined, and then only facts whose value does not depend on which thread ran first.

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class ThreadBasics {
    // shared heap: every thread sees the same list, so it must be a thread-safe one
    static final List results = Collections.synchronizedList(new ArrayList<>());
    static volatile boolean flagRestored;

    // each call lives in a frame on the CALLING thread's stack: three threads can
    // recurse through this at once and n never interferes between them
    static int depth(int n) {
        if (n == 0) return 0;
        return 1 + depth(n - 1);
    }

    static class Picker extends Thread {                               // 1. subclass Thread
        private final String sku;
        Picker(String sku) { super("picker-" + sku); this.sku = sku; }
        @Override public void run() { results.add(sku + " depth=" + depth(500)); }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread a = new Picker("BOLT-7");
        Thread b = new Thread(() -> results.add("NUT-3 depth=" + depth(700)), "picker-NUT-3");   // 2. Runnable
        Thread c = Thread.ofPlatform().name("picker-CAM-9")                                       // 3. builder (Java 21)
                         .start(() -> results.add("CAM-9 depth=" + depth(900)));              //    already started

        Thread housekeeping = new Thread(() -> {
            while (true) { try { Thread.sleep(50); } catch (InterruptedException e) { return; } }
        }, "housekeeping");
        housekeeping.setDaemon(true);          // a daemon does not keep the JVM alive
        housekeeping.start();

        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(10_000); }
            catch (InterruptedException e) {
                Thread.currentThread().interrupt();                    // restore the flag for whoever is above us
                flagRestored = Thread.currentThread().isInterrupted();
            }
        }, "sleeper");
        sleeper.start();
        sleeper.interrupt();                   // cooperative: sleep throws, the loop above decides what to do

        a.start(); b.start();
        a.join(); b.join(); c.join(); sleeper.join();                  // nothing below runs until all four have finished

        List sorted = new ArrayList<>(results);
        Collections.sort(sorted);
        System.out.println("all joined           : " + (!a.isAlive() && !b.isAlive() && !c.isAlive()));
        System.out.println("results (sorted)     : " + sorted);
        System.out.println("states after join    : " + a.getState() + " " + b.getState() + " " + c.getState());
        System.out.println("interrupt restored   : " + flagRestored);
        System.out.println("daemon still running : " + housekeeping.isAlive() + " (the JVM exits regardless)");
        System.out.println("this thread          : " + Thread.currentThread().getName());
    }
}

Four things to take from it:

  • Subclassing Thread is the oldest form and the worst. It couples the work to the worker. Pass a Runnable (or, from §5 on, submit it to a pool) so the same task can run on any thread. The Java 21 builder Thread.ofPlatform() is the modern spelling and has a sibling, ofVirtual(), in §7.
  • start() creates the thread; run() does not. Calling a.run() directly would execute the picker's code on main, sequentially, with no second thread at all — a mistake that compiles and "works".
  • join() is how a thread waits for another to finish. It is also a memory barrier: after it returns you are guaranteed to see everything the joined thread wrote (§2). That is why the results are read only after the joins.
  • The daemon is still alive when main ends, and the JVM exits anyway. The JVM shuts down when the last non-daemon thread finishes. Forget setDaemon(true) on a background loop and your program never exits; set it on a thread doing real work and that work is cut off mid-write.

Thread states

A thread is always in exactly one of six states, and Thread.getState() reports it. The names matter because they are what a thread dump shows you when something is stuck.

count++ is three operations

The compiler turns count++ on a field into a load from the heap into a register, an add, and a store back. Between any two of those steps the scheduler can switch to another thread, which does the same three steps on the same field. Seeing it happen for real

Four pickers each increment a plain int a million times, and in parallel an AtomicInteger the same number of times. A CountDownLatch holds all four at a start line so they genuinely run together. The program prints the comparison, not the number: the number is different on every run and every machine, which is itself the lesson.

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class LostUpdate {
    static int plain;                                   // plain++ is load, add, store: three steps
    static final AtomicInteger atomic = new AtomicInteger();
    static final int PICKERS = 4, PER_PICKER = 1_000_000;

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch go = new CountDownLatch(1);      // a start gate, so all four run at once
        Thread[] pickers = new Thread[PICKERS];
        for (int t = 0; t < PICKERS; t++) {
            pickers[t] = new Thread(() -> {
                try { go.await(); } catch (InterruptedException e) { return; }
                for (int i = 0; i < PER_PICKER; i++) {
                    plain++;                            // RACE: another thread can store between our load and our store
                    atomic.incrementAndGet();           // one indivisible read-modify-write
                }
            }, "picker-" + t);
            pickers[t].start();
        }
        go.countDown();
        for (Thread p : pickers) p.join();

        int expected = PICKERS * PER_PICKER;
        System.out.println("expected               : " + expected);
        System.out.println("plain int lost updates : " + (plain < expected));
        System.out.println("AtomicInteger exact    : " + (atomic.get() == expected));
    }
}
  
expected               : 4000000
plain int lost updates : true
AtomicInteger exact    : true

Run it yourself and print plain: you will typically see somewhere between one and three million, different every time. Nothing about the program is random. The variation is the scheduler, and a program whose answer depends on the scheduler has a race condition.

A seeded scheduler runs each thread for a random slice of load / add / store steps before switching. Every switch that lands between a load and its store costs an increment. This is a model of the race, not a JVM; press Run again for a different interleaving.

Stopping a thread: interruption is a request

There is no safe way to kill a thread from outside; Thread.stop() was removed in Java 20 because it left locks and data in whatever state they happened to be in. What exists instead is a flag. t.interrupt() sets it; the target thread checks it, or is woken from a blocking call by InterruptedException, and decides for itself how to stop cleanly. Three rules keep this cooperative scheme working:

// a loop that does not block must check the flag itself
while (!Thread.currentThread().isInterrupted()) {
    pickNextOrder();                 // CPU work, no sleeping or waiting
}
// fall out of the loop: release resources, return normally

isInterrupted() reads the flag and leaves it set. The static Thread.interrupted() reads and clears it, which is almost never what you want in a loop condition.

// a blocking call throws InterruptedException AND CLEARS THE FLAG
try {
    queue.take();                    // or sleep(), join(), wait(), Future.get()
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // put the flag back for the code that called us
    return;                               // then stop what we were doing
}

If you cannot propagate the exception (because a Runnable cannot throw it), restoring the flag is how the next layer up — a pool worker, a loop — finds out it was asked to stop. This is exactly what the sleeper thread in the worked example does.

try {
    Thread.sleep(1_000);
} catch (InterruptedException e) { }    // the interruption is now lost forever

The empty catch is the single most common concurrency bug an IDE will write for you. The flag was cleared by sleep, you threw the exception away, and the thread that asked you to stop will wait for you indefinitely. At minimum, restore the flag.

When a service hangs, the first diagnostic is a thread dump: jstack <pid>, or jcmd <pid> Thread.print, or Ctrl+Break on Windows and kill -3 elsewhere. It lists every thread, its state, and its stack. Here are two entries from a stuck warehouse, annotated:

Read it bottom-up per thread, and look for the same monitor address in a waiting to lock line and a locked line. Here picker-NUT-3 holds monitor 0x…3c40 while doing network I/O, and picker-BOLT-7 is BLOCKED waiting for it. One slow socket has serialised every picker in the building. The fix is in §3: never hold a lock across I/O. A dump with many threads BLOCKED on one address is contention; two threads each waiting to lock what the other has locked is deadlock, and modern dumps print Found one Java-level deadlock at the bottom to save you the search.

Thread gotchas
  • An exception in a thread kills only that thread. run() throwing an unchecked exception prints a stack trace to stderr and the thread dies; main never hears about it and the JVM carries on. Install Thread.setDefaultUncaughtExceptionHandler to log and alert, and prefer executors (§5), whose Future captures the exception for you.
  • ThreadLocal leaks in pools. A value set on a pool thread stays on it after the task ends, and the next task — possibly a different user's request — inherits it. Always remove() in a finally. Java 21 adds ScopedValue (preview) for exactly this reason.
  • Priorities are hints the OS may ignore. setPriority does nothing on most Linux configurations. Code that relies on a high-priority thread running first is wrong on the machine it will be deployed to.
  • sleep and wait are not the same kind of thing. Thread.sleep pauses and holds any locks it owns. Object.wait releases the monitor it is called on and must be called inside synchronized — it is a signalling primitive (§3), not a delay.
  • Platform threads are expensive. Each reserves roughly a megabyte of stack and costs a kernel call to create and to switch. Creating one per request works until the first busy day; §5 and §7 are the answers.

Check yourself

1.A colleague replaces picker.start() with picker.run() "because it's clearer". The program still prints the right results. What actually changed?

B. run() is an ordinary method; calling it executes the body on whichever thread called it. Only start() asks the OS for a new thread and then invokes run() on it. The results are correct because the work still happened — just with no concurrency, which is why this mistake survives code review.

A is the misconception exactly. C: the thread object stays NEW because it never started; join() on a NEW thread simply returns immediately. D: that exception comes from calling start() twice, not from calling run().

2.In the worked example, the sleeper's catch block calls Thread.currentThread().interrupt() after catching InterruptedException. Why is that necessary?

C. Blocking methods clear the flag as they throw. If the catch block cannot propagate the exception — a Runnable cannot — re-setting the flag is the only way a pool worker or an outer loop can learn that the thread was asked to stop.

A: interrupt() is called on the current thread, not on the interrupter. B would be true of a loop that slept again, but the point is the opposite — to stop, not to keep throwing. D: a thread terminates when run() returns, flag or no flag.

3.main has returned. Which of these threads keep the JVM running? Select all that apply.

A and C. The JVM exits when the last non-daemon thread ends, and a thread's state — sleeping, blocked, running — is irrelevant to that rule. Both A and C are ordinary platform threads, non-daemon by default, so each alone keeps the process alive, possibly forever.

B is a daemon: the JVM abandons it at exit, loop or no loop. D: virtual threads are always daemon threads (§7), so a program whose only remaining work is on virtual threads exits — a surprise the first time it happens.
