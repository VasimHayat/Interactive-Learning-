Section 4

Atomics and concurrent collections

A lock is a pessimist: it assumes a conflict and makes everyone else wait. For a single-word update — a counter, a reference, a stock level — there is a cheaper optimist: do the computation without any lock, then ask the CPU to install the result only if nobody else changed the value meanwhile, and retry if someone did. That instruction is compare-and-swap (CAS), every modern processor has it, and java.util.concurrent is built on it from the atomics up to ConcurrentHashMap.

// what AtomicInteger.compareAndSet(expected, update) does, as one indivisible hardware step:
if (memory[address] == expected) { memory[address] = update; return true; }
else                             { return false; }

Because the compare and the swap are one instruction, two threads that both read 500, both compute 499, and both try to CAS — one succeeds and one is told no. The loser re-reads (499), recomputes (498), tries again. Nobody blocked, no lock was held, and no update was lost. Under light contention this beats a lock comfortably; under heavy contention the retries pile up, which is where LongAdder comes in.

Worked example: counting and reserving without a lock

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.AtomicReference;
import java.util.concurrent.atomic.LongAdder;

public class Atomics {

    /* A bounded decrement with compare-and-swap: read, compute, try to swap,
       and retry if another thread moved the value first. No lock, and the
       invariant (never below zero) still holds. */
    static final class Stock {
        private final AtomicInteger units;
        Stock(int units) { this.units = new AtomicInteger(units); }

        boolean reserve(int qty) {
            while (true) {
                int current = units.get();
                if (current < qty) return false;            // refuse: nothing to swap
                if (units.compareAndSet(current, current - qty)) return true;
                // CAS failed: someone else changed units between get and CAS — loop
            }
        }
        int units() { return units.get(); }
    }

    record Price(String sku, int cents) { }

    static void runAll(int threads, Runnable body) throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1), done = new CountDownLatch(threads);
        for (int t = 0; t < threads; t++) {
            new Thread(() -> {
                try { start.await(); body.run(); } catch (InterruptedException e) { }
                done.countDown();
            }).start();
        }
        start.countDown();
        done.await();
    }

    public static void main(String[] args) throws InterruptedException {
        // ── incrementAndGet is one indivisible operation ────────────────────
        AtomicInteger picks = new AtomicInteger();
        runAll(8, () -> { for (int i = 0; i < 100_000; i++) picks.incrementAndGet(); });
        System.out.println("picks            = " + picks.get() + " (expected 800000)");

        // ── CAS loop: 8 threads fight over 600 units, 100 attempts each ─────
        Stock stock = new Stock(600);
        AtomicInteger reserved = new AtomicInteger(), refused = new AtomicInteger();
        runAll(8, () -> {
            for (int i = 0; i < 100; i++) {
                if (stock.reserve(1)) reserved.incrementAndGet(); else refused.incrementAndGet();
            }
        });
        System.out.println("reserved         = " + reserved.get());
        System.out.println("refused          = " + refused.get());
        System.out.println("units left       = " + stock.units());
        System.out.println("never negative   = " + (stock.units() >= 0 && reserved.get() + stock.units() == 600));

        // ── LongAdder: the counter for write-heavy contention ────────────────
        LongAdder cents = new LongAdder();
        runAll(8, () -> { for (int i = 0; i < 10_000; i++) cents.add(25); });
        System.out.println("revenue (cents)  = " + cents.sum());

        // ── AtomicReference: swap an immutable record atomically ────────────
        AtomicReference price = new AtomicReference<>(new Price("BOLT-7", 80));
        runAll(4, () -> {
            for (int i = 0; i < 1_000; i++) {
                Price old, updated;
                do {
                    old = price.get();
                    updated = new Price(old.sku(), old.cents() + 1);
                } while (!price.compareAndSet(old, updated));
            }
        });
        System.out.println("price after 4000 = " + price.get());
    }
}

The reserve loop is the pattern to memorise: read, decide, CAS, retry. The refusal happens before the CAS, on the value you just read, and the CAS guarantees that the value you decided on is the value you are decrementing. Note that the result is deterministic even though the interleaving is not: 800 attempts against 600 units must produce exactly 600 reservations, because the invariant is enforced on every path. The AtomicReference variant shows the same loop on an object: because Price is an immutable record, "update" means "build a new one and swap the reference", and a torn read is impossible.

Every round, all the threads that are still running read the same current value and compute the same candidate, exactly one CAS wins, and the rest discover their expected is stale and go round again. With n contenders, finishing the whole batch costs about n(n+1)/2 CAS attempts for n successful updates — quadratic wasted work. That is the contention cost of optimism, and the reason the next two tools exist.

LongAdder, and the ABA problem

LongAdder is a counter that notices contention and splits itself into per-thread cells; sum() adds them up on read. Writes stop colliding, so eight threads incrementing see almost no retries, at the cost of a sum() that is a snapshot rather than an atomic value and cannot be used for a CAS. Use it for statistics and metrics — things you increment constantly and read occasionally. Use AtomicLong when you need compareAndSet or an exact read-modify-write result.

ABA is the one blind spot of CAS. Thread 1 reads value A and gets descheduled. Thread 2 changes A to B and back to A. Thread 1 wakes, its CAS sees A, and succeeds — even though the world changed underneath it. For a plain counter that is harmless. For a reference to the head of a lock-free list it is a corruption, because the node that looks the same may now have a different next. AtomicStampedReference pairs the reference with a version counter so that an A that went away and came back no longer compares equal. In practice you will rarely write such a structure; you need to recognise the hazard when reading one.

Worked example: the concurrent collections

Each collection in java.util.concurrent makes a specific promise, and the shape of the API tells you what it is. ConcurrentHashMap.merge is atomic for that key, which is what makes it safe to count from eight threads without a lock. computeIfAbsent is atomic too, which is what makes "create the list if missing, then add" safe. A CopyOnWriteArrayList lets you iterate while others write, by copying the array on every write. An ArrayBlockingQueue blocks a producer when full and a consumer when empty. And a ConcurrentSkipListMap is the sorted map you reach for when a TreeMap would need a lock.

import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentSkipListMap;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.CountDownLatch;

public class ConcurrentMaps {

    enum Category { FASTENER, STRUCTURAL, MOTION }
    record Product(String sku, Category category) { }

    static final List CATALOGUE = List.of(
        new Product("BOLT-7", Category.FASTENER), new Product("NUT-3", Category.FASTENER),
        new Product("PIN-2", Category.FASTENER),  new Product("GIRD-1", Category.STRUCTURAL),
        new Product("ROD-4", Category.STRUCTURAL), new Product("CAM-9", Category.MOTION));

    static void runAll(int threads, Runnable body) throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1), done = new CountDownLatch(threads);
        for (int t = 0; t < threads; t++) {
            new Thread(() -> { try { start.await(); body.run(); } catch (InterruptedException e) { } done.countDown(); }).start();
        }
        start.countDown();
        done.await();
    }

    public static void main(String[] args) throws InterruptedException {
        // ── merge: an atomic read-modify-write per key ──────────────────────
        ConcurrentHashMap picks = new ConcurrentHashMap<>();
        runAll(8, () -> {
            for (int i = 0; i < 1_000; i++) {
                Product p = CATALOGUE.get(i % CATALOGUE.size());
                picks.merge(p.sku(), 1, Integer::sum);           // never lost, never double-counted
            }
        });
        System.out.println("picks by sku       = " + new TreeMap<>(picks));
        int total = picks.values().stream().mapToInt(Integer::intValue).sum();
        System.out.println("total picks        = " + total + " (expected 8000)");

        // ── computeIfAbsent: build a multimap without a race on the list ────
        ConcurrentHashMap> byCategory = new ConcurrentHashMap<>();
        runAll(4, () -> {
            for (Product p : CATALOGUE) {
                byCategory.computeIfAbsent(p.category(), k -> new CopyOnWriteArrayList<>()).addIfAbsent(p.sku());
            }
        });
        System.out.println("by category        = " + new TreeMap<>(byCategory));

        // ── compute: a conditional decrement that cannot go negative ────────
        ConcurrentHashMap onHand = new ConcurrentHashMap<>(Map.of("BOLT-7", 500));
        runAll(8, () -> {
            for (int i = 0; i < 100; i++) {
                onHand.compute("BOLT-7", (k, v) -> v != null && v > 0 ? v - 1 : v);   // 800 attempts, floor at 0
            }
        });
        System.out.println("BOLT-7 on hand     = " + onHand.get("BOLT-7") + " (800 attempts against 500)");

        // ── CopyOnWriteArrayList: iterate a snapshot while others write ─────
        CopyOnWriteArrayList listeners = new CopyOnWriteArrayList<>(List.of("audit", "metrics"));
        for (String l : listeners) {                       // the iterator holds the old array ...
            if (l.equals("audit")) listeners.add("alerts");  // ... so this write does not throw
        }
        System.out.println("listeners          = " + listeners);

        // ── ArrayBlockingQueue: hand-off with a poison pill ─────────────────
        BlockingQueue queue = new ArrayBlockingQueue<>(8);
        int n = 2_000;
        long[] consumed = new long[1];
        Thread producer = new Thread(() -> {
            try { for (int i = 1; i <= n; i++) queue.put(i); queue.put(-1); }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        Thread consumer = new Thread(() -> {
            try { for (int v; (v = queue.take()) != -1; ) consumed[0] += v; }
            catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        producer.start(); consumer.start();
        producer.join(10_000); consumer.join(10_000);
        System.out.println("consumed sum       = " + consumed[0] + " (expected " + ((long) n * (n + 1) / 2) + ")");
        System.out.println("queue drained      = " + queue.isEmpty());

        // ── ConcurrentSkipListMap: concurrent AND sorted ────────────────────
        ConcurrentSkipListMap sorted = new ConcurrentSkipListMap<>();
        runAll(4, () -> { for (Product p : CATALOGUE) sorted.merge(p.sku(), 1, Integer::sum); });
        System.out.println("skip list          = " + sorted);
        System.out.println("first / last key   = " + sorted.firstKey() + " / " + sorted.lastKey());

        // ── nulls are rejected at runtime, not by the compiler ──────────────
        try { picks.put("HUB-8", null); }
        catch (NullPointerException e) { System.out.println("null value         = NullPointerException"); }
    }
}

Every printed line is a fact that holds on any machine — totals after every thread has joined, maps copied into a TreeMap for a stable order. The CopyOnWriteArrayList loop is the one that would have thrown ConcurrentModificationException on an ArrayList (Fundamentals §12); here the iterator walks the array that existed when it was created, and the write builds a new one. And the last line is a trap that compiles cleanly: ConcurrentHashMap rejects null keys and values at runtime, because in a concurrent map "get returned null" must mean absent unambiguously — there is no safe moment to call containsKey afterwards.

Inside ConcurrentHashMap

The table is the same array of bins as HashMap (Intermediate §11). A write to an empty bin is a single CAS on the array slot — no lock at all. A write to an occupied bin synchronizes on that bin's first node, so two writers collide only if their keys hash to the same bin. With 16 bins that is frequent; with 65,536 it almost never happens. Resizing is cooperative: threads that arrive during a resize help move bins instead of waiting.

The older design, lock striping (Java 5–7's 16 "segments"), is where the mental model "a concurrent map is N small synchronized maps" comes from. It is still a useful picture, and still the right technique when you build your own.

  • Atomic per key: put, putIfAbsent, remove(k, v), replace, compute, computeIfAbsent, computeIfPresent, merge. The remapping function runs while the bin is locked, so it must be short and must not touch the same map — doing so throws IllegalStateException: Recursive update, or deadlocks on older versions.
  • Not atomic across keys: moving stock from BOLT-7 to NUT-3 is two operations, and a reader in between sees the units in neither place. For a cross-key invariant you are back to a lock (§3) or a transaction.
  • Not atomic at all: if (!map.containsKey(k)) map.put(k, v) — a check-then-act that another thread can interleave. The fix is the single-call putIfAbsent. The same bug on Collections.synchronizedMap is the classic one: every method is synchronized, and every pair of methods is a race.
  • Reads never block. get takes no lock; it relies on volatile node fields (§2) to see a completed write. A read that races with a write sees either the old value or the new one, never a torn mixture.
  • size() is an estimate. It is computed from counter cells (the LongAdder trick) and may be stale by the time you read it. Use mappingCount(), which returns a long, and never write if (map.size() == 0) as a synchronisation device.
  • Iterators are weakly consistent. They never throw ConcurrentModificationException, they reflect the state at some point since creation, and they may or may not show a write made during iteration. That is the right contract for a map being modified under you; it is also why you cannot count on an iteration seeing a concurrent insert.

Concurrent-collection gotchas
  • A thread-safe collection does not make your code thread-safe. Every compound action — check-then-put, read-then-update, "get the list then add to it" — is still a race unless you use the single atomic method that does both.
  • A mutable value inside a concurrent map is unprotected. map.get(k).add(x) on an ArrayList value races just as it would anywhere. Either the value is itself concurrent (as the CopyOnWriteArrayList above), or you update it inside compute.
  • computeIfAbsent with an expensive function runs it while the bin is locked, blocking other writers to that bin. Compute outside, then putIfAbsent, if the work is slow.
  • CopyOnWriteArrayList as a work queue is a classic performance bug: every add copies the array, so N adds cost O(N²). It is for rarely-changing lists only.
  • Blocking queues and interruption. put/take throw InterruptedException; swallowing it and looping makes the thread uncancellable. Restore the flag or propagate.

Check yourself

1.Eight threads each run if (!stock.containsKey(sku)) stock.put(sku, 100); on a ConcurrentHashMap. What can go wrong?

B. containsKey and put are each atomic; the pair is not. Here the overwrite is harmless (same value), but with put(sku, new Stock()) one thread's object is lost and any reference it handed out points at an orphan. putIfAbsent and computeIfAbsent make the check and the write one atomic step.

A is the misconception this section exists to remove. C — concurrent maps never throw it. D — the map's own invariant (one entry per key) is always maintained; the race is in your logic, not its structure.

2.A metrics counter is incremented by 64 threads thousands of times per second and read once a minute. Which type fits best?

C. Write-heavy, read-rare, no need for an exact atomic read-modify-write: that is the LongAdder profile exactly. Sixty-four threads hitting one AtomicLong would spend most of their time retrying a failed CAS on the same cache line.

A is correct but slow under this contention. B is wrong, not merely slow: volatile makes the read and the write each visible, but ++ is still read-add-write and loses updates (§2). D works and serialises 64 threads through one monitor.

3.Which statements about ConcurrentHashMap are true? Select all that apply.

A and D. Weakly consistent iteration is the contract; and the remapping function executing under the bin lock is why it must be fast and must not re-enter the map.

B is false — null is rejected with NullPointerException, because get returning null must unambiguously mean absent. C is false — atomicity is per key; two merge calls are two independent operations with a visible gap between them.
