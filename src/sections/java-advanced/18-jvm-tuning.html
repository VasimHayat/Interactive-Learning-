Section 9

Heap sizing, JVM flags and reading GC logs

Section 8 explained what the collector does. This section is about the knobs on the outside of it, and about the evidence the JVM leaves behind when something is wrong. Nothing here is a verified program: every number depends on the machine, the container and the workload, which is precisely why you have to learn to read the JVM's own output rather than trust a rule of thumb.

The mental model to hold: the JVM process is bigger than its heap. The heap is the part -Xmx bounds. Around it sit Metaspace (class metadata), the code cache (JIT output), thread stacks (one per thread), GC bookkeeping, direct byte buffers and whatever native libraries allocate. Most production incidents filed as "the JVM ran out of memory" are one of those other regions, or the container limit, not the heap.

The flags that matter

There are hundreds of -XX flags. These are the ones you will actually set, in roughly the order you will reach for them.

# Heap bounds. Set both to the same value in production so the heap never
# resizes under load; the JVM then skips the shrink/grow cycles.
java -Xms2g -Xmx2g ...

# In a container, size the heap as a share of the cgroup limit instead.
# The JVM reads the limit itself (it has since JDK 10). Default is 25%.
java -XX:MaxRAMPercentage=75.0 ...

# Pick the collector explicitly rather than relying on ergonomics.
java -XX:+UseG1GC ...                 # the default on server-class machines
java -XX:+UseZGC -XX:+ZGenerational ...   # sub-millisecond pauses, more CPU and memory
java -XX:+UseSerialGC ...             # one core, tiny heap: a sidecar or CLI tool

# A goal, not a guarantee: G1 sizes the young generation to try to meet it.
java -XX:MaxGCPauseMillis=100 ...

# Metaspace starts small and grows; set the initial size to avoid early full GCs
# in apps that load many classes (anything with a framework).
java -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m ...

# Thread stack size. 1 MB is the 64-bit default; thousands of platform threads
# add up. Virtual threads (§7) do not use this.
java -Xss512k ...

# Always on in production: the one artefact you need after an OOM.
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps ...

# Unified logging. Cheap enough to leave on permanently.
java -Xlog:gc*:file=/var/log/app/gc.log:time,uptime:filecount=5,filesize=20m ...

# What did ergonomics actually choose? Ask, do not guess.
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|UseG1GC|UseZGC|MaxRAMPercentage'
Ergonomics, and why the defaults surprise people

With no flags at all, the JVM picks a collector and a heap size from what it can see: G1 if there are at least two CPUs and 2 GB, Serial otherwise; a maximum heap of one quarter of available memory. On a developer laptop that is 8 GB of heap and nobody notices. In a 1 GB container it is 256 MB, and the first real load test fails with an OutOfMemoryError that goes away when someone "adds memory" — by which they mean raises the container limit, which raises the 25%. The fix was always MaxRAMPercentage or an explicit -Xmx.

Worked example: reading a GC log

This is the output of -Xlog:gc from a G1 collector on JDK 21 — the default log level, one line per collection. It is the first thing to look at when a service is slow, and the format is stable enough to be worth memorising.

[0.012s][info][gc] Using G1
[0.351s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 24M->4M(256M) 3.412ms
[1.204s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 100M->12M(256M) 5.118ms
[2.980s][info][gc] GC(2) Pause Young (Concurrent Start) (G1 Humongous Allocation) 180M->60M(256M) 7.905ms
[2.981s][info][gc] GC(3) Concurrent Mark Cycle
[3.040s][info][gc] GC(3) Pause Remark 72M->70M(256M) 1.233ms
[3.071s][info][gc] GC(3) Pause Cleanup 74M->74M(256M) 0.182ms
[3.072s][info][gc] GC(3) Concurrent Mark Cycle 91.014ms
[3.500s][info][gc] GC(4) Pause Young (Prepare Mixed) (G1 Evacuation Pause) 150M->64M(256M) 6.200ms
[3.900s][info][gc] GC(5) Pause Young (Mixed) (G1 Evacuation Pause) 140M->40M(256M) 9.871ms
[9.414s][info][gc] GC(6) Pause Full (G1 Compaction Pause) 250M->200M(256M) 212.556ms

Take line GC(1) field by field. [1.204s] is uptime when the event was logged. GC(1) is the collection's sequence number; every line about the same collection shares it, which is how the four GC(3) lines belong together. Pause Young is the kind of collection — the whole application was stopped and only the young generation was collected. (Normal) is G1's sub-type; (G1 Evacuation Pause) is the cause, here simply "the young generation filled up". Then the part you read first: 100M->12M(256M) — heap occupancy before, occupancy after, and the total committed heap in parentheses. Finally 5.118ms, the pause duration, which is what your latency percentiles feel.

Now read the shape rather than the lines. Young pauses drop occupancy from ~100 M to ~12 M each time: most objects die young, exactly as §8 predicted. GC(2) was triggered by a humongous allocation — an object bigger than half a G1 region, almost always a large array — and it also started a concurrent mark cycle, which ran for 91 ms alongside the application with only two short pauses (Remark, Cleanup). The mark found garbage in the old generation, so the next young collections became Mixed, reclaiming old regions too. And then GC(6): a Pause Full, 212 ms, from 250 M to only 200 M. That line is the problem. Full collections mean G1 could not keep up concurrently; a full collection that frees little means the live set is genuinely ~200 M in a 256 M heap, and the next one will come sooner. Either the heap is too small for the workload or something is being retained that should not be.

Will it fit in the container?

The question every deployment has to answer and few do explicitly. The JVM sizes its heap from the cgroup limit, but the heap is not the whole process, and the kernel counts the whole process.

Heap + non-heap + thread stacks against a memory limit

The percentage form and the explicit form give the same heap; the explicit form is better when something else shares the container's memory — a logging sidecar, a cache process — because then "75% of the limit" is 75% of a number that no longer describes what the JVM may use. State what you mean in megabytes.

Starting points by workload

# A request/response service in a 2 GB container, moderate allocation rate.
java -XX:MaxRAMPercentage=70 -XX:+UseG1GC -XX:MaxGCPauseMillis=100 \
     -XX:+HeapDumpOnOutOfMemoryError -Xlog:gc*:file=gc.log:time,uptime \
     -jar inventory.jar

G1 is the right default: it balances throughput and pause time and needs almost no tuning. Leave 30% for non-heap and the unexpected. Do not set -Xmn or survivor ratios — G1 sizes those itself, and fixing them removes its ability to meet the pause goal.

# A nightly re-pricing job: pauses are irrelevant, total runtime is everything.
java -Xms6g -Xmx6g -XX:+UseParallelGC -XX:ParallelGCThreads=8 \
     -Xlog:gc:file=gc.log -cp inventory.jar com.acme.Reprice

The Parallel collector has the highest throughput: it stops the world and uses every core to collect. A 200 ms pause in a job that runs for twenty minutes costs nothing. Fix -Xms to -Xmx so no time is spent growing the heap in the first minute.

# A reservation API with a 20 ms p99 target and a large live set.
java -Xms8g -Xmx8g -XX:+UseZGC -XX:+ZGenerational \
     -XX:+AlwaysPreTouch -XX:+HeapDumpOnOutOfMemoryError \
     -Xlog:gc*:file=gc.log:time,uptime -jar reservations.jar

ZGC keeps pauses under a millisecond regardless of heap size, paying with more CPU for its concurrent work and more memory headroom (it needs room to allocate while collecting). AlwaysPreTouch commits and touches the whole heap at start-up so the first requests do not pay page faults. Budget 20–30% more memory than the live set.

When it is already broken: dumps and jcmd

A heap dump is a snapshot of every object and every reference. It is the only tool that answers "what is holding this memory" rather than "how much memory is held". The workflow:

jcmd 12345 GC.heap_dump /var/dumps/inv.hprof     # live objects only, after a full GC
jmap -histo:live 12345 | head -20                # quick look: instance counts by class
# Open inv.hprof in Eclipse MAT (or VisualVM) and go straight to the
# Dominator Tree: it ranks objects by the memory that would be freed if that
# one reference were cut. A leak is a single entry retaining far more than its
# own size — a HashMap whose "retained heap" is 1.4 GB.
Useful jcmd commands
jcmd <pid> …Tells you

GC.heap_infoGeneration sizes and occupancy right now, without a dump
Thread.printA thread dump: every thread's state and stack. Three of these ten seconds apart find most deadlocks and stuck pools (§3, §5)
VM.native_memory summaryWhere non-heap memory went, by region — needs -XX:NativeMemoryTracking=summary at start-up
GC.class_histogramLive instance counts by class, cheaper than a dump
JFR.start duration=60s filename=rec.jfrStart a flight recording on a running JVM (§13)
Tuning gotchas
  • A bigger heap is not faster. It delays collections and makes each full collection longer. If the live set is 300 MB, a 16 GB heap means a very rare but very long pause. Size for the live set plus allocation headroom, then let the collector work.
  • System.gc() in application code forces a full collection with G1 and Parallel. It is almost always a leftover from a benchmark. -XX:+DisableExplicitGC exists for exactly that reason.
  • Copying flags from a blog post written for JDK 8 (-XX:+UseConcMarkSweepGC, PermSize) makes JDK 21 refuse to start or silently ignore them. Check PrintFlagsFinal after any change.
  • Metaspace is not bounded by default. A classloader leak grows it until the container dies. Set MaxMetaspaceSize so it fails as a Java error with a dump instead.
  • GC logs are cheap; the absence of them is expensive. There is no way to reconstruct what the collector did yesterday. Leave -Xlog:gc* on with rotation.

Check yourself

1.A service runs with no JVM flags in a 1 GB container and dies with OutOfMemoryError: Java heap space under load. On a 16 GB laptop the same load runs fine. What is the most likely explanation?

C. The default maximum heap is one quarter of what the JVM can see. In the container that is 256 MB; on the laptop, 4 GB. Same code, same load, sixteen times the heap. Set -XX:MaxRAMPercentage or -Xmx.

A would show as long pauses or GC overhead limit exceeded, not a plain heap-space OOM at a small size. B is backwards — the JVM has honoured cgroup limits since JDK 10, which is why the heap is small. D is invented; collectors are part of every JDK and JRE build.

2.In the log line GC(5) Pause Young (Mixed) (G1 Evacuation Pause) 140M->40M(256M) 9.871ms, what does (256M) mean?

B. before->after(total): occupancy went from 140 M to 40 M in a heap that currently has 256 M committed. The parenthesised number can grow between lines as the JVM expands the heap towards -Xmx.

A is 140 − 40 = 100M, computed, not printed. C is not shown at this log level (-Xlog:gc+heap prints generation sizes). D is only equal to the committed size once the heap has grown to its maximum, or when -Xms equals -Xmx.

3.A container is restarted by the orchestrator every few hours with exit code 137. The JVM's own logs show no error and the heap never exceeded 70% of -Xmx. Which statements are correct? Select all that apply.

A and D. Exit 137 is SIGKILL from the OOM killer: the whole process — heap, metaspace, code cache, thread stacks, direct buffers — outgrew the limit while the heap itself was fine. Non-heap is where to look, so VM.native_memory and the thread count are the right next steps.

B makes it worse: a larger heap ceiling leaves less room for everything else under the same limit. C is wrong because no OutOfMemoryError was ever thrown — the JVM never got the chance; the kernel killed it mid-instruction.
