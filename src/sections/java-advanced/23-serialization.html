Section 14

Serialization, records and the HTTP client

Objects leave the JVM two ways: as bytes handed to something you control (a file, a cache, another JVM) or as a request to a service. Java has a built-in answer for the first, Java serialization, which is thirty years old, still everywhere (RMI, HTTP sessions, caches, message queues), and the source of more critical security advisories than any other feature of the platform. You need to know how it works in order to know why you should rarely use it and how to make it safe where you must. For the second, the JDK's java.net.http.HttpClient replaced the 1997-era HttpURLConnection, and you should know its shape well enough to never reach for the old one.

Worked example: what a round trip does and does not preserve

import java.io.*;

public class SerializeRecord {

    record Product(String sku, long priceInCents) implements Serializable {
        Product {
            if (sku == null || sku.isBlank()) throw new IllegalArgumentException("sku required");
            if (priceInCents < 0) throw new IllegalArgumentException("negative price");
            VALIDATIONS++;
        }
        static int VALIDATIONS = 0;
    }

    static final class Session implements Serializable {
        private static final long serialVersionUID = 1L;
        private final String user;
        private transient String cachedToken;          // never written to the stream

        Session(String user, String token) { this.user = user; this.cachedToken = token; }
        String user() { return user; }
        String cachedToken() { return cachedToken; }
    }

    static final class Registry implements Serializable {
        private static final long serialVersionUID = 1L;
        static final Registry INSTANCE = new Registry();
        private Registry() {}
        // the stream carries a copy; readResolve swaps it for the real singleton
        private Object readResolve() throws ObjectStreamException { return INSTANCE; }
    }

    static byte[] write(Object o) throws IOException {
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) { out.writeObject(o); }
        return bytes.toByteArray();
    }

    static Object read(byte[] data, ObjectInputFilter filter) throws IOException, ClassNotFoundException {
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(data))) {
            if (filter != null) in.setObjectInputFilter(filter);
            return in.readObject();
        }
    }

    public static void main(String[] args) throws Exception {
        Product bolt = new Product("BOLT-7", 80);
        int before = Product.VALIDATIONS;
        Product copy = (Product) read(write(bolt), null);
        System.out.println("record equal after round trip   = " + bolt.equals(copy));
        System.out.println("record is a different instance  = " + (bolt != copy));
        System.out.println("canonical constructor ran again = " + (Product.VALIDATIONS == before + 1));

        Session s = (Session) read(write(new Session("vasim", "tok-123")), null);
        System.out.println("session user survived           = " + s.user());
        System.out.println("transient token after read      = " + s.cachedToken());

        Registry r = (Registry) read(write(Registry.INSTANCE), null);
        System.out.println("readResolve kept the singleton  = " + (r == Registry.INSTANCE));

        // an allow-list filter: only our own classes and the JDK types they need
        ObjectInputFilter allow = ObjectInputFilter.Config.createFilter(
                "SerializeRecord$Product;java.lang.*;java.util.*;!*");
        System.out.println("filtered read of Product        = " + ((Product) read(write(bolt), allow)).sku());
        try {
            read(write(new Session("x", "y")), allow);
            System.out.println("filtered read of Session        = allowed");
        } catch (InvalidClassException e) {
            System.out.println("filtered read of Session        = rejected (" + e.getMessage().replaceAll("\\s+", " ").trim() + ")");
        }
    }
}

  • Ordinary classes are deserialized without running any constructor. Session's fields are set directly from the stream by the JVM; the final keyword and every invariant you check in the constructor are bypassed. transient fields are simply left at their default, which is why the token comes back null.
  • Records are different, and better. A record is deserialized by calling its canonical constructor with the stream's component values, so the compact constructor's validation runs again. A stream with a negative price throws IllegalArgumentException at read time instead of producing an impossible object. This is the single strongest reason to make serializable value types records.
  • readResolve lets you substitute the object that comes out — here, to preserve a singleton — and writeReplace does the same on the way in. Together they are how you serialize an object as something simpler (an enum, an id) and rebuild it on read.
  • The filter is the security control. Without one, readObject will instantiate any class on the class path that the bytes name. The allow-list refuses Session before a single byte of it is used.

Why "deserialization of untrusted data" has its own CVE category

The bytes of a serialized stream are not data; they are instructions to the JVM: "create an instance of this class, set these fields, then call its readObject." Thousands of classes on a typical class path have readObject methods or readResolve hooks that do something — call a method on a field, look up a JNDI name, invoke a Comparator — and an attacker who controls the bytes chooses which classes, with which field values. Chaining a handful of such classes from common libraries into a sequence that ends in Runtime.exec is called a gadget chain, and public tools generate them. The 2015 Apache Commons Collections chain compromised application servers worldwide; the 2021 Log4Shell exploit used JNDI deserialization as its payload stage. None of that requires a bug in your code, only that you call readObject on bytes someone else produced.

private void writeObject(ObjectOutputStream out) throws IOException {
    out.defaultWriteObject();                // the non-transient fields
    out.writeInt(cache.size());              // then a hand-written form of the transient part
    for (var e : cache.entrySet()) { out.writeUTF(e.getKey()); out.writeInt(e.getValue()); }
}

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();
    int n = in.readInt();
    if (n < 0 || n > 10_000) throw new InvalidObjectException("absurd cache size " + n);   // validate!
    cache = new HashMap<>();
    for (int i = 0; i < n; i++) cache.put(in.readUTF(), in.readInt());
}

The private, oddly-signed writeObject/readObject pair is found by reflection. readObject is effectively a public constructor that takes a byte array, so it must validate as strictly as one. Externalizable is the all-manual variant: you write every field yourself and the class must have a public no-arg constructor.

public final class StockLevel implements Serializable {
    private final String sku; private final int onHand;
    // ... constructor validates ...

    private Object writeReplace() { return new Proxy(sku, onHand); }     // what actually gets written
    private void readObject(ObjectInputStream in) throws InvalidObjectException {
        throw new InvalidObjectException("use the proxy");               // nobody can bypass the proxy
    }
    private record Proxy(String sku, int onHand) implements Serializable {
        private Object readResolve() { return new StockLevel(sku, onHand); }   // the real constructor runs
    }
}

Effective Java item 90. The stream contains only a dumb record; reading it goes through the real constructor, so invariants hold and the class's private representation can change freely. Records made this pattern mostly unnecessary for value types, because a record is its own proxy.

The rule: Java serialization is acceptable between two JVMs you both control, running the same code, with an allow-list filter. For anything that crosses a trust boundary or a version boundary, use a format with a schema.

The HTTP client

java.net.http.HttpClient (Java 11) speaks HTTP/1.1 and HTTP/2, follows redirects if told to, has a synchronous and an asynchronous API over the same request object, and pairs naturally with virtual threads because a blocked send parks the virtual thread rather than a carrier. The shape to memorise is: one long-lived client, one immutable request per call, a body handler that says what to turn the response into.

// ONE client for the application: it owns the connection pool and the executor
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(3))               // establishing the connection
        .followRedirects(HttpClient.Redirect.NORMAL)        // not from https to http
        .version(HttpClient.Version.HTTP_2)                 // falls back to 1.1 per server
        .build();

HttpRequest req = HttpRequest.newBuilder(URI.create("https://stock.acme.example/stock/BOLT-7"))
        .timeout(Duration.ofSeconds(5))                     // the whole exchange — always set one
        .header("Accept", "application/json")
        .GET()                                              // or .POST(BodyPublishers.ofString(json))
        .build();

// synchronous: blocks this thread (fine on a virtual thread)
HttpResponse<String> res = client.send(req, HttpResponse.BodyHandlers.ofString());
if (res.statusCode() != 200) throw new IOException("stock service returned " + res.statusCode());
StockLevel level = parse(res.body());

// asynchronous: composes with everything in §6
CompletableFuture<StockLevel> future = client
        .sendAsync(req, HttpResponse.BodyHandlers.ofString())
        .thenApply(HttpResponse::body)
        .thenApply(SerializationDemo::parse)
        .orTimeout(5, TimeUnit.SECONDS);

The following program is the same API against a server it starts itself, so it runs and verifies during the build of this page with no network access. The port is chosen by the OS and never printed.

import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

public class HttpLocal {
    public static void main(String[] args) throws Exception {
        // port 0 = any free port; the real port is never printed, so the output is stable
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
        server.createContext("/stock/BOLT-7", exchange -> {
            byte[] body = "{\"sku\":\"BOLT-7\",\"onHand\":42}".getBytes(StandardCharsets.UTF_8);
            exchange.getResponseHeaders().add("Content-Type", "application/json");
            exchange.sendResponseHeaders(200, body.length);
            try (var out = exchange.getResponseBody()) { out.write(body); }
        });
        server.start();
        int port = server.getAddress().getPort();

        try {
            HttpClient client = HttpClient.newBuilder()
                    .connectTimeout(Duration.ofSeconds(5))
                    .build();

            HttpRequest ok = HttpRequest.newBuilder(URI.create("http://127.0.0.1:" + port + "/stock/BOLT-7"))
                    .timeout(Duration.ofSeconds(5))
                    .header("Accept", "application/json")
                    .GET()
                    .build();

            HttpResponse sync = client.send(ok, HttpResponse.BodyHandlers.ofString());
            System.out.println("sync  status = " + sync.statusCode());
            System.out.println("sync  body   = " + sync.body());
            System.out.println("sync  type   = " + sync.headers().firstValue("Content-Type").orElse("?"));

            CompletableFuture async = client.sendAsync(ok, HttpResponse.BodyHandlers.ofString())
                    .thenApply(HttpResponse::body)
                    .thenApply(body -> body.contains("\"onHand\":42") ? "42 on hand" : "unexpected");
            System.out.println("async result = " + async.get(5, TimeUnit.SECONDS));

            HttpRequest missing = HttpRequest.newBuilder(URI.create("http://127.0.0.1:" + port + "/stock/NOPE"))
                    .timeout(Duration.ofSeconds(5)).build();
            System.out.println("miss  status = " + client.send(missing, HttpResponse.BodyHandlers.discarding()).statusCode());
        } finally {
            server.stop(0);
        }
        System.out.println("server stopped");
    }
}

Gotchas
  • A 404 is not an exception. send throws only for transport failures (connect refused, timeout). Every HTTP status is a normal return; check statusCode() yourself.
  • No timeout means forever. The request builder's timeout defaults to none. A hung server then pins a platform thread for as long as the socket survives. Set it on every request, and connectTimeout on the client.
  • One client, not one per request. Each HttpClient owns a connection pool and threads. Creating one per call leaks both; it is the HttpClient equivalent of opening a new database connection per query.
  • serialVersionUID defaults are a time bomb. Add a method to a serializable class without a declared UID and every cached or persisted instance becomes unreadable with InvalidClassException: local class incompatible.
  • Serializable is inherited and permanent. If a superclass implements it, every subclass is serializable whether it wants to be or not, and once instances exist in storage, the serialized form is part of your API forever.
  • Jackson's default typing is Java serialization with a JSON syntax. @JsonTypeInfo(use = Id.CLASS) or enableDefaultTyping lets the document name the class to instantiate: the same gadget-chain attack, and the same mitigation (an allow-list of subtypes).

Check yourself

1.A record Price(long cents) with a compact constructor rejecting negatives is deserialized from a stream an attacker edited to contain -1. What happens?

C. Records are reconstructed through their canonical constructor, so validation in a compact constructor protects deserialization exactly as it protects new. This is one of the design goals of records.

A is true of ordinary classes, not records; that difference is the point. B invents a rule; the stream is structurally valid. D is not something any part of serialization does.

2.Your service reads a serialized Order from a message queue that other teams also publish to. Which single change most reduces the risk of remote code execution?

B. The attack works by naming gadget classes in the stream; a filter that admits only Order and the JDK types it contains refuses every gadget before it is instantiated. The better fix is to stop using Java serialization on that queue, but among these options the filter is the one that closes the hole.

A helps versioning, not security; a UID mismatch only matters for classes the attacker is not choosing. C does nothing: the JVM sets fields directly, final or not. D catches the wrong thing; gadget classes are, by construction, present on the class path.

3.Which statements about java.net.http.HttpClient are true? Select all that apply.

A and D. Status codes are data; only transport problems throw. The async API hands you an ordinary CompletableFuture.

B is the trap: there is no default request timeout at all. C is backwards: the client is the pool, and one per request leaks threads and sockets; it is designed to be shared across the whole application.
