Section 5

Executors, thread pools and Future

Creating a platform thread costs a system call, a megabyte or so of reserved stack, and a scheduler entry; and a server that creates one per request will, under load, create ten thousand of them and fall over. A thread pool separates the two decisions that new Thread(task).start() fuses together: what work to run, and how many threads should run it. You submit tasks; a fixed set of worker threads pulls them from a queue. The number of threads is a resource budget you set once, and the queue is where the overflow waits.

The abstraction is ExecutorService: submit a Runnable (no result) or a Callable<T> (a result, and it may throw), and get back a Future<T> — a handle to a result that does not exist yet. get() blocks until it does; get(timeout) gives up; cancel interrupts; and an exception thrown by the task is stored and re-thrown from get, wrapped in ExecutionException.

Worked example: a pool's whole life

One program, five lessons: a fixed pool running twenty Callables through invokeAll; a task that throws; an orderly shutdown; a scheduled task; and then a deliberately tiny pool that is handed more work than it can hold, twice — once with the default abort policy and once with caller-runs.

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.Callable;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Future;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.ThreadFactory;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class PoolExecutors {

    record Reservation(String sku, int qty) { }

    static final String[] SKUS = { "BOLT-7", "NUT-3", "CAM-9", "GIRD-1", "ROD-4" };

    public static void main(String[] args) throws Exception {
        // ── a fixed pool runs 20 Callables; invokeAll waits for every one ───
        ExecutorService pool = java.util.concurrent.Executors.newFixedThreadPool(4, named("picker"));
        List> tasks = new ArrayList<>();
        for (int i = 0; i < 20; i++) {
            final int n = i;
            tasks.add(() -> new Reservation(SKUS[n % SKUS.length], n + 1));
        }
        List> futures = pool.invokeAll(tasks);

        int totalQty = 0;
        List skus = new ArrayList<>();
        for (Future f : futures) {
            Reservation r = f.get();                       // already complete after invokeAll
            totalQty += r.qty();
            if (!skus.contains(r.sku())) skus.add(r.sku());
        }
        System.out.println("tasks completed    = " + futures.stream().allMatch(Future::isDone));
        System.out.println("total qty          = " + totalQty + " (1+2+...+20)");
        System.out.println("skus (sorted)      = " + skus.stream().sorted().toList());

        // ── a task that throws: the exception travels inside the Future ─────
        Future bad = pool.submit(() -> { throw new IllegalStateException("BOLT-7 out of stock"); });
        try {
            bad.get(5, TimeUnit.SECONDS);
        } catch (ExecutionException e) {
            System.out.println("wrapped cause      = " + e.getCause().getClass().getSimpleName() + ": " + e.getCause().getMessage());
        }

        // ── orderly shutdown: no new tasks, finish queued ones, then wait ───
        pool.shutdown();
        System.out.println("terminated         = " + pool.awaitTermination(10, TimeUnit.SECONDS));

        // ── scheduling: run once after a delay ──────────────────────────────
        ScheduledExecutorService scheduler = java.util.concurrent.Executors.newSingleThreadScheduledExecutor(named("repricer"));
        ScheduledFuture reprice = scheduler.schedule(() -> "reprice done", 20, TimeUnit.MILLISECONDS);
        System.out.println("scheduled result   = " + reprice.get(5, TimeUnit.SECONDS));
        scheduler.shutdown();

        // ── rejection: 1 thread, a queue of 1, 3 tasks that block ───────────
        CountDownLatch gate = new CountDownLatch(1);
        ThreadPoolExecutor tiny = new ThreadPoolExecutor(
            1, 1, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1), named("tiny"),
            new ThreadPoolExecutor.AbortPolicy());                    // the default handler
        Runnable blocker = () -> { try { gate.await(5, TimeUnit.SECONDS); } catch (InterruptedException e) { } };
        tiny.execute(blocker);                                          // taken by the one thread
        tiny.execute(blocker);                                          // sits in the queue
        try {
            tiny.execute(blocker);                                      // nowhere to go
            System.out.println("third task         = accepted");
        } catch (RejectedExecutionException e) {
            System.out.println("third task         = rejected (RejectedExecutionException)");
        }
        gate.countDown();
        tiny.shutdown();
        System.out.println("tiny terminated    = " + tiny.awaitTermination(10, TimeUnit.SECONDS));

        // ── CallerRunsPolicy: the submitting thread does the work itself ────
        CountDownLatch gate2 = new CountDownLatch(1);
        ThreadPoolExecutor polite = new ThreadPoolExecutor(
            1, 1, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1), named("polite"),
            new ThreadPoolExecutor.CallerRunsPolicy());
        AtomicInteger ranOnMain = new AtomicInteger();
        Runnable blocker2 = () -> { try { gate2.await(5, TimeUnit.SECONDS); } catch (InterruptedException e) { } };
        polite.execute(blocker2);
        polite.execute(blocker2);
        polite.execute(() -> { if (Thread.currentThread().getName().equals("main")) ranOnMain.incrementAndGet(); });
        System.out.println("overflow ran on    = " + (ranOnMain.get() == 1 ? "the caller (main)" : "a pool thread"));
        gate2.countDown();
        polite.shutdown();
        System.out.println("polite terminated  = " + polite.awaitTermination(10, TimeUnit.SECONDS));
    }

    // name your threads: a dump full of "pool-3-thread-7" is useless at 3 a.m.
    static ThreadFactory named(String prefix) {
        AtomicInteger n = new AtomicInteger();
        return r -> new Thread(r, prefix + "-" + n.incrementAndGet());
    }
}

Two details carry most of the weight. First, shutdown() is polite: it stops accepting work and lets queued tasks finish, and the pool is only terminated once the last one has — which is what awaitTermination waits for. shutdownNow() instead interrupts every worker and returns the tasks that never started; it is the emergency stop, and it only works on tasks that honour interruption. Forget to shut a pool down and its non-daemon workers keep the JVM alive after main returns — the classic "my program never exits". Second, the tiny pool: one worker takes the first task directly, the second sits in the one-slot queue, and the third has nowhere to go. What happens next is the rejection policy — the default throws, and CallerRunsPolicy makes the submitting thread do the work itself, which is a crude but effective form of back-pressure: a producer that is busy running a task is not producing more.

Watch a pool fill up

A ThreadPoolExecutor has a core size, a maximum size and a queue, and the order in which it uses them surprises almost everyone. It does not grow to the maximum when the core threads are busy. It queues. Only when the queue is full does it add threads beyond the core, and only when both the queue and the maximum are exhausted does it reject.

For a service that must survive a burst, construct ThreadPoolExecutor yourself with a bounded queue and a rejection policy you chose on purpose. The work-stealing pool is the ForkJoinPool, and the one you get from ForkJoinPool.commonPool() is shared with every parallel stream in the JVM: a blocking task submitted there starves every parallelStream() in the process.

Scheduling, and the exception that kills it

var scheduler = Executors.newScheduledThreadPool(1, named("repricer"));

// fixed RATE: starts every 60 s regardless of how long the last run took (runs may pile up)
scheduler.scheduleAtFixedRate(repricer::run, 0, 60, TimeUnit.SECONDS);

// fixed DELAY: waits 60 s after the previous run FINISHES — the safer default for most jobs
scheduler.scheduleWithFixedDelay(repricer::run, 0, 60, TimeUnit.SECONDS);

If a scheduled task throws, the scheduler does not log it, does not retry it, and does not run it again: the exception is captured in the ScheduledFuture nobody is reading, and the job silently stops forever. Every periodic task should catch Throwable at its top level, log, and return — or be wrapped by a utility that does.

Executor gotchas
  • A task that throws into execute() kills its worker thread and the exception goes to the thread's UncaughtExceptionHandler — usually stderr, usually unnoticed. A task submitted with submit() stores the exception in its Future instead, and if nobody calls get(), it is lost entirely. Either way: catch inside the task.
  • Blocking inside a pool on a result from the same pool — task A submits task B and calls get() — deadlocks the moment all workers are doing the same thing. Nobody is free to run B. The fix is CompletableFuture (§6), or two pools.
  • No shutdown, no exit. Pool threads are non-daemon by default; a forgotten shutdown() keeps the JVM running after main. Java 19+ ExecutorService is AutoCloseable: try (var pool = …) shuts down and waits.
  • Default thread names make a thread dump unreadable. Pass a ThreadFactory that names threads after the pool's purpose.
  • Future.cancel(true) only interrupts. A task that never checks isInterrupted() or calls a blocking method keeps running to completion, holding its thread.
  • ThreadLocal values survive between tasks on a pooled thread. Clear them in finally, or the next task inherits the previous request's user.

Check yourself

1.A ThreadPoolExecutor has core 4, max 16, and an unbounded LinkedBlockingQueue. Under sustained load, how many threads will it run?

C. Growth beyond core happens only when the queue rejects an offer. An unbounded queue never rejects, so maximumPoolSize is dead configuration: the pool runs 4 threads and the queue grows until memory runs out. This is the single most common thread-pool misconfiguration.

A is what everyone assumes and what the executor does not do. B would require the executor to watch queue length, which it does not; it only reacts to an offer failing. D — rejection needs a full queue and a full pool; this queue is never full.

2.A task submitted with submit() throws a NullPointerException, and the caller never calls get() on the returned Future. Where does the exception go?

B. submit wraps the task in a FutureTask, which catches everything and stores it for get() to re-throw as ExecutionException. No get(), no report — the worker thread quietly moves on to the next task.

A is what happens with execute(), which does not wrap the task; the exception then kills the worker and the pool replaces it. C — the task has not even run when submit returns. D — nothing an individual task does shuts a pool down.

3.Your program finishes main but the process never exits. Which are plausible causes? Select all that apply.

A and C. Both create non-daemon threads, and the JVM exits only when every non-daemon thread has ended. The fixed pool's idle core threads live forever; the scheduler's thread is waiting for the next run.

B — ForkJoinPool workers are daemon threads, so they never hold the JVM open (which is also why work left in the common pool at exit is simply abandoned). D — an unread Future is an object, not a thread; it holds nothing open.
