Section 2

The Java memory model: visibility and happens-before

Section 1 showed two threads corrupting a counter because an increment is three steps. This section is about a stranger problem: a thread writes a field, and another thread never sees the write at all. Not late — never. The reason is that "memory" is not one place. Each core has its own caches and a store buffer that holds writes before they reach shared memory; the JIT compiler keeps fields in registers and hoists reads out of loops; the CPU executes instructions out of order when they do not depend on each other. Every one of those optimisations is invisible to a single thread, which is exactly why they are legal. A second thread can see all of them.

The Java Memory Model (JLS chapter 17) is the contract that says when a write by one thread is guaranteed to be visible to a read by another. It is stated in terms of one relation, happens-before: if action A happens-before action B, then B sees the effects of A. If two threads touch the same field, at least one of them writes, and there is no happens-before between them, the program has a data race, and the JMM promises almost nothing about what the reader sees.

Worked example

Three guaranteed-visible patterns, each printing a fact that the JMM promises. There is deliberately no fourth program showing the failure: a racy read may happen to see the write on your machine today, so a demonstration of it cannot be verified. The failure is shown as a step-through below instead.

import java.util.concurrent.CountDownLatch;

public class Visibility {
    static volatile boolean stop;      // volatile: a write is guaranteed to become visible, promptly
    static int reserved;               // plain: visible to another thread only across a happens-before edge
    static int payload;                // plain, but published under a volatile write below
    static volatile int ready;

    public static void main(String[] args) throws InterruptedException {
        // 1. a volatile flag stops a spinning reader
        CountDownLatch spinning = new CountDownLatch(1);
        Thread reader = new Thread(() -> {
            spinning.countDown();
            while (!stop) Thread.onSpinWait();         // without volatile the JIT may hoist this read out of the loop
        }, "reader");
        reader.start();
        spinning.await();
        stop = true;
        reader.join(5_000);
        System.out.println("reader stopped         : " + !reader.isAlive());

        // 2. Thread.join is a happens-before edge: the plain write is visible after it
        Thread writer = new Thread(() -> reserved = 42, "writer");
        writer.start();
        writer.join();
        System.out.println("seen after join        : " + reserved);

        // 3. piggybacking: a plain write BEFORE a volatile write is visible AFTER the volatile read
        Thread producer = new Thread(() -> { payload = 7; ready = 1; }, "producer");
        producer.start();
        while (ready == 0) Thread.onSpinWait();
        System.out.println("payload after volatile : " + payload);
        producer.join();
    }
}
  
reader stopped         : true
seen after join        : 42
payload after volatile : 7

Take stop and delete the word volatile. The program is now allowed to hang: the JIT, seeing a loop that reads a field no one in this thread writes, may read it once into a register and spin on the register forever. On HotSpot it frequently does exactly that once the loop gets hot. The second block shows that you do not always need volatile: join() is itself an edge, so reserved is plain and still correctly seen. The third block is the pattern the JDK's own collections rely on — one volatile write "publishes" every plain write that preceded it in program order.

The happens-before edges

There are only a handful of ways to create the relation, and every concurrency utility in the JDK is built from them. Within one thread, program order is an edge; between threads, you need one of the rows below. The relation is transitive, which is what makes piggybacking work: plain write → volatile write → volatile read → plain read chains into one guarantee.

What volatile is, and is not

A volatile field gives you two things: every read sees the most recent write (visibility), and the compiler and CPU may not move memory operations across it in the forbidden directions (ordering). It gives you nothing about atomicity. volatile int hits; hits++ is still a load, an add and a store, and two threads still lose updates — the only difference from §1 is that each load is guaranteed fresh, which does not help. The rule of thumb:

  • A flag or a reference that one thread writes and others read: volatile is enough and cheaper than a lock.
  • A value that is read-modified-written: a lock (§3) or an atomic (§4). Never volatile alone.
  • Several fields that must change together: a lock. volatile on each of them individually does not make the combination consistent.

Safe publication and the cheapest correct answer

Most visibility bugs are publication bugs: one thread builds an object and another thread reaches it through a shared reference before, or in the middle of, construction. The final-field rule in the table removes the problem for immutable objects: once a constructor has finished writing final fields, any thread that obtains a reference to the object afterwards — through any path, locked or not — sees those fields correctly initialised. A record (Intermediate §8) is therefore safe to hand between threads with no synchronisation at all. The single most effective concurrency technique is to make shared data immutable and share it freely.

When you genuinely need a lazily created, shared mutable singleton, the two correct shapes are:

class PriceTable {
    private static volatile PriceTable instance;    // volatile is the whole point: without it a thread can see a non-null reference to a half-built object
    static PriceTable get() {
        PriceTable p = instance;                    // one volatile read on the fast path
        if (p == null) {
            synchronized (PriceTable.class) {
                p = instance;
                if (p == null) instance = p = new PriceTable();
            }
        }
        return p;
    }
}

// simpler, just as lazy, and no volatile: class initialization is done once, under a lock the JVM owns (§10)
class PriceTable2 {
    private static class Holder { static final PriceTable2 INSTANCE = new PriceTable2(); }
    static PriceTable2 get() { return Holder.INSTANCE; }
}

Double-checked locking without the volatile was the canonical broken idiom of the early 2000s, and it is still broken. The holder idiom avoids the question entirely, which is why it should be your default.

Memory model gotchas
  • "It works on my machine" proves nothing. A racy program is allowed to behave as you hoped. It will stop doing so on a different CPU, after a JIT recompilation, or at 3 a.m. under load. The only evidence that matters is a happens-before edge you can point to.
  • Synchronising the writer alone is not enough. The edge is from an unlock to a later lock of the same monitor. A synchronized setter and an unsynchronised getter is still a data race.
  • volatile on an array or collection reference covers the reference only. volatile int[] counts makes the assignment of a new array visible; counts[3]++ is still a plain, racy read-modify-write of an element. The same holds for a volatile List.
  • 64-bit plain fields may tear. A non-volatile long or double write is permitted to happen as two 32-bit halves, so a reader can see a value that was never written. In practice 64-bit JVMs do not tear, but the specification allows it; volatile forbids it.
  • Leaking this from a constructor defeats the final guarantee. Registering the object as a listener, or starting a thread that captures it, inside the constructor publishes it before the freeze. Use a static factory that constructs, then registers.
  • VarHandle offers finer modes. setRelease/getAcquire give the ordering half of volatile without the full fence, and setOpaque gives only progress. They are for library authors; §11 shows the mechanism.

Check yourself

1.static volatile int hits; and two threads each run hits++ a million times. After both join, what can hits be?

B. volatile guarantees that each load sees the latest store and that stores are ordered; it does nothing to make the three steps of ++ one step. Two threads can still load the same value and both store value+1. The theoretical minimum is tiny because, pathologically, almost every increment could be overwritten.

A and C confuse visibility with atomicity; no architecture makes a three-instruction sequence atomic by itself. D: it compiles fine, which is precisely the trap. Use AtomicInteger (§4).

2.The writer sets reserved = 42 inside synchronized (lockA). The reader reads reserved inside synchronized (lockB), where lockB is a different object. Is the reader guaranteed to see 42?

C. The monitor rule is per object. Locking lockB says nothing about writes made under lockA, so this is a data race dressed up as synchronised code — slower than no locks and exactly as wrong.

A describes a mental model ("flush the caches") that HotSpot does not implement and the JMM does not promise. B: wall-clock order is not happens-before; "after" in real time guarantees nothing without an edge. D: a final field cannot be reassigned, so the scenario could not exist; the final rule is about construction, not later writes.

3.Which of these create a happens-before edge between two threads? Select all that apply.

A, B and C. Thread start, thread termination observed through join, and the documented hand-off of every java.util.concurrent synchroniser are all edges in the table above.

D is the one that looks like it works. Sleeping orders nothing: when the reader wakes it performs an ordinary load, and the JMM permits that load to return the stale value no matter how long it waited. Code that "fixes" a visibility bug with a sleep has hidden it.
