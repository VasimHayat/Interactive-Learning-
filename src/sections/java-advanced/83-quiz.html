Self-assessment quiz

Sixteen questions covering all fourteen learning objectives. Answer every one, then submit — nothing is marked until you do, and the explanations stay hidden until then. Your answers are saved locally, so you can leave and come back.

1.Two threads share one int count and each runs count++ once. Both start with count == 41. Which final values are possible?

C. count++ is load, add, store. If both threads load 41 before either stores, both store 42 and one increment is lost; if they run one after the other, 43. A is the intuition the bug relies on. B: memory writes never throw; a race is silent. D: each thread stores at least 42, so 41 cannot survive.

2.Thread t = new Thread(task); t.start(); t.start(); — what happens on the second line's second call?

B. A Thread object goes NEW → RUNNABLE → … → TERMINATED once; start() on anything but NEW throws, even after termination. A and C describe a reusable worker, which is what a thread pool is for. D is what calling run() directly does — the classic mistake, but not this one.

3.Thread W writes price = 80 (a plain field) and then does X. Thread R does Y and then reads price. Which (X, Y) pairs guarantee R reads 80? Select all that apply.

B, C and D. Each creates a happens-before edge: volatile write → volatile read (and everything before the write rides along), countDown → await returning, and thread termination → join. A is the one people reach for and it guarantees nothing: time is not synchronisation; without an edge the JIT may hoist R's read out of a loop and R can spin forever on a stale value.

4.A team "fixes" a lost-update bug by changing int hits to volatile int hits, leaving hits++ in place. What did they get?

C. volatile orders and publishes individual reads and writes; hits++ is still three of them. A is the single most common memory-model misconception. B: it compiles fine, which is the problem. D: the race is in the Java semantics, not the hardware; it loses updates everywhere. The fix is AtomicInteger or a lock.

5.Predict the output:

static synchronized void reserve() { audit(); System.out.println("reserved"); }
static synchronized void audit()   { System.out.println("audited"); }
public static void main(String[] a) { reserve(); }

A. Both methods lock the same monitor (the Class object), and a thread that already owns a monitor may enter it again; the JVM counts the depth. B would be true of a non-reentrant lock — Java has none in the standard library except StampedLock. C is thrown by wait/notify without owning the monitor, not by nested entry. D: nothing is ever skipped.

6.transfer(a, b) locks a then b; a concurrent transfer(b, a) locks b then a. Which change makes deadlock impossible?

B. A global order over a stable, unique key breaks the circular wait. A is almost right and is the textbook trap: identity hash codes can collide, and when they do the tie must be broken with a third lock, or the order is undefined. C locks only this — the other account is unprotected, so the invariant breaks instead of deadlocking. D changes the timing, which makes the deadlock rarer and therefore harder to reproduce; it removes nothing.

7.Eight threads count picks per SKU in a ConcurrentHashMap<String, Integer> picks. Which line is correct?

C. merge performs the read-modify-write atomically for that key, inside the bin lock. A is a check-then-act in two calls; a concurrent map makes each call safe, not the pair. B locks on a String — two equal SKUs from different sources may be different objects, and interned literals are shared with the whole JVM; either way it is the wrong lock. D does not compile: get returns a value, not a variable, and the increment would be on an unboxed copy anyway.

8.Which statements about compare-and-swap are true? Select all that apply.

A and D. B is the opposite of the point: CAS never blocks; the caller reloads and retries. C: incrementAndGet is a retry loop around CAS, which is why LongAdder exists for hot counters — under heavy contention the retries pile up.

9.new ThreadPoolExecutor(2, 8, 60, SECONDS, new LinkedBlockingQueue<>()) receives 1,000 quick tasks at once. How many threads does it run at peak?

B. The growth rule is core → queue → max → reject, and the queue step only passes when offer fails. An unbounded queue never refuses, so maximumPoolSize is dead configuration. A is what everyone assumes. C describes newCachedThreadPool, whose SynchronousQueue always "fails" to queue. D needs a full queue first.

10.pool.submit(() -> { throw new IllegalStateException("boom"); }); and nobody calls get(). Where does the exception go?

C. submit wraps the task in a FutureTask that catches everything; the worker thread survives and the exception is only observable through get(). A is what happens with execute() — the difference is a frequent interview follow-up. B: submit returns before the task runs. D: the worker is unharmed, which is precisely why nothing is logged.

11.Predict the output on a thread named main:

CompletableFuture<Integer> done = CompletableFuture.completedFuture(1);
boolean onMain = done.thenApply(x -> Thread.currentThread().getName().equals("main")).join();
System.out.println(onMain);

A. A non-async stage runs on whichever thread completes the previous stage; when that stage is already complete at attach time, the attaching thread runs it inline. That is how a "callback" ends up doing heavy work on a request thread. B is the rule for thenApplyAsync with no executor. C: the rule is deterministic here. D: join is an ordinary method.

12.cf = supplyAsync(() -> { throw new IllegalStateException("offline"); }, pool).thenApply(v -> v + 1).exceptionally(e -> -1); Which are true? Select all that apply.

B and C. A failed stage skips every dependent value-stage (A is false: the function is never invoked) and passes the failure, wrapped in a CompletionException, to the first recovery stage — which is why code in exceptionally should unwrap with getCause() before matching on type. D: get() throws ExecutionException with the original as its cause; join() throws CompletionException. Neither throws the original bare.

13.A JDK 21 service moves its JDBC-heavy request handling from a 200-thread pool to one virtual thread per request. The driver does its socket reads inside synchronized methods. What happens under load?

C. In 21 a virtual thread blocking inside a monitor cannot unmount, so each carrier is held for the duration of the read — -Djdk.tracePinnedThreads shows it. A driver using ReentrantLock would be fine; JEP 491 in Java 24 fixes synchronized. A is the promise, broken by pinning. B: virtual threads are not native threads; that error belongs to platform threads. D: socket reads are exactly the blocking the JVM detects.

14.A G1 log shows a Full GC every ten minutes; each one reclaims the heap from 3.9 GB back to a steadily rising 1.2, 1.5, 1.9, 2.4 GB. What is the most likely diagnosis and first action?

B. After a Full GC only reachable objects remain, so a post-GC floor that climbs is a live set that keeps growing — something is retaining references. A buys time and moves the crash later. C changes how the garbage is collected, not how much is not garbage. D: old gen filling is normal; its post-collection minimum rising is not.

15.Predict the output:

class Prices { static final int MAX = 8; static { System.out.println("init"); } }
public class Main { public static void main(String[] a) { System.out.println(Prices.MAX); } }

A. static final int MAX = 8 is a constant variable (JLS §4.12.4); javac copies the literal into Main, and Prices is not an active use. Drop final, or make it Integer.valueOf(8), and B becomes correct. C: the JVM has no memory between runs. D: initialisation is synchronous and happens-before the first use.

16.Which statements are true? Select all that apply.

A, C and D. A is strong encapsulation of the JDK (default since 16). C was confirmed against JDK 21: the canonical constructor runs on every read and its IllegalArgumentException arrives wrapped in InvalidObjectException. D: the default retention is CLASS, kept in the bytecode but not loaded. B is false — forking isolates JVMs; it does nothing about dead-code elimination, which removes an unused result and the work that produced it. Return the value or sink it into a Blackhole.
