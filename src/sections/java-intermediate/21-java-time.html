Section 12

Dates and times with java.time

Every order has a placed timestamp, every SLA is a deadline, and every report is a window. Getting those wrong does not throw — it silently ships an order a day late twice a year, or double-counts the hour that happens twice in October. java.time (Java 8) was designed around the two ideas that the older java.util.Date never separated: a point on the timeline is not the same thing as a reading on a wall clock, and the mapping between them depends on a zone whose rules change.

Every type in the package is immutable and thread-safe, every "setter" returns a new value, months are numbered from 1, and arithmetic is explicit about whether it counts calendar units or elapsed seconds. Those four properties are what you are buying; the rest of this section is about using them correctly.

Which type holds what

The core java.time types, what each stores, and what to use it for

OffsetDateTimeDate + time + fixed offsetfixed offsetInterchange with systems that want 2026-03-28T23:30+01:00. No rules, so no surprises — and no DST.

Rule of thumb: store an Instant, display a ZonedDateTime, schedule with a ZonedDateTime. A LocalDateTime in a database column is a bug waiting for the first user outside the server's zone.

Worked example

Spring 2026 in London: at 01:00 on Sunday 29 March the clocks jump to 02:00, so the hour 01:00–01:59 never happens. In October the reverse: 01:00–01:59 on the 25th happens twice. The program below places an order the evening before the spring change and then does the things people do to timestamps.

import java.time.DayOfWeek;
import java.time.Duration;
import java.time.Instant;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.Period;
import java.time.YearMonth;
import java.time.ZoneId;
import java.time.ZonedDateTime;
import java.time.format.DateTimeFormatter;
import java.time.temporal.ChronoUnit;
import java.util.Locale;

public class Times {
    public static void main(String[] args) {
        ZoneId london = ZoneId.of("Europe/London");

        // an order placed the night before the clocks go forward (29 Mar 2026, 01:00 -> 02:00)
        ZonedDateTime placed = LocalDateTime.of(2026, 3, 28, 23, 30).atZone(london);
        System.out.println("placed            = " + placed);
        System.out.println("plusDays(1)       = " + placed.plusDays(1));     // same wall clock, 23h later
        System.out.println("plusHours(24)     = " + placed.plusHours(24));   // 24h later, different wall clock

        // a time that does not exist, and one that exists twice
        ZonedDateTime inGap = LocalDateTime.of(2026, 3, 29, 1, 30).atZone(london);
        System.out.println("01:30 in the gap  = " + inGap);
        ZonedDateTime overlap = LocalDateTime.of(2026, 10, 25, 1, 30).atZone(london);
        System.out.println("01:30 in overlap  = " + overlap + " / later: " + overlap.withLaterOffsetAtOverlap());

        // one instant, three views
        Instant at = placed.toInstant();
        System.out.println("instant           = " + at);
        System.out.println("same instant NYC  = " + at.atZone(ZoneId.of("America/New_York")));
        System.out.println("same instant Tokyo= " + at.atZone(ZoneId.of("Asia/Tokyo")));

        // Period counts calendar units; Duration counts elapsed time
        LocalDate due = placed.toLocalDate().plusDays(10);
        System.out.println("SLA period        = " + Period.between(placed.toLocalDate(), due));
        System.out.println("elapsed to +1 day = " + Duration.between(placed, placed.plusDays(1)));

        // formatting: ISO is locale-free; a pattern needs a Locale
        DateTimeFormatter uk = DateTimeFormatter.ofPattern("dd MMM yyyy HH:mm", Locale.UK);
        System.out.println("ISO_LOCAL_DATE    = " + placed.format(DateTimeFormatter.ISO_LOCAL_DATE));
        System.out.println("pattern, UK       = " + placed.format(uk));

        // calendar arithmetic clamps rather than overflowing
        LocalDate jan31 = LocalDate.of(2026, 1, 31);
        System.out.println("31 Jan + 1 month  = " + jan31.plusMonths(1));
        System.out.println("truncated to hour = " + placed.truncatedTo(ChronoUnit.HOURS).toLocalDateTime());
        YearMonth ym = YearMonth.from(placed);
        System.out.println("year-month        = " + ym + " (" + ym.lengthOfMonth() + " days)");
        System.out.println("day of week       = " + placed.getDayOfWeek() + ", weekend=" + (placed.getDayOfWeek() == DayOfWeek.SATURDAY));
        System.out.println("parsed + 1 week   = " + LocalDate.parse("2026-10-15").plusWeeks(1));

        // every java.time type is immutable: this line does nothing
        placed.plusDays(30);
        System.out.println("still placed on   = " + placed.toLocalDate());
    }
}

Read the first three lines together. plusDays(1) and plusHours(24) look interchangeable and are not: the first keeps the wall clock at 23:30 and lands on the 29th, only 23 real hours later, because the day it crossed had 23 hours. The second adds exactly 24 hours of elapsed time and lands at 00:30 on the 30th. Neither is wrong — they answer different questions. "Same time tomorrow" is a calendar question; "the 24-hour timeout expires" is an elapsed-time question. Pick the method that matches the question, not the one that reads most naturally.

The Z versus +01:00 at the end of each value is the offset java.time resolved from the zone rules at that instant. The zone (Europe/London) is stable; the offset is a consequence. That is also why the gap line prints 02:30: there was no 01:30, so the value was pushed forward by the length of the gap and given the post-change offset. In the overlap, 01:30 exists twice and the earlier one (still on summer time, +01:00) is chosen unless you ask for the later.

Period is a calendar, Duration is a stopwatch

A Period is years, months and days as fields — P10D above is "ten days", and P1M is "one month" whatever length that month turns out to have. A Duration is a count of seconds — PT23H — with no idea what a month is; Duration.ofDays(1) is sugar for 86,400 seconds. The consequence on a ZonedDateTime:

  • plus(Period), plusDays, plusMonths, plusYears work on the local date-time and then re-resolve the zone. Wall clock preserved; elapsed time varies.
  • plus(Duration), plusHours, plusMinutes, plusSeconds work on the instant. Elapsed time preserved; wall clock varies.

On a LocalDateTime there is no zone, so the two agree and plusDays(1) is always 24 hours. That is exactly why it is the wrong type for anything that will later be shown in a zone: the arithmetic is done before the question of "which 24 hours" can be asked.

Month arithmetic clamps. 31 January + 1 month is 28 February, and 28 February + 1 month is 28 March — so plusMonths(1).minusMonths(1) does not necessarily return where it started. If you need "same day next month or the last day if there is none", that is the behaviour you already have; if you need something else, say it explicitly with TemporalAdjusters.lastDayOfMonth().

ZoneId versus ZoneOffset

A ZoneId such as Europe/London names a set of rules maintained in the IANA tz database that the JDK ships and updates: which offset applies when, including every historical and scheduled DST change. A ZoneOffset such as +01:00 is a fixed number of seconds from UTC and knows nothing. A ZonedDateTime holds both — the id you gave it and the offset it derived — and re-derives the offset whenever the date-time changes. An OffsetDateTime holds only the offset, which is why adding a day to it never crosses a DST boundary: it cannot.

Use ZoneId.of("Europe/London"), never ZoneId.of("BST") or "GMT+1": the three-letter abbreviations are ambiguous (CST is three different zones) and a fixed offset silently stops being right in March. When you need the server's zone, ZoneId.systemDefault() exists — but code that depends on it behaves differently on every machine it runs on, which is the problem java.time was designed to let you avoid.

Formatting and parsing

Two families of formatter. The ISO constants (ISO_LOCAL_DATE, ISO_INSTANT, ISO_ZONED_DATE_TIME) are locale-independent, round-trip exactly, and are what toString() and parse(CharSequence) use; they are the right choice for anything machine-read. Pattern formatters from ofPattern are for humans, and a human has a locale: month names, day names, am/pm markers and even digits vary. Always pass one — ofPattern("dd MMM yyyy", Locale.UK) — because the overload without a locale uses the JVM default, and the same build will print Mar on one machine and mars on another.

The pattern letters are case-sensitive and the cases are traps. MM is month, mm is minute. HH is 0–23, hh is 1–12 and is meaningless without a. yyyy is the year of era, uuuu is the proleptic year (they differ only before year 1), and YYYY is the week-based year — the one that prints 2025 for 30 December 2024, because that Monday starts ISO week 1 of 2025. YYYY has appeared in more production date bugs than any other four characters; if you did not specifically want week numbering, you wanted yyyy.

Parsing is strict by default: LocalDate.parse("2026-2-3") throws DateTimeParseException because the ISO format requires two-digit months. That strictness is a feature — a lenient parser is how 31/02/2026 turns into 3 March without anyone noticing.

The legacy types, and testable time

java.util.Date is a mutable millisecond timestamp with a misleading name; Calendar is mutable, zero-indexes its months, and is not thread-safe. You will still meet them at the edges — JDBC drivers, old libraries, java.sql.Timestamp — so know the bridges and keep them at the boundary: date.toInstant() and Date.from(instant); calendar.toInstant(); timestamp.toLocalDateTime(). Convert on the way in, work in java.time, convert on the way out.

Code that calls Instant.now() or LocalDate.now() directly cannot be tested for "what happens at midnight" or "what happens during the DST overlap" without waiting for those moments. Every now() has an overload taking a Clock; inject one. In production, Clock.systemUTC(). In a test, Clock.fixed(Instant.parse("2026-10-25T00:30:00Z"), ZoneId.of("Europe/London")), and the overlap is now a unit test that runs in a millisecond. That is also why every program in this module uses fixed dates: the output has to be the same on the day you read it as on the day it was built.

Five ways to get it wrong without an exception
  • Ignoring the return value. placed.plusDays(30); on its own does nothing — every java.time type is immutable, and the new value was discarded. The program above does exactly this on its highlighted last lines to prove it. Static analysis tools flag it; the compiler does not.
  • YYYY in a pattern. Week-based year. Correct for 51 weeks and wrong at the one moment nobody is watching.
  • Storing a LocalDateTime for an event. Without a zone it is not a point in time. Two servers in two zones will disagree about when it happened, and there is no way back to the truth.
  • Duration.ofDays(1) where you meant "tomorrow". It is 86,400 seconds. Twice a year, in every zone with DST, that is not one calendar day.
  • equals on ZonedDateTime. It compares the zone and the local fields, so the same instant viewed from London and Tokyo is not equal. Use isEqual, or compare the Instants.

Check yourself

1.A courier promise says "delivered within 24 hours of the order being placed". An order is placed at 23:30 on 28 March 2026 in London. Which expression gives the deadline, and when is it?

C. "Within 24 hours" is elapsed time, so it is a Duration question and plusHours(24) is the right tool. The night of 28–29 March has only 23 hours in London, so 24 real hours after 23:30 is 00:30 on the 30th.

A is what plusDays(1) really produces, but it is only 23 hours later — the courier would be judged against a deadline one hour too early. B and D each pair a method with the result the other method gives.

2.You are storing a customer's chosen delivery slot — "Tuesday 7 April 2027, 09:00, at their address in Madrid" — to be acted on next year. Which type should the field be?

B. A future appointment is a wall-clock promise in a place. If Spain changes its DST rules before April 2027 — governments do — a ZonedDateTime re-resolves to the new correct instant when the JDK's tz data is updated, and still means 09:00 on the customer's clock.

A freezes the instant under today's rules; after a rule change it would be an hour off and nothing would flag it. "Store instants" is the rule for things that have happened, not for promises about the future. C loses the zone entirely — "obvious from the address" is not something the type system can see, and the next developer will call atZone(systemDefault()). D hard-codes an offset that is only correct in summer; it is the fixed-offset mistake with a type to make it look deliberate.

3.What does LocalDate.of(2024, 12, 30).format(DateTimeFormatter.ofPattern("YYYY-MM-dd", Locale.UK)) produce?

C. Upper-case Y is the week-based year. 30 December 2024 is a Monday, and under the UK's ISO week rules that Monday begins week 1 of 2025, so the year field prints 2025 while the month and day still print December 30. The result is a date that does not exist.

A is what yyyy prints and what the author meant. B: Y is perfectly valid, which is the whole problem. D: a pattern is a runtime string; the compiler has no opinion about its contents.
