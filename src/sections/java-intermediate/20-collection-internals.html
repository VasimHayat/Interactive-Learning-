Section 11

Inside the collections

Fundamentals §12 told you which collection to pick and what each operation costs. This section opens them up, because the costs are not laws of nature: they hold only while certain conditions do. HashMap.get is O(1) only if the hash function spreads keys and the key never changes. ArrayList.add is O(1) only on average, with occasional O(n) pauses. Knowing the mechanism is what lets you predict when the guarantee is about to break, and the warehouse's stock map, keyed by SKU and consulted on every pick, is exactly where that prediction matters.

HashMap, one put at a time

A HashMap is an array of bins (the table), each holding zero or more entries. Putting a key means finding its bin, then checking the entries already there:

int h = key.hashCode();                 // 1. the key's own 32-bit hash
h = h ^ (h >>> 16);                     // 2. "spread": fold the high bits into the low ones
int index = (table.length - 1) & h;     // 3. the bin: a mask, not a modulo, because length is a power of 2
// 4. walk the bin: an entry with the same hash AND key.equals(existing) means replace, else append
  • Step 3 only uses the low bits of h, which is why step 2 exists: a hashCode whose variation is all in the high bits (think of keys that are multiples of 65536) would otherwise collide into one bin.
  • Each bin is a linked list of entries. Once a bin holds 8 entries and the table has at least 64 bins, the list is converted to a red-black tree so that lookups in that bin become O(log n) instead of O(n). This is the JDK defending itself against a bad hashCode; it needs the keys to be Comparable to do a good job.
  • The full hash is stored in each entry, so the walk compares ints first and calls equals only on a hash match. A cheap hashCode and an exact equals is the pair the structure is built for.

Load factor and resizing

Bins fill up as entries arrive, and long bins make every operation slower. So the map tracks a threshold, capacity × loadFactor, and when the entry count exceeds it the table doubles and every entry is re-inserted. The default load factor of 0.75 is the trade-off the JDK authors settled on: on average under one entry per bin, with the table only a third empty. Watch what that costs as a map grows.

Grow a HashMap and watch it resize

Three consequences follow from the resize rule. The amortised cost of put is still O(1), because doublings are geometric: a map that reached 200 entries did about 200 + 100 + 50 + … ≈ 400 re-insertions in total, not 200 × 200. A map whose size you know in advance should be created with that capacity (divided by the load factor), which skips every resize. And iteration order changes on resize: entries move to new bins when the mask gains a bit, so code that "worked" because a HashMap happened to iterate in insertion order breaks the day it grows past 12 entries.

Worked example

The mutable-key failure, three idioms that replace get-check-put, the ordered maps, and the fail-fast iterator, all in one program.

import java.util.ArrayList;
import java.util.ConcurrentModificationException;
import java.util.HashMap;
import java.util.Iterator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

public class MapInternals {

    static final class Bin {                        // a mutable key: the mistake this section is about
        String code;
        Bin(String code) { this.code = code; }
        @Override public boolean equals(Object o) { return o instanceof Bin b && b.code.equals(code); }
        @Override public int hashCode() { return code.hashCode(); }
    }

    public static void main(String[] args) {
        Map stock = new HashMap<>();
        Bin key = new Bin("A-01");
        stock.put(key, 40);
        key.code = "A-02";                           // the hash changes; the entry stays in the old bucket
        System.out.println("size=" + stock.size()
                + "  containsKey(A-01)=" + stock.containsKey(new Bin("A-01"))
                + "  containsKey(A-02)=" + stock.containsKey(new Bin("A-02"))
                + "  containsKey(key)=" + stock.containsKey(key));

        Map> byCategory = new TreeMap<>();
        byCategory.computeIfAbsent("FASTENER", k -> new ArrayList<>()).add("BOLT-7");
        byCategory.computeIfAbsent("FASTENER", k -> new ArrayList<>()).add("NUT-3");
        byCategory.computeIfAbsent("STRUCTURAL", k -> new ArrayList<>()).add("GIRD-1");
        System.out.println("multimap  " + byCategory);

        Map picks = new TreeMap<>();
        for (String sku : List.of("BOLT-7", "NUT-3", "BOLT-7", "BOLT-7")) picks.merge(sku, 1, Integer::sum);
        System.out.println("counts    " + picks + "  CAM-9 -> " + picks.getOrDefault("CAM-9", 0));

        Map linked = new LinkedHashMap<>();
        Map sorted = new TreeMap<>();
        for (String sku : List.of("ROD-4", "BOLT-7", "NUT-3")) { linked.put(sku, 1); sorted.put(sku, 1); }
        System.out.println("linked    " + linked.keySet() + "  insertion order");
        System.out.println("tree      " + sorted.keySet() + "  sorted order");

        TreeMap bands = new TreeMap<>(Map.of(0, "small", 100, "medium", 1_000, "large"));
        System.out.println("250c is " + bands.floorEntry(250).getValue() + ", bands under 1000: " + bands.headMap(1_000).keySet());

        Map lru = new LinkedHashMap<>(16, 0.75f, true) {   // true = access order
            @Override protected boolean removeEldestEntry(Map.Entry e) { return size() > 2; }
        };
        lru.put("BOLT-7", 1); lru.put("NUT-3", 1);
        lru.get("BOLT-7");                           // touching it makes NUT-3 the eldest
        lru.put("CAM-9", 1);
        System.out.println("lru       " + lru.keySet() + "  NUT-3 evicted: least recently used");

        List toShip = new ArrayList<>(List.of("BOLT-7", "NUT-3", "CAM-9", "ROD-4"));
        try {
            for (String s : toShip) if (s.startsWith("B")) toShip.remove(s);
        } catch (ConcurrentModificationException e) {
            System.out.println("for-each remove -> ConcurrentModificationException, list now " + toShip);
        }
        toShip.removeIf(s -> s.startsWith("N"));
        for (Iterator it = toShip.iterator(); it.hasNext();) if (it.next().startsWith("C")) it.remove();
        System.out.println("removeIf + Iterator.remove -> " + toShip);
    }
}

The first line is the one to stare at. The map holds one entry and cannot find it by any key, including the very object that was used to put it. The entry sits in the bin chosen for the hash of "A-01"; a lookup for "A-02" goes to a different bin, and a lookup for "A-01" reaches the right bin but then fails the equals check against a key that now says "A-02". Nothing throws. The entry is simply unreachable until a resize happens to move it, at which point it may become reachable under the new key, which is worse, because now the behaviour depends on how many other entries exist. The cure is the one §10 gave: keys are immutable, full stop. Records and strings are good keys; anything with a setter is not.

computeIfAbsent (lines 30 to 32) is the idiom for a map of collections: one call creates the list on first sight of the key and returns the existing one afterwards. merge (line 36) is the idiom for counting and summing. Both replace a three-line get, null check, put dance that is easy to get wrong and, on concurrent maps, impossible to make atomic by hand.

The other structures

A plain Object[] plus a size. get(i) is an array read. add writes at size and increments it; when the array is full, a new one of 1.5× the length is allocated and the old contents copied with System.arraycopy. That copy is O(n), but it happens only every 1.5× growth, so the cost per add averages out to O(1): amortised constant time.

  • new ArrayList<>(expected) skips the growth copies. ensureCapacity(n) does the same later; trimToSize() gives back the slack after a bulk load.
  • add(0, x) and remove(0) shift everything: O(n). A queue built on ArrayList is a quadratic accident waiting to happen; use ArrayDeque.
  • Removing never shrinks the array. A list that once held a million elements and now holds ten still owns a million slots until you trimToSize() or replace it.

A ring buffer: an array with a head and tail index that wrap around the end. Adding at either end moves one index; nothing shifts. When the ring is full it doubles and the elements are copied into the new array in order.

  • O(1) at both ends makes it the right stack and the right queue. Stack is a synchronized legacy class; LinkedList pays a node allocation per element and scatters them across the heap.
  • No index access by design: get(i) does not exist, which is the API telling you what the structure is for.
  • Rejects null elements, because poll() returns null to mean "empty".

A red-black tree: a binary search tree that rebalances itself on every insert and delete so that its height stays within 2 log₂ n. Every operation walks from the root, comparing with compareTo or the comparator at each node: O(log n) and never worse, regardless of insertion order.

  • No hashing, no equals, no resizing. Keys must be mutually comparable or the first put throws ClassCastException.
  • Pays for its order with navigation: firstKey, floorEntry(k) (the greatest key ≤ k, used for the price bands above), ceilingKey, headMap, tailMap, subMap. The sub-map views are live: writes to them go into the tree.
  • About 3–5× slower than HashMap for plain lookups and heavier per entry. Pick it for the navigation, not for the sort; a one-off sorted report is cheaper as HashMap plus a sort.

A HashMap whose entries are also threaded onto a doubly linked list. Lookups use the hash table; iteration follows the list, so the order is predictable: insertion order by default, or access order when constructed with the three-argument constructor's true, in which every get moves the entry to the tail.

  • Access order plus an overridden removeEldestEntry is a complete LRU cache in six lines, as the worked example shows.
  • Costs one extra pair of references per entry and slightly slower writes. Iteration is usually faster than HashMap's, which has to skip empty bins.
  • Resizing does not change iteration order, which removes the HashMap surprise described above. Tests that assert on a map's printed form should use this or TreeMap, never HashMap.

Fail-fast iterators

Every collection in java.util keeps a modCount that each structural change increments. An iterator remembers the count it saw at creation and compares on every next(); a mismatch throws ConcurrentModificationException. The name is misleading: no threads are involved, as the worked example shows with a single-threaded loop. The check exists because an iterator over a resized table or a shifted array would otherwise return garbage or skip elements, and a loud failure is preferable.

TechniqueSafe?Why
for-each + list.remove(x)NoThe hidden iterator's count no longer matches. Often throws on the next iteration, not the removal itself; removing the second-to-last element throws nothing, because hasNext() returns false first
Iterator.remove()YesThe iterator performs the removal and updates its own expected count
removeIf(predicate)YesOne pass, implemented by the collection itself; also the fastest option on ArrayList
Indexed loop downwards with remove(i)YesRemoval shifts only the elements already visited
Iterate a copy, modify the originalYesTwo collections, two counts; costs a copy
ConcurrentHashMap / CopyOnWriteArrayListYesWeakly consistent iterators: they never throw and reflect some or all changes made since creation. The subject of Java Advanced
Where the O(1) quietly stops being true
  • A constant hashCode is legal and catastrophic. Every key lands in one bin; the map becomes a linked list (or, past 8 entries with a 64-bin table, a tree of keys that must also be Comparable to be ordered well). Lookups go from O(1) to O(n) and nothing warns you.
  • computeIfAbsent must not modify the map inside its function. Doing so throws ConcurrentModificationException since Java 9, because the map is mid-insertion. Compute, then put, if the computation needs other entries.
  • Map.of and Set.of randomise iteration order per JVM run. Deliberately. If a test passes on your machine and fails in CI with the same code, this is a likely reason; it is also the reason none of the verified programs in this module print a HashSet.
  • Collections.unmodifiableMap on a LinkedHashMap keeps the order; Map.copyOf does not. The copy is a plain immutable map with the randomised order above. Use the view, or a TreeMap, when order must survive.
  • ArrayList.remove(int) and remove(Object) are different overloads, and a List<Integer> hits the index version with list.remove(3). Fundamentals §2 warned about it; it is worth repeating because it corrupts data silently.

Check yourself

1.A HashMap was created with default settings and has just received its 13th entry. What happened?

B. Default capacity 16, load factor 0.75, threshold 12. The 13th entry pushes the size past the threshold, the table doubles, every entry is rehashed into the larger table, and because the index mask gained a bit, entries can move to different bins and iterate in a different order.

A confuses the threshold with the capacity. C is the ArrayList rule; hash tables double so that the mask stays a power of two. D happens only when a single bin reaches 8 entries, which 13 well-spread keys will not do.

2.A Bin object is used as a HashMap key, then one of the fields its hashCode depends on is changed. What is true afterwards?

C. The entry was filed under the old hash's bin. A lookup for the new value goes to a different bin; a lookup for the old value reaches the right bin but fails equals against a key that now holds the new value. The map has no way to know a key changed, so it cannot react.

A: modCount tracks structural changes to the map, not to keys. B: nothing is re-filed except during a resize, and then the entry lands under its current hash, which can make it reappear unpredictably. D: the map does store the reference, and the worked example shows containsKey(key) returning false anyway, because the lookup recomputes the hash from the mutated object first.

3.Which of these remove matching elements from an ArrayList without risking ConcurrentModificationException? Select all that apply.

A, C and D. removeIf is implemented by the list itself in a single pass. Iterator.remove keeps the iterator's expected count in step. A downward indexed loop never uses an iterator and only shifts elements it has already passed.

B is the classic: the for-each hides an iterator, the remove bumps modCount behind its back, and the next next() throws. Worse, if the match is the second-to-last element it does not throw, because hasNext() sees cursor == size and stops, silently skipping the last element. An ascending indexed loop has the sibling bug of skipping the element that slides into the removed slot.
