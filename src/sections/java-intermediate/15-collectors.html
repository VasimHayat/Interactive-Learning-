Section 6

Collectors and grouping

A terminal operation has to put the elements somewhere. collect is the general-purpose one, and a Collector is its recipe: how to create a container, how to add one element to it, how to merge two containers (for parallel streams), and how to finish. You will almost never write one — the Collectors class ships every recipe a report needs, and they compose: a groupingBy takes a downstream collector that decides what happens to the elements inside each group.

That composition is the whole skill. Once you can read groupingBy(classifier, mapFactory, downstream) as "bucket by this, into that kind of map, then do this to each bucket", every report in the warehouse is a one-liner, and you stop writing the nested-loop-and-temporary-map code that §11 of Fundamentals was full of.

Worked example

Seven collectors against the stock list. Every line of the output below was produced by running this program during the build.

import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;
import java.util.stream.Collectors;

public class Grouping {

    enum Category { FASTENER, STRUCTURAL, MOTION }

    record Product(String sku, Category category, int priceInCents, int onHand) {
        long stockValueInCents() { return (long) priceInCents * onHand; }
    }

    public static void main(String[] args) {
        List stock = List.of(
            new Product("BOLT-7", Category.FASTENER,        80,  400),
            new Product("NUT-3",  Category.FASTENER,        25, 1200),
            new Product("PIN-2",  Category.FASTENER,        15,    6),
            new Product("GIRD-1", Category.STRUCTURAL, 120_000,    3),
            new Product("ROD-4",  Category.STRUCTURAL,   4_500,   40),
            new Product("CAM-9",  Category.MOTION,       2_300,    2));

        // 1. groupingBy with a map factory and a downstream: stock value per category
        Map valueByCategory = stock.stream()
            .collect(Collectors.groupingBy(Product::category, TreeMap::new,
                     Collectors.summingLong(Product::stockValueInCents)));
        System.out.println("value by category = " + valueByCategory);

        // 2. partitioningBy: always exactly two keys, even when one side is empty
        Map> lowStock = stock.stream()
            .collect(Collectors.partitioningBy(p -> p.onHand() < 10,
                     Collectors.mapping(Product::sku, Collectors.toList())));
        System.out.println("low stock         = " + lowStock.get(true));
        System.out.println("healthy           = " + lowStock.get(false));

        // 3. collectingAndThen unwraps the Optional that maxBy produces
        Map priciest = stock.stream()
            .collect(Collectors.groupingBy(Product::category, TreeMap::new,
                     Collectors.collectingAndThen(
                         Collectors.maxBy(Comparator.comparingInt(Product::priceInCents)),
                         opt -> opt.map(Product::sku).orElse("-"))));
        System.out.println("priciest per cat  = " + priciest);

        // 4. joining with a separator, prefix and suffix
        String skus = stock.stream().map(Product::sku).sorted()
            .collect(Collectors.joining(", ", "[", "]"));
        System.out.println("all skus          = " + skus);

        // 5. toMap with a merge function: three FASTENER prices collide on one key
        Map cheapest = stock.stream()
            .collect(Collectors.toMap(Product::category, Product::priceInCents,
                     Math::min, TreeMap::new));
        System.out.println("cheapest per cat  = " + cheapest);

        // 6. teeing: two collectors over one pass, merged into one result
        String summary = stock.stream()
            .collect(Collectors.teeing(
                Collectors.counting(),
                Collectors.summingLong(Product::stockValueInCents),
                (count, total) -> count + " products worth " + total + "c"));
        System.out.println("summary           = " + summary);

        // 7. toMap WITHOUT a merge function throws on the first duplicate key
        try {
            stock.stream().collect(Collectors.toMap(Product::category, Product::sku));
        } catch (IllegalStateException e) {
            System.out.println("no merge fn       = " + e.getMessage());
        }
    }
}

Three things to notice. The highlighted groupingBy has three arguments — classifier, map factory, downstream — and the two-argument form groupingBy(classifier, downstream) is the same thing with a HashMap, which is why the output would be in an unspecified order without TreeMap::new. maxBy returns an Optional because a collector cannot know its group will be non-empty, so collectingAndThen exists to apply one last function to the finished container. And the final line is the error you get from the two-argument toMap: it does not pick a winner, it refuses — the merge function in step 5 is what tells it how.

These wrap another collector and change what it sees or what it returns. They are pointless on a bare stream — map and filter do that — and essential inside a group, where there is no stream to call map on.

Downstream adapter collectors

That filtering subtlety is the common one: groupingBy(Product::category, filtering(p -> p.onHand() < 10, toList())) gives you every category, some mapped to an empty list. filter(…) before the collect gives you only the categories that have a low-stock item. Both are correct; they answer different questions.

All four. partitioningBy is the only grouping that guarantees both keys. teeing is the only way to run two collectors over one pass. toMap with a merge function is the idiom for "sum into a map by key"; without Integer::sum the second line for a SKU would throw. And summarizingInt is one pass for all four statistics, where counting plus averagingInt plus minBy plus maxBy would be four.

When a loop is clearer

Collectors earn their place when the shape of the result is a standard one — a map of groups, a joined string, a summary. They stop earning it when you find yourself nesting three downstreams deep to express a rule that is two if statements in a loop, or when the "collector" needs to update two unrelated structures at once. The test is whether a colleague can read the result type and know what it contains: Map<Category, Map<Boolean, Long>> is still readable; Map<Category, Map<Boolean, Map<String, Optional<Product>>>> is a sign to write a small record and a plain loop.

Collector gotchas
  • toMap throws on duplicates and on null values. The duplicate rule is deliberate — silently keeping one would hide a data problem — but it surprises everyone once. The null value rule differs from HashMap.put, which accepts null; use Optional or a sentinel, or fall back to a loop.
  • counting() returns Long. Map<Category, Integer> n = … groupingBy(…, counting()) does not compile. Declare Long, or use summingInt(p -> 1) if you genuinely need an Integer.
  • groupingBy rejects null keys. A classifier that returns null — a product with no category — throws NullPointerException mid-collection. Map it to a sentinel first, or filter it out and report it separately.
  • The map you get back is mutable but unspecified. groupingBy and toMap promise a Map, not a HashMap; do not cast, and do not rely on its iteration order unless you supplied the factory.
  • Collectors.toList() is not Stream.toList(). The collector gives a list you may modify (today it is an ArrayList; the Javadoc does not promise it). The Java 16 stream method gives an unmodifiable list. Code that adds to the result after collecting works with one and throws UnsupportedOperationException with the other.

Check yourself

1.No product has zero stock. What does stock.stream().collect(groupingBy(p -> p.onHand() == 0)).get(true) return, and what does the same with partitioningBy return?

C. groupingBy only creates a key when an element maps to it, so with no out-of-stock products the key true never exists and Map.get returns null. partitioningBy is specified to always contain both true and false, so the answer is an empty list — safe to iterate without a null check.

A and B assume the two behave alike; the difference is the entire reason partitioningBy exists. D is wrong because Map.get never throws for a missing key — that is what makes the null dangerous.

2.You want the total onHand per SKU. The stream contains two lines for BOLT-7. Which call is correct?

B. The merge function receives the value already in the map and the new value for the same key, and Integer::sum adds them. groupingBy(Product::sku, summingInt(Product::onHand)) would also be correct and is arguably clearer.

A throws IllegalStateException: Duplicate key BOLT-7 the moment the second line arrives. C counts lines per SKU, not quantity — it would say 2 for BOLT-7 regardless of stock. D compiles and runs, but keeps only the last value for each SKU, silently discarding the first line's quantity.

3.Which of these statements about groupingBy(Product::category, filtering(p -> p.onHand() < 10, toList())) are true? Select all that apply.

A and D. The classifier runs on every element, so every category becomes a key; the downstream filtering then decides what goes into each bucket, which can be nothing.

B is the trap: filtering before the collect removes whole categories whose products are all healthy, so those keys never appear. C is wrong because the two-argument groupingBy uses a HashMap; you would need the three-argument form with TreeMap::new.
