Section 5

Streams: pipelines and laziness

A stream is not a collection. It holds no elements; it is a description of a computation over a source — a List, an array, a range of numbers, lines of a file — expressed as a chain of operations. Nothing happens when you build the chain. The work starts only when a terminal operation asks for a result, and then elements flow through the whole chain one at a time, each operation pulling from the one before it. That single fact — vertical, element-by-element, on demand — explains every behaviour in this section, including the ones that look like magic and the ones that look like bugs.

The vocabulary: a source (stock.stream()), zero or more intermediate operations that return a new stream (filter, map, sorted, limit…), and exactly one terminal operation that produces a value or a side effect and consumes the stream (toList, count, findFirst, forEach…).

Worked example: proving laziness

The println calls inside the lambdas are there only to make the order of execution visible. Read the trace against the pipeline that produced it.

import java.util.List;
import java.util.Optional;

public class StreamLazy {
    public static void main(String[] args) {
        List skus = List.of("BOLT-7", "NUT-3", "GIRD-1", "CAM-9");

        System.out.println("-- no terminal operation: nothing runs --");
        skus.stream()
            .filter(s -> { System.out.println("  filter " + s); return !s.startsWith("B"); })
            .map(s -> { System.out.println("  map    " + s); return s.toLowerCase(); });
        System.out.println("(pipeline built, zero elements processed)");

        System.out.println("-- findFirst: one element at a time, and it stops early --");
        Optional first = skus.stream()
            .filter(s -> { System.out.println("  filter " + s); return !s.startsWith("B"); })
            .map(s -> { System.out.println("  map    " + s); return s.toLowerCase(); })
            .findFirst();
        System.out.println("result: " + first.orElse("none"));

        System.out.println("-- sorted is a barrier: every element arrives before any leaves --");
        List out = skus.stream()
            .filter(s -> { System.out.println("  filter " + s); return !s.startsWith("N"); })
            .sorted()
            .map(s -> { System.out.println("  map    " + s); return s.toLowerCase(); })
            .limit(2)
            .toList();
        System.out.println("result: " + out);
    }
}

Three lessons, one per block:

  • No terminal, no work. The first pipeline has filter and map but nothing printed. A stream you forget to terminate is a no-op, not an error — and a common bug.
  • Elements flow vertically, not in stages. BOLT-7 went through filter and was rejected before NUT-3 was even looked at. NUT-3 passed, was mapped, and reached findFirst, which had what it needed and stopped. GIRD-1 and CAM-9 were never touched. That is short-circuiting.
  • Stateful operations break the flow. sorted cannot emit its first element until it has seen its last — the smallest might be at the end. So every element is filtered first, then the sorted ones start moving: BOLT-7, CAM-9 are mapped, and limit(2) stops the third before map ever sees it.

Worked example: a real report

The laziness demonstration above is contrived. This is what stream code looks like in practice — a stock-value report, with the seven operations you will use most, each commented with the rule it illustrates.

import java.util.Comparator;
import java.util.List;
import java.util.stream.IntStream;

public class StreamPipeline {

    enum Category { FASTENER, STRUCTURAL, TOOLING }
    record Product(String sku, Category category, int priceInCents, int onHand) {
        int stockValueInCents() { return priceInCents * onHand; }
    }
    record OrderLine(String sku, int qty) {}
    record Order(String id, List lines) {}

    public static void main(String[] args) {
        List stock = List.of(
            new Product("BOLT-7", Category.FASTENER,   80,      500),
            new Product("NUT-3",  Category.FASTENER,   25,      2_000),
            new Product("GIRD-1", Category.STRUCTURAL, 120_000, 2),
            new Product("ROD-4",  Category.STRUCTURAL, 9_500,   12),
            new Product("CAM-9",  Category.TOOLING,    4_250,   3));

        // 1. filter -> sorted -> limit -> map -> collect: the three most valuable non-tooling lines
        List report = stock.stream()
            .filter(p -> p.category() != Category.TOOLING)
            .sorted(Comparator.comparingInt(Product::stockValueInCents).reversed())
            .limit(3)
            .map(p -> p.sku() + "=" + p.stockValueInCents() / 100 + ".00")
            .toList();
        System.out.println("top value:     " + report);

        // 2. primitive streams: no boxing, statistics built in
        int totalUnits = stock.stream().mapToInt(Product::onHand).sum();
        double avgPrice = stock.stream().mapToInt(Product::priceInCents).average().orElse(0);
        System.out.printf("units=%d avgPrice=%.1f%n", totalUnits, avgPrice);

        // 3. flatMap: an order has many lines; flatten them before counting
        List orders = List.of(
            new Order("A1", List.of(new OrderLine("BOLT-7", 40), new OrderLine("NUT-3", 100))),
            new Order("A2", List.of(new OrderLine("BOLT-7", 10))),
            new Order("A3", List.of()));
        int boltsOrdered = orders.stream()
            .flatMap(o -> o.lines().stream())
            .filter(l -> l.sku().equals("BOLT-7"))
            .mapToInt(OrderLine::qty)
            .sum();
        System.out.println("bolts ordered: " + boltsOrdered);

        // 4. reduce: the identity must be neutral for the operation (0 is right for max of lengths, wrong for min)
        int longestSku = stock.stream().map(Product::sku).mapToInt(String::length).reduce(0, Math::max);
        System.out.println("longest sku:   " + longestSku);

        // 5. anyMatch short-circuits; distinct is stateful (it remembers what it has seen)
        boolean anyEmpty = orders.stream().anyMatch(o -> o.lines().isEmpty());
        long categories = stock.stream().map(Product::category).distinct().count();
        System.out.println("empty order:   " + anyEmpty + ", distinct categories: " + categories);

        // 6. a range as a source
        String bins = IntStream.rangeClosed(1, 4).mapToObj(i -> "BIN-" + i).reduce((a, b) -> a + "," + b).orElse("");
        System.out.println("bins:          " + bins);

        // 7. a stream is single-use
        var once = stock.stream();
        once.count();
        try { once.count(); }
        catch (IllegalStateException e) { System.out.println("second use:    " + e.getMessage()); }
    }
}

Two of those deserve a closer look. flatMap takes a function that returns a stream per element and splices all those streams into one — the only way to get from a list of orders to a flat sequence of their lines. reduce folds the elements with a binary operator; the two-argument form needs an identity that leaves any value unchanged (0 for sum or max-of-non-negatives, 1 for product, "" for concatenation), and the one-argument form returns an Optional because an empty stream has nothing to fold. Pass a non-neutral identity and the result is quietly wrong, which is why block 6 uses the Optional form rather than reduce("", …) and a leading comma.

Build the pipeline

The report wanted is the SKUs of the three alphabetically-first products that are in stock. Put the six operations in the only order that type-checks and gives the right answer.

  1. 1 .sorted()
  2. 2 List<String> skus = stock.stream()
  3. 3 .toList();
  4. 4 .map(Product::sku)
  5. 5 .limit(3)
  6. 6 .filter(p -> p.onHand() > 0)

Correct. filter must come before map because it reads onHand(), which only a Product has; after map the elements are Strings. sorted() with no comparator needs Comparable elements — String is, Product is not, so it must follow map. limit(3) after sorted gives the three smallest; before it, you would sort whichever three happened to come first. And sorted is a barrier: it drains everything upstream before limit can short-circuit anything, so put filter ahead of it to give it less to drain.

Stateless, stateful, short-circuiting

Stream operations by category
CategoryOperationsBehaviour
Stateless intermediatefilter, map, mapToInt, flatMap, peekEach element handled alone; can stream forever; cheap.
Stateful intermediatesorted, distinctsorted buffers everything; distinct keeps a set of what it has seen. Both are barriers to laziness and both need memory proportional to the input.
Short-circuiting intermediatelimit, takeWhileCan finish an infinite stream. limit after a stateful op still has to wait for it.
Short-circuiting terminalfindFirst, findAny, anyMatch, allMatch, noneMatchStop pulling as soon as the answer is known.
Full terminaltoList, collect, count, sum, reduce, forEach, maxConsume every element.
Gotchas
  • A stream is single-use. Once a terminal operation has run, the stream is spent; a second one throws IllegalStateException: stream has already been operated upon or closed. Store the collection and call stream() again.
  • Side effects in map and filter are a smell. A lambda that writes to a list outside the pipeline works until someone adds parallel(), and then it corrupts the list. Collect results with the terminal operation; use peek only for debugging.
  • map boxes, mapToInt does not. stock.stream().map(Product::onHand).reduce(0, Integer::sum) allocates an Integer per element and unboxes it again; mapToInt(Product::onHand).sum() works on int throughout. For numeric work, go primitive at the earliest opportunity.
  • parallel() is not a free speed-up. It splits the source across the common fork-join pool, which pays off for large, splittable sources with CPU-heavy, side-effect-free operations — and costs more than it gains for small lists, I/O, or anything with a synchronized inside. Measure before and after; never add it by reflex. Java Advanced covers the machinery.
  • Encounter order is not guaranteed everywhere. forEach on a parallel stream runs in whatever order threads arrive; forEachOrdered preserves it. findAny may return something other than the first.

Check yourself

1.skus.stream().map(s -> { System.out.println(s); return s.trim(); }).filter(s -> !s.isEmpty()); — with four non-empty SKUs in the list, how many lines are printed?

D. There is no terminal operation. map and filter are intermediate; they build a pipeline and return it, and nobody ever asks the pipeline for an element. The lambdas are never invoked.

A is what you get after appending .toList() or .count(). B misunderstands the chain: each element passes through map once, whatever comes after. C: map never short-circuits; only operations like findFirst and limit do.

2.Prices are [90, 10, 50, 20]. What do prices.stream().sorted().limit(2).toList() and prices.stream().limit(2).sorted().toList() return?

B. Order of operations is the order of the pipeline. The first sorts all four, then keeps the two smallest. The second keeps the first two in encounter order — 90, 10 — and then sorts those, giving [10, 90].

A is the intuition that stream operations are declarative set operations; they are not, they are sequential stages. C forgets that sorted still runs in the second pipeline, just on fewer elements. D: sorted is happy with any finite stream, including one limit truncated.

3.Stream<Product> s = stock.stream(); long n = s.count(); List<Product> all = s.toList(); — what happens on the third statement?

C. A terminal operation closes the pipeline; the stream object records that it has been operated upon and rejects any further use with IllegalStateException: stream has already been operated upon or closed. Create a fresh stream from the collection for each query.

A describes a collection, not a stream — the source is reusable, the pipeline is not. B is how an exhausted Iterator behaves, and streams chose to fail loudly instead. D: the compiler has no notion of single-use variables; this is purely a runtime check.
