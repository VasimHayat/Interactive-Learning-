Self-assessment quiz

Sixteen questions covering all twelve learning objectives. Answer every one, then submit — nothing is marked until you do, and the explanations stay hidden until then. Your answers are saved locally, so you can leave and come back.

1.A method restock(List<…> dst) adds three Perishable objects to dst and reads nothing back. Which parameter type accepts the most callers while still compiling?

B. The method only writes, so the list is a consumer and Consumer Super applies: any list that a Perishable fits in — List<Perishable>, List<Product>, even List<Object> — is accepted, and add(Perishable) compiles inside. A is the producer form: it would accept a List<Milk> and then forbid add, because a Perishable is not necessarily a Milk. C forbids adding anything but null. D compiles but accepts only the exact type, rejecting a perfectly safe List<Product>.

2.Which of these are rejected by the compiler as a direct consequence of type erasure? Select all that apply.

A, B and D. After erasure the method body sees T as Object and has no class to construct (A); every List is the same runtime class so there is nothing for instanceof to test (B); and both overloads erase to f(List), the "same erasure" error (D). C is legal and ordinary — an unbounded wildcard accepts any parameterisation; it is the typed, safe alternative to a raw List.

3.class Order { class Cursor { } } — from a static void main in another class you write Order.Cursor c = new Order.Cursor();. What happens?

C. A nested class without static is inner: every instance carries a hidden this$0 reference to an Order, passed as a secret constructor argument, so it cannot be created without one. Either construct it through an instance — order.new Cursor(), or more usually a method on Order — or, if it never uses the outer instance, make it static. A describes what a static nested class would allow. B invents a rule; nothing is implicit. D cannot happen because the compiler refuses first.

4.int n = 0; Runnable r = () -> System.out.println(n); n = 1; r.run(); — what happens?

D. A lambda copies the value of a captured local, so a later assignment would leave two copies that disagree; the language forbids the situation rather than pick a meaning. The rule is checked per variable, not per use — one assignment anywhere in the method makes n uncapturable — and the error is reported at the capture, not at the assignment, which is why C has the location wrong. A is what would happen if the rule did not exist, and is exactly the surprise it prevents. B describes closures in languages that share variables; Java's do not.

5.class Base { public String describe() { return "base"; } }, interface Priced { default String describe() { return "priced"; } }, class Bolt extends Base implements Priced { }. What does new Bolt().describe() return?

A. Rule one of default resolution: a concrete method from a superclass, however far up, wins over every interface default. This is what makes defaults safe to add to published interfaces — they cannot change what an existing class hierarchy does. B applies the "more specific" rule to the wrong pair; that rule only ranks interfaces against each other. C is the outcome only when two unrelated interfaces supply the default and no class does. D: declaration order never affects resolution.

6.Predict the output:

String prefix = "SKU-";
Function f = prefix::concat;
prefix = "PART-";       // compiles: prefix is reassigned, but the reference was already built
System.out.println(f.apply("7"));

A. prefix::concat is a bound instance reference: the receiver expression is evaluated once, when the reference is created, and the resulting Function holds that String object. Reassigning the variable afterwards changes nothing the function can see. The call is "SKU-".concat("7"). B would require the reference to re-read the variable at call time, which only a lambda s -> prefix.concat(s) would do — and that lambda would not compile, for the reason in D. D is wrong here because a bound method reference evaluates its receiver immediately and does not capture the variable; the effectively-final rule applies to lambdas and to references whose receiver is a captured local inside a lambda body, not to this form. C has the receiver and argument swapped — that is what the unbound String::concat applied as (a, b) -> a.concat(b) might suggest, but this reference is bound.

7.Predict the output:

List.of("a", "bb", "ccc").stream()
    .peek(s -> System.out.print(s + " "))
    .filter(s -> s.length() > 1)
    .findFirst();

B. findFirst is a terminal operation, so the pipeline runs — vertically, one element at a time. "a" is peeked, fails the filter, and the next element is pulled; "bb" is peeked, passes, and reaches findFirst, which has what it needs and stops. "ccc" is never read. A is what toList() would print, since it consumes everything. C forgets that peek runs before the filter and sees the rejected element too. D: discarding the result does not undo the terminal operation; only a pipeline with no terminal at all is a no-op.

8.Which intermediate operation must receive every upstream element before it can emit its first one?

B. The smallest element might be the last one in, so sorted is a barrier: it buffers the whole upstream, then emits in order. A limit placed after it still has to wait, and the buffer costs memory proportional to the input. A and D are stateless — each element is handled alone and passed on immediately. C is the opposite of a barrier: it is short-circuiting, and stops the upstream early.

9.The stream holds two FASTENER products. What does stock.stream().collect(toMap(Product::category, Product::sku)) do?

C. The two-argument toMap refuses to choose a winner: a second value for an existing key throws, naming the key and both values. That is deliberate, because silently keeping one would hide a data problem. To say what should happen, use the three-argument form — (a, b) -> b for A's behaviour, (a, b) -> a for B's, Integer::sum to total. D is wrong: the two-argument overload exists and compiles; the failure is at runtime.

10.What is the type of stock.stream().collect(groupingBy(Product::category, counting()))?

B. The downstream collector decides the value type, and counting() always produces Long. Declaring the result as Map<Category, Integer> (A) is the single most common compile error with groupingBy; use summingInt(p -> 1) if you genuinely need an Integer. C is the one-argument groupingBy, whose implicit downstream is toList(). D: the two-argument form promises a Map backed by a HashMap; a TreeMap needs the three-argument form with TreeMap::new as the middle argument.

11.In which of these positions should Optional not appear, according to its designers? Select all that apply.

A, B and C. A field (A) is not Serializable, doubles the memory of every nullable field, and can itself still be null; expose a nullable field through an accessor that returns Optional instead. A parameter (B) forces every caller to wrap, and the method must still guard against a null argument — two overloads are the idiom. A map value (C) gives Map.get two ways to say "nothing": null for an absent key and Optional.empty() for a present one. D is the one intended use: a return type that says "may be absent" so the caller cannot forget.

12.Predict the output:

record Line(String sku, int qty) {
    Line {
        sku = sku.strip().toUpperCase();
        if (qty <= 0) throw new IllegalArgumentException("qty");
    }
}
System.out.println(new Line("  bolt-7 ", 2).equals(new Line("BOLT-7", 2)));

A. In a compact constructor the body runs before the compiler's automatic this.sku = sku; this.qty = qty;, so reassigning the parameter is exactly how you normalise: both records end up with the field "BOLT-7", and the generated equals compares fields, not the arguments that were passed. B and D both misdescribe the generated equals — it is component-wise, on the stored values. C is backwards: assigning this.sku in a compact constructor is the compile error, because the field is assigned for you afterwards.

13.sealed interface Discount permits PercentOff, FixedOff, both records. Does this compile?

long apply(Discount d, long gross) {
    return switch (d) {
        case PercentOff(int pct)                 -> gross * (100 - pct) / 100;
        case FixedOff(int c) when c >= gross     -> 0;
    };
}

C. A guard is not a case. case FixedOff(int c) when c >= gross handles only the vouchers worth more than the line; the compiler cannot prove anything about the rest, so the switch is not exhaustive and the error names FixedOff — the type you thought you had handled. Add an unguarded case FixedOff(int c) -> gross - c after it. A counts case labels instead of coverage. B describes separate-compilation drift, not a program the compiler has just seen. D is the opposite of the design: exhaustiveness without default is the whole point of sealing, and a default would hide the next subtype.

14.Predict the output:

List src  = new ArrayList<>(List.of("BOLT-7"));
List view = Collections.unmodifiableList(src);
List copy = List.copyOf(src);
src.add("NUT-3");
System.out.println(view.size() + " " + copy.size());

B. The view stores no elements; it forwards every read to src, so it sees the second element the moment it is added. The copy walked src once and owns its own storage, fixed at that instant. "Unmodifiable" describes the window, not the room. A treats the view as a snapshot; C treats the copy as a view. D: a view only refuses writes made through itself; the original list is unaffected by having been wrapped.

15.London's clocks go forward at 01:00 on 29 March 2026. Predict the output:

ZonedDateTime placed = ZonedDateTime.of(2026, 3, 28, 23, 30, 0, 0, ZoneId.of("Europe/London"));
System.out.println(Duration.between(placed, placed.plusDays(1)).toHours());

A. plusDays is calendar arithmetic on a ZonedDateTime: it keeps the wall clock at 23:30 and re-resolves the offset, so the result is 23:30 on the 29th — and because the night in between lost an hour, that is 23 real hours later. Duration.between measures elapsed time and reports it honestly. B is what plusHours(24) would give, landing at 00:30 on the 30th; it is also what a LocalDateTime would always say, having no zone to consult. C is the October overlap, not the March gap. D: 23:30 exists on both days; only 01:00–01:59 on the 29th is missing, and even a time in the gap is shifted forward rather than rejected.

16.Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8); — which of these guarantee the file handle it opened is released? Select all that apply.

A and C. Files.lines reads on demand, so the returned stream owns an open file descriptor until close() runs; Stream implements AutoCloseable for exactly this reason, and try-with-resources is the idiom. B is the trap: a terminal operation consumes the elements and marks the stream as used, but does not close it — on Windows the file then cannot be deleted, and on Linux the descriptor leaks silently. D relies on the garbage collector finalising the stream, which may happen hours later or never. The same applies to Files.walk and Files.list.
