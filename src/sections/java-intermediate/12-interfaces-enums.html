Section 3

Interfaces and enums in depth

Fundamentals §8 drew the line between an abstract class and an interface: state on one side, pure contract on the other. That line moved in Java 8. An interface can now ship behaviour — default methods with bodies, static factories, and since Java 9 private helpers — while still carrying no instance state. The reason was pragmatic: Collection.stream() had to be added to an interface that thousands of third-party classes already implemented, without breaking a single one of them. A method with a body that implementers inherit automatically was the only way.

That convenience creates one genuinely new problem — a class can now inherit two bodies for the same method — and the language resolves it with three rules you need to know by heart. The second half of this section does the same for enum, which is far more than a list of names: each constant is a singleton object that can carry fields, constructors, and its own method bodies.

Four kinds of interface method

Interface member kinds, their modifiers and what they are for
KindWritten asImplementers getUse it for
Abstractint priceInCents();an obligation — implicitly public abstractthe contract itself
Defaultdefault String describe() { … }a body they may keep or overrideevolving a published interface; convenience built on the abstract methods
Staticstatic Priced of(int c) { … }nothing — called only as Priced.of(…), never inheritedfactories and utilities that belong with the type
Privateprivate int handling() { … }nothing — invisible outside the interfacesharing code between two defaults without exposing it

A field in an interface is always public static final whether you write the modifiers or not. It is a constant, not state — an interface still has no instance fields and never will.

Worked example: all three resolution rules

Three classes, each inheriting describe() from more than one place. The output shows which body ran and the comments name the rule that chose it.

public class DefaultMethods {

    interface Priced {
        int priceInCents();
        default String describe() { return "priced at " + priceInCents() + "c"; }
        static Priced of(int cents) { return () -> cents; }        // static: called as Priced.of(...)
    }

    interface Shippable {
        int shippingInCents();
        default String describe() { return "ships for " + shippingInCents() + "c"; }
        default int totalInCents(int price) { return price + shippingInCents() + handling(); }
        private int handling() { return 50; }                        // private: shared by defaults only
    }

    // rule 3: two unrelated defaults with one signature -> the class MUST override
    static class Bolt implements Priced, Shippable {
        public int priceInCents() { return 80; }
        public int shippingInCents() { return 150; }
        @Override public String describe() {
            return Priced.super.describe() + ", " + Shippable.super.describe();
        }
    }

    interface Fragile extends Shippable {
        @Override default String describe() { return "fragile: " + Shippable.super.describe(); }
    }
    // rule 2: the more specific interface wins -> Fragile's default, not Shippable's
    static class Lens implements Shippable, Fragile {
        public int shippingInCents() { return 900; }
    }

    static class Base { public String describe() { return "a plain class method"; } }
    // rule 1: a superclass method always beats an interface default
    static class Girder extends Base implements Priced {
        public int priceInCents() { return 120_000; }
    }

    public static void main(String[] args) {
        System.out.println("Bolt:   " + new Bolt().describe());
        System.out.println("Lens:   " + new Lens().describe());
        System.out.println("Girder: " + new Girder().describe());
        System.out.println("total:  " + new Lens().totalInCents(1_000));
        System.out.println("static: " + Priced.of(25).describe());
    }
}
  
Bolt:   priced at 80c, ships for 150c
Lens:   fragile: ships for 900c
Girder: a plain class method
total:  1950
static: priced at 25c

The rules, in the order the compiler applies them:

  1. A class wins over any interface. If a superclass — however far up — supplies a concrete method, every interface default with that signature is ignored. Girder prints Base's text and Priced.describe never runs. This is what keeps old code old: adding a default to an interface cannot change what an existing class hierarchy does.
  2. A more specific interface wins over a less specific one. Fragile extends Shippable and overrides the default, so for Lens the Fragile body is chosen even though Lens names Shippable first. Declaration order is irrelevant.
  3. Otherwise the class must decide. Priced and Shippable are unrelated and both supply describe(). Delete Bolt's override and the compiler says class Bolt inherits unrelated defaults for describe() from types Priced and Shippable. The override may do anything, including delegate to one or both with the Interface.super.method() syntax — the only place that form is legal.

Note the private helper: handling() is callable from totalInCents but not from Lens, so the interface can factor out shared logic without widening its public surface.

Functional interfaces, briefly

An interface with exactly one abstract method — default, static and private methods do not count — is a functional interface, and that single method is what a lambda implements. Priced above qualifies, which is why Priced.of could return () -> cents. Comparator, Runnable and everything in java.util.function are functional interfaces. §4 is about nothing else.

Enums are classes

An enum declares a class with a fixed, compiler-known set of instances. Each constant is created once, during class initialisation, by calling the enum's constructor — which is why that constructor is always private and why == is the correct way to compare enum values. Everything a class can have, an enum can have: fields, methods, constructors, interfaces, and even a different method body per constant.

import java.util.EnumMap;
import java.util.EnumSet;
import java.util.Map;

public class Enums {

    interface Describable { String describe(); }

    enum Category implements Describable {
        FASTENER("Fasteners", 1.0) {
            @Override int shippingInCents(int weightGrams) { return 150; }            // flat rate
        },
        STRUCTURAL("Structural steel", 2.5) {
            @Override int shippingInCents(int weightGrams) { return weightGrams * 3; }
        },
        TOOLING("Tooling", 1.2) {
            @Override int shippingInCents(int weightGrams) { return 500 + weightGrams; }
        };

        private final String label;
        private final double multiplier;

        Category(String label, double multiplier) {      // always private: nobody else can call new
            this.label = label;
            this.multiplier = multiplier;
        }

        abstract int shippingInCents(int weightGrams);   // every constant must supply a body

        String label() { return label; }
        double multiplier() { return multiplier; }

        @Override public String describe() { return label + " (x" + multiplier + ")"; }
    }

    public static void main(String[] args) {
        for (Category c : Category.values()) {
            System.out.printf("%-10s ordinal=%d  %-22s ship(200g)=%d%n",
                    c, c.ordinal(), c.describe(), c.shippingInCents(200));
        }

        Category parsed = Category.valueOf("TOOLING");
        System.out.println("valueOf -> " + parsed + ", same object: " + (parsed == Category.TOOLING));

        Map stockByCategory = new EnumMap<>(Category.class);
        stockByCategory.put(Category.TOOLING, 4);
        stockByCategory.put(Category.FASTENER, 1_200);
        System.out.println("EnumMap keeps declaration order: " + stockByCategory);

        EnumSet heavy = EnumSet.of(Category.STRUCTURAL, Category.TOOLING);
        System.out.println("complement of " + heavy + " is " + EnumSet.complementOf(heavy));

        String storage = switch (parsed) {               // exhaustive: no default needed
            case FASTENER   -> "bin";
            case STRUCTURAL -> "yard";
            case TOOLING    -> "locked cage";
        };
        System.out.println("switch -> " + storage);

        try {
            Category.valueOf("tooling");
        } catch (IllegalArgumentException e) {
            System.out.println("valueOf is exact-match only: " + e.getMessage());
        }
    }
}

Three things in that program deserve a closer look.

Writing { … } after a constant's arguments creates an anonymous subclass of the enum for that one constant. An abstract method on the enum then forces every constant to supply its own body, and the compiler refuses a new constant that forgets. This replaces the switch (this) inside a method that silently falls through when someone adds a constant — the behaviour lives next to the data it belongs to.

The cost is that FASTENER.getClass() is a subclass, not Category itself. Use getDeclaringClass() if you ever need the enum type reflectively.

An enum has a known number of constants, each with a fixed ordinal(). EnumMap exploits that: it is an array indexed by ordinal, so get and put are a single array access with no hashing, no boxing and no collisions, and iteration is always in declaration order. EnumSet is a bit vector — one long for up to 64 constants — which makes contains, union and complementOf single machine instructions.

Prefer them over HashMap/HashSet whenever the key is an enum. They are also the right way to represent a set of flags; a bit-mask int is what they replace.

Inside a switch on an enum you write the bare constant name — case TOOLING, not case Category.TOOLING. The compiler knows the type from the selector. A switch expression (the arrow form that yields a value) must be exhaustive: cover every constant and you need no default, and adding a fourth constant later becomes a compile error at every such switch rather than a silent fall-through. §9 takes this further with sealed types.

Avoid writing a default in an enum switch expression that could be exhaustive. It compiles today, and it hides tomorrow's missing case.

Gotchas
  • Never persist ordinal(). It is the constant's position in the source file. Insert a constant in the middle and every stored number now means something else. Store name(), or an explicit field such as a database code, and look it up on the way back in.
  • valueOf is exact and throws. It compares the full name, case-sensitively, and raises IllegalArgumentException — not null — on a miss. User input needs a guard: normalise it, or loop over values() comparing with equalsIgnoreCase.
  • A default method cannot override Object methods. default String toString() in an interface is a compile error. Every class already has one from Object, and rule 1 says the class would win anyway.
  • Defaults do not let an interface hold state. A default method can only call other interface methods. If it needs a field, you wanted an abstract class.
  • An enum is the correct singleton. enum Registry { INSTANCE; … } is serialisation-safe and reflection-proof, which the double-checked-locking singleton is not. Java Advanced revisits why.

Check yourself

1.class Cart implements Priced, Shippable, where both unrelated interfaces declare default String describe() and Cart does not override it. What happens?

D. Rule 3: two unrelated defaults with the same signature are a conflict the class must resolve, and the compiler refuses to guess. The override can pick one with Priced.super.describe(), combine both, or do something new.

A is a common guess but declaration order never affects resolution. B confuses this with dynamic dispatch, which picks among overrides in a class hierarchy, not among interface defaults. C describes what can happen when a class file is compiled against one version of an interface and run against another — a binary-compatibility problem, not a source one.

2.A team stores each product's category in the database as category.ordinal(). A year later someone adds ELECTRICAL between FASTENER and STRUCTURAL. What is the consequence?

B. An ordinal is nothing more than the source-order index. Shifting the constants shifts every number, and nothing fails loudly: the data simply reads back as the wrong category. Persist name() or a dedicated code field instead.

A is false — the ordinal is fixed at compile time from the declaration order. C: the array just got longer; index 1 is valid and returns the wrong constant. D: the compiler has no notion of an enum being "published" and allows any edit.

3.interface Audited { default String toString() { return "audited"; } } — does this compile, and why?

C. The language forbids it outright, and rule 1 explains why it would be pointless anyway: every class already inherits toString from Object, a class, and a class method always beats an interface default.

A would require interfaces to beat classes, which is backwards. B: toString is not final — you override it all the time. D is invented; default methods can return anything.
