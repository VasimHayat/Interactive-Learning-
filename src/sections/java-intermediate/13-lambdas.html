Section 4

Lambdas, functional interfaces and method references

A lambda is a compact way to write an object that implements a functional interface — an interface with exactly one abstract method (§3). p -> p.onHand() < 5 is not a function floating free; it becomes an instance of whatever single-method interface the surrounding code expects, and that interface's method body is the lambda. Nothing else about it is new. What makes lambdas worth a whole section is how the compiler decides which interface, what the lambda may touch from its surroundings, and the four shorthand forms called method references that replace most lambdas you would otherwise write.

The mental model to carry through streams (§5) and collectors (§6): a lambda has no type of its own. The same text x -> x is a Function<String,String> in one place and a UnaryOperator<Integer> in another, and in a place with no target type at all it is a compile error.

The interfaces you will actually use

Almost every lambda in real code targets one of the interfaces in java.util.function. Learn these shapes and you can read any stream pipeline.

Worked example

Every lambda and every kind of method reference, applied to stock levels. Read the comments on the right of each declaration first; they name which of the four reference forms it is.

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.function.BiFunction;
import java.util.function.Function;
import java.util.function.Predicate;
import java.util.function.Supplier;
import java.util.function.UnaryOperator;

public class Lambdas {

    record Product(String sku, int priceInCents, int onHand) {}

    static boolean isLowStock(Product p) { return p.onHand() < 5; }

    public static void main(String[] args) {
        List stock = List.of(
                new Product("BOLT-7", 80, 500),
                new Product("GIRD-1", 120_000, 2),
                new Product("CAM-9", 425, 3));

        // a lambda has no type of its own: each one below is typed by its target
        Predicate low = p -> p.onHand() < 5;
        Function sku = Product::sku;                 // unbound instance method
        Supplier> fresh = ArrayList::new;               // constructor
        BiFunction max = Math::max;        // static method
        Product sample = stock.get(0);
        Supplier boundSku = sample::sku;                      // bound instance method

        System.out.println("low stock:         " + stock.stream().filter(low).map(sku).toList());
        System.out.println("fresh list empty:  " + fresh.get().isEmpty());
        System.out.println("max:               " + max.apply(80, 4_250));
        System.out.println("bound receiver:    " + boundSku.get());

        // composition builds new functions from old ones without a class in sight
        Predicate cheap = p -> p.priceInCents() < 1_000;
        Predicate reorder = low.and(cheap.negate());
        System.out.println("low and not cheap: " + stock.stream().filter(reorder).map(Product::sku).toList());

        Function addTax = cents -> cents + cents / 5;
        Function addShipping = cents -> cents + 150;
        System.out.println("tax then shipping: " + addTax.andThen(addShipping).apply(1_000));
        System.out.println("shipping then tax: " + addTax.compose(addShipping).apply(1_000));

        // capture: the lambda copies the VALUE of threshold, so threshold must never change
        int threshold = 5;
        Predicate under = p -> p.onHand() < threshold;
        // threshold = 6;   // uncomment: "local variables referenced from a lambda expression must be final or effectively final"
        System.out.println("under threshold:   " + stock.stream().filter(under).count());

        Comparator byPrice = Comparator.comparingInt(Product::priceInCents);
        List sorted = new ArrayList<>(stock);
        sorted.sort(byPrice.reversed());
        System.out.println("priciest first:    " + sorted.stream().map(Product::sku).toList());
        System.out.println("own static helper: " + stock.stream().filter(Lambdas::isLowStock).count());

        UnaryOperator shout = String::toUpperCase;
        System.out.println(shout.apply("ready"));
    }
}

andThen and compose are the same two functions in opposite orders: f.andThen(g) runs f first, f.compose(g) runs g first. The 30-cent difference in the output is tax applied before or after the shipping charge — exactly the kind of thing a pricing bug is made of, so read these carefully in code review. Four kinds of method reference

A method reference is a lambda whose body is a single call that forwards its parameters unchanged. The compiler expands it; there is nothing a reference can do that a lambda cannot, and the reverse is also true. The four forms differ in where the receiver comes from.

Expand a method reference
Bound versus unbound is the one that bites

sample::sku and Product::sku look alike and differ completely. The first is bound: the receiver sample is evaluated once, when the reference is created, and the resulting Supplier takes no parameters. The second is unbound: the receiver arrives later as the first parameter, so it is a Function<Product,String>. System.out::println is bound to the System.out object that existed at that moment — reassign System.setOut afterwards and the reference still prints to the old stream.

What a lambda can touch

A lambda body can use the enclosing method's local variables, the enclosing instance's fields, and this. The rules for each are different, and the difference is the source of most lambda bugs.

A captured local must be effectively final: assigned exactly once and never changed, whether or not you wrote final. The reason is that the lambda copies the value when it is created. The lambda may outlive the method — be stored in a field, run on another thread — long after the method's stack frame is gone, so there is no variable left to share. Allowing writes would give you two copies that silently disagree, so the compiler forbids them on both sides.

If you need a mutable counter, the fix is not int[] count = {0} — that compiles because the reference is effectively final, but it is a thread-unsafe hack. Use a reduce or count() on the stream, or an AtomicInteger if you genuinely need shared mutable state.

Inside a lambda, this means the enclosing instance — the same object it meant on the line before the lambda. A lambda introduces no new scope for this, which is why this::isLowStock works in an instance method and why a lambda can read fields with no qualifier.

Inside an anonymous class, this is the anonymous object itself, and the enclosing instance is Outer.this. This is the single behavioural difference between a lambda and an anonymous class that implements the same interface, and it is why an IDE's "convert to lambda" can change meaning if the body uses this. §2 covered the anonymous-class side.

None of the java.util.function interfaces declare throws. So path -> Files.readString(path) does not compile as a Function: readString throws IOException, and apply is not allowed to. The error message — unreported exception IOException; must be caught or declared to be thrown — points at the lambda body.

Your options are to catch inside the lambda and wrap in an UncheckedIOException, to declare your own functional interface whose method does throws, or to move the I/O out of the pipeline entirely. Wrapping is the usual answer; silently swallowing the exception in a catch that returns null is the usual mistake.

Gotchas
  • Overloads plus lambdas confuse inference. submit(() -> doWork()) on an ExecutorService has both a Runnable and a Callable overload. If doWork returns a value the Callable wins; if not, Runnable. Change the method's return type and you silently change which overload is called.
  • @FunctionalInterface is a promise, not a requirement. Any single-abstract-method interface works as a lambda target. The annotation makes the compiler reject a second abstract method, which protects callers who rely on lambdas. Put it on every interface you intend to be used that way.
  • A lambda is not always a new object. A non-capturing lambda is typically allocated once and reused; a capturing one is allocated per evaluation. Do not compare lambdas with == or use them as map keys.
  • Long lambdas are a smell. A body of more than a few lines belongs in a named method, referenced with this::name. The name documents it, and a stack trace through lambda$main$3 tells you nothing.

Check yourself

1.Inside a method: int shipped = 0; orders.forEach(o -> shipped += o.qty()); — what happens?

C. A lambda captures a copy of the local's value, so a write inside the body could never reach the variable outside. Rather than let that silently happen, the language refuses to compile any lambda that assigns to a captured local — or any method that assigns to a local a lambda has captured.

B is what would happen if the rule did not exist, and is exactly the surprise the rule prevents. A requires shared variables, which Java lambdas do not have. D is about modifying a collection during iteration, which this code does not do. Use orders.stream().mapToInt(Order::qty).sum().

2.Comparator<String> c = String::compareToIgnoreCase; — which kind of method reference is this, and what does it expand to?

B. compareToIgnoreCase is an instance method, and String:: names the type rather than an object, so the reference is unbound: the first parameter of the target method becomes the receiver and the rest become arguments. Two parameters in, one receiver plus one argument out — the arities line up.

A would need a static method, and there is none with that name. C would need an expression before the ::, not a type. D is the trap: the counts do match once you account for the receiver, which is the whole point of the unbound form.

3.Which of these can the lambda (a, b) -> a + b be assigned to without error? Select all that apply.

A and D. Both targets have a two-parameter abstract method, and + works on the inferred types — numeric addition for Integer, concatenation for String. The same lambda text means two different things depending on the target, which is the lesson of this section.

B fails because Function.apply takes one argument and the lambda declares two. C fails because var infers from the initialiser and a lambda has no intrinsic type to infer.
