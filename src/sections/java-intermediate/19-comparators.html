Section 10

Comparable, Comparator and immutability

Two ideas that look unrelated and are not. Ordering is a contract: compareTo promises things about every pair of values, and TreeSet, TreeMap and every sort rely on those promises without checking them. Immutability is the strongest way to keep such contracts true, because a value that cannot change cannot drift out of the order it was inserted under, cannot be mutated by one caller behind another's back, and can be shared and cached without a second thought. The warehouse reports in §5 and §6 sort products and group them; this section is what makes that safe.

Comparable: the natural order

A class implements Comparable<T> to say "my instances have one obvious ordering". String compares lexicographically, Integer numerically, LocalDate chronologically. The method returns a negative number, zero or a positive number, and must obey three rules for every a, b and c:

  • Antisymmetry: sgn(a.compareTo(b)) == -sgn(b.compareTo(a)). If a < b then b > a.
  • Transitivity: a < b and b < c imply a < c. A sort that gets inconsistent answers may loop or throw IllegalArgumentException: Comparison method violates its general contract.
  • Consistency with equals, strongly recommended: a.compareTo(b) == 0 exactly when a.equals(b). Sorted collections use compareTo to decide duplicates, so when the two disagree, a TreeSet and a HashSet hold different elements for the same input.

Worked example

import java.util.ArrayList;
import java.util.Arrays;
import java.util.Collections;
import java.util.Comparator;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

public class Sorting {

    static final class Product implements Comparable {
        private final String sku;
        private final int priceInCents;
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        String sku() { return sku; }
        int priceInCents() { return priceInCents; }
        @Override public int compareTo(Product o) { return sku.compareTo(o.sku); }   // natural order: by SKU
        @Override public String toString() { return sku + "@" + priceInCents; }
    }

    public static void main(String[] args) {
        List cart = new ArrayList<>(List.of(
                new Product("NUT-3", 25), new Product("BOLT-7", 80),
                new Product("CAM-9", 80), new Product("ROD-4", 300)));

        Collections.sort(cart);                                      // natural order via compareTo
        System.out.println("natural           " + cart);

        cart.sort(Comparator.comparingInt(Product::priceInCents));   // stable: BOLT-7 stays before CAM-9
        System.out.println("by price (stable) " + cart);

        cart.sort(Comparator.comparing(Product::priceInCents).thenComparing(Product::sku).reversed());
        System.out.println("(price,sku) rev   " + cart);

        cart.sort(Comparator.comparing(Product::priceInCents, Comparator.reverseOrder()).thenComparing(Product::sku));
        System.out.println("price desc, sku   " + cart);

        List skus = new ArrayList<>(Arrays.asList("NUT-3", null, "BOLT-7"));
        skus.sort(Comparator.nullsFirst(Comparator.naturalOrder()));
        System.out.println("nulls first       " + skus);

        // a comparator inconsistent with equals: the set treats equal-priced products as duplicates
        Set byPrice = new TreeSet<>(Comparator.comparingInt(Product::priceInCents));
        byPrice.addAll(cart);
        System.out.println("TreeSet by price  " + byPrice + "  size=" + byPrice.size() + " of " + cart.size());

        int a = Integer.MAX_VALUE, b = -1;
        System.out.println("a - b             " + (a - b) + "  (overflow: wrong sign)");
        System.out.println("Integer.compare   " + Integer.compare(a, b));
    }
}

Line 29 shows a stable sort: BOLT-7 and CAM-9 both cost 80, and they keep the relative order they had before. Every object sort in the JDK is stable, which is what makes "sort by category, then by price" achievable as two successive sorts as well as one chained comparator. Lines 32 and 35 produce different results from what look like the same ingredients; the reason is the gotcha below. The last two lines are why you never write return a - b in a comparator: the subtraction overflows, and Integer.compare does not.

comparing(price).thenComparing(sku).reversed() means "the reverse of (price, then sku)": price descending and sku descending, which is why line 32 printed CAM-9 before BOLT-7. It is a method on the comparator you have built so far, so it cannot know you meant only the last key. To reverse one key, reverse that key's comparator: comparing(price, reverseOrder()).thenComparing(sku), as on line 35.

A second trap in the same family: Comparator.comparing(Product::priceInCents).reversed() compiles, but Comparator.comparing(p -> p.priceInCents()).reversed() does not. With a lambda the compiler cannot infer p's type before it sees reversed(), which gives it nothing to go on. A method reference carries the type; a lambda needs Comparator.comparing((Product p) -> …).

Where sorting happens

cart.sort(null);                       // natural order (List.sort, Java 8+): sorts in place
cart.sort(byPrice);                    // same, with a comparator
Collections.sort(cart);                // the older spelling; delegates to list.sort

Both sort in place using TimSort: a stable merge sort that runs in O(n) on already-sorted or nearly-sorted input and O(n log n) otherwise. An immutable list (List.of) throws UnsupportedOperationException; copy it first.

int[] prices = { 300, 25, 80, 80 };
Arrays.sort(prices);                   // dual-pivot quicksort: fast, NOT stable, primitives only

Product[] items = …;
Arrays.sort(items, byPrice);           // TimSort: stable, any Comparator
Arrays.parallelSort(items, byPrice);   // splits across cores; worth it from ~10⁴ elements

Stability is meaningless for primitives, since two equal ints are indistinguishable, so the JDK uses a faster unstable algorithm for them. For objects it must preserve order among "equal" elements and uses TimSort.

List cheapest = cart.stream().sorted(byPrice).limit(3).toList();   // a new list; source untouched

Set ordered = new TreeSet<>(byPrice);     // kept sorted on every insert, O(log n) each
Map stock = new TreeMap<>();      // sorted by key; needs Comparable keys or a comparator

sorted() on a stream is a stateful operation: it must see every element before it can emit the first one, so it buffers the whole stream (§5). A TreeSet keeps its order incrementally and is the right choice when elements arrive over time and you repeatedly need the smallest, the largest, or a range.

Immutability: unmodifiable is not immutable

Java has two ideas that are easy to confuse. An unmodifiable view is a wrapper that refuses writes through itself but shows whatever its underlying collection currently holds. An immutable collection owns its elements, has no underlying collection, and cannot change through any reference. The difference is invisible until someone keeps a reference to the original.

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Immutable {

    static final class Order {
        private final List skus;                          // final reference to a mutable object
        Order(List skus) { this.skus = new ArrayList<>(skus); }        // defensive copy in
        List skus() { return Collections.unmodifiableList(skus); }     // read-only view out
    }

    public static void main(String[] args) {
        List source = new ArrayList<>(List.of("BOLT-7", "NUT-3"));
        List view = Collections.unmodifiableList(source);
        List copy = List.copyOf(source);

        source.add("CAM-9");
        System.out.println("source " + source);
        System.out.println("view   " + view + "   a view: it follows the source");
        System.out.println("copy   " + copy + "   a snapshot: fixed at copy time");

        try { view.add("ROD-4"); }
        catch (UnsupportedOperationException e) { System.out.println("view.add            -> UnsupportedOperationException"); }

        try { List.of("BOLT-7", null); }
        catch (NullPointerException e) { System.out.println("List.of(.., null)   -> NullPointerException"); }

        List input = new ArrayList<>(List.of("PIN-2"));
        Order order = new Order(input);
        input.add("HUB-8");                                       // the caller keeps mutating its own list
        System.out.println("order  " + order.skus() + "   unaffected: the constructor copied");

        try { order.skus().add("HUB-8"); }
        catch (UnsupportedOperationException e) { System.out.println("order.skus().add    -> UnsupportedOperationException"); }

        System.out.println("List.copyOf(copy) == copy ? " + (List.copyOf(copy) == copy) + "   already immutable, so no new object");
    }
}

The three rules of an immutable class

  1. Every field is private final and set once, in the constructor. final on a field means the reference cannot be reassigned. It says nothing about the object at the other end, which is why rule 2 exists.
  2. Mutable inputs are copied on the way in, and either copied or wrapped on the way out. The Order above copies the list in its constructor, so a caller who keeps mutating their own list cannot reach inside. Its accessor returns an unmodifiable view, which is safe here precisely because nobody else holds the private list. A Date or an array needs the same treatment; a String, a record of primitives, or a List.copyOf result does not, because they are already immutable.
  3. The class is final, or its constructors are private. Otherwise a subclass can add mutable state and override methods, and code that trusts "an Order never changes" is trusting something a subclass can break. Records satisfy all three rules by construction, which is why §8 recommends them for this job.

Immutable collections from List.of, Set.of, Map.of and the copyOf methods add three behaviours of their own: they reject null elements and keys, they are value-based (never compare them with ==; the JDK may return the same instance or a new one as it sees fit, as the last line of the program shows), and Set.of and Map.of deliberately randomise iteration order per JVM run so that no code can accidentally depend on it.

All four correct. The two list APIs differ only in whether the result follows the source; the two comparator APIs are the fixes for the two most common comparator bugs, a NullPointerException from a null element and a reversed() that reversed too much.

Gotchas worth a second read
  • A sorted collection with a comparator inconsistent with equals loses elements. TreeSet asks the comparator, never equals, whether two elements are the same. If you want "sort by price but keep every product", sort a list; if you need a set, give the comparator a tie-breaker that only returns 0 for genuinely equal elements: comparingInt(price).thenComparing(sku).
  • Mutating an element after inserting it into a TreeSet corrupts the tree. The element sits where its old key put it; lookups by the new key miss, and the set may now contain "duplicates". The same disease as a mutable HashMap key (§11), and the same cure: immutable keys.
  • final is not immutability. private final List<String> skus = new ArrayList<>() prevents skus = other and nothing else. skus.add(…) still compiles and still runs.
  • Arrays.asList is fixed-size but not immutable. set works and writes through to the array; add throws. It is neither a copy nor a true view in the sense above.
  • Equal by compareTo, unequal by equals breaks Collections.sort expectations too. BigDecimal is the famous case: new BigDecimal("1.0") and new BigDecimal("1.00") compare as 0 but are not equals, so a HashSet holds both and a TreeSet holds one.

Check yourself

1.You want products ordered by price descending, and among equal prices by SKU ascending. Which comparator does that?

C. Reverse the price key alone by giving comparing a reversed key comparator, then add the ascending tie-breaker. Nothing after it is affected.

A reverses both keys: price descending, sku descending. B reverses twice, which puts price back to ascending and sku to descending, the exact opposite of what was asked. D sorts primarily by sku, with price as the tie-breaker, and then reverses both.

2.Order stores private final List<String> skus, assigned straight from the constructor parameter, and exposes it with return skus;. A caller does List<String> mine = new ArrayList<>(); Order o = new Order(mine); mine.add("X");. What does o.skus() now contain, and what is the fix?

B. The field and the caller's variable point at the same ArrayList. The defensive copy on the way in gives Order its own list; the view or copy on the way out stops callers writing to it.

A is the classic misunderstanding: final fixes the reference, not the object. C wraps the caller's list in a view, so the caller's later add still shows through; a view protects against writes through itself only. D confuses this with iterator fail-fast behaviour, which needs an iteration in progress.

3.Four products are added to new TreeSet<>(comparingInt(Product::priceInCents)). Two of them cost 80. What is the set's size and why?

D. A sorted set has no hash table and never calls equals or hashCode. Its only notion of "same element" is a comparator result of zero, so the second 80-cent product is silently not added. This is what "consistent with equals" guards against.

A and B both assume equals is consulted; it is not. C: the comparator is perfectly valid. Returning 0 for distinct objects is allowed by the contract; it is merely inconsistent with equals, which the documentation warns about but cannot detect.
