Section 8

Records

Fundamentals §10 ended with the observation that equals, hashCode and toString are forty lines of ceremony you get wrong once per career, and that a record gives you all three for free. Here is the full story. A record is a class whose entire state is declared in its header, and from that header the compiler derives everything a value type needs: a private final field per component, a canonical constructor that takes them all, an accessor per component, and equals, hashCode and toString that use every component. What you give up is exactly the freedom that made the hand-written versions error-prone: no extra instance fields, no setters, no superclass, no subclasses.

The design intent is the phrase "a transparent carrier for immutable data". OrderLine is one: three values, no identity beyond them, equal when the values are equal. InventoryService is not: it has behaviour, mutable state and a lifecycle. Knowing which of your classes are records and which are not is most of the skill.

Worked example

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class Records {

    record OrderLine(String sku, int qty, int unitPriceInCents) {
        // compact constructor: no parameter list; runs BEFORE the fields are assigned
        OrderLine {
            if (sku == null || sku.isBlank()) throw new IllegalArgumentException("sku required");
            if (qty <= 0) throw new IllegalArgumentException("qty must be positive: " + qty);
            sku = sku.strip().toUpperCase();          // reassigns the PARAMETER; the field is set from it after
        }
        int totalInCents() { return qty * unitPriceInCents; }
    }

    record Address(String city, String country) { }

    record Order(long id, Address shipTo, List lines) {
        Order {
            lines = List.copyOf(lines);               // defensive, immutable copy
        }
        static Order of(long id, Address shipTo, OrderLine... lines) {   // static factory
            return new Order(id, shipTo, List.of(lines));
        }
        int totalInCents() { return lines.stream().mapToInt(OrderLine::totalInCents).sum(); }
    }

    record Bag(List items) { }                // NO defensive copy: deliberately leaky

    public static void main(String[] args) {
        OrderLine a = new OrderLine("  bolt-7 ", 10, 80);
        OrderLine b = new OrderLine("BOLT-7", 10, 80);
        System.out.println("toString  = " + a);
        System.out.println("equals    = " + a.equals(b) + ", same hash = " + (a.hashCode() == b.hashCode()));
        System.out.println("accessor  = " + a.sku() + " x" + a.qty());

        try { new OrderLine("NUT-3", 0, 25); }
        catch (IllegalArgumentException e) { System.out.println("rejected  = " + e.getMessage()); }

        OrderLine nut = new OrderLine("NUT-3", 4, 25);
        List lines = new ArrayList<>(List.of(a, nut));
        Order order = Order.of(1001L, new Address("Leeds", "UK"), a, nut);
        Order copied = new Order(1001L, new Address("Leeds", "UK"), lines);
        lines.add(new OrderLine("CAM-9", 1, 2_300));  // the caller mutates its own list afterwards
        System.out.println("totals    = " + order.totalInCents() + "c and " + copied.totalInCents() + "c (the copy did not change)");
        System.out.println("nested eq = " + order.equals(copied));

        Map picked = new HashMap<>();
        picked.merge(a, 1, Integer::sum);
        picked.merge(b, 1, Integer::sum);               // an equal record is the same key
        System.out.println("map keys  = " + picked.size() + ", picks of BOLT-7 = " + picked.get(b));

        // shallow immutability: the reference cannot change, the list behind it can
        List items = new ArrayList<>(List.of("x"));
        Bag bag = new Bag(items);
        items.add("y");
        System.out.println("leaky bag = " + bag.items());

        // a local record is a named, typed intermediate for a pipeline
        record SkuTotal(String sku, int total) { }
        List totals = order.lines().stream()
            .map(l -> new SkuTotal(l.sku(), l.totalInCents()))
            .toList();
        System.out.println("per line  = " + totals);
    }
}

Read the first three output lines against the highlighted record. " bolt-7 " went in; BOLT-7 came out, because the compact constructor normalised the parameter and the compiler-generated assignment this.sku = sku ran afterwards. Two lines built from different input strings are equal and share a hash code, because both derived members use the normalised fields. And nested eq is true because record equality recurses: Order.equals compares its Address with Address.equals and its List with List.equals, element by element.

The red line is the counter-example. Bag stores the caller's ArrayList as-is, so the caller's later add is visible through bag.items(). The record's reference is final; the object it refers to is whatever you put there. Order avoids this with List.copyOf, which is both a copy and immutable — and is a no-op when handed a list that is already immutable, so the of factory's List.of costs nothing extra.

What the compiler writes for you

record OrderLine(String sku, int qty, int unitPriceInCents) { }

The header is the whole state. Components are listed once and become fields, constructor parameters, accessors and the members of equals/hashCode/toString, in that order.

final class OrderLine extends java.lang.Record {
    private final String sku;
    private final int qty;
    private final int unitPriceInCents;

    OrderLine(String sku, int qty, int unitPriceInCents) {   // canonical constructor
        this.sku = sku; this.qty = qty; this.unitPriceInCents = unitPriceInCents;
    }
    public String sku() { return sku; }                       // accessors: no "get" prefix
    public int qty() { return qty; }
    public int unitPriceInCents() { return unitPriceInCents; }

    public boolean equals(Object o) { /* same class and every component equal */ }
    public int hashCode()           { /* combined from every component */ }
    public String toString()        { /* OrderLine[sku=…, qty=…, unitPriceInCents=…] */ }
}

Every one of these may be declared explicitly to override the generated version. Do it for an accessor that must return a defensive copy, or a toString that must hide a secret — and never for equals unless you can state why two records with equal components should be unequal.

// Canonical: full parameter list, you MUST assign every field yourself
record OrderLine(String sku, int qty, int unitPriceInCents) {
    OrderLine(String sku, int qty, int unitPriceInCents) {
        if (qty <= 0) throw new IllegalArgumentException("qty");
        this.sku = sku.strip();
        this.qty = qty;
        this.unitPriceInCents = unitPriceInCents;
    }
}

// Compact: no parameter list, parameters are in scope, fields are assigned
// from the (possibly reassigned) parameters AFTER your body runs
record OrderLine(String sku, int qty, int unitPriceInCents) {
    OrderLine {
        if (qty <= 0) throw new IllegalArgumentException("qty");
        sku = sku.strip();          // legal: it is the parameter
        // this.sku = sku;          // compile error: the field is assigned for you
    }
}

Use the compact form unless you need to do something the automatic assignment cannot. Any other constructor you add (a two-argument convenience, say) must delegate with this(…) to the canonical one, so validation runs exactly once on every path.

Put the compact constructor in order

Five lines of a validating, normalising compact constructor for Address. Order them so that the record can never hold a blank city and always stores the country code in upper case. Remember that the compact body has no parameter list and never assigns this.x.

  1. 1 country = country.strip().toUpperCase();
  2. 2 }
  3. 3 Address {
  4. 4 if (country.length() != 2) throw new IllegalArgumentException("ISO country code required");
  5. 5 if (city == null || city.isBlank()) throw new IllegalArgumentException("city required");

Correct. Validate the cheap, independent condition first; normalise country before checking its length, so " gb " is accepted as GB rather than rejected for its padding. The implicit this.city = city; this.country = country; runs after the closing brace, picking up the normalised parameter. Swapping lines 3 and 4 would also compile — but then " gb " would throw.

The rules, and the reasons

Record restrictions and their rationale
RuleBecause
No instance fields beyond the componentsThe header must be the complete state, or the generated equals would be wrong. Static fields are allowed.
Implicitly final; cannot be abstractA subclass could add state the header does not know about.
Cannot extends anythingEvery record already extends java.lang.Record. It may implement interfaces, including Comparable.
Components are final; no setters are generatedImmutability is the point. "Change" one by constructing a new record — withQty(int) style methods are a common addition.
Accessors are name(), not getName()A deliberate break from the JavaBeans convention; frameworks that reflect on getters have mostly caught up.
Native methods are forbidden; instance initialiser blocks are forbiddenAll initialisation must be visible in the constructor.
May be nested, local, or generic: record Pair<A, B>(A first, B second)A nested record is implicitly static; a local one cannot capture locals from the enclosing method.

When not to use one

  • The thing has identity. A Customer whose name can change is still the same customer; two records with equal components are indistinguishable by design. If "same object" matters, it is a class.
  • The thing changes. InventoryService mutates. A record of its state could be a snapshot, but the service itself is a class.
  • It needs a superclass. Records cannot extend. Share behaviour through an interface with default methods (§3) or composition.
  • It is a JPA entity or a framework bean that requires a no-argument constructor and setters. Records have neither, by design.
  • Some components are derived. If total is always qty * price, it is a method, not a component — otherwise two lines can disagree with themselves and equals will notice.

What is left — DTOs, map keys, multi-value returns, stream intermediates, configuration values, messages, coordinates, money — is most of the small classes in any codebase. And because a record's components are exactly its accessors, the pattern-matching switch in §9 can take one apart: case OrderLine(var sku, var qty, var price) is only possible because the compiler knows the record's shape.

Record gotchas
  • Immutability is shallow. A component of type List, array or Date is a reference, and the record cannot stop anyone mutating what it points to. Copy in the compact constructor (List.copyOf, array.clone()) and, for arrays, copy again in the accessor.
  • Arrays make equals useless. The generated equals uses Objects.equals on each component, and for arrays that is identity. A record Row(int[] cells) is never equal to another Row with the same numbers. Use a List.
  • A mutable component breaks hash-based collections. Same lesson as Fundamentals §10: if a component's own hashCode can change, the record's can, and a HashSet loses it.
  • Overriding an accessor changes toString but not equals. equals and hashCode read the fields directly, not the accessors. An accessor that returns a copy is fine; one that returns something different from the field makes the record lie.
  • Adding a component is a breaking change for every caller. The canonical constructor's signature changes. Keep a static factory or an explicit convenience constructor as the public entry point if the shape is likely to evolve.

Check yourself

1.Inside a compact constructor you write this.sku = sku.strip();. What happens?

B. In a compact constructor the fields are definitely assigned by the compiler at the end of the body, so assigning this.sku yourself is an error ("cannot assign a value to final variable"). The idiom is to reassign the parameter — sku = sku.strip(); — which the automatic assignment then picks up.

A describes the canonical (full-parameter-list) constructor, where you do assign fields yourself. C would be a terrible design and is not what happens — the compiler rejects the code instead. D is wrong: any statement is allowed, including logging, normalisation and computation; only field assignment is reserved.

2.record Order(long id, List<OrderLine> lines) { } with no explicit constructor. A caller does var l = new ArrayList<OrderLine>(); var o = new Order(1, l); l.add(line);. What is o.lines().size()?

C. The generated canonical constructor is a plain this.lines = lines. The record's field is final, but it refers to the caller's ArrayList, which the caller can still change. This is the Bag case from the worked example. A compact constructor with lines = List.copyOf(lines); is the fix, and it is the first thing to write for any record with a collection component.

A and B credit records with behaviour they do not have — nothing is copied or frozen unless you write it. D is wrong: a component can be any type, which is exactly why shallow immutability is a trap.

3.Which of these should not be a record?

A. A cart mutates and has identity — two carts with the same contents are two different customers' carts. You could model it as a record holding a mutable list, but then its equals and hashCode change under it, and nothing about it is "transparent immutable data". It is a class.

B, C and D are textbook records: values with no identity, compared by content, never changed after construction. D is the interesting one — the stock changes, but a snapshot of it does not, and a record is the right way to say so.
