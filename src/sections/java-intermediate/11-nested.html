Section 2

Nested, inner, local and anonymous classes

Java lets you declare a class inside another class, inside a method, or inside an expression. The four forms look similar and are not: they differ in what they can see, what they secretly hold a reference to, and when they are the right tool. Lambdas (§4) are the fifth member of the family, and most of what makes them simple is that they drop the baggage described here.

The question to ask of any nested class is: does it need an instance of the enclosing class to exist? If not, it is static and is merely a class that lives in a namespace. If so, it is inner, and every one of its instances carries a hidden pointer to the outer instance that created it.

Worked example

import java.util.ArrayList;
import java.util.List;

public class Nested {

    // 1. STATIC NESTED: a class placed inside another for namespacing. No outer instance.
    static class Line {
        final String sku; final int qty;
        Line(String sku, int qty) { this.sku = sku; this.qty = qty; }
        @Override public String toString() { return sku + "x" + qty; }
    }

    private final List lines = new ArrayList<>();
    private final String orderId;

    Nested(String orderId) { this.orderId = orderId; }

    // 2. INNER: every instance carries a hidden reference to the enclosing Nested (Nested.this)
    class Cursor {
        private int pos = 0;                                       // the cursor's own state
        boolean hasNext() { return pos < lines.size(); }           // `lines` means Nested.this.lines
        Line next() { return lines.get(pos++); }
        String owner() { return Nested.this.orderId; }             // the qualified form, written out
    }

    Cursor cursor() { return new Cursor(); }                       // `this` becomes the new Cursor's outer

    int totalQty() {
        int base = 100;                                            // a local that a local class will capture

        // 3. LOCAL: declared inside a method; sees the method's effectively-final locals
        class Counter {
            int sum = base;                                        // `base` is COPIED into the Counter at construction
            void add(Line l) { sum += l.qty; }
        }
        Counter c = new Counter();
        for (Line l : lines) c.add(l);
        // base = 0;   // uncomment: "local variables referenced from an inner class must be final or effectively final"
        return c.sum - base;
    }

    public static void main(String[] args) {
        Nested order = new Nested("ORD-1");
        order.lines.add(new Line("BOLT-7", 3));
        order.lines.add(new Line("NUT-3", 10));

        Line standalone = new Nested.Line("CAM-9", 1);             // static nested: no outer instance needed
        System.out.println("static nested = " + standalone);

        Nested.Cursor cur = order.cursor();                        // inner: created THROUGH an instance
        Nested.Cursor other = order.new Cursor();                  // the explicit (and rarely seen) form
        System.out.println("inner owner   = " + cur.owner() + " / " + other.owner());
        StringBuilder walked = new StringBuilder();
        while (cur.hasNext()) walked.append(cur.next()).append(' ');
        System.out.println("walked        = " + walked.toString().trim());

        System.out.println("local class   = " + order.totalQty());

        // 4. ANONYMOUS: a one-off implementation declared at the point of use
        Runnable report = new Runnable() {
            @Override public void run() {
                // `this` here is the anonymous Runnable itself, never the enclosing class
                System.out.println("anonymous     = this is a " + this.getClass().getSuperclass().getSimpleName()
                        + ", simple name '" + this.getClass().getSimpleName() + "'");
            }
        };
        report.run();

        // A lambda has no `this` of its own; it captures the enclosing instance's, if there is one
        Runnable lambda = () -> System.out.println("lambda        = " + order.lines.size() + " lines captured");
        lambda.run();
    }
}

Line is static: it is a value type that happens to be scoped under Nested, and new Nested.Line(…) needs no order to exist. Cursor is inner: lines inside it is really Nested.this.lines, resolved through a hidden field the compiler added, which is why it can only be created from an instance — order.cursor(), or the explicit order.new Cursor(). Counter is local to one method and copies the local base into itself. The anonymous Runnable is a class with no name (getSimpleName() is empty) whose superclass is Object, because Runnable is an interface.

The four forms side by side

public class Order {
    public static class Line { … }      // Order.Line — a top-level class in all but name
}
Order.Line l = new Order.Line("BOLT-7", 3);
  • Sees: the outer class's static members, including private ones. No outer instance.
  • Holds: nothing extra. Same memory footprint as a top-level class.
  • Use for: helper types that belong with their owner — a builder, a node, a value type like Map.Entry. Default to this form.
public class Order {
    private final List lines = …;
    public class Cursor {               // no `static`: each Cursor has an Order.this
        Line next() { return lines.get(pos++); }
    }
}
Order.Cursor c = order.new Cursor();    // or, far more usually, a method on Order that does this
  • Sees: everything in the outer instance, as if it were written inside it. Name clashes are resolved with Order.this.field.
  • Holds: a synthetic final Order this$0 field, set by a constructor parameter you never see. The outer object cannot be garbage-collected while the inner one lives.
  • Use for: iterators, cursors and views that are meaningless without their owner. ArrayList.Itr is an inner class for exactly this reason.
int totalQty() {
    int base = 100;                     // must be effectively final to be captured
    class Counter {
        int sum = base;                 // reads a COPY, taken when the Counter is constructed
    }
    return new Counter().sum;
}
  • Sees: the enclosing instance (if the method is not static) plus the method's locals and parameters — but only those that are never reassigned.
  • Holds: the outer this (in an instance method) and a private copy of each captured local, as synthetic val$base fields.
  • Use for: rarely. A local record or enum (§8) is the modern reason to reach for this form: a throwaway tuple scoped to one method.
Comparator byQty = new Comparator() {   // declares AND instantiates a subclass
    @Override public int compare(Line a, Line b) { return Integer.compare(a.qty, b.qty); }
};
// since Java 8, for a single-method interface, write a lambda instead:
Comparator byQty2 = (a, b) -> Integer.compare(a.qty, b.qty);
  • Sees: the same as a local class. Same capture rules.
  • Holds: the same hidden fields as a local class. this inside it is the anonymous object, so this.toString() is its toString, not the outer one.
  • Use for: implementing an interface with more than one abstract method, or subclassing a class, at the point of use. For a single abstract method, a lambda is shorter, clearer, and does not allocate a class.

Nested-class gotchas
  • An inner class keeps its outer alive. Register an inner-class listener with a long-lived registry and the whole enclosing object — and everything it references — cannot be collected until the listener is removed. This is the classic Android and Swing memory leak. If the nested class does not use the outer instance, make it static; the compiler will tell you nothing is broken, and -Xlint stays silent too.
  • Serialising an inner class serialises its outer. The hidden this$0 is a field like any other, so the enclosing object goes to the stream too — and if it is not Serializable, you get a NotSerializableException naming a class you never asked to serialise.
  • this means different things in an anonymous class and a lambda. In the anonymous class it is the anonymous object; in a lambda it is the enclosing instance. Converting one to the other changes the meaning of every this and every unqualified call to an inherited method — IDEs warn, but only if you read the warning.
  • Shadowing is silent. An inner class field named lines hides the outer lines for the whole inner body. Reach past it with Outer.this.lines. A lambda, by contrast, cannot shadow a local — redeclaring base as a lambda parameter is a compile error — which is one reason lambdas are easier to read.
  • Effectively final is checked per variable, not per use. A single i++ anywhere in the method, even after the capture, makes i uncapturable everywhere. The error points at the capture, not at the increment.

Check yourself

1.This method does not compile. What is the smallest change that fixes it while still counting?
int count = 0; lines.forEach(l -> { if (l.qty() > 5) count++; }); return count;

D. The lambda captures count by copy, so count++ inside it could only ever increment the copy — which is why the compiler rejects it rather than let it silently do nothing. The honest fixes stop mutating a captured local: a loop, or a stream that produces the count as its result.

A makes the problem worse — a final variable cannot be incremented anywhere. B is false: anonymous classes have exactly the same capture rule as lambdas. C compiles, and is wrong in a way the compiler cannot see: a static field is shared by every call on every thread, so two concurrent counts corrupt each other. The int[1] or AtomicInteger trick also compiles, but exists mainly to work around the rule in callbacks you cannot restructure.

2.Inside an instance method of Order, you replace new Runnable() { public void run() { log(this.toString()); } } with () -> log(this.toString()). What changes?

B. An anonymous class is a real object with its own this; a lambda is not, so this inside it is lexically the enclosing instance — the Order. The behaviour changes from logging something like Order$1@1b6d3586 to logging the order itself.

A is the common assumption and the reason this refactoring is a known trap. C is wrong: this is legal in a lambda inside an instance method; it is illegal only in a static context, where there is no instance at all. D invents a rule — this is captured at creation like any other value.

3.A code review flags class Builder nested inside Order because it is not static, although it never touches an Order field. Which consequences of leaving it non-static are real? Select all that apply.

A and D. A non-static nested class is inner, full stop: it gets a this$0 field whether or not the body uses it (A), and it can only be instantiated through an existing outer instance (D) — which for a builder, whose whole purpose is to exist before the Order, is absurd. The fix is one keyword.

B is what you would hope for, but javac and -Xlint:all say nothing; only IDE inspections catch it. C is not real — the extra field costs memory and retention, not time.
