Section 13

Files, paths and I/O

Stock arrives as a CSV export, orders leave as a report, and both must survive a machine that was not the one you developed on. Java has two generations of file API. java.io (1996) is a family of streams — byte pipes and character pipes you wrap around each other. java.nio.file (Java 7) adds Path and Files: a model of the file system plus static helpers that do the common jobs in one call and open the right stream for you underneath. Use the second; understand the first, because it is what the second returns when the one-liner is not enough.

Path is a value, not a file

A Path is an immutable, parsed path string — segments plus a root — with no requirement that anything exists on disk. Every method below is pure string manipulation; only Files touches the file system. Given Path base = Path.of("data", "2026"):

Common Path operations with their results
ExpressionResultWhat it does
base.resolve("stock.csv")data/2026/stock.csvAppends a relative path. If the argument is absolute, the result is the argument — a classic surprise with user input.
base.resolveSibling("2027")data/2027Replaces the last segment.
base.relativize(Path.of("data/2026/archive/x.csv"))archive/x.csvThe path from base to the argument. Both must be relative or both absolute.

On Windows the separator is \ and a root is C:\; on everything else it is /. Path.of("data", "stock.csv") with separate segments is correct everywhere; Path.of("data/stock.csv") happens to work on Windows too, but Path.of("data\\stock.csv") is a single file name on Linux.

Worked example

Write a small stock file, read it back three different ways, copy it into an archive, list what exists, and clean up. Everything happens in a fresh temporary directory, and only names relative to it are printed, so the output is identical on every machine.

import java.io.BufferedReader;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.NoSuchFileException;
import java.nio.file.Path;
import java.nio.file.StandardCopyOption;
import java.util.List;
import java.util.stream.Stream;

public class FilesDemo {
    public static void main(String[] args) throws IOException {
        Path dir = Files.createTempDirectory("inventory-");   // somewhere under java.io.tmpdir
        Path csv = dir.resolve("stock.csv");

        Files.writeString(csv, """
                # sku,qty
                BOLT-7,10
                NUT-3,4

                CAM-9,2
                """, StandardCharsets.UTF_8);
        System.out.println("file             = " + csv.getFileName());
        System.out.println("size in bytes    = " + Files.size(csv));

        // 1. the whole file in memory
        List all = Files.readAllLines(csv, StandardCharsets.UTF_8);
        System.out.println("readAllLines     = " + all.size() + " lines");

        // 2. a lazy stream - the file stays open until the try block ends
        long units;
        try (Stream lines = Files.lines(csv, StandardCharsets.UTF_8)) {
            units = lines.map(String::strip)
                         .filter(l -> !l.isEmpty() && !l.startsWith("#"))
                         .mapToLong(l -> Long.parseLong(l.split(",")[1]))
                         .sum();
        }
        System.out.println("units via lines  = " + units);

        // 3. a buffered reader, one line at a time
        int skus = 0;
        try (BufferedReader in = Files.newBufferedReader(csv, StandardCharsets.UTF_8)) {
            String line;
            while ((line = in.readLine()) != null) {
                if (line.isBlank() || line.startsWith("#")) continue;
                skus++;
            }
        }
        System.out.println("skus via reader  = " + skus);

        // directories, copies, and a walk
        Path archive = Files.createDirectories(dir.resolve("archive"));
        Path copy = Files.copy(csv, archive.resolve("stock-2026-10-15.csv"), StandardCopyOption.REPLACE_EXISTING);
        System.out.println("copied to        = " + slashes(dir.relativize(copy)));
        try (Stream walk = Files.walk(dir)) {
            System.out.println("regular files    = " + walk.filter(Files::isRegularFile)
                    .map(p -> slashes(dir.relativize(p)))
                    .sorted()
                    .toList());
        }
        System.out.println("exists           = " + Files.exists(copy)
                + ", notExists(nope.csv) = " + Files.notExists(dir.resolve("nope.csv")));

        // a missing file is a specific IOException, not a null
        try {
            Files.readString(dir.resolve("nope.csv"));
        } catch (NoSuchFileException e) {
            System.out.println("NoSuchFile       = " + Path.of(e.getFile()).getFileName());
        }

        // delete children before parents; a non-empty directory refuses
        Files.delete(copy);
        Files.delete(archive);
        Files.delete(csv);
        Files.delete(dir);
        System.out.println("cleaned up       = " + Files.notExists(dir));
    }

    // Windows separates with '\'; print '/' so the lesson reads the same everywhere
    static String slashes(Path p) { return p.toString().replace(p.getFileSystem().getSeparator(), "/"); }
}

Thirty-seven bytes for five lines: the text block normalises every line ending to \n regardless of the platform the source was saved on, and UTF-8 encodes these ASCII characters one byte each. readAllLines gives five strings including the comment and the blank; the stream version filters both out and sums the quantities; the reader counts the SKUs. Three tools for three shapes of problem, and the choice between them is the subject of the next three subsections.

Notice what the walk returned: a sorted list of relative paths. Files.walk yields paths in file-system order, which is not specified and differs between NTFS and ext4, so a program that prints or compares them unsorted is non-deterministic. Also notice the order of the four delete calls. Files.delete on a directory that still has a file in it throws DirectoryNotEmptyException; children first, then parents.

Three layers, one file

// InputStream / OutputStream: raw bytes, no idea what a character is
try (InputStream in = new BufferedInputStream(Files.newInputStream(csv))) {
    byte[] header = in.readNBytes(9);          // "# sku,qty" as UTF-8 bytes
    int b;
    while ((b = in.read()) != -1) { /* one byte at a time, buffered underneath */ }
}
  • The bottom layer. Images, zips, sockets, anything binary.
  • read() returns an int 0–255, or −1 at end of stream — the int is so that −1 cannot collide with a byte value.
  • Unbuffered, every read() is a system call. Wrap in BufferedInputStream or read in chunks.
// Reader / Writer: characters, decoded from bytes by a Charset you choose
try (BufferedReader in = new BufferedReader(
        new InputStreamReader(Files.newInputStream(csv), StandardCharsets.UTF_8))) {
    String line = in.readLine();               // null at end of stream
}
// ...which is exactly what Files.newBufferedReader(csv, UTF_8) builds for you
  • Text. InputStreamReader is the bridge: it decodes bytes into chars using the charset you pass.
  • BufferedReader adds the buffer and readLine(), which handles \n, \r\n and \r alike.
  • FileReader and FileWriter exist; before Java 11 they could not take a charset. Prefer the Files factories.
String whole      = Files.readString(csv, UTF_8);            // small text file
List rows = Files.readAllLines(csv, UTF_8);          // small text file, by line
byte[] raw        = Files.readAllBytes(csv);                 // small binary file
try (Stream s = Files.lines(csv, UTF_8)) { ... }     // any size, lazily
Files.writeString(out, text, UTF_8);                         // create or truncate
Files.write(out, rows, UTF_8, StandardOpenOption.APPEND);    // explicit options
  • Each helper opens the right stream, buffers it, and closes it — except lines and walk, which return a stream that you must close.
  • The readAll* family loads the entire file into memory. Fine for a config file; wrong for a 4 GB log.
  • Write options default to CREATE, TRUNCATE_EXISTING, WRITE — a silent overwrite unless you say APPEND or CREATE_NEW.

Charsets: say what you mean

A file is bytes. Turning bytes into text requires a charset, and a charset is not a property of the file — nothing in stock.csv records that it was written as UTF-8. If the writer and the reader disagree, there is no exception: é written as the two UTF-8 bytes C3 A9 and read as ISO-8859-1 comes back as Ã©, and the first anyone hears of it is a customer complaint. Until Java 17 the no-argument overloads used the platform default, which was UTF-8 on Linux and windows-1252 on most Windows machines, so code passed its tests on the developer's laptop and corrupted data on the server. Java 18 (JEP 400) made UTF-8 the default everywhere, but the rule has not changed: pass the charset explicitly, because explicit is what a reader six months from now can verify.

Buffering, and why readLine is not expensive

A file system call costs microseconds; a Java method call costs nanoseconds. An unbuffered stream makes one system call per read(); a BufferedReader makes one per 8 KB and serves readLine() from memory. The difference on a hundred-megabyte file is seconds versus minutes. Every Files helper is buffered already. If you build a stream by hand, wrap it — and wrap the outermost layer you read from, so the buffer sits between you and the decoder, not between the decoder and the disk.

Lazy streams hold the file open

Files.lines and Files.walk are the two Files helpers that return a Stream. The stream reads on demand, which is what lets it handle a file bigger than memory — and it means the file descriptor stays open until the stream is closed. Stream implements AutoCloseable precisely for this: always put it in a try-with-resources, as the worked example does on its highlighted lines. Without that, the handle is released only when the garbage collector finalises the stream, which may be never; on Windows the file cannot be deleted or renamed in the meantime, and on any OS a loop that forgets this will eventually hit too many open files.

For a large file, Files.lines or newBufferedReader and a loop are the only options. readAllLines is simpler, and the right choice when the file is known to be small — but "known" means a config file you ship, not a CSV a customer uploads.

Tokenised input: Scanner

Scanner splits a source on whitespace (or a regex you supply) and parses tokens on demand: nextInt(), nextLine(), hasNext(). It is convenient for small structured input and for System.in. It has two traps. It is slow — it compiles regular expressions per token — so it is not for bulk files. And nextInt() leaves the line terminator unread, so a following nextLine() returns an empty string; the fix is an extra nextLine() to consume it, or reading whole lines and parsing them yourself, which is clearer anyway. Construct it as new Scanner(path, StandardCharsets.UTF_8) — the charset argument exists for the same reason as everywhere else.

The exceptions are specific

Subclasses of IOException thrown by java.nio.file and what each means
ExceptionThrown whenUsually fix by
NoSuchFileExceptionThe path does not existChecking the working directory — relative paths resolve from where the JVM was started.

MalformedInputExceptionBytes that are not valid in the charset you decoded withUsing the charset the file was actually written in.

All of these extend IOException, so a bare catch (IOException e) catches them all — and throws away the diagnosis. Catch the specific one when you can act on it (a missing optional config file is not an error; a missing required one is), and let the rest propagate with the message intact. Files.exists before readString does not replace this: the file can disappear between the two calls, and the check costs a system call that the read was going to make anyway.

For recursive operations, Files.walk plus a stream is usually enough; Files.walkFileTree with a FileVisitor is the heavier tool when you need to react to directories before and after their contents, or to continue past unreadable subtrees. And if an old API hands you a java.io.File, file.toPath() converts it, and path.toFile() goes back; do the conversion at the boundary and stay in java.nio.file.

Where file code goes wrong
  • Files.lines(path).count() with no try. Compiles, runs, leaks a file handle every call. The symptom shows up hours later as a failed delete or an exhausted descriptor table.
  • Relative paths and the working directory. Path.of("config.properties") resolves against the directory the JVM was launched from. It works from your IDE and fails from systemd. Resolve against a known base, or read from the classpath.
  • Files.write truncates by default. Writing a log line with the default options replaces the log. Pass StandardOpenOption.APPEND, and CREATE if the file may not exist.
  • Trusting resolve with user input. base.resolve(userSupplied) returns userSupplied unchanged if it is absolute, and .. segments walk out of base. Normalise, then check startsWith(base), before touching the disk.
  • readAllBytes on a file you did not size first. Arrays are limited to 231 elements and your heap is smaller than that. Stream anything that could be large.

Check yourself

1.On a Windows server, long n = Files.lines(report, UTF_8).count(); runs and returns the right number, but the scheduled job that then calls Files.delete(report) fails with AccessDeniedException. Why?

C. Files.lines opens the file and the returned Stream owns that handle; a terminal operation consumes the elements but does not close the stream. The handle is released when close() runs — which here is never, or whenever the garbage collector gets round to it. Windows enforces sharing locks, so an open file cannot be deleted; on Linux the delete would succeed and the leak would go unnoticed for longer.

A invents a state: a consumed stream is just a closed-for-reuse stream, not a lock, and the resource is released by close(), not by exit. B would fail every run, not only the ones after a count. D: lines uses an ordinary buffered reader, not a memory map, and even mapped files can be deleted on Linux.

2.A customer's export was written by a tool that uses windows-1252. Your import reads it with Files.readAllLines(p, StandardCharsets.UTF_8). The file contains a product called Écrou M8. What happens?

B. In windows-1252, É is the single byte C9. A UTF-8 decoder reads C9 as the start of a two-byte sequence and finds 63 (c) next, which is not a valid continuation byte. The Files helpers use a decoder configured to report malformed input, so you get an exception naming the position. That is the good outcome: the import stops instead of storing garbage.

A: nothing in a file declares its encoding and Java does not guess. C is what a hand-built InputStreamReader does — its decoder defaults to replacing bad input with U+FFFD, which is why the same bug in older code is silent. D confuses code points with bytes: the character is the same, the bytes are not.

3.An upload endpoint saves files as uploads.resolve(filename) where filename comes from the request. Which checks are needed to keep the write inside uploads? Select all that apply.

A and D. uploads.resolve("../../etc/passwd") is a legal path that normalize() turns into something outside uploads; the segment-wise startsWith check catches it. And uploads.resolve("/etc/passwd") is simply /etc/passwd — the documented behaviour for an absolute argument — so absolute input must be rejected before or by the same check. Simplest of all is to keep only Path.of(filename).getFileName(), which cannot contain a separator.

B is incomplete: on Windows \ is also a separator, and it does nothing about ... C is the assumption that makes directory-traversal bugs.
