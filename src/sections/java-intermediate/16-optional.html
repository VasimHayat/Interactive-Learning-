Section 7

Optional

Fundamentals §11 diagnosed the NullPointerException and §L's findById returned null for a miss, with a note that the modern alternative was coming. This is it. Optional<T> is a container that holds either one value or nothing, and its only real purpose is to make a return type say "this may be absent" so loudly that the caller cannot forget. A method returning Product might return null and you have to read the Javadoc to know. A method returning Optional<Product> has told you, in the signature, and the compiler will not let you treat the result as a Product without deciding what to do about the empty case.

That decision is the whole API. Every method on Optional is a different way of answering "and if it is empty?" — substitute a value, substitute another lookup, throw, do nothing, or carry the emptiness forward through a chain so the question is answered once, at the end.

Worked example

import java.util.List;
import java.util.Map;
import java.util.Optional;

public class Optionals {

    record Product(String sku, int priceInCents, String supplierSku) { }   // supplierSku may be null

    static final Map CATALOGUE = Map.of(
        "BOLT-7", new Product("BOLT-7", 80, "ACME-0071"),
        "NUT-3",  new Product("NUT-3", 25, null),
        "FREE-1", new Product("FREE-1", 0, "ACME-0999"));

    // The return type says it: a lookup may find nothing.
    static Optional findBySku(String sku) {
        return Optional.ofNullable(CATALOGUE.get(sku));
    }

    static Optional supplierOf(Product p) {
        return Optional.ofNullable(p.supplierSku());
    }

    static int fallbackPrice() {
        System.out.println("  (fallbackPrice() was called)");
        return 999;
    }

    public static void main(String[] args) {
        // map transforms the content when present; an empty Optional just flows through
        int bolt = findBySku("BOLT-7").map(Product::priceInCents).orElse(-1);
        int nope = findBySku("NOPE").map(Product::priceInCents).orElse(-1);
        System.out.println("BOLT-7 price = " + bolt + ", NOPE price = " + nope);

        // flatMap for a step that itself returns an Optional (no Optional>)
        String s1 = findBySku("BOLT-7").flatMap(Optionals::supplierOf).orElse("no supplier");
        String s2 = findBySku("NUT-3").flatMap(Optionals::supplierOf).orElse("no supplier");
        System.out.println("suppliers    = " + s1 + " / " + s2);

        // filter turns a present value that fails the test into empty
        String priced = findBySku("FREE-1").filter(p -> p.priceInCents() > 0)
                                           .map(Product::sku).orElse("not priced");
        System.out.println("FREE-1       = " + priced);

        // orElse evaluates its argument ALWAYS; orElseGet only when empty
        System.out.println("orElse on a present value:");
        int a = findBySku("BOLT-7").map(Product::priceInCents).orElse(fallbackPrice());
        System.out.println("orElseGet on a present value:");
        int b = findBySku("BOLT-7").map(Product::priceInCents).orElseGet(Optionals::fallbackPrice);
        System.out.println("both gave " + a + " and " + b);

        // or() supplies an alternative Optional; orElseThrow names the failure
        Product p = findBySku("NOPE").or(() -> findBySku("NUT-3"))
                                     .orElseThrow(() -> new IllegalStateException("no product"));
        System.out.println("fallback     = " + p.sku());

        // ifPresentOrElse replaces the isPresent()/get() pair
        findBySku("CAM-9").ifPresentOrElse(
            x -> System.out.println("found " + x.sku()),
            () -> System.out.println("CAM-9 is not in the catalogue"));

        // Optional.stream(): keep only the hits, no isPresent() filter needed
        List found = List.of("BOLT-7", "NOPE", "NUT-3").stream()
            .flatMap(sku -> findBySku(sku).stream())
            .map(Product::sku)
            .toList();
        System.out.println("found        = " + found);

        // of() refuses null; ofNullable() is the one that maps null to empty
        try {
            Optional.of(CATALOGUE.get("NOPE"));
        } catch (NullPointerException e) {
            System.out.println("Optional.of(null) threw NullPointerException");
        }
    }
}

The line marked in red is the one people get wrong in production. orElse(fallbackPrice()) is an ordinary method call: Java evaluates the argument before calling orElse, whether or not the Optional is empty — so fallbackPrice() ran and printed its trace even though BOLT-7 was found. orElseGet takes a Supplier, and only invokes it when needed. For a constant, orElse is fine and reads better; for anything that does work — a database query, a default built from a file, logging — it must be orElseGet.

OptionalInt, OptionalLong and OptionalDouble are what the primitive streams return from max(), average() and findFirst(). They avoid boxing, and have the same methods with primitive names — getAsInt, orElse(int) — but no map or filter. Convert with stream().boxed() if you need the full API.

Where Optional must not go

Its designers were explicit: Optional is for return types. Everywhere else it adds an allocation, a level of indirection and a second way to be empty (the Optional reference itself can still be null) without adding information.

Places Optional does not belong and what to use instead
Do not writeWhyInstead
A field: private Optional<String> supplier;It is not Serializable, it doubles the memory of every nullable field, and the field can still be null.A nullable field with an accessor that returns Optional: Optional<String> supplier() { return Optional.ofNullable(supplier); }
A parameter: void price(Optional<Discount> d)Every caller must wrap, and the method still has to handle a null argument.Two overloads, or a nullable parameter documented as such.
Optional<List<Product>>An empty list already means "none". Two ways to say nothing means two checks.Return the empty list.
As a collection element or map valueMap.get then returns null for a missing key and Optional.empty for a present-but-empty one — a distinction nobody wants.Store the value or nothing; Map.get and Optional.ofNullable at the read site.
Optional.of(x).map(…).orElse(…) on a value you know is presentIt is a verbose ternary.x == null ? d : f(x), or just f(x).
Optional gotchas
  • get() is orElseThrow() with a friendly name. It throws NoSuchElementException on empty, so findBySku(s).get() is a NullPointerException with a different class. If you must unwrap unconditionally, write orElseThrow() so the intent is visible.
  • isPresent() then get() is a null check in costume. It is exactly if (x != null) use(x) with more characters. The chain methods exist so that you never write it.
  • orElse(expensive()) always runs expensive(). Shown above. A logging statement inside the default method is the usual way this is discovered.
  • Returning null from a method typed Optional is the worst of both worlds. The caller trusted the signature and will call .map on null. Return Optional.empty(), always.
  • Optional is a value-based class. Do not synchronise on it, compare it with ==, or use it as a map key. Equality is by content: Optional.of(1).equals(Optional.of(1)) is true.

Check yourself

1.loadDefault() reads a configuration file and prints "loading" when it runs. What does findBySku("BOLT-7").map(Product::priceInCents).orElse(loadDefault()) print when BOLT-7 exists?

C. orElse is a normal method, and Java evaluates every argument before entering a method. The file is read, "loading" is printed, and then the value is thrown away because the Optional was present. orElseGet(Optionals::loadDefault) is the fix.

A is what people expect, and is exactly the behaviour of orElseGet, not orElse. B is backwards: orElseGet takes the Supplier; orElse takes a plain value, which is why it is eager. D is wrong because map never sees loadDefault at all.

2.supplierOf returns Optional<String>. What is the type of findBySku("NUT-3").map(Optionals::supplierOf)?

B. map wraps whatever the function returns, and the function returns an Optional, so you get an Optional inside an Optional. It compiles, and then .orElse("none") fails to compile because the outer content is not a String. flatMap is defined for exactly this: its function must return an Optional, and that Optional is used as the result directly.

A describes flatMap. C is wrong because map accepts any function; it has no idea Optional is special. D is wrong because no Optional method silently unwraps — that is the entire design.

3.Which uses of Optional are considered correct by its own designers? Select all that apply.

A and C. A return type is the intended use, and Optional.stream() was added in Java 9 precisely so that a lookup returning Optional composes with flatMap to drop the misses.

B fails twice: Optional is not Serializable, so the entity will not serialise, and the field itself can still be null. D forces every caller to wrap — price(p, Optional.empty()) — and the method must still guard against a null argument; an overload price(Product) is the idiom.
