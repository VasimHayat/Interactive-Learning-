Rehearsal

Interview questions

Twelve questions that actually get asked about this material, with the answer a strong candidate gives. Say your answer out loud before opening the reveal — recognising an answer and being able to produce one are different skills.

Easy  1. What does PECS stand for, and how do you apply it?

Producer Extends, Consumer Super. Look at what the method does with the collection parameter. If it only reads elements out, the collection is a producer and the parameter should be List<? extends T>, so callers can pass a list of any subtype; inside, you may read as T but the compiler forbids add. If it only writes elements in, it is a consumer and should be List<? super T>, so a list of any supertype — even List<Object> — is accepted; inside, you may add a T but read only as Object. If it does both, no wildcard: the exact type, or a generic method <T>. The JDK's own Collections.copy(List<? super T> dest, List<? extends T> src) is the canonical example, and Comparable<? super T> in every sort signature is the same rule — the comparator consumes a T.

Easy  2. Why is a List<Integer> not a List<Number>, when an Integer is a Number?

Because if it were, you could write List<Number> nums = integers; nums.add(2.5); and put a Double into a list that other code still believes holds only Integers. The failure would appear later, as a ClassCastException at some unrelated get. Generic types are therefore invariant: List<A> and List<B> are unrelated however A and B relate. Arrays made the opposite choice — Integer[] is a Number[] — and pay for it with ArrayStoreException at runtime, which the generics designers regarded as a mistake not to repeat. The way to get the flexibility back safely is a wildcard: List<? extends Number> accepts the List<Integer> and, in exchange, forbids add.

Easy  3. What is the difference between a lambda and an anonymous inner class?

A lambda can only implement a functional interface — one abstract method — and has no identity of its own: this inside it is the enclosing instance, it cannot shadow a local, it introduces no new scope for names, and the compiler may reuse one instance for a non-capturing lambda. An anonymous class is a real class: it can implement several methods or extend a class, this is the anonymous object, it can have fields and shadow outer names, and every evaluation allocates a new object that holds a hidden reference to the enclosing instance. Both capture locals by copy and both require captured locals to be effectively final. The practical consequence: an IDE's "convert to lambda" silently changes the meaning of this and of any unqualified call to an inherited method, so a body that uses either must be reviewed, not just converted.

Easy  4. When would you use a record instead of a class, and what does "shallow immutability" mean?

A record is for a transparent carrier of immutable data: a value with no identity, equal when its components are equal, never changed after construction — DTOs, map keys, multi-value returns, stream intermediates. The compiler derives fields, canonical constructor, accessors, equals, hashCode and toString from the header, and a compact constructor lets you validate and normalise before the automatic assignment runs. It is the wrong tool for anything with identity (a customer whose name changes is the same customer), anything that mutates, or anything that needs a superclass or a no-argument constructor. "Shallow" means the record's references are final but the objects behind them are whatever you passed: a List component can still be mutated by whoever holds the original. The idiom is lines = List.copyOf(lines); in the compact constructor, and a List rather than an array, since the generated equals compares arrays by identity.

Medium  5. A class inherits two default methods with the same signature. Which one runs?

Three rules, applied in order. First, a class wins over any interface: if a superclass anywhere up the chain has a concrete method with that signature, every interface default is ignored — this is what guarantees that adding a default to an interface cannot change what existing class hierarchies do. Second, a more specific interface wins: if Fragile extends Shippable and both define describe(), Fragile's body is chosen regardless of declaration order. Third, if the two interfaces are unrelated, the class must override the method itself or the compiler rejects it with "inherits unrelated defaults". Inside that override you may delegate to one with Shippable.super.describe(), the only place that syntax is legal. A follow-up they often add: a default cannot override an Object method such as toString, because rule one would make it pointless and the language forbids it outright.

Medium  6. What does laziness buy a stream pipeline, and which operations break it?

Nothing runs until a terminal operation asks for a result; then elements are pulled one at a time through the whole chain, vertically rather than stage by stage. That buys three things: short-circuiting (findFirst or limit can stop after examining two of a million elements), the ability to process sources bigger than memory or infinite (Files.lines, Stream.iterate), and fusion — filter and map run in a single pass with no intermediate collections. Stateful operations break it: sorted cannot emit its first element until it has seen the last, so it is a barrier that drains everything upstream and buffers it, and distinct must remember what it has seen. Put filter before sorted to give it less to drain. Two related points worth volunteering: a pipeline with no terminal operation is a silent no-op, and a stream is single-use — a second terminal throws IllegalStateException.

Medium  7. groupingBy versus partitioningBy — and what happens when toMap sees a duplicate key?

groupingBy(classifier, downstream) buckets elements by any key and applies a downstream collector to each bucket; keys appear only for values that actually occurred, so a lookup for an absent bucket returns null. partitioningBy(predicate, downstream) is the boolean special case with one extra guarantee: both true and false keys are always present, even when one side is empty. That guarantee is the only reason to prefer it, and it removes a null check. The two-argument toMap(keyFn, valueFn) throws IllegalStateException: Duplicate key … the moment a second element maps to an existing key — it refuses to pick a winner silently, which is deliberate. Supply the three-argument form with a merge function — Integer::sum, Math::min, (a, b) -> a — to say what should happen, and the four-argument form with a map supplier if you need TreeMap or LinkedHashMap order. Also worth knowing: toMap rejects null values, unlike HashMap.put, and counting() returns Long.

Medium  8. Where should Optional be used, and where is it misused?

Its designers intended one use: a return type that says "this may be absent" so loudly the caller cannot forget. The right way to consume one is the chain — map, flatMap, filter, then orElse, orElseGet, orElseThrow or ifPresentOrElse — so the question "and if empty?" is answered once, at the end. The misuses: get(), which is orElseThrow with a friendlier name, and isPresent() followed by get(), which is a null check in costume. As a field it is not Serializable, doubles the memory of every nullable field, and can itself still be null; as a parameter it forces every caller to wrap and the method must still guard against a null argument; as a collection element or wrapper around a collection it creates two ways to say "nothing". One performance trap: orElse(expensive()) evaluates its argument eagerly, present or not — use orElseGet for anything that does work. And never return null from a method typed Optional.

Medium  9. What does "consistent with equals" mean for a comparator, and what goes wrong without it?

The Comparable contract recommends that compareTo returns 0 exactly when equals returns true. It is not enforced, and the sorted collections are where the gap shows: TreeSet and TreeMap have no hash table and never call equals or hashCode — their only notion of "same element" is a comparison result of 0. Build a TreeSet with comparingInt(Product::priceInCents), add four products of which two cost 80, and the set silently holds three. The same input in a HashSet holds four. BigDecimal is the famous JDK case: 1.0 and 1.00 compare as 0 but are not equals. The fix is a tie-breaker that only returns 0 for genuinely equal elements — comparingInt(price).thenComparing(sku) — or a list instead of a set if duplicates by price are fine. Two more comparator points interviewers like: a - b overflows where Integer.compare does not, and reversed() reverses the whole chain built so far, not the last key.

Hard  10. When would you choose a sealed type with a pattern switch over ordinary polymorphism?

They solve opposite halves of the expression problem — no single design makes both adding types and adding operations cheap. Polymorphism puts each operation as a method on each type; adding a type is one new class and nothing else changes, but adding an operation touches every class. A sealed hierarchy with pattern switches puts each operation in one place with a case per type; adding an operation is one new method, and adding a type is a compile error at every switch that must now handle it — because a switch expression over a sealed type must be exhaustive and the compiler knows the complete set of permitted subtypes. So: sealed switch when the types are fixed and the operations keep growing (discount kinds, AST nodes, messages), polymorphism when the operations are fixed and the types keep growing (shapes in a drawing app). The one rule that makes the sealed version safe is to write no default: a default does not add safety, it removes it, by letting the new subtype fall silently into the fallback path in production. Record patterns and guards (when) let each case deconstruct and qualify in one line, and case null is needed because a pattern switch throws on null.

Hard  11. What does a HashMap do when it resizes, and why is a mutable key fatal?

The table is an array of bins whose length is a power of two; a key's bin is (length − 1) & hash, after spreading the hash with h ^ (h >>> 16) so the mask sees the high bits too. The map tracks a threshold of capacity × load factor, 16 × 0.75 = 12 by default; when the entry count exceeds it, the table doubles and every entry is re-inserted into its new bin. That rehash is O(n), but doublings are geometric so put stays amortised O(1); pre-sizing with the expected count divided by 0.75 skips every resize. Two consequences to volunteer: iteration order changes on resize, so code that happened to see insertion order breaks past 12 entries; and a bin that reaches 8 entries in a table of at least 64 bins becomes a red-black tree, which is the JDK defending against a bad hashCode. A mutable key breaks the structure because the entry sits in the bin chosen for its original hash: after mutation, a lookup by the new value goes to a different bin, a lookup by the old value reaches the right bin but fails equals, and even the original key object cannot find its own entry. Nothing throws; the entry is simply unreachable — until a resize happens to move it, at which point behaviour depends on how many other entries exist. Keys must be immutable: strings, records, boxed primitives.

Hard  12. How does daylight-saving time break date arithmetic, and why do you store Instants?

A point on the timeline and a reading on a wall clock are different things, and the mapping between them depends on a zone whose rules change twice a year. In London on 29 March 2026 the hour 01:00–01:59 does not exist; on 25 October it happens twice. So placed.plusDays(1) on a ZonedDateTime keeps the wall clock at 23:30 and lands only 23 real hours later, while plusHours(24) adds elapsed time and lands at 00:30 the day after. Neither is wrong — "same time tomorrow" is a Period question, "the 24-hour deadline" is a Duration question — and choosing the method that matches the question is the whole skill. A LocalDateTime cannot ask the question at all, because without a zone it is not a point in time: two servers in two zones will disagree about when it happened. So for anything that has happened you store an Instant, which is UTC and unambiguous, and convert to a ZonedDateTime with a region id like Europe/London — never a fixed offset or a three-letter abbreviation — only to display. For a future appointment you store the ZonedDateTime instead, because the customer means 09:00 on their clock even if the rules change before then. And inject a Clock, so the overlap is a unit test rather than a 2 a.m. incident in October.
