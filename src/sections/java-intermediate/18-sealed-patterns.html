Section 9

Sealed types, switch expressions and pattern matching

Fundamentals §8 taught the object-oriented answer to "the behaviour depends on the type": put the method on the type and let dynamic dispatch choose. That works beautifully when the set of operations is fixed and the set of types keeps growing. The warehouse's pricing rules are the opposite shape: there are three kinds of Discount and there will be three next year, but the operations on them multiply — price a line, describe it on a receipt, decide whether two offers may stack, export it to the accounting system. Putting all of those on each record class scatters one business concept across many files.

Java 21 gives you the other answer. A sealed type declares exactly which subtypes exist, and a pattern-matching switch handles each one in a single place, with the compiler proving that no case has been forgotten. This section is about that pair, and about the switch expression and pattern syntax that make it work.

Sealing a hierarchy

sealed interface Discount permits PercentOff, FixedOff, BuyNGetOne {}

record PercentOff(int percent) implements Discount {}       // records are implicitly final
record FixedOff(int cents)     implements Discount {}
record BuyNGetOne(int n)       implements Discount {}

sealed class Shipment permits Parcel, Freight {}
final class Parcel extends Shipment {}                      // a permitted subclass must say what it is:
non-sealed class Freight extends Shipment {}                // final, sealed, or non-sealed (open again)
  • Every permitted subtype must be final, sealed or non-sealed. A record or enum is already final.
  • The permitted subtypes must live in the same package as the sealed type (or the same named module). If they are all in the same source file you may omit permits and the compiler infers it.
  • Sealing says nothing about instances: there may be a million PercentOff objects. It constrains the set of classes, which is what exhaustiveness checking needs.

Worked example

Pricing a line under any discount, plus a nested record pattern that takes an OrderLine and the Product inside it apart in one expression.

import java.util.List;

public class SealedSwitch {

    record Product(String sku, int priceInCents) {}
    record Line(Product product, int qty) {}

    sealed interface Discount permits PercentOff, FixedOff, BuyNGetOne {}
    record PercentOff(int percent) implements Discount {
        PercentOff {
            if (percent < 0 || percent > 100) throw new IllegalArgumentException("percent out of range: " + percent);
        }
    }
    record FixedOff(int cents) implements Discount {}
    record BuyNGetOne(int n) implements Discount {}

    static int lineTotal(Line line, Discount discount) {
        int gross = line.product().priceInCents() * line.qty();
        return switch (discount) {                              // no default: the compiler knows every case
            case PercentOff(int pct)                     -> gross - gross * pct / 100;
            case FixedOff(int cents) when cents >= gross -> 0;  // guard: a voucher never goes negative
            case FixedOff(int cents)                     -> gross - cents;
            case BuyNGetOne(int n)                       -> gross - (line.qty() / (n + 1)) * line.product().priceInCents();
        };
    }

    static String describe(Line line) {
        // a nested record pattern takes the line AND the product inside it apart in one go
        if (line instanceof Line(Product(String sku, int price), int qty) && qty > 1) {
            return qty + " x " + sku + " @ " + price + "c";
        }
        return "single " + line.product().sku();
    }

    public static void main(String[] args) {
        Line bolts = new Line(new Product("BOLT-7", 80), 10);
        List offers = List.of(new PercentOff(10), new FixedOff(100), new FixedOff(5_000), new BuyNGetOne(4));
        for (Discount d : offers) {
            System.out.printf("%-20s -> %4d%n", d, lineTotal(bolts, d));
        }
        System.out.println(describe(bolts));
        System.out.println(describe(new Line(new Product("GIRD-1", 120_000), 1)));
    }
}

BuyNGetOne[n=4]      ->  640

single GIRD-1

Four things to notice in lineTotal. It is a switch expression: it produces the value that return hands back, so there is no mutable result variable and no way to forget an assignment. Each case is a record pattern: PercentOff(int pct) both tests the type and binds the component, so the body never calls an accessor. The when clause is a guard: the first FixedOff case applies only when the voucher is worth more than the line, and because it comes first, the second FixedOff case is reached only when the guard failed. And there is no default, which is not laziness but the whole point.

Exhaustiveness: let the compiler count

A switch expression must yield a value for every possible input, so the compiler checks that the cases cover the type. For an int or a String that is impossible without default. Hierarchy and fallback

The lesson the sandbox is making: a default on a sealed switch does not add safety, it removes it. Without one, adding a subtype breaks every switch that needs updating, at compile time, with the file and line. With one, the new subtype silently takes the fallback path in production.

Switch: statement, expression, and the pattern forms

// statement: does things, yields nothing, need not be exhaustive (unless it uses patterns)
switch (sku) {
    case "BOLT-7", "NUT-3" -> band = "small";
    default                -> band = "standard";
}

// expression: IS a value, must be exhaustive, every branch yields the same kind of thing
String band = switch (sku) {
    case "BOLT-7", "NUT-3" -> "small";
    default                -> "standard";
};

Prefer the expression whenever the switch exists to compute something. It cannot forget a branch, cannot leave a variable unassigned, and reads as the single thing it is. One subtlety: a switch statement that uses patterns (type or record patterns, or case null) must also be exhaustive, so the old "it compiles with cases missing" behaviour applies only to the legacy constant forms.

int days = switch (category) {
    case FASTENER   -> 1;                 // arrow: one expression, no fall-through, no break
    case STRUCTURAL -> 14;
    case TOOLING    -> {                  // arrow with a block: must yield
        int base = 3;
        yield base * 2;
    }
};

int legacy = switch (category) {          // colon form in an expression: fall-through still exists
    case FASTENER:
    case STRUCTURAL: yield 7;             // both labels reach this yield
    default:         yield 0;
};

Use the arrow form. Fall-through, the reason every C-family language has a "forgot the break" bug, is impossible with arrows: each case is a self-contained expression or block. yield exists only to get a value out of a block; it is not return and will not leave the enclosing method.

A type pattern on instanceof works the same way: if (o instanceof String s) tests and binds in one step, and s is in scope wherever the compiler can prove the test passed, including after an early return in the negated form.

Patterns outside the sealed case

Patterns are not only for sealed types. The same machinery handles Object, enums, strings and primitives, with dominance rules that decide which case may come first.

public class Patterns {

    enum Category { FASTENER, STRUCTURAL, TOOLING }

    static String classify(Object o) {
        return switch (o) {
            case null                 -> "null, handled as a case: no NullPointerException";
            case Integer i when i < 0 -> "negative int " + i;
            case Integer i            -> "int " + i;
            case String s             -> "string of length " + s.length();
            case int[] arr            -> "int array of " + arr.length;
            default                   -> "something else: " + o.getClass().getSimpleName();
        };
    }

    static int leadTimeDays(Category c) {
        return switch (c) {                 // exhaustive over the enum: no default needed
            case FASTENER   -> 1;
            case STRUCTURAL -> 14;
            case TOOLING    -> {            // a block body must yield its value
                int base = 3;
                yield base * 2;
            }
        };
    }

    static String shippingBand(String sku) {
        switch (sku) {                      // the statement form: no value, no exhaustiveness check
            case "BOLT-7", "NUT-3" -> { return "small"; }
            case "GIRD-1"          -> { return "freight"; }
            default                -> { return "standard"; }
        }
    }

    static String label(Object o) {
        if (!(o instanceof String s)) return "not a string";
        return "string " + s.toUpperCase();   // s is in scope: the compiler saw the early return
    }

    public static void main(String[] args) {
        System.out.println(classify(null));
        System.out.println(classify(-4));
        System.out.println(classify(42));
        System.out.println(classify("BOLT-7"));
        System.out.println(classify(new int[3]));
        System.out.println(classify(3.5));
        for (Category c : Category.values()) System.out.println(c + " -> " + leadTimeDays(c) + " days");
        System.out.println(shippingBand("NUT-3") + ", " + shippingBand("GIRD-1") + ", " + shippingBand("CAM-9"));
        System.out.println(label("rod-4") + " / " + label(7));
    }
}

The order of the two Integer cases is not a style choice. A case that would match everything a later case matches dominates it, and the compiler rejects the program: swap them and you get error: this case label is dominated by a preceding case label, because the guarded case could never be reached. The same rule puts case CharSequence cs after case String s, never before. default is exempt and may appear anywhere, though convention keeps it last.

In label, the pattern variable s is usable on the line after the if. The compiler reasons about flow: the only way past that statement is for the instanceof to have succeeded, so the binding is in scope. The same reasoning allows o instanceof String s && s.length() > 3, because && evaluates its right side only when the left was true, and forbids o instanceof String s || s.isEmpty(), where the right side runs exactly when s does not exist.

Five ways this goes wrong
  • A pattern switch throws on null unless you say otherwise. The legacy forms did too, but a case Object o looks like it would catch anything and does not. Write case null explicitly, or case null, default to merge the two.
  • A guard is not a case. case FixedOff(int c) when c >= gross covers some FixedOff values. You still need an unguarded FixedOff case, or the switch is not exhaustive and the error message names the type you thought you had handled.
  • Exhaustiveness is checked at compile time against the classes the compiler saw. If a sealed interface is recompiled with a new subtype but a dependent jar is not, the old switch is still exhaustive as far as its bytecode knows. At runtime the JVM throws MatchException from the switch, which is the correct, loud failure; just do not mistake "it compiled last year" for proof.
  • Record patterns match on type, not on accessor calls. case Product(String sku, int price) invokes the accessors to bind, so an accessor you overrode to compute something runs during matching. Keep accessors cheap and side-effect free.
  • yield inside a lambda inside a switch block does not yield from the switch. It is a statement with its own scope rules; the compiler will tell you, but the error is confusing until you know why.

Sealed switch or polymorphic method?

When to prefer a sealed switch over a polymorphic method
The situationReach forBecause
Types keep being added; the operations are few and stable (shapes in a drawing app)Polymorphism: an abstract method on the supertypeA new type is one new class, and nothing else changes
Types are fixed and known; operations keep being added (discount kinds; AST nodes; messages)A sealed type and pattern switchesA new operation is one new method, and the compiler lists every switch when a type is eventually added
The operation needs data from several types at once (do these two offers stack?)A switch over a record of both, or nested patternsDispatch on one receiver cannot see the other's concrete type
The behaviour belongs to the type's own invariants (validation, formatting of itself)A method on the recordIt changes when the record changes, and nowhere else

Both tools solve one axis of the expression problem, which is the observation that no single design makes both adding types and adding operations cheap. The practical rule: ask which one will change more often in this hierarchy, and put the compiler's checking on that axis.

Check yourself

1.A switch expression over sealed interface Discount permits PercentOff, FixedOff, BuyNGetOne has cases for all three and no default. A colleague adds record Clearance() implements Discount and Clearance to the permits list. What happens to the switch?

B. That compile error is the feature. The sealed type tells the compiler the complete set of subtypes; the switch expression must cover it; the new subtype is uncovered; the build fails at every switch that needs a Clearance rule, with file and line.

A is what happens only in the separate-compilation case, when the switch's class file predates the new subtype and is not rebuilt; a normal build recompiles it. C invents a warning; exhaustiveness is an error, never a warning. D confuses the interface, which has no behaviour, with a case label.

2.Which of these fails to compile?

C. Every String is a CharSequence, so the first case matches everything the second could, and the second is unreachable. The compiler reports that the label is dominated by a preceding one.

A is the correct order for a guard: the narrower, guarded case first, the unguarded one as the catch-all for that type. B is the same pair as C in the legal order, specific before general. D is legal and is the idiom for "handle null together with anything I did not list".

3.For which of these can the compiler verify that a switch expression is exhaustive without a default? Select all that apply.

A and D. Exhaustiveness needs a closed set that the compiler can enumerate: an enum's constants, or a sealed type's permitted subtypes (recursively, if those are sealed too). Record patterns count as covering their record type when every component pattern is total, as int cents is.

B: the set of strings is infinite and the compiler has no idea which ones are "current SKUs"; a default is mandatory. C: an open interface may gain an implementation in any jar at any time, so three cases today prove nothing; the compiler will demand a default, which is also the hint that you may want to seal the interface.
