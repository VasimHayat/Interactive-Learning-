Section 11

Testing the data layer

Repository code fails in ways unit tests with mocks cannot see: a derived query whose name parses differently from what you meant, a mapping that produces the wrong SQL, an N+1 that only appears with real associations, a constraint the database enforces and your Java does not. So data-layer tests run against a real database, inside a real persistence context, through real repository proxies. Spring Boot's answer is the test slice @DataJpaTest: a cut-down application context with only the JPA machinery, an embedded database, and — the part that surprises people — every test method wrapped in a transaction that is rolled back at the end.

Rollback is what makes these tests fast and independent: no cleanup scripts, no ordering between tests, no leftover rows. It is also the source of the classic data-layer test bug, because a transaction that never commits may never flush, and a statement that is never sent cannot fail. JUnit cannot run inside this page's build, so the worked example reproduces what the test framework does, step by step, with a TransactionTemplate in a plain Spring Boot application. The real test classes follow it, unverified, as reference.

Worked example: what a test transaction actually does

Five experiments. Each is a "test body" run inside a transaction that ends in a rollback, exactly as @DataJpaTest would end it — except experiment 2, which commits for contrast.

package lm.testing;

import jakarta.persistence.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.core.io.ByteArrayResource;
import org.springframework.dao.DataAccessException;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.init.ResourceDatabasePopulator;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;

import javax.sql.DataSource;
import java.nio.charset.StandardCharsets;
import java.util.Map;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class RollbackHarness {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        int priceInCents;
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        @Override public String toString() { return sku + "=" + priceInCents + "c"; }
    }

    public interface ProductRepository extends JpaRepository<Product, Long> {}

    @PersistenceContext EntityManager em;

    @Bean CommandLineRunner demo(ProductRepository repo, PlatformTransactionManager txm, DataSource ds) {
        JdbcTemplate jdbc = new JdbcTemplate(ds);
        TransactionTemplate tx = new TransactionTemplate(txm);
        return args -> {
            System.out.println("-- 1. what a test transaction does: run, assert, roll back --");
            tx.executeWithoutResult(status -> {
                repo.save(new Product("BOLT-7", 80));
                repo.save(new Product("NUT-3", 25));
                em.flush();
                System.out.println("inside the transaction, count = " + repo.count());
                status.setRollbackOnly();                       // what @DataJpaTest does for you at the end
            });
            System.out.println("after rollback, rows = " + jdbc.queryForObject("select count(*) from product", Long.class));

            System.out.println("-- 2. the same body, committed --");
            tx.executeWithoutResult(status -> {
                repo.save(new Product("BOLT-7", 80));
                repo.save(new Product("NUT-3", 25));
            });
            System.out.println("after commit, rows = " + jdbc.queryForObject("select count(*) from product", Long.class));

            System.out.println("-- 3. the flush trap: an assertion that cannot fail --");
            boolean detected = false;
            try {
                tx.executeWithoutResult(status -> {
                    repo.save(new Product("BOLT-7", 1));          // duplicate sku — but nothing is flushed
                    status.setRollbackOnly();                     // ...and the rollback discards it unflushed
                });
            } catch (DataAccessException e) { detected = true; }
            System.out.println("duplicate detected without flush: " + detected);
            String caught = "nothing";
            try {
                tx.executeWithoutResult(status -> {
                    repo.saveAndFlush(new Product("BOLT-7", 1)); // flush through the repository proxy
                    status.setRollbackOnly();
                });
            } catch (DataAccessException e) { detected = true; caught = e.getClass().getSimpleName(); }
            System.out.println("duplicate detected with flush: " + detected + " (" + caught + ")");

            System.out.println("-- 4. the first-level cache hides the database --");
            tx.executeWithoutResult(status -> {
                Product p = repo.save(new Product("CAM-9", 2300));
                em.flush();
                Product again = repo.findById(p.id).orElseThrow();
                System.out.println("same instance without clear(): " + (p == again));
                em.clear();                                       // TestEntityManager.clear()
                Product fresh = repo.findById(p.id).orElseThrow();
                System.out.println("same instance after clear(): " + (p == fresh));
                status.setRollbackOnly();
            });

            System.out.println("-- 5. what @Sql does: a script before the body --");
            String script = """
                insert into product (id, sku, price_in_cents) values (1001, 'SEED-1', 10);
                insert into product (id, sku, price_in_cents) values (1002, 'SEED-2', 20);
                """;
            new ResourceDatabasePopulator(new ByteArrayResource(script.getBytes(StandardCharsets.UTF_8))).execute(ds);
            System.out.println("rows after script = " + repo.count());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(RollbackHarness.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:testing;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false",
            "logging.level.org.hibernate.orm.jdbc.error", "OFF"));   // H2 names its constraints; keep them out of stdout
        app.run(args).close();
    }
}

  1. Run, assert, roll back. Inside the transaction two inserts were flushed and count() saw them. After setRollbackOnly() the template rolled back instead of committing, and a JDBC count — outside any transaction — found zero rows. That is the whole contract of a test transaction: the database ends every test exactly as it started.
  2. Committed, the rows stay. The same body without the rollback flag leaves two rows. A test annotated @Commit behaves like this, and every test after it then runs against those rows.
  3. The flush trap. The SKU BOLT-7 now exists, so saving another must fail — yet the first attempt printed detected without flush: false and no insert appeared in the SQL. The insert was queued, the transaction rolled back, and the queue was discarded unsent. A test asserting "saving a duplicate throws" would pass for the wrong reason, or a test asserting "this save works" would pass when production fails. With saveAndFlush the insert is sent inside the test, H2 rejects it, and the failure arrives — translated, because it came through the repository proxy — as DataIntegrityViolationException.
  4. The first-level cache. Within one persistence context, findById returned the very instance just saved, without touching the database (there is no select before the first fact). A test that saves, then loads, then asserts is checking the Java object it already had, not what the mapping wrote and reads back. After clear() the load is a real select and a new instance. This is what TestEntityManager.flush() plus clear() is for.
  5. Seeding with a script. ResourceDatabasePopulator ran two plain SQL inserts — the mechanism behind @Sql — and the count went from 2 to 4. Note the script wrote columns by their database names, price_in_cents: scripts see the schema, not the entity.

The real test classes

These are JUnit 5 test sources. They are not compiled or run by this page's build; run them with spring-boot-starter-test (and spring-boot-testcontainers plus a Docker daemon for the last one) on the test class path.

Test source — run with JUnit, not verified by this build.

@DataJpaTest
class ProductRepositoryTest {

    @Autowired TestEntityManager tem;
    @Autowired ProductRepository repo;

    @Test
    void rejectsDuplicateSku() {
        tem.persistAndFlush(new Product("BOLT-7", 80));

        assertThatThrownBy(() -> repo.saveAndFlush(new Product("BOLT-7", 90)))
            .isInstanceOf(DataIntegrityViolationException.class);   // flushed, so it really ran
    }

    @Test
    void roundTripsThroughTheMapping() {
        Long id = tem.persistAndGetId(new Product("CAM-9", 2300), Long.class);
        tem.clear();                                               // defeat the first-level cache

        assertThat(repo.findById(id)).get()
            .extracting(Product::priceInCents).isEqualTo(2300);
    }
}

Test source — run with JUnit, not verified by this build.

@DataJpaTest(properties = "spring.jpa.properties.hibernate.generate_statistics=true")
@Sql("/orders-with-lines.sql")                       // runs before each test, inside its transaction
class OrderQueriesTest {

    @Autowired OrderRepository orders;
    @Autowired EntityManagerFactory emf;
    @Autowired TestEntityManager tem;

    @Test
    void listingIsOneStatementNotNPlusOne() {
        Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
        tem.clear();
        stats.clear();

        orders.findAllWithLines().forEach(o -> o.getLines().size());

        assertThat(stats.getPrepareStatementCount()).isEqualTo(1);   // a regression guard for §6
    }
}

A statement-count assertion is the cheapest N+1 regression test there is: someone removing the @EntityGraph turns it red immediately, long before a slow page is noticed in production.

@ServiceConnection replaces the older @DynamicPropertySource boilerplate. A static container is started once per test class; with Boot's context caching and a shared base class, it is started once per test run.

Mock collaborators of a service with @MockitoBean; do not mock repositories in a data-layer test, because the repository is the thing under test. A test that mocks the repository is a test of Mockito.

Testing gotchas
  • No flush, no failure. A test that saves and never flushes never sends SQL, so constraint, length and mapping errors cannot happen. Use saveAndFlush or tem.flush() before asserting on anything the database decides.
  • No clear, no round trip. Loading what you just saved returns the same Java object. Clear the persistence context so the test exercises the mapping.
  • H2 is not your production database. It accepts syntax PostgreSQL rejects, locks differently, and has its own sequence and identity behaviour. Keep a Testcontainers suite against the real engine for queries, locking and migrations.
  • Rollback hides commit-time behaviour. @TransactionalEventListener(AFTER_COMMIT) listeners (§8), deferred constraints and commit-time validation never run in a rolled-back test. Test those with @Commit or TestTransaction.end(), and clean up after.
  • Each distinct test configuration is a new context. Spring caches contexts between test classes with identical configuration; every different properties, @MockitoBean or profile builds another, and a suite of fast tests becomes a slow one.

Check yourself

1.In a @DataJpaTest, a test does repo.save(new Product("BOLT-7", 1)) when BOLT-7 already exists, then assertThat(repo.count()).isEqualTo(1). The SKU column is unique. What happens?

B. count() is a JPQL query on Product, and with flush mode AUTO Hibernate flushes pending changes to that entity first so the query sees them (JPA §7). The insert is sent then, the database rejects it, and the exception appears on a line that looks innocent. Had the test asserted nothing that queried Product, it would have passed — the worked example's step 3.

A: with SEQUENCE ids, save only queues the insert. C is what happens with no query before the rollback. D would require the database to accept a duplicate under a unique index.

2.A test saves a Product with a 20-character SKU into a length = 16 column, then loads it with findById and asserts the SKU matches. It passes on H2. Why is it worthless?

C. findById by primary key checks the persistence context first and returned the object the test had just saved (step 4 of the worked example). The too-long value never met the column. saveAndFlush plus clear() would have produced a DataIntegrityViolationException.

A: H2 rejects values too long for a varchar(16); it was simply never asked. B: it runs in the test's transaction, which is precisely why it shares the cache. D invents a mode that does not exist.

3.Which of these will a default, rolled-back @DataJpaTest fail to exercise? Select all that apply.

A and D. An after-commit listener needs a commit, which a rolled-back test never performs. And the slice does not load @Service beans at all, so the service and its transactional proxy are absent — use @SpringBootTest for that.

B is exactly what the slice is good at: the query runs for real. C: with a flush, the statement reaches the database inside the test, so the constraint fires.
