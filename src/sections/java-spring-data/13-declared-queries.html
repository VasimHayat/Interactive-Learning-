Section 4

@Query, modifying queries and projections

A derived name is a specification written in a tiny language. When the language runs out — an aggregate, parentheses around an or, a fetch join, a constructor expression, a vendor function — you write the query yourself and put it on the method with @Query. Spring Data still does the plumbing: it binds the parameters, appends a Sort, derives or uses a count query for a Page, and maps the result to whatever return type you declared. The query string is still parsed at startup, so a misspelt attribute in JPQL fails the boot exactly as a misspelt derived name does.

This section also covers the other half of "I do not want the whole entity": projections. A read screen that shows a SKU and a price does not need a managed Product with its snapshot, its dirty check and its lazy associations; it needs two columns. Spring Data offers three ways to ask for them, and they do not all do what they look like they do.

Worked example

Seven declared queries, five projections and the two forms of @Modifying, over six products. The SQL line above each result is the evidence for every claim in the rest of the section.

package lm.declared;

import jakarta.persistence.*;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.data.repository.query.Param;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionTemplate;
import java.util.List;
import java.util.Map;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class DeclaredQueries {

    public enum Category { FASTENER, STRUCTURAL, MOTION }

    @Entity(name = "Product")
    @Table(name = "product")
    @NamedQuery(name = "Product.cheaperThan",
                query = "select p from Product p where p.priceInCents < :max order by p.sku")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        @Column(nullable = false) String name;
        @Enumerated(EnumType.STRING) @Column(nullable = false, length = 16) Category category;
        int priceInCents;
        boolean active;
        protected Product() {}
        Product(String sku, String name, Category category, int priceInCents, boolean active) {
            this.sku = sku; this.name = name; this.category = category; this.priceInCents = priceInCents; this.active = active;
        }
        public String getSku() { return sku; }
        public int getPriceInCents() { return priceInCents; }
        @Override public String toString() { return sku + "@" + priceInCents; }
    }

    /* Projections: three ways to say "I do not want the whole entity". */
    public interface SkuAndPrice { String getSku(); int getPriceInCents(); }              // closed: only these columns
    public interface SkuLabel { @Value("#{target.sku + ' @ ' + target.priceInCents + 'c'}") String getLabel(); }  // open: all columns
    public record SkuPrice(String sku, int priceInCents) {}                                // DTO: only these columns
    public interface SkuCents { String getSku(); int getCents(); }                         // for the native query's aliases

    public interface ProductRepository extends JpaRepository {

        @Query("select p from Product p where p.category = :category and p.priceInCents <= :max order by p.sku")
        List affordable(@Param("category") Category category, @Param("max") int max);

        @Query("select p from Product p where p.sku like ?1 order by p.sku")
        List skuLike(String pattern);

        @Query("select p from Product p where p.category = :category")
        List byCategory(@Param("category") Category category, Sort sort);

        @Query(value = "select p from Product p where p.active = true",
               countQuery = "select count(p) from Product p where p.active = true")
        Page activePage(Pageable pageable);

        @Query(value = "select sku, price_in_cents as cents from product where price_in_cents > :min order by sku",
               nativeQuery = true)
        List nativeAbove(@Param("min") int min);

        List cheaperThan(@Param("max") int max);          // resolved to the @NamedQuery "Product.cheaperThan"

        @Query("select count(p) from #{#entityName} p")
        long total();

        @Modifying @Transactional
        @Query("update Product p set p.priceInCents = p.priceInCents + :delta where p.category = :category")
        int repriceStale(@Param("category") Category category, @Param("delta") int delta);

        @Modifying(clearAutomatically = true) @Transactional
        @Query("update Product p set p.priceInCents = p.priceInCents + :delta where p.category = :category")
        int repriceClearing(@Param("category") Category category, @Param("delta") int delta);

        @Modifying @Transactional
        @Query("delete from Product p where p.active = false")
        int purgeInactive();

        List findByCategoryOrderBySku(Category category);                       // closed projection
        List findByPriceInCentsGreaterThanOrderBySku(int min);                      // open projection
        List findByCategoryAndActiveTrueOrderBySku(Category category);              // DTO, derived
        @Query("select new lm.declared.DeclaredQueries$SkuPrice(p.sku, p.priceInCents) from Product p where p.category = :category order by p.sku")
        List prices(@Param("category") Category category);                          // DTO, declared
         List findByCategoryOrderBySkuDesc(Category category, Class type);           // dynamic projection
    }

    @Bean TransactionTemplate tx(PlatformTransactionManager manager) { return new TransactionTemplate(manager); }

    @Bean CommandLineRunner demo(ProductRepository repo, TransactionTemplate tx) {
        return args -> {
            repo.saveAll(List.of(
                new Product("BOLT-7", "Hex bolt M8", Category.FASTENER, 80, true),
                new Product("NUT-3", "Hex nut M8", Category.FASTENER, 25, true),
                new Product("PIN-2", "Split pin", Category.FASTENER, 15, false),
                new Product("GIRD-1", "Steel girder 6m", Category.STRUCTURAL, 120_000, true),
                new Product("ROD-4", "Threaded rod 1m", Category.STRUCTURAL, 4_500, true),
                new Product("CAM-9", "Cam follower", Category.MOTION, 2_300, true)));

            System.out.println("-- declared JPQL --");
            System.out.println("affordable        = " + repo.affordable(Category.FASTENER, 50));
            System.out.println("positional like   = " + repo.skuLike("%-%"));
            System.out.println("sort appended     = " + repo.byCategory(Category.STRUCTURAL, Sort.by("priceInCents").descending()));
            Page page = repo.activePage(PageRequest.of(1, 2, Sort.by("sku")));
            System.out.println("page 2 of active  = " + page.getContent() + " of " + page.getTotalElements() + " in " + page.getTotalPages() + " pages");
            System.out.println("native            = " + repo.nativeAbove(1_000).stream().map(r -> r.getSku() + "=" + r.getCents()).toList());
            System.out.println("named query       = " + repo.cheaperThan(100));
            System.out.println("#{#entityName}    = " + repo.total());

            System.out.println("-- projections --");
            System.out.println("closed interface  = " + repo.findByCategoryOrderBySku(Category.FASTENER).stream().map(p -> p.getSku() + "/" + p.getPriceInCents()).toList());
            System.out.println("open interface    = " + repo.findByPriceInCentsGreaterThanOrderBySku(2_000).stream().map(SkuLabel::getLabel).toList());
            System.out.println("record, derived   = " + repo.findByCategoryAndActiveTrueOrderBySku(Category.FASTENER));
            System.out.println("record, declared  = " + repo.prices(Category.STRUCTURAL));
            System.out.println("dynamic -> record = " + repo.findByCategoryOrderBySkuDesc(Category.FASTENER, SkuPrice.class));
            System.out.println("dynamic -> entity = " + repo.findByCategoryOrderBySkuDesc(Category.FASTENER, Product.class));

            System.out.println("-- @Modifying without clearAutomatically: the managed copy goes stale --");
            tx.executeWithoutResult(status -> {
                Product bolt = repo.findById(1L).orElseThrow();
                int changed = repo.repriceStale(Category.FASTENER, 10);
                Product again = repo.findById(1L).orElseThrow();
                System.out.println("rows updated      = " + changed);
                System.out.println("managed copy says = " + bolt.priceInCents + " (same instance: " + (bolt == again) + ")");
            });
            System.out.println("database says     = " + repo.findById(1L).orElseThrow().priceInCents);

            System.out.println("-- @Modifying(clearAutomatically = true): the context is emptied, so the next read hits the database --");
            tx.executeWithoutResult(status -> {
                Product bolt = repo.findById(1L).orElseThrow();
                int changed = repo.repriceClearing(Category.FASTENER, 10);
                Product again = repo.findById(1L).orElseThrow();
                System.out.println("rows updated      = " + changed);
                System.out.println("stale copy says   = " + bolt.priceInCents + ", fresh copy says " + again.priceInCents + " (same instance: " + (bolt == again) + ")");
            });

            System.out.println("-- @Modifying delete --");
            System.out.println("purged            = " + repo.purgeInactive());
            System.out.println("remaining         = " + repo.total());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(DeclaredQueries.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:declared;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

Reading the output

  • Named and positional parameters. affordable binds :category and :max through @Param; skuLike binds ?1 by position. Both become plain ? placeholders in the SQL, so neither can be injected into. Never build JPQL by string concatenation to "add a parameter".
  • escape '' on the declared like. Compare it with §3's escape '\'. In a declared query you supply the pattern ("%-%") and nothing is escaped for you: a user-supplied % is a wildcard here. If the value comes from a user, either escape it yourself or use a derived Containing.
  • A Sort parameter is appended. byCategory's JPQL has no order by; the SQL has order by p1_0.price_in_cents desc. Spring Data rewrote the query string before handing it to Hibernate. It validates the sort property against the entity, which is why an unknown property in a client-supplied sort fails instead of injecting SQL.
  • A Page costs two statements. activePage ran the offset … fetch first select and then the countQuery. Give a declared paged query its own countQuery whenever the select has joins or fetches; the count Spring Data would otherwise derive by rewriting your select can be wrong or slow (§7 goes deeper).
  • Native SQL goes through untouched. nativeAbove's SQL is exactly the string in the annotation, aliases and all, and its result maps to the SkuCents interface by alias name. You give up portability, entity graphs and automatic count derivation; you gain every feature of your database.
  • A named query is found by convention. cheaperThan has no annotation; Spring Data looked up Product.cheaperThan among the entity's @NamedQuerys before trying to derive the name. #{#entityName} in total() is SpEL substituted with the entity name, so a query in a generic base repository works for every entity.

Projections: what the SQL actually selects

The five projection lines are the most instructive part of the output, because the method signatures look alike and the SQL does not.

Two details from the output: the open projection's SQL selects id, active, category, name, price_in_cents, sku even though the label uses two of them, so it saves nothing over loading the entity. And the declared constructor expression names the record by its binary name, DeclaredQueries$SkuPrice, because it is nested; a top-level record would be lm.declared.SkuPrice. Spring Data's derived DTO projection needed no such string — it inspected the record's constructor itself.

Drag a projection onto what its SQL selects, or click one then click the other

All four correct. The practical rule: for a read model, use a closed interface or a record; reach for an open projection only when the computed value needs data you would have loaded anyway; load the entity only when you intend to change it.

@Modifying: one statement, and a stale persistence context

An update or delete in JPQL is a bulk operation: Hibernate turns it into one SQL statement (update product p1_0 set price_in_cents=(p1_0.price_in_cents+cast(? as integer)) where p1_0.category=?) and the database changes every matching row. The persistence context is not consulted and not updated (JPA §6). The output shows the consequence exactly:

  • Without clearAutomatically, BOLT-7 was loaded at 80, the update raised it to 90 in the database, and the second findById returned the same instance from the first-level cache — no select was emitted for it — still saying 80. Only after the transaction ended did a fresh read say 90. Any business logic after the update in that transaction worked on wrong numbers, and had the code then modified that entity, the flush would have written the stale price back over the update.
  • With clearAutomatically = true, Spring Data calls EntityManager.clear() after the update. The next findById emitted a select and got a new instance at 100, while the old reference still said 90. Clearing detaches everything, so unflushed changes to other entities would be lost — pair it with flushAutomatically = true when the transaction has pending writes.
  • The delete is one delete from product p1_0 where p1_0.active=false: no select, no cascades, no @PreRemove. That is the point of it, and also the risk.

A @Modifying method must run inside a writable transaction. A declared query method gets none of its own, so it needs @Transactional on the method (as here) or a caller's transaction (§5). Without one you get TransactionRequiredException: Executing an update/delete query.

Choosing the form

  • Derive when the name reads as a sentence: one or two conditions, a sort, maybe a limit.
  • Declare when you need parentheses, aggregates, group by, case, a fetch join, a subquery, or a constructor expression — or when the derived name would pass forty characters.
  • Name the method for its purpose once you declare: affordable(category, max) says why the query exists; findByCategoryAndPriceInCentsLessThanEqualOrderBySku only says how.
  • A Specification (§9) is the answer when the conditions are chosen at run time from a filter form.

A Stream<T> return holds a JDBC cursor open. It needs a surrounding transaction and must be closed, or the connection leaks back to the pool late or never:

@Transactional(readOnly = true)
public long exportActive(Writer out) {
    try (Stream<SkuAndPrice> rows = repo.streamAllActive()) {     // @QueryHints fetch size below
        return rows.peek(r -> write(out, r)).count();
    }
}

@QueryHints(@QueryHint(name = org.hibernate.jpa.HibernateHints.HINT_FETCH_SIZE, value = "500"))
@Query("select p.sku as sku, p.priceInCents as priceInCents from Product p where p.active = true")
Stream<SkuAndPrice> streamAllActive();

@QueryHints passes JPA or Hibernate hints straight through: HINT_FETCH_SIZE for streaming, HINT_READ_ONLY to skip snapshots for entities you will not change, jakarta.persistence.query.timeout for a statement deadline.

Declared-query gotchas
  • A bulk update leaves managed entities stale in the same transaction, as the output shows. Use clearAutomatically (with flushAutomatically if there are pending changes), or run the update in its own transaction.
  • Bulk operations skip @Version, callbacks, cascades and the second-level cache. An optimistic lock is not checked; increment the version column in the JPQL yourself (set p.version = p.version + 1) if other writers rely on it.
  • A declared like does not escape. escape '' in the output: user input containing % or _ becomes a wildcard.
  • An open projection is not a projection. It loads the entity. Use it for convenience, never for performance.
  • select new needs the fully qualified (binary) class name. A nested record is Outer$Record; a typo fails at startup with a class-resolution error.
  • A native Page without countQuery makes Spring Data guess a count by rewriting your SQL, which fails or lies on anything non-trivial.

A is wrong: findById checks the persistence context first. C describes behaviour Hibernate does not have — bulk operations bypass the context entirely, which is why clearAutomatically exists. D: nothing detects the divergence; the stale value is silently used.

2.A report needs only sku and price from a wide table. Which return type keeps the selected columns to those two?

C. The closed interface and the record both produced select p1_0.sku,p1_0.price_in_cents in the output.

A is an open projection: its SQL selected every column, because SpEL may touch any property of target. B skips the dirty-check snapshot but still selects and hydrates whole entities. D is false; nothing analyses which getters you call.

3.Which are true of @Modifying @Query("delete from Product p where p.active = false")? Select all that apply.

A and D. The output's single delete from product p1_0 where p1_0.active=false is the bulk statement; JPA requires a transaction for any bulk update or delete.

B and C describe entity-level removal — what §3's derived deleteBySku did by loading first. A bulk JPQL delete never loads the entities, so there is nothing to call back on and nothing to cascade from; child rows with a foreign key make it fail instead.
