Section 6

Fetching and N+1 in a Spring application

JPA §5 showed the N+1 problem with a bare EntityManager: one query for the parents, one more per parent the moment a lazy collection is touched. Spring changes nothing about the mechanism and everything about where it bites, because Spring decides where the persistence context begins and ends. In a plain JPA program you open and close the EntityManager yourself. In a Spring application the context is opened by the @Transactional proxy when a service method starts and closed when it returns — unless spring.jpa.open-in-view is on, in which case it stays open for the whole web request, including view rendering, which is where the lazy loads then quietly run.

So the question "will this lazy collection load?" has a Spring-specific answer: only inside the transaction that loaded its owner. Touch it in the service and you get an N+1; touch it after the service returned and you get a LazyInitializationException; touch it in a template with open-in-view on and you get an N+1 you cannot see in any Java file. This section measures all of those with Hibernate's statistics, then shows the two tools Spring Data adds for fixing them at the repository: @EntityGraph and fetch queries in @Query.

Worked example: six ways to read the same report

Five orders, two lines each, totalling 65 units. The ReportService is @Transactional(readOnly = true), so every method runs inside one transaction and one persistence context. The runner clears the statistics before each phase and prints the prepared-statement count after it.

package lm.fetching;

import jakarta.persistence.*;
import org.hibernate.Hibernate;
import org.hibernate.LazyInitializationException;
import org.hibernate.Session;
import org.hibernate.SessionFactory;
import org.hibernate.stat.Statistics;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class SpringFetching {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        protected Product() {}
        Product(String sku) { this.sku = sku; }
        String getSku() { return sku; }
    }

    @Entity(name = "Order")
    @Table(name = "orders")
    public static class Order {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true) String reference;
        @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)        // LAZY by default
        List lines = new ArrayList<>();
        protected Order() {}
        Order(String reference) { this.reference = reference; }
        String getReference() { return reference; }
        List getLines() { return lines; }
        void addLine(Product p, int qty) { OrderLine l = new OrderLine(p, qty); l.order = this; lines.add(l); }
    }

    @Entity(name = "OrderLine")
    @Table(name = "order_line")
    public static class OrderLine {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @ManyToOne(fetch = FetchType.LAZY, optional = false) Order order;
        @ManyToOne(fetch = FetchType.LAZY, optional = false) Product product;
        int qty;
        protected OrderLine() {}
        OrderLine(Product product, int qty) { this.product = product; this.qty = qty; }
        int getQty() { return qty; }
        Product getProduct() { return product; }
    }

    public interface ProductRepository extends JpaRepository {}

    public interface OrderRepository extends JpaRepository {
        List findAllByOrderByReference();                                  // lazy: the N+1 shape

        @EntityGraph(attributePaths = {"lines", "lines.product"})
        List findWithGraphByOrderByReference();                            // one statement

        @Query("select distinct o from Order o join fetch o.lines l join fetch l.product order by o.reference")
        List findAllFetched();                                             // one statement, explicit
    }

    public record OrderSummary(String reference, int lineCount, int totalQty) {}

    @Service
    @Transactional(readOnly = true)
    public static class ReportService {
        private final OrderRepository orders;
        @PersistenceContext private EntityManager em;
        ReportService(OrderRepository orders) { this.orders = orders; }

        public int totalQtyLazy() { return sum(orders.findAllByOrderByReference()); }
        public int totalQtyGraph() { return sum(orders.findWithGraphByOrderByReference()); }
        public int totalQtyFetchQuery() { return sum(orders.findAllFetched()); }
        public int totalQtyBatched() {
            em.unwrap(Session.class).setFetchBatchSize(8);                        // what default_batch_fetch_size does globally
            return sum(orders.findAllByOrderByReference());
        }
        public Order firstOrder() { return orders.findAllByOrderByReference().get(0); }           // entity escapes the transaction
        public OrderSummary firstOrderSummary() {                                                // DTO: nothing lazy escapes
            Order o = orders.findWithGraphByOrderByReference().get(0);
            return new OrderSummary(o.getReference(), o.getLines().size(), sum(List.of(o)));
        }
        private static int sum(List os) {
            int t = 0;
            for (Order o : os) for (OrderLine l : o.getLines()) t += l.getQty();
            return t;
        }
    }

    @Bean CommandLineRunner demo(ProductRepository products, OrderRepository orders, ReportService report, EntityManagerFactory emf) {
        return args -> {
            Product bolt = products.save(new Product("BOLT-7"));
            Product nut = products.save(new Product("NUT-3"));
            for (int i = 1; i <= 5; i++) {
                Order o = new Order("ORD-" + i);
                o.addLine(bolt, i);
                o.addLine(nut, 10);
                orders.save(o);
            }
            Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();

            System.out.println("-- A: lazy collection in a loop --");
            stats.clear();
            System.out.println("total = " + report.totalQtyLazy() + ", statements = " + stats.getPrepareStatementCount());

            System.out.println("-- B: @EntityGraph --");
            stats.clear();
            System.out.println("total = " + report.totalQtyGraph() + ", statements = " + stats.getPrepareStatementCount());

            System.out.println("-- C: join fetch in @Query --");
            stats.clear();
            System.out.println("total = " + report.totalQtyFetchQuery() + ", statements = " + stats.getPrepareStatementCount());

            System.out.println("-- D: batch fetching, size 8 --");
            stats.clear();
            System.out.println("total = " + report.totalQtyBatched() + ", statements = " + stats.getPrepareStatementCount());

            System.out.println("-- E: an entity leaves the transaction (open-in-view=false) --");
            Order escaped = report.firstOrder();
            System.out.println("lines initialised = " + Hibernate.isInitialized(escaped.getLines()));
            try {
                System.out.println("line count = " + escaped.getLines().size());
            } catch (LazyInitializationException e) {
                System.out.println("caught " + e.getClass().getSimpleName());
            }

            System.out.println("-- F: a DTO leaves instead --");
            System.out.println(report.firstOrderSummary());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(SpringFetching.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:fetching;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.properties.hibernate.generate_statistics", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

Read the phases against the statement counts; the SQL between them is the evidence.

  • A, six statements. One for the orders, then where l1_0.order_id=? five times as getLines() initialises each proxy collection. This is N+1 at N = 5, inside a transaction that was opened for exactly this method. At N = 500 it is 501 round trips, and nothing in totalQtyLazy() looks wrong.
  • B, one statement. @EntityGraph(attributePaths = {"lines", "lines.product"}) on the repository method turns the derived query into a left join over lines and products. The method name still drives the where and order by; the graph only says what to fetch. Note the left join: a graph keeps orders that have no lines.
  • C, one statement, by hand. The @Query with join fetch produces the same shape with an inner join and a distinct (Hibernate 6+ deduplicates the parent entities without passing distinct to SQL, so it is harmless to write). Prefer B when the fetch plan is the only thing you need to say; prefer C when the query itself is custom.
  • D, two statements. With a fetch batch size of 8 the first touched collection loads the lines for up to eight orders in one in (?,?,?,?,?,?,?,?). Set globally as spring.jpa.properties.hibernate.default_batch_fetch_size it is the safety net that turns every forgotten N+1 into N/8+1; it does not replace B and C, it caps the damage when they are missing.
  • E, the exception. firstOrder() returns a managed entity; the transaction commits on return and the persistence context closes. Back in the runner, Hibernate.isInitialized(lines) is false and size() throws LazyInitializationException. With spring.jpa.open-in-view=true (the default in a web application) the context would still be open here and the call would silently run the collection query — which is the whole open-in-view argument in one line.
  • F, the right shape. firstOrderSummary() fetches what it needs inside the transaction and returns a record. Nothing lazy crosses the boundary, so nothing can throw later, and the caller cannot accidentally trigger a query from a template.

Where will the lazy load run?

What happens when the collection is touched

Open-in-view: why it is on, and why you turn it off

In a web application Spring Boot registers an OpenEntityManagerInViewInterceptor. It binds an EntityManager to the request thread before the controller runs and closes it after the view has rendered. Every @Transactional service call in between reuses that same persistence context, and after the last transaction commits the context stays open — detached entities are not detached, lazy collections still load, and a template can walk order.lines[i].product.name without anyone having planned a fetch.

That is why it is on by default: it makes naive code work. Spring Boot logs a warning at startup (spring.jpa.open-in-view is enabled by default) precisely because "works" and "scales" are different claims. Setting the property to false, as every program in this module does, makes E above throw instead of query — which is the behaviour you want to find in development, not in production under load.

  • A connection for the whole request. The first lazy load after the service returns needs a JDBC connection; Hibernate takes one from the pool and, with the context still open, keeps it until the view is rendered. Slow templates and slow clients now hold pool connections. Under load the pool empties and unrelated requests queue on HikariPool … connection is not available.
  • N+1 in places that are not Java. The loop in A at least sits in a method you can profile. The same loop in a template is invisible to statistics taken in the service, so the fix (B or C) is never applied where it is needed.
  • Reads after the transaction are not transactional. Lazy loads outside the @Transactional method run in auto-commit mode on whatever the database shows now, so a page can show an order from one moment and its lines from another.
  • The fix is a shape, not a flag. With open-in-view off, every read method must fetch what its caller needs (B, C) or return a DTO (F). That constraint is the design: it makes each query's cost visible at the method that runs it.
// attribute paths, nested with dots — the usual form
@EntityGraph(attributePaths = {"lines", "lines.product"})
List<Order> findWithGraphByOrderByReference();

// a named graph declared on the entity, reused by several methods
@NamedEntityGraph(name = "Order.full", attributeNodes = {
    @NamedAttributeNode(value = "lines", subgraph = "lines"),
    @NamedAttributeNode("customer") },
    subgraphs = @NamedSubgraph(name = "lines", attributeNodes = @NamedAttributeNode("product")))
@EntityGraph("Order.full")
Optional<Order> findByReference(String reference);

// FETCH (default): listed attributes eager, every other one LAZY regardless of mapping
// LOAD: listed attributes eager, the rest as mapped
@EntityGraph(attributePaths = "lines", type = EntityGraph.EntityGraphType.LOAD)
List<Order> findByReferenceStartingWith(String prefix);

A graph applies to derived queries, findById, findAll and @Query methods alike. Two List collections in one graph throw MultipleBagFetchException exactly as two join fetches would (JPA §5); use a Set for one of them or fetch in two queries. And a graph combined with a Pageable fetches the join in full and pages in memory with Hibernate's HHH90003004 warning — §7 shows the shape that avoids it.

Fetching gotchas specific to Spring
  • Returning entities from a service is the bug, not the symptom. E throws only because open-in-view is off; with it on, the same code runs an unplanned query from the caller. Return DTOs or fetch-complete entities; never let a lazy proxy cross the service boundary.
  • @Transactional(readOnly = true) is not optional on read services. It gives you one context per call (so B and C can dedupe and the identity map works), tells Hibernate to skip dirty-check snapshots, and lets a replica-aware data source route the read. Without it every repository call is its own transaction and its own context, and a loop over two repositories loads the same Product many times.
  • default_batch_fetch_size is a net, not a plan. Set it (8–32) in every application, then still fix the N+1s you find; a page that needs 500 collections still runs 500/16 + 1 statements.
  • Statistics are the test. hibernate.generate_statistics costs little; a @DataJpaTest that asserts getPrepareStatementCount() == 1 after calling the report method is how regressions are caught. §11 shows the harness.
  • Turning open-in-view off is a migration, not a toggle. Every template and serializer that walked a lazy association will start throwing. Do it early in a project, or do it with statistics and a log of LazyInitializationExceptions to drive the fixes.

Check yourself

1.In phase E the runner calls escaped.getLines().size() after firstOrder() returned and gets LazyInitializationException. Which single change makes that call succeed without changing the service?

C — and it is the wrong fix, which is the point. Open-in-view keeps the persistence context open past the service, so the lazy load runs in the caller with an extra query and a connection held for the rest of the request. It only applies to web requests (the interceptor is request-scoped), so in this command-line program even that would not help; in a controller it would.

A: a @Bean method's returned lambda is not a proxied bean, so @Transactional on it does nothing; and even a real transaction in the caller would be a new context that does not contain escaped. B is the wrong association: lines is the collection that is lazy, and making OrderLine.order eager changes how lines load their parent, not how orders load their lines. D: a detached collection can be reattached (merge) or initialised inside a new transaction with Hibernate.initialize after a reload — it is the context that is gone, not the data.

2.A service method is @Transactional(readOnly = true) and runs orders.findAllByOrderByReference() for 400 orders, then touches each getLines(). The application sets spring.jpa.properties.hibernate.default_batch_fetch_size=16. How many statements run?

B. Phase D at scale: each time an uninitialised collection is touched, Hibernate loads it together with up to 15 other uninitialised collections of the same role that are already in the persistence context, keyed by the owners' ids. 400 orders, 16 per batch, 25 batches, plus the order query.

A: default_batch_fetch_size is exactly the global form of @BatchSize; the annotation overrides it per collection. C describes @Fetch(FetchMode.SUBSELECT), which re-runs the original query as a subselect — a different, explicit annotation. D: a batch size never changes the shape of the original query; only a graph or a fetch join does that.

3.Which of the following are true of @EntityGraph(attributePaths = {"lines", "notes"}) on a repository method, where both lines and notes are Lists? Select all that apply.

A and D. A graph is translated into joins, so it inherits the join rules from JPA §5: two bags cannot be fetched in one result set, and one bag plus one set can but produces the cartesian product. The practical answers are two queries in one transaction, a batch size, or a DTO.

B is false — the generated SQL in phase B shows the joins. C: graphs apply to findById, findAll, derived and @Query methods alike.
