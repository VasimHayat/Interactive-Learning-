Section 5

@Transactional: boundaries, propagation and the proxy

In the JPA module you opened and committed transactions by hand. In a Spring application you almost never do: you put @Transactional on a service method and the transaction begins before the method runs and commits (or rolls back) after it returns. That convenience is implemented by a proxy — an object Spring puts in front of your bean that intercepts each call, consults the annotation, talks to the PlatformTransactionManager, and only then calls your code. Every surprising behaviour of @Transactional follows from that one fact: the annotation does nothing unless the call goes through the proxy.

The boundary matters because the persistence context lives exactly as long as the transaction (JPA §3). Inside it, entities are managed, lazy associations load, and dirty checking writes your changes at commit. Outside it, entities are detached. Where you draw the boundary decides what is consistent, what is atomic, and how long a database connection is held.

Worked example

Ten experiments in one application. show_sql is off here — the evidence is the transaction state itself, read through TransactionSynchronizationManager (the thread-bound registry Spring uses to track the current transaction), Hibernate's transaction counter, and which rows survive.

package lm.tx;

import jakarta.persistence.*;
import org.hibernate.SessionFactory;
import org.hibernate.stat.Statistics;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.transaction.autoconfigure.TransactionManagerCustomizer;
import org.springframework.orm.jpa.JpaTransactionManager;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.stereotype.Service;
import org.springframework.transaction.IllegalTransactionStateException;
import org.springframework.transaction.NestedTransactionNotSupportedException;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionSynchronizationManager;
import org.springframework.transaction.support.TransactionTemplate;
import java.util.Map;
import java.util.Optional;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class Transactions {

    @Entity(name = "StockLevel")
    @Table(name = "stock_level")
    public static class StockLevel {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        int onHand;
        protected StockLevel() {}
        StockLevel(String sku, int onHand) { this.sku = sku; this.onHand = onHand; }
    }

    public interface StockRepository extends JpaRepository {
        Optional findBySku(String sku);
    }

    static String txName() {
        return TransactionSynchronizationManager.isActualTransactionActive()
            ? TransactionSynchronizationManager.getCurrentTransactionName() : "(no transaction)";
    }

    /* A second bean: calling it goes through a proxy, so REQUIRES_NEW takes effect. */
    @Service
    public static class Auditor {
        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public String inner() { return txName(); }

        @Transactional(propagation = Propagation.NESTED)
        public void stockAndFail(StockRepository repo, String sku) {
            repo.saveAndFlush(new StockLevel(sku, 1));     // flushed so the savepoint rollback has a row to undo
            throw new IllegalStateException("boom inside NESTED");
        }
    }

    @Service
    public static class InventoryService {
        private final StockRepository repo;
        private final Auditor auditor;
        InventoryService(StockRepository repo, Auditor auditor) { this.repo = repo; this.auditor = auditor; }

        @Transactional
        public void twoCallsOneTransaction() {
            repo.save(new StockLevel("BOLT-7", 100));
            repo.save(new StockLevel("NUT-3", 40));
        }

        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public String inner() { return txName(); }

        @Transactional
        public void selfInvocation() {
            System.out.println("outer runs in     = " + txName());
            System.out.println("this.inner() in   = " + inner());              // the trap: no proxy, no new transaction
            System.out.println("auditor.inner() in= " + auditor.inner());      // another bean: proxied, REQUIRES_NEW honoured
        }

        @Transactional
        public void addThenFail(String sku) {
            repo.save(new StockLevel(sku, 5));
            throw new IllegalStateException("runtime failure after save");
        }

        @Transactional
        public void addThenFailChecked(String sku) throws Exception {
            repo.save(new StockLevel(sku, 5));
            throw new Exception("checked failure after save");
        }

        @Transactional(rollbackFor = Exception.class)
        public void addThenFailCheckedRollback(String sku) throws Exception {
            repo.save(new StockLevel(sku, 5));
            throw new Exception("checked failure, rollbackFor set");
        }

        @Transactional(readOnly = true)
        public void tryToModify(String sku) {
            StockLevel s = repo.findBySku(sku).orElseThrow();
            s.onHand = 999;                                   // dirty, but a read-only transaction never flushes
            System.out.println("read-only tx      = " + TransactionSynchronizationManager.isCurrentTransactionReadOnly());
        }

        @Transactional(propagation = Propagation.MANDATORY)
        public void requiresCaller() { }

        @Transactional
        public void nestedSavepoint() {
            repo.save(new StockLevel("CAM-9", 7));
            try { auditor.stockAndFail(repo, "GIRD-1"); }
            catch (NestedTransactionNotSupportedException e) {
                System.out.println("NESTED refused    = " + e.getClass().getSimpleName());   // JPA has no savepoints
            }
            repo.save(new StockLevel("ROD-4", 3));            // the outer transaction carries on and commits
        }
    }

    @Bean TransactionTemplate tx(PlatformTransactionManager manager) {
        TransactionTemplate t = new TransactionTemplate(manager);
        t.setName("lm.tx.Transactions.template");            // a template has no method to be named after
        return t;
    }

    /* Boot's JpaTransactionManager refuses NESTED unless told otherwise. */
    @Bean TransactionManagerCustomizer allowNested() {
        return manager -> manager.setNestedTransactionAllowed(true);
    }

    @Bean CommandLineRunner demo(StockRepository repo, InventoryService service, TransactionTemplate tx, EntityManagerFactory emf) {
        Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
        return args -> {
            System.out.println("-- 1. every repository call outside a service transaction is its own transaction --");
            long before = stats.getTransactionCount();
            repo.count(); repo.count();
            System.out.println("runner runs in    = " + txName());
            System.out.println("transactions used = " + (stats.getTransactionCount() - before));

            System.out.println("-- 2. a @Transactional service method: two calls, one transaction --");
            before = stats.getTransactionCount();
            service.twoCallsOneTransaction();
            System.out.println("transactions used = " + (stats.getTransactionCount() - before));

            System.out.println("-- 3. self-invocation bypasses the proxy --");
            service.selfInvocation();

            System.out.println("-- 4/5/6. what rolls back --");
            try { service.addThenFail("PIN-2"); } catch (IllegalStateException e) { }
            System.out.println("after runtime ex  = " + repo.findBySku("PIN-2").isPresent());
            try { service.addThenFailChecked("HUB-8"); } catch (Exception e) { }
            System.out.println("after checked ex  = " + repo.findBySku("HUB-8").isPresent());
            try { service.addThenFailCheckedRollback("WIDGET-1"); } catch (Exception e) { }
            System.out.println("with rollbackFor  = " + repo.findBySku("WIDGET-1").isPresent());

            System.out.println("-- 7. readOnly = true: dirty entities are never flushed --");
            service.tryToModify("BOLT-7");
            System.out.println("BOLT-7 on hand    = " + repo.findBySku("BOLT-7").orElseThrow().onHand);

            System.out.println("-- 8. programmatic: TransactionTemplate --");
            String name = tx.execute(status -> { repo.save(new StockLevel("TMPL-1", 1)); return txName(); });
            System.out.println("template tx name  = " + name);

            System.out.println("-- 9. MANDATORY outside any transaction --");
            try { service.requiresCaller(); }
            catch (IllegalTransactionStateException e) { System.out.println("threw             = " + e.getClass().getSimpleName()); }

            System.out.println("-- 10. NESTED: a savepoint inside the outer transaction --");
            service.nestedSavepoint();
            System.out.println("CAM-9 present     = " + repo.findBySku("CAM-9").isPresent());
            System.out.println("GIRD-1 present    = " + repo.findBySku("GIRD-1").isPresent());
            System.out.println("ROD-4 present     = " + repo.findBySku("ROD-4").isPresent());
            System.out.println("rows              = " + repo.count());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Transactions.class);
        app.setDefaultProperties(Map.ofEntries(                     // Map.of stops at ten pairs
            Map.entry("spring.main.web-application-type", "none"),
            Map.entry("spring.main.banner-mode", "off"),
            Map.entry("spring.main.log-startup-info", "false"),
            Map.entry("logging.level.root", "WARN"),
            Map.entry("logging.pattern.console", "%level %logger{0}: %msg%n"),
            Map.entry("spring.datasource.url", "jdbc:h2:mem:tx;DB_CLOSE_DELAY=-1"),
            Map.entry("spring.jpa.hibernate.ddl-auto", "create-drop"),
            Map.entry("spring.jpa.show-sql", "false"),
            Map.entry("spring.jpa.properties.hibernate.generate_statistics", "true"),
            Map.entry("spring.jpa.open-in-view", "false")));
        app.run(args).close();
    }
}

Reading the output, experiment by experiment

  1. No service, no shared transaction. The runner itself is in (no transaction), and two repo.count() calls used two transactions. Every SimpleJpaRepository method carries its own @Transactional (read-only for reads), so a repository called directly from outside a transaction opens and commits one per call. Two calls are not atomic together, and entities returned by the first are detached before the second runs.
  2. A service method draws the boundary. twoCallsOneTransaction made two save calls and Hibernate counted one transaction: the repository's own @Transactional uses the default propagation REQUIRED, which joins the transaction the service already opened.
  3. Self-invocation. this.inner() is annotated REQUIRES_NEW and still ran in …InventoryService.selfInvocation — the outer transaction. this is the target object, not the proxy, so nothing intercepted the call and the annotation was never read. The same method on another bean, auditor.inner(), went through that bean's proxy and got its own transaction, named after itself.
  4. An unchecked exception rolls back. PIN-2 was saved, then an IllegalStateException left the method: the proxy rolled back and the row is absent.
  5. A checked exception commits. HUB-8 survived a thrown Exception. Spring's default rollback rule — inherited from EJB — is "roll back on RuntimeException and Error, commit on checked exceptions", on the theory that a checked exception is an expected business outcome. Very few teams want that; most set a rule.
  6. rollbackFor = Exception.class changes the rule for that method: WIDGET-1 was rolled back.
  7. readOnly = true suppresses the flush. The method changed a managed entity's onHand to 999, and the database still says 100. Spring tells Hibernate the session is read-only, which sets the flush mode to manual and skips dirty-check snapshots; the change is simply never written. It also passes the read-only flag to the JDBC driver, which some databases and routing data sources use to send the work to a replica.
  8. TransactionTemplate is the programmatic form: the same begin/commit/rollback logic around a lambda, with no proxy involved. Use it where an annotation cannot reach — a runner, a loop that wants one transaction per item, or code that must not be a separate bean.
  9. MANDATORY refuses to run without a caller's transaction: IllegalTransactionStateException. It documents and enforces "this method is only ever a step inside something bigger".
  10. NESTED is not available here. NESTED means "a savepoint inside the current transaction": roll back to it on failure, keep the outer work. Even with nestedTransactionAllowed switched on, Spring's JpaTransactionManager refused it in this stack with NestedTransactionNotSupportedException, so GIRD-1 was never written; the outer transaction carried on and committed CAM-9 and ROD-4. Savepoints are a JDBC feature (DataSourceTransactionManager supports them for plain JDBC work). With JPA, model "try this step, keep the rest" as a REQUIRES_NEW call on another bean, accepting that it commits independently.

Propagation, interactively

Propagation answers one question: when a transactional method is called and a transaction may already exist, what happens? Pick an outer context, an inner propagation and what the inner method does. Where the annotation goes, and what it cannot do

Spring Boot proxies classes with CGLIB by default: it generates a subclass that overrides each public method to add the transaction logic, then delegates to your instance. That design has hard limits:

  • Self-invocation is invisible — experiment 3. Move the method to another bean, inject the bean into itself lazily, or use a TransactionTemplate.
  • private methods cannot be intercepted; a subclass cannot override them. The annotation is silently ignored.
  • final methods and final classes cannot be overridden either. Kotlin classes are final by default, which is why Spring's Kotlin plugin opens them.
  • Calls made before the proxy exists — from a constructor or @PostConstruct on the same bean — run without a transaction.
  • On the service layer, around one use case: "reserve stock and record the reservation" is one transaction. Repositories already have their own; controllers should not hold one.
  • On the class for a default, overridden on methods: a common shape is @Transactional(readOnly = true) on the class and plain @Transactional on the few writing methods.
  • On concrete classes, not interfaces. Interface annotations work for interface-based proxies but are easy to lose with class-based ones.
  • Keep it short. A transaction holds a connection and, for writes, row locks. No remote calls, file uploads or user think-time inside one.

The most confusing exception in Spring transactions comes from catching an inner failure:

@Transactional
public void placeOrder(Order o) {
    orders.save(o);
    try {
        loyalty.addPoints(o.customer(), 10);   // @Transactional (REQUIRED) on another bean; throws
    } catch (RuntimeException e) {
        log.warn("points failed, carrying on");  // looks handled …
    }
}                                              // … UnexpectedRollbackException here

addPoints joined the outer transaction. When it threw, its proxy could not roll back a transaction it does not own, so it marked the shared transaction rollback-only. The catch hid the exception, placeOrder returned normally, its proxy tried to commit, found the mark, rolled back, and threw UnexpectedRollbackException to tell you the order you thought was saved was not. Fixes: let it propagate, make addPoints REQUIRES_NEW so its failure is its own, or decide the call is optional and set noRollbackFor on it.

  • isolation — READ_COMMITTED, REPEATABLE_READ… (JPA §7's table). Only applies when the method begins the transaction; a joining method cannot change it.
  • timeout — seconds; passed to JPA as a query timeout for statements in the transaction.
  • rollbackFor / noRollbackFor — adjust the rule from experiments 4–6.
  • transactionManager — pick one by bean name when the application has several data sources.
  • JTA — for transactions spanning several resources (two databases, a database and a message broker) Spring delegates to a JTA transaction manager instead of JpaTransactionManager. Most applications avoid distributed transactions and use the outbox pattern (§8) instead.
Transaction gotchas
  • Checked exceptions commit by default. Experiment 5. Set rollbackFor = Exception.class, or throw unchecked domain exceptions.
  • Self-invoked and private transactional methods do nothing. No warning, no error; the method just runs in whatever transaction (or none) the caller had.
  • Catching an exception from a joined transaction leaves it rollback-only and ends in UnexpectedRollbackException at commit.
  • Repository calls from a controller or runner are separate transactions. Experiment 1. Two saves there are not atomic, and lazy loads between them fail.
  • readOnly = true silently discards changes to managed entities. That is the feature; it is also a bug if a "read" method is later taught to write.
  • Long transactions are the real performance problem, not their number: a transaction held across a slow HTTP call holds a pooled connection the whole time.

Check yourself

1.In InventoryService, a @Transactional method reserveAll() calls this.reserveOne(sku) in a loop, where reserveOne is annotated @Transactional(propagation = REQUIRES_NEW) so each item commits on its own. One item fails with a RuntimeException that reserveAll lets propagate. What happens?

C. Experiment 3 shows this.inner() running in the outer method's transaction despite REQUIRES_NEW. The per-item transactions never existed, so the exception rolls back the whole loop.

A is what the author intended, and what happens if reserveOne moves to another bean. B: mixing propagations is normal and nothing is checked at startup. D assumes the annotation took effect, which is precisely what self-invocation prevents.

2.A @Transactional method saves an order and then throws OutOfStockException extends Exception. No rollbackFor is set. Is the order in the database afterwards?

B. Experiment 5: after checked ex = true. The default rule rolls back only on RuntimeException and Error.

A is the rule most people assume and the reason for rollbackFor. C: whether the insert was flushed is irrelevant — the proxy commits, which flushes. D: the decision is made by the proxy when the exception passes through it, before the caller sees it.

3.Which of these run without the transaction behaviour their annotation asks for? Select all that apply.

A and C. Both are calls that never pass through the proxy: a private method cannot be overridden by the CGLIB subclass and is called on this; @PostConstruct runs on the target during initialisation, also via this.

B works as asked: an external call through the proxy, read-only transaction begun. D also behaves exactly as its annotation says — experiment 9 shows MANDATORY throwing IllegalTransactionStateException, which is the requested behaviour, not a bypass.
