Section 12

Configuration, profiles and production settings

Every program in this module has passed the same dozen properties to setDefaultProperties, and so far that has been treated as boilerplate. It is not. A Spring Boot application is shaped by its configuration more than by its code: the same jar behaves as a laptop sandbox, a CI fixture or a production service depending on which properties reach it, from where, and which one wins when two sources disagree. Most production incidents in the data layer trace back to a property — a pool too big for the database, ddl-auto left at update, show-sql logging every statement under load, a password in a properties file.

This section covers the machinery: the property sources and their precedence, profiles that switch beans and settings, type-safe binding with @ConfigurationProperties, how spring.jpa.* reaches Hibernate, how the Hikari pool should be sized, and how SQL initialisation interleaves with Hibernate's schema generation. It ends with the property set each environment should actually run with.

Worked example: one application, every configuration path

The program writes a three-line seed script, sets one JVM system property, then starts with the dev profile active. The runner prints what each mechanism resolved to.

package lm.config;

import com.zaxxer.hikari.HikariDataSource;
import jakarta.persistence.*;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Profile;
import org.springframework.core.env.Environment;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.stereotype.Component;
import org.springframework.validation.annotation.Validated;

import javax.sql.DataSource;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.Map;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
@EnableConfigurationProperties(Profiles.WarehouseProps.class)
public class Profiles {

    // ── a tiny entity so the data source and the seed script have something to hit ──
    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        int priceInCents;
        protected Product() {}
    }
    public interface ProductRepository extends JpaRepository<Product, Long> {}

    // ── one interface, two implementations, one of them active per profile ──
    public interface PricingPolicy { String describe(); }

    @Component @Profile("dev")
    public static class ListPricePolicy implements PricingPolicy {
        public String describe() { return "list price, no rounding (dev)"; }
    }
    @Component @Profile("prod")
    public static class ContractPricePolicy implements PricingPolicy {
        public String describe() { return "contract price with psychological rounding (prod)"; }
    }

    // ── type-safe, validated configuration ──
    @ConfigurationProperties(prefix = "warehouse")
    @Validated
    public record WarehouseProps(@NotBlank String region,
                                 @Min(1) int reorderThreshold,
                                 List<String> prioritySkus) {}

    @Bean CommandLineRunner show(Environment env, PricingPolicy pricing, WarehouseProps props,
                                 DataSource dataSource, EntityManagerFactory emf, ProductRepository products,
                                 @Value("${warehouse.currency:EUR}") String currency) {
        return args -> {
            System.out.println("active profiles = " + String.join(",", env.getActiveProfiles()));
            System.out.println("pricing policy  = " + pricing.describe());
            System.out.println("props           = " + props);
            System.out.println("currency        = " + currency + "   (not set anywhere: the @Value default)");

            HikariDataSource hikari = (HikariDataSource) dataSource;
            System.out.println("pool            = " + hikari.getPoolName() + ", max " + hikari.getMaximumPoolSize()
                    + ", min idle " + hikari.getMinimumIdle());
            System.out.println("batch_size      = " + emf.getProperties().get("hibernate.jdbc.batch_size")
                    + "   (reached Hibernate through spring.jpa.properties.*)");

            System.out.println("seeded rows     = " + products.count() + "   (inserted by the spring.sql.init script, not by Hibernate)");

            System.out.println("warehouse.site  = " + env.getProperty("warehouse.site")
                    + "   (default properties said 'default-properties')");
            System.out.println("warehouse.region= " + env.getProperty("warehouse.region")
                    + "   (only the default properties define it)");
        };
    }

    public static void main(String[] args) throws Exception {
        // a seed script Spring Boot will run after Hibernate has created the schema
        Path seed = Path.of("warehouse-seed.sql");
        Files.writeString(seed, """
            insert into product (id, sku, price_in_cents) values (1, 'BOLT-7', 80);
            insert into product (id, sku, price_in_cents) values (2, 'NUT-3', 25);
            insert into product (id, sku, price_in_cents) values (3, 'CAM-9', 2300);
            """);
        // a system property outranks the application's default properties
        System.setProperty("warehouse.site", "system-property");
        try {
            SpringApplication app = new SpringApplication(Profiles.class);
            app.setDefaultProperties(Map.ofEntries(
                Map.entry("spring.main.web-application-type", "none"),
                Map.entry("spring.main.banner-mode", "off"),
                Map.entry("spring.main.log-startup-info", "false"),
                Map.entry("logging.level.root", "WARN"),
                Map.entry("logging.pattern.console", "%level %logger{0}: %msg%n"),
                Map.entry("spring.profiles.active", "dev"),
                Map.entry("spring.datasource.url", "jdbc:h2:mem:config;DB_CLOSE_DELAY=-1"),
                Map.entry("spring.datasource.hikari.pool-name", "warehouse-pool"),
                Map.entry("spring.datasource.hikari.maximum-pool-size", "4"),
                Map.entry("spring.datasource.hikari.minimum-idle", "1"),
                Map.entry("spring.jpa.hibernate.ddl-auto", "create-drop"),
                Map.entry("spring.jpa.show-sql", "true"),
                Map.entry("spring.jpa.open-in-view", "false"),
                Map.entry("spring.jpa.properties.hibernate.jdbc.batch_size", "20"),
                Map.entry("spring.jpa.defer-datasource-initialization", "true"),
                Map.entry("spring.sql.init.mode", "always"),
                Map.entry("spring.sql.init.data-locations", "file:warehouse-seed.sql"),
                Map.entry("warehouse.region", "eu-west"),
                Map.entry("warehouse.reorder-threshold", "25"),
                Map.entry("warehouse.priority-skus", "BOLT-7,GIRD-1"),
                Map.entry("warehouse.site", "default-properties")));
            app.run(args).close();
        } finally {
            Files.deleteIfExists(seed);
        }
    }
}

Read it top to bottom against the configuration that produced it:

  • The DDL, then nothing. Hibernate creates the table, and the three seed rows appear without a single insert in the log. They were executed by Spring's spring.sql.init machinery straight through JDBC, so Hibernate's show_sql never saw them. If your seed data seems to load "silently", that is why.
  • active profiles = dev and pricing policy = list price…: two @Component classes implement PricingPolicy, and the runner asks for exactly one. That works only because @Profile("prod") kept the other one out of the context. Start with prod and you get the other bean; start with neither and the injection fails with NoSuchBeanDefinitionException, which is the right behaviour — no environment should run with an implicit pricing rule.
  • props = WarehouseProps[…]: three properties bound into an immutable, validated record. Note warehouse.reorder-threshold (kebab-case in the source) landed in reorderThreshold, and the comma-separated string became a List. Breaking @Min(1) fails startup, not the first request.
  • currency = EUR: no source defines warehouse.currency, so @Value("${warehouse.currency:EUR}") fell back to its default. Without the :EUR the context would refuse to start.
  • pool = warehouse-pool, max 4, min idle 1: the spring.datasource.hikari.* keys bind directly onto the HikariDataSource Spring Boot created.
  • batch_size = 20: spring.jpa.properties.hibernate.jdbc.batch_size was stripped of its spring.jpa.properties. prefix and handed to Hibernate verbatim — it is visible in the EntityManagerFactory's own property map.
  • warehouse.site = system-property: the default properties said default-properties, but System.setProperty outranks them. warehouse.region, defined only in the defaults, shows the defaults still apply wherever nothing overrides them.

Where a property comes from, and who wins

Spring Boot assembles one Environment from an ordered list of property sources and, for each key, takes the first match from the top. The list below runs from highest to lowest priority, abridged to the sources a data application actually uses:

  1. Test overrides: @DynamicPropertySource, @TestPropertySource, @SpringBootTest(properties = …) (§11).
  2. Command-line arguments: --spring.jpa.show-sql=true.
  3. SPRING_APPLICATION_JSON — a whole JSON document in one environment variable or system property.
  4. JVM system properties: -Dwarehouse.site=… or System.setProperty.
  5. OS environment variables: SPRING_DATASOURCE_URL=….
  6. Config files, where profile-specific beats plain and outside-the-jar beats inside: application-prod.properties next to the jar, then application.properties next to the jar, then the same two packaged inside it.
  7. @PropertySource on a configuration class.
  8. Default properties — SpringApplication.setDefaultProperties, which is all the programs in this module use.

The rule of thumb behind the order: the closer a source is to the person deploying, the more it wins. The jar's packaged application.properties holds sensible defaults, the deployment overrides them with environment variables or an external file, and a command-line flag overrides everything for one run. YAML (application.yml) is interchangeable with .properties; if both exist at the same location, .properties wins.

The property-precedence sandbox in §1 lets you tick sources on and off and watch which one wins; it is worth a second visit with this list beside it.

Relaxed binding and environment variables

Property names are matched loosely: warehouse.reorder-threshold, warehouse.reorderThreshold and warehouse.reorder_threshold all bind to the same field. Environment variables cannot contain dots or dashes, so they follow a fixed recipe — replace dots with underscores, drop the dashes, upper-case the lot:

SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/warehouse
SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE=8        # spring.datasource.hikari.maximum-pool-size
SPRING_JPA_OPENINVIEW=false                       # spring.jpa.open-in-view
WAREHOUSE_REORDERTHRESHOLD=25                     # warehouse.reorder-threshold
WAREHOUSE_PRIORITYSKUS=BOLT-7,GIRD-1              # a list, comma-separated

The recipe only works for keys bound to a @ConfigurationProperties class; a plain @Value("${warehouse.reorder-threshold}") looks up the canonical name, which still resolves from an environment variable, but uncommon forms are easy to get wrong. That is one of several reasons to prefer type-safe binding.

Profiles

A profile is a named switch. It does two jobs: it selects which beans exist (@Profile("dev") on a component or @Bean method, with negation @Profile("!prod") and expressions @Profile("dev & local")), and it selects which config files load (application-dev.properties layered over application.properties). Activate profiles with spring.profiles.active=prod — as an environment variable SPRING_PROFILES_ACTIVE=prod in a real deployment.

  • Groups name a set: spring.profiles.group.prod=prod-db,prod-cache lets you activate prod and get both, so the deployment does not have to know the decomposition.
  • spring.profiles.include unconditionally adds profiles from inside a config file; groups are usually clearer.
  • Profiles are for environments, not features. A profile per customer or per feature flag multiplies combinations nobody tests. Use a @ConfigurationProperties flag for a feature, and keep profiles to dev, test, prod and the occasional local.

How spring.jpa.* reaches Hibernate

There are two families of keys and confusing them is a common, silent bug:

  • spring.jpa.* and spring.jpa.hibernate.* bind to Spring Boot's own JpaProperties class, which knows a fixed set: show-sql, open-in-view, database-platform, defer-datasource-initialization, hibernate.ddl-auto, hibernate.naming.*. Boot translates them into Hibernate settings.
  • spring.jpa.properties.* is a pass-through map. Everything after the prefix goes to Hibernate unchanged — spring.jpa.properties.hibernate.jdbc.batch_size becomes hibernate.jdbc.batch_size, as the output showed.

So spring.jpa.hibernate.jdbc.batch_size=20, which looks right, matches nothing: JpaProperties.Hibernate has no such field, and nothing complains. If a Hibernate setting from JPA §9 seems to have no effect, check the prefix first.

The connection pool

Spring Boot picks HikariCP when it is on the class path, which spring-boot-starter-data-jpa guarantees. The knobs that matter:

HikariCP settings and their meaning
Property (spring.datasource.hikari.…)DefaultWhat it controls
maximum-pool-size10The hard cap on open connections per application instance. The number to size.
minimum-idlesame as maxIdle connections kept ready. Hikari recommends leaving it equal to the maximum: a fixed-size pool never has to open connections during a traffic spike.
connection-timeout30 sHow long a thread waits for a free connection before SQLTransientConnectionException. Lower it so an exhausted pool fails fast instead of piling up waiting requests.
max-lifetime30 minRetires each connection after this long. Must be shorter than any timeout the database, firewall or proxy applies, or the pool hands out connections that were already cut.
idle-timeout10 minRetires idle connections above minimum-idle; irrelevant for a fixed-size pool.
leak-detection-thresholdoffLogs a stack trace when a connection is held longer than this — the way to find the code that never returns one. A diagnostic, not a permanent setting.

Bigger is not better. A database server with eight cores runs eight things at once; give it eighty connections and seventy-two of them queue inside the database instead of inside the pool, where they also contend for locks and memory. HikariCP's starting formula — cores × 2 + effective spindle count — is a budget for the whole database, so it must be shared by every instance of every service that connects to it. Then check the demand side with Little's law: connections busy at once equals requests per second times the database time per request.

SQL initialisation and Hibernate's schema

Spring Boot can run SQL scripts at startup: schema.sql and data.sql from the class path by default, or the files named in spring.sql.init.schema-locations / data-locations. Two settings decide whether and when:

  • spring.sql.init.mode — embedded (the default: only for H2, HSQLDB and Derby), always, or never. The default is deliberate: scripts that recreate data are a convenience for an in-memory database and a hazard for a real one.
  • spring.jpa.defer-datasource-initialization — by default the scripts run before the EntityManagerFactory exists, which suits a hand-written schema.sql. If Hibernate generates the schema (ddl-auto), a data.sql that inserts into its tables needs true, or it runs against tables that do not exist yet. The program sets it for exactly that reason.

In production neither mechanism should own the schema: a migration tool should. Put Flyway or Liquibase on the class path and Spring Boot runs it before JPA starts, configured under spring.flyway.* or spring.liquibase.*, with migrations in db/migration. Combine it with ddl-auto=validate so Hibernate checks the migrated schema against the entities (JPA §10). Do not mix script-based initialisation with a migration tool; choose one owner for the schema.

Secrets

A database password in application.properties is committed to version control, copied into every build artefact and readable by anyone with the jar. Supply it at runtime instead: an environment variable (SPRING_DATASOURCE_PASSWORD) injected by the platform, a mounted file imported with spring.config.import=configtree:/run/secrets/, or a secret store such as Vault through its Spring integration. The property name stays the same; only the source changes — which is precisely what the precedence list is for.

Configuration gotchas
  • Seed rows with explicit ids collide with the sequence. The program's script inserted ids 1, 2 and 3 directly. The first entity Hibernate persists afterwards asks product_seq for a value, gets 1, and fails on the primary key. Either let seed scripts call the sequence (next value for product_seq), restart the sequence after seeding, or seed through the application.
  • A misspelt key is silently ignored. spring.jpa.hibernate.jdbc.batch_size, spring.datasource.hikari.max-pool-size and spring.jpa.open_in_view all bind to nothing. Your own @ConfigurationProperties classes can opt into strictness with ignoreUnknownFields = false; Spring's own keys cannot, so verify the effective value, as the program does.
  • Every instance has its own pool. Ten pods with the default pool of 10 open 100 connections, which is PostgreSQL's entire default max_connections. A rolling deployment briefly doubles it.
  • spring.profiles.active in a packaged application.properties sets the profile for every environment that does not override it, including production if someone forgets. Leave it out of the jar and set it where the application is deployed.
  • An @Profile that matches no active profile removes the bean. If the only implementation of an interface is @Profile("prod"), every other environment fails at startup. That is usually what you want; make sure it is not a surprise.

Check yourself

1.warehouse.site is set in the packaged application.properties, as an environment variable WAREHOUSE_SITE, as a system property -Dwarehouse.site, and as a command-line argument --warehouse.site. Which value does Environment.getProperty return?

D. Command-line arguments sit above every other runtime source; only test overrides rank higher. The order follows who is closest to this particular run: the person typing the command beats the deployment, which beats the build.

A is the lowest of the four — a packaged file holds defaults meant to be overridden. B loses to system properties, which are more specific to one JVM than the process environment. C would win if the command-line argument were absent; the worked example showed a system property beating the default properties for the same reason.

2.An application uses spring.jpa.hibernate.ddl-auto=create-drop on H2 and has a data.sql that inserts into the product table Hibernate generates. It does not set spring.jpa.defer-datasource-initialization. What happens at startup?

B. By default script initialisation runs before the EntityManagerFactory is built, so the insert targets a table that does not exist and the context fails to start. Setting spring.jpa.defer-datasource-initialization=true moves the scripts after Hibernate's schema generation, which is why the worked example sets it.

A describes the deferred behaviour, not the default. C is wrong for H2: the default mode embedded does run scripts against an in-memory database; always is needed only for a real one. D gets the order backwards — and Hibernate's drop happens at shutdown, not after the scripts.

3.Which line actually changes Hibernate's JDBC batch size?

C. spring.jpa.properties.* is the pass-through map: the remainder of the key reaches Hibernate unchanged. The worked example read it back from the EntityManagerFactory as batch_size = 20.

A looks plausible but binds to Spring Boot's JpaProperties.Hibernate, which knows only ddl-auto and the naming strategies, so it is silently ignored. B is not a key anything binds to. D sits in Spring's Environment, but nothing copies arbitrary hibernate.* keys from the environment into the persistence unit — only the spring.jpa.properties prefix does that.

4.Twelve instances of a service each use Hikari's default pool against a PostgreSQL server with 8 cores and max_connections = 100. Response times rise sharply under load. Which changes help? Select all that apply.

A and D. Twelve pools of 10 ask for 120 connections from a server that can usefully run about 17 (8 × 2 + 1) and refuses beyond 100. Shrinking the pools moves the queue out of the database, where waiting connections compete for CPU and locks, into the pool, where waiting is cheap. Reducing database time per request lowers the demand side of Little's law directly.

B makes it worse: 600 requested connections, most refused, and the rest contending inside an overloaded server. C only lets requests wait longer before failing; it hides the saturation and lets threads pile up behind it.
