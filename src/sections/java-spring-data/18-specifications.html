Section 9

Dynamic queries: Specifications and Query by Example

A search screen has six optional filters. A derived query name cannot express "category if given, price range if given, SKU prefix if given": you would need one method per combination, and six filters make sixty-four. A @Query string cannot either, unless you start concatenating JPQL — which is how injection bugs and unreadable code are born. What you need is a query assembled at runtime from whichever criteria are present, with the type checking and parameter binding of a real query.

That is the JPA Criteria API (JPA §6), and Spring Data wraps it in one small idea. A Specification<T> is a function (root, query, cb) -> Predicate: given the query being built, return the condition this criterion contributes. Because each criterion is a value, you can name it, test it, store it in a list and combine it with and, or and not. A repository that also extends JpaSpecificationExecutor<T> gains findAll(spec), count(spec), exists(spec) and delete(spec), and Spring Data turns the composed predicate into one JPQL query. Query by Example is the lighter sibling: hand it a half-filled entity and it builds the equality and string-matching predicates for you.

Worked example: one repository, eight queries, no strings

Six products from two suppliers. Every criterion is a static factory on ProductSpecs; the runner composes them in different ways and the SQL shows exactly what each composition became.

package lm.specs;

import jakarta.persistence.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.domain.*;
import org.springframework.data.jpa.domain.Specification;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.JpaSpecificationExecutor;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;

import static org.springframework.data.domain.ExampleMatcher.GenericPropertyMatchers.startsWith;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class Specifications {

    public enum Category { FASTENER, STRUCTURAL, MOTION }

    @Entity(name = "Supplier")
    @Table(name = "supplier")
    public static class Supplier {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true) String name;
        protected Supplier() {}
        Supplier(String name) { this.name = name; }
    }

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        @Enumerated(EnumType.STRING) @Column(nullable = false) Category category;
        int priceInCents;
        boolean active = true;
        @ManyToOne(fetch = FetchType.LAZY) Supplier supplier;
        protected Product() {}
        Product(String sku, Category category, int priceInCents, boolean active, Supplier supplier) {
            this.sku = sku; this.category = category; this.priceInCents = priceInCents; this.active = active; this.supplier = supplier;
        }
        @Override public String toString() { return sku + "/" + category + "/" + priceInCents + (active ? "" : "/inactive"); }
    }

    /* One static factory per criterion. Each returns a Specification, so they compose. */
    public static final class ProductSpecs {
        static Specification<Product> inCategory(Category c) {
            return (root, query, cb) -> cb.equal(root.get("category"), c);
        }
        static Specification<Product> priceBetween(int lo, int hi) {
            return (root, query, cb) -> cb.between(root.get("priceInCents"), lo, hi);
        }
        static Specification<Product> skuStartsWith(String prefix) {
            return (root, query, cb) -> cb.like(root.get("sku"), prefix + "%");
        }
        static Specification<Product> isActive() {
            return (root, query, cb) -> cb.isTrue(root.get("active"));
        }
        static Specification<Product> suppliedBy(String supplierName) {
            return (root, query, cb) -> {
                if (query != null) query.distinct(true);        // query is null for count/exists/delete
                return cb.equal(root.join("supplier").get("name"), supplierName);
            };
        }
        /* The "ignore absent criteria" pattern: every null argument means "no filter". */
        static Specification<Product> filter(Category c, Integer minPrice, Integer maxPrice, String skuPrefix, Boolean activeOnly) {
            List<Specification<Product>> parts = new ArrayList<>();
            if (c != null) parts.add(inCategory(c));
            if (minPrice != null || maxPrice != null) {
                parts.add(priceBetween(minPrice == null ? 0 : minPrice, maxPrice == null ? Integer.MAX_VALUE : maxPrice));
            }
            if (skuPrefix != null) parts.add(skuStartsWith(skuPrefix));
            if (Boolean.TRUE.equals(activeOnly)) parts.add(isActive());
            return Specification.allOf(parts);                   // empty list → no where clause at all
        }
    }

    public interface ProductRepository extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> {}
    public interface SupplierRepository extends JpaRepository<Supplier, Long> {}

    @Bean CommandLineRunner demo(ProductRepository products, SupplierRepository suppliers) {
        return args -> {
            Supplier acme = suppliers.save(new Supplier("Acme"));
            Supplier bolt = suppliers.save(new Supplier("BoltCo"));
            products.saveAll(List.of(
                new Product("BOLT-7", Category.FASTENER, 80, true, bolt),
                new Product("BOLT-9", Category.FASTENER, 95, false, bolt),
                new Product("NUT-3", Category.FASTENER, 25, true, acme),
                new Product("GIRD-1", Category.STRUCTURAL, 120_000, true, acme),
                new Product("ROD-4", Category.STRUCTURAL, 4_500, true, acme),
                new Product("CAM-9", Category.MOTION, 2_300, true, bolt)));
            Sort bySku = Sort.by("sku");

            System.out.println("-- 1. one criterion --");
            System.out.println(products.findAll(ProductSpecs.inCategory(Category.FASTENER), bySku));

            System.out.println("-- 2. and / or / not --");
            Specification<Product> cheapFasteners = Specification.where(ProductSpecs.inCategory(Category.FASTENER))
                    .and(ProductSpecs.priceBetween(0, 90));
            System.out.println(products.findAll(cheapFasteners.or(ProductSpecs.inCategory(Category.MOTION)), bySku));
            System.out.println(products.findAll(Specification.not(ProductSpecs.isActive()), bySku));

            System.out.println("-- 3. allOf / anyOf --");
            System.out.println(products.findAll(Specification.anyOf(
                    ProductSpecs.skuStartsWith("BOLT"), ProductSpecs.skuStartsWith("CAM")), bySku));

            System.out.println("-- 4. the null-tolerant filter --");
            System.out.println(products.findAll(ProductSpecs.filter(null, null, null, null, null), bySku));
            System.out.println(products.findAll(ProductSpecs.filter(Category.STRUCTURAL, 1_000, null, null, true), bySku));

            System.out.println("-- 5. a page needs two statements --");
            Page<Product> page = products.findAll(ProductSpecs.isActive(), PageRequest.of(0, 2, bySku));
            System.out.println("page 0 of " + page.getTotalPages() + ": " + page.getContent() + " total=" + page.getTotalElements());

            System.out.println("-- 6. a join inside a spec --");
            System.out.println(products.findAll(ProductSpecs.suppliedBy("BoltCo"), bySku));

            System.out.println("-- 7. count / exists / delete --");
            System.out.println("count structural = " + products.count(ProductSpecs.inCategory(Category.STRUCTURAL)));
            System.out.println("exists inactive = " + products.exists(Specification.not(ProductSpecs.isActive())));
            System.out.println("deleted inactive = " + products.delete((root, cb) -> cb.isFalse(root.get("active"))));

            System.out.println("-- 8. Query by Example --");
            Product probe = new Product();
            probe.sku = "bo";
            // one probe field only: with two, the order of the and-ed predicates is not guaranteed
            ExampleMatcher matcher = ExampleMatcher.matching()
                    .withIgnoreNullValues()
                    .withIgnorePaths("id", "priceInCents", "active")   // primitives are never null, so they must be ignored explicitly
                    .withMatcher("sku", startsWith())
                    .withIgnoreCase();
            System.out.println(products.findAll(Example.of(probe, matcher), bySku));
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Specifications.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:specs;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

Read the SQL against the composition that produced it:

  1. One criterion becomes one predicate: where p1_0.category=?. The enum is a bound parameter, never spliced into the string.
  2. where(a).and(b).or(c) is evaluated left to right as (a and b) or c. Hibernate prints it without parentheses — category=? and price_in_cents between ? and ? or category=? — because SQL's and binds tighter than or, so the brackets would be redundant. If you meant a and (b or c), build b.or(c) first and pass it to and; the fluent chain will not guess. Specification.not becomes not(p1_0.active).
  3. anyOf joins its arguments with or; allOf with and. Notice like ? escape '': a Criteria cb.like with no escape character means a % or _ typed into a search box is a wildcard. A derived StartingWith (§3) escapes for you, emitting escape '\'; a hand-written spec does not.
  4. The null-tolerant filter with every argument null produced a query with no where clause at all — allOf of an empty list is "unrestricted", not where 1=1. With three arguments present, three predicates appear, joined by and. This is the pattern a search endpoint wants.
  5. Paging costs two statements: the page itself with offset ? rows fetch first ? rows only, then select count(p1_0.id) … where p1_0.active. Spring Data re-applies the same specification to a count query, so the total always matches the filter (§7).
  6. A join inside a spec — root.join("supplier") — becomes an inner join, and query.distinct(true) becomes select distinct. The guard if (query != null) matters: Spring Data 4 calls the same spec for count, exists and delete, where there is no CriteriaQuery to set distinct on.
  7. count, exists and delete reuse specs too. exists is select 1 … fetch first ? rows only — it stops at the first match. delete here takes a PredicateSpecification, Spring Data JPA 4's query-independent form (root, cb) -> …, and runs one bulk delete: no entities are loaded, no lifecycle callbacks fire, and the persistence context is not told (JPA §6).
  8. Query by Example turned a probe with sku = "bo", matched with startsWith and ignoring case, into lower(p1_0.sku) like ? escape '\'. Primitive fields are never null, so priceInCents and active would have become = 0 and = false — the matcher must ignore them explicitly. Only BOLT-7 comes back because step 7 deleted the inactive BOLT-9. While this page was being built, a probe with two fields (SKU and category) emitted its two predicates in a different order on different runs: Query by Example walks the entity's attributes in an order nobody promises. The rows are the same either way, but never write a test that asserts on its SQL text.

Build a filter

Compose a Specification from whichever criteria are present

The rows are the six products from the worked example, filtered in the browser by the same rules the database applies. The price range is "off" at its extremes, mirroring the null-tolerant factory: an absent bound contributes no predicate.

Which tool for which query

Choosing between derived queries, @Query, Specifications and Query by Example
The query is…Reach forWhy
Fixed, one or two conditionsDerived query (§3)The name is the documentation, validated at startup.
Fixed but complex: joins, aggregates, projections@Query (§4)One readable JPQL string, validated at startup.
Shape decided at runtime from optional inputsSpecificationComposable, typed, parameters always bound.
"Find things like this one", equality and string matching onlyQuery by ExampleZero query code; the probe is the filter.
Ranges, or across fields, nested properties of collectionsSpecificationQuery by Example cannot express them.
Reporting with grouping, window functionsNative @Query or jOOQCriteria becomes harder to read than the SQL it emits.

Treat specifications like small pure functions. Each factory knows one criterion and nothing else; the screen or service decides which to combine. That gives you criteria you can unit-test in isolation, reuse across repositories with the same attribute names, and name after the business rule — overdue(), restockCandidate(threshold) — rather than after the columns.

static Specification<Product> restockCandidate(int threshold) {
    return Specification.allOf(isActive(), stockBelow(threshold), not(discontinued()));
}

// the caller adds what the request supplied
Specification<Product> spec = restockCandidate(10);
if (req.category() != null) spec = spec.and(inCategory(req.category()));
List<Product> hits = products.findAll(spec, Sort.by("sku"));

Composition is immutable: spec.and(x) returns a new specification and leaves spec alone, so a shared base filter cannot be corrupted by one caller.

Query by Example needs only QueryByExampleExecutor, which JpaRepository already extends. The probe's non-null fields become predicates; the ExampleMatcher decides how strings compare (exact, starts with, contains, ends with, regex where supported) and whether case matters.

  • It can: equality on any property, including nested single-valued ones (supplier.name); string matching; ignoring paths; matchingAll versus matchingAny.
  • It cannot: ranges (between, >), in lists, or on the same property, conditions on collection elements, is null unless you opt in with withIncludeNullValues().
  • The primitive trap: an int field is 0, never null, so it is always included unless you ignore its path. Prefer wrapper types on probes, or ignore paths explicitly as the worked example does.

root.get("priceInCents") is a string. Rename the field and every spec still compiles, then fails at runtime with an IllegalArgumentException about an unknown attribute. Two cures:

  • The JPA static metamodel. Add hibernate-processor as an annotation processor and Hibernate generates Product_ with typed attributes, so the spec reads root.get(Product_.priceInCents) and a rename becomes a compile error. Not on this module's class path, so the worked example uses strings.
  • Querydsl generates QProduct and a fluent, typed predicate language (product.priceInCents.between(lo, hi)); Spring Data integrates it via QuerydslPredicateExecutor. It is a separate dependency and code generator — worth it on a large query surface, overkill for a handful of filters.
Specification gotchas
  • A fetch join in a spec breaks paging. root.fetch("lines") is reused for the count query, where Hibernate rejects fetching an association whose owner is not selected. Guard it with if (Long.class != query.getResultType()), or keep fetch plans in an @EntityGraph on the repository method (§6).
  • Joins multiply rows. A join to a collection returns one row per element; without distinct the same product appears several times, and the total in a Page counts the duplicates.
  • The fluent chain is left-associative. a.and(b).or(c) is (a and b) or c. Build the bracketed part as its own specification when you mean something else.
  • User input in like is a pattern. cb.like(root.get("sku"), prefix + "%") treats % and _ in prefix as wildcards. Escape them, or use the three-argument cb.like(expr, pattern, '\\').
  • Every filter combination is a different SQL string. Six optional filters can produce dozens of statement shapes, each parsed and planned separately by the database and each a separate entry in Hibernate's query plan cache. Usually fine; worth knowing when a database's statement cache starts thrashing.

Check yourself

1.A search endpoint receives no filters at all and calls products.findAll(Specification.allOf(List.of())). What SQL runs?

B. The worked example's step 4 shows it: allOf of nothing is the unrestricted specification, and Spring Data omits the where clause entirely. That is what makes the null-tolerant filter pattern work without special cases.

A would make the pattern unusable, and Spring Data deliberately allows it. C is what string-building code tends to produce, not what Criteria emits. D would be the result of anyOf semantics taken literally ("at least one of nothing"), which is not how an empty conjunction behaves.

2.You need: active products whose category is FASTENER or whose price is under 100 cents. Which composition is correct?

C. The or must be built first, then and-ed with isActive(): active and (category = ? or price < ?).

A groups left to right as (active and fastener) or cheap, so an inactive product under 100 cents is returned — exactly the shape step 2 of the worked example printed. B makes all three alternatives, returning every active product regardless of category or price. D is wrong: Hibernate faithfully renders the tree you built; it only omits parentheses that SQL precedence makes redundant.

3.Which of these can Query by Example express? Select all that apply.

A and D. String matching with a matcher, equality, and nested single-valued properties are exactly what a probe can describe. Step 8 of the worked example is the SKU half of case A; adding the category is one more field on the probe.

B: a probe holds one value per property, so there is no way to say "between". C: one property cannot hold two values, and matchingAny ors different properties, not alternatives for the same one. Both need a Specification.
