Section 3

Derived queries: method names that become SQL

A repository interface in §2 had no implementation and still worked, because Spring Data generated a proxy for it. This section is about the part of that proxy that reads your mind: declare List<Product> findByCategoryAndPriceInCentsLessThan(Category c, int max) with no body and no annotation, and at startup Spring Data parses the method name into a predicate tree, checks every property against the entity's metamodel, builds a JPQL query from it, and from then on every call runs that query. The name is the specification. Get it wrong and the application refuses to start, which is the best place to be wrong.

The grammar is small. A subject (find…By, count…By, exists…By, delete…By, with optional Distinct, First/Top and a limit), then a predicate made of property names, comparison keywords and And/Or, then an optional OrderBy with properties and directions. Parameters are bound to the predicate's placeholders by position, left to right, so the parameter order must follow the name. Everything else — the SQL, the parameter escaping, the fetch first clause, the upper() for a case-insensitive match — is derived.

Worked example

One repository with eighteen derived methods, exercised over seven products. Two of them have no name on purpose (findByNameIsNull), two are inactive, and the SKUs are chosen so that each string keyword matches something different. Read the Hibernate: line above each result: it is the SQL the name became.

package lm.derived;

import jakarta.persistence.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.domain.Sort;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;
import java.util.Collection;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.stream.Stream;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class DerivedQueries {

    public enum Category { FASTENER, STRUCTURAL, MOTION }

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        String name;                                        // nullable on purpose: see findByNameIsNull
        @Enumerated(EnumType.STRING) @Column(nullable = false, length = 16) Category category;
        int priceInCents;
        boolean active;
        protected Product() {}
        Product(String sku, String name, Category category, int priceInCents, boolean active) {
            this.sku = sku; this.name = name; this.category = category; this.priceInCents = priceInCents; this.active = active;
        }
        @Override public String toString() { return sku; }
    }

    // Every method below is implemented by Spring Data from its NAME alone.
    public interface ProductRepository extends JpaRepository {
        List findByCategoryOrderBySkuAsc(Category category);
        List findByCategoryAndPriceInCentsLessThanOrderBySku(Category category, int max);
        List findByPriceInCentsBetweenOrderByPriceInCents(int low, int high);
        List findBySkuStartingWithOrderBySku(String prefix);
        List findBySkuContainingOrderBySku(String part);
        List findBySkuEndingWithOrderBySku(String suffix);
        Optional findByNameIgnoreCase(String name);
        List findBySkuInOrderBySku(Collection skus);
        List findByActiveTrueOrderBySku();
        List findByNameIsNullOrderBySku();
        List findFirst3ByOrderByPriceInCentsDesc();
        Optional findTopByCategoryOrderByPriceInCentsAsc(Category category);
        long countByCategory(Category category);
        boolean existsBySku(String sku);
        long countByActiveFalse();
        long deleteBySku(String sku);                        // derived delete: needs a transaction
        List findByCategory(Category category, Sort sort);
        Stream findByPriceInCentsGreaterThanOrderBySku(int min);   // needs an open transaction
    }

    @Bean TransactionTemplate tx(PlatformTransactionManager manager) { return new TransactionTemplate(manager); }

    @Bean CommandLineRunner demo(ProductRepository repo, TransactionTemplate tx) {
        return args -> {
            repo.saveAll(List.of(
                new Product("BOLT-7", "Hex bolt M8", Category.FASTENER, 80, true),
                new Product("NUT-3", "Hex nut M8", Category.FASTENER, 25, true),
                new Product("PIN-2", null, Category.FASTENER, 15, false),
                new Product("GIRD-1", "Steel girder 6m", Category.STRUCTURAL, 120_000, true),
                new Product("ROD-4", "Threaded rod 1m", Category.STRUCTURAL, 4_500, true),
                new Product("CAM-9", "Cam follower", Category.MOTION, 2_300, true),
                new Product("HUB-8", null, Category.MOTION, 7_900, false)));

            System.out.println("-- equality, comparison, range --");
            System.out.println("fasteners         = " + repo.findByCategoryOrderBySkuAsc(Category.FASTENER));
            System.out.println("cheap fasteners   = " + repo.findByCategoryAndPriceInCentsLessThanOrderBySku(Category.FASTENER, 50));
            System.out.println("2000..8000        = " + repo.findByPriceInCentsBetweenOrderByPriceInCents(2_000, 8_000));

            System.out.println("-- string matching --");
            System.out.println("starts BOLT       = " + repo.findBySkuStartingWithOrderBySku("BOLT"));
            System.out.println("contains -        = " + repo.findBySkuContainingOrderBySku("D-"));
            System.out.println("ends 9            = " + repo.findBySkuEndingWithOrderBySku("9"));
            System.out.println("name ignore case  = " + repo.findByNameIgnoreCase("hex BOLT m8").map(p -> p.sku).orElse("none"));

            System.out.println("-- collections, booleans, nulls --");
            System.out.println("in list           = " + repo.findBySkuInOrderBySku(List.of("NUT-3", "CAM-9", "NOPE")));
            System.out.println("active            = " + repo.findByActiveTrueOrderBySku());
            System.out.println("unnamed           = " + repo.findByNameIsNullOrderBySku());

            System.out.println("-- limiting and ordering --");
            System.out.println("top 3 by price    = " + repo.findFirst3ByOrderByPriceInCentsDesc());
            System.out.println("cheapest motion   = " + repo.findTopByCategoryOrderByPriceInCentsAsc(Category.MOTION).map(p -> p.sku).orElse("none"));
            System.out.println("sorted by param   = " + repo.findByCategory(Category.STRUCTURAL, Sort.by(Sort.Direction.DESC, "priceInCents")));

            System.out.println("-- counts and existence --");
            System.out.println("count structural  = " + repo.countByCategory(Category.STRUCTURAL));
            System.out.println("exists ROD-4      = " + repo.existsBySku("ROD-4"));
            System.out.println("inactive          = " + repo.countByActiveFalse());

            System.out.println("-- streaming and deleting need a transaction --");
            tx.executeWithoutResult(status -> {
                try (Stream s = repo.findByPriceInCentsGreaterThanOrderBySku(1_000)) {
                    System.out.println("streamed          = " + s.map(p -> p.sku).toList());
                }
                System.out.println("deleted           = " + repo.deleteBySku("PIN-2"));
            });
            System.out.println("remaining         = " + repo.count());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(DerivedQueries.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:derived;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

Six things in that output are worth reading twice:

  • like ? escape '\'. StartingWith, Containing and EndingWith all become like, but Spring Data builds the pattern itself (BOLT%, %D-%, %9) and escapes any % or _ in your argument first. A user searching for 50% finds SKUs containing "50%", not everything starting with 50. §4 shows the declared-query version, which does not escape for you.
  • in (?,?,?). In with a three-element collection expands to three placeholders. A different collection size is a different SQL string, which matters for statement caching and for the database's bind limit (Oracle stops at 1,000).
  • fetch first ? rows only. First3 and Top become the dialect's limit clause. H2 and PostgreSQL say fetch first; MySQL would say limit. You wrote neither.
  • upper(p1_0.name)=upper(?). IgnoreCase wraps both sides in upper(), which also means the index on name is useless for that query unless it is a functional index. Think before adding IgnoreCase to a hot path.
  • exists is a select p1_0.id … fetch first ? rows only, not a count. It stops at the first match.
  • The derived deleteBySku ran a select before its delete. A derived delete loads the entities and removes them one by one through the persistence context, so cascades and lifecycle callbacks fire. A @Modifying @Query("delete …") (§4) is one statement and fires nothing.

Parsing rules you will hit

findByOrderCustomerName(String name) is resolved greedily: Spring Data first looks for a property called orderCustomerName, then splits from the right — orderCustomer.name, then order.customerName, then order.customer.name — until a path through the metamodel matches. Each association in the path becomes a join in the SQL.

List<OrderLine> findByOrderCustomerName(String name);     // order.customer.name — two joins
List<OrderLine> findByOrder_Customer_Name(String name);   // the same, written unambiguously

The underscore is the disambiguator for when the greedy split would pick the wrong path — an entity with both an address association and a addressZip field, for example. Use it whenever the name has more than one plausible reading, and never rely on the reader guessing the same way the parser did.

Or splits the name first, then And inside each part: findByCategoryAndActiveTrueOrPriceInCentsLessThan means (category = ?1 and active = true) or priceInCents < ?2. There are no parentheses in a method name, so you cannot express category = ?1 and (active = true or priceInCents < ?2) at all — that is a @Query.

Parameters bind by position to the predicate parts that take one: Category for part one, nothing for ActiveTrue, int for part three. Put the parameters in a different order and the application starts, the types coerce, and the query is silently wrong — the only keyword-grammar mistake that is not caught at boot.

A derived method may also take a trailing Sort, Pageable or Limit parameter; it is applied after the name's own OrderBy. Combining OrderBy in the name with a Sort parameter sorts by both, name first.

Every method name is parsed when the repository bean is created. A property that does not exist stops the application before it serves a request, with a message that names the type and the property:

Caused by: org.springframework.data.mapping.PropertyReferenceException:
  No property 'pricelnCents' found for type 'Product'
  Did you mean 'priceInCents'?
  at org.springframework.data.mapping.PropertyPath.<init>(PropertyPath.java:91)

  at org.springframework.data.repository.query.parser.PartTree$Predicate.buildTree(…)

The "did you mean" is computed by edit distance against the entity's properties. This fail-fast check is a large part of the value of derived queries: a renamed field breaks the build of every query that used it, which a string inside @Query only does if query validation at startup is on (it is, by default — §4).

When a derived name is the wrong tool
  • It no longer reads as a sentence. findByCategoryAndActiveTrueAndPriceInCentsBetweenAndSupplierCountryInOrderByPriceInCentsDescSkuAsc is a 90-character specification nobody will review. Past roughly forty characters, or past two Ands, write a @Query and give the method a name that says what it is for.
  • It needs an aggregate, a group, a join on a non-association, or a projection with expressions. The grammar has none of these. sum, group by, case, coalesce are @Query territory.
  • It needs a fetch join. A derived method can declare @EntityGraph (§6), but a JPQL join fetch cannot be derived.
  • It hides a scan. findByNameContaining is a leading-wildcard like: no B-tree index helps it. The name looks innocent; the plan is a full table scan.
  • It is a derived delete over many rows. It loads each entity first. Use a @Modifying delete, or a batch job, past a few hundred rows.

1.List<Product> findBySkuContaining(String part) is called with "50%". Which rows match?

C. The worked example's SQL says like ? escape '\': Spring Data wraps the argument in %…% and escapes any % or _ inside it, so the user's percent sign is matched literally.

A and D would be true of a @Query("… like ?1") where you pass the pattern yourself — §4 shows that version emits escape '', no escaping. B invents a validation that does not exist; any string is a valid argument.

2.A repository declares findByCategoryAndActiveTrueOrPriceInCentsLessThan(Category c, int max). Which predicate does it run?

B. The parser splits on Or first, then on And within each part — the only precedence a method name can express.

A needs parentheses, which the grammar has no syntax for; that query must be a @Query. C is wrong: mixing is allowed, with exactly this precedence. D is wrong because True/False/IsNull are the keywords that take no parameter; the two parameters bind to Category and LessThan.

3.Which of these would be caught when the application starts, before any request? Select all that apply.

A and D. Both are PropertyReferenceExceptions: the name is parsed against the metamodel when the repository bean is built, and a property or path that does not exist fails there.

B starts fine — parameters bind by position and the types are checked only loosely — and returns wrong results, which is why the positional rule deserves care. C is a performance problem the parser cannot see; the query is valid, the plan is the issue.
