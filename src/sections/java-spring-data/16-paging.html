Section 7

Pagination, sorting, slices and keyset scrolling

Nobody wants all 400,000 products. A screen wants twenty, sorted somehow, and a way to ask for the next twenty. JPA gives you setFirstResult/setMaxResults and leaves the rest — the sort, the total, the "is there a next page" — to you. Spring Data turns that into three types you pass in and three you get back: a Pageable (page number, size, Sort) goes into any repository method, and a Page, Slice or Window comes out carrying the content plus exactly as much metadata as you asked to pay for.

"Pay for" is the right phrase. A Page knows the total, which costs a second count query on every request. A Slice knows only whether there is a next page, which costs one extra row. And both use offset, which makes page 5,000 as expensive as reading 100,000 rows the database then throws away. The scrolling API's keyset position fixes that by remembering where the last page ended instead of how many rows to skip. This section runs all of them against 23 products and reads the SQL each one produces.

Worked example: eight ways to ask for a few rows

Twenty-three products, three categories, prices that are deliberately not in SKU order so a two-level sort has something to do.

package lm.paging;

import jakarta.persistence.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.domain.*;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.data.repository.query.Param;
import java.util.List;
import java.util.Map;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class Paging {

    public enum Category { FASTENER, STRUCTURAL, TOOLING }

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        @Enumerated(EnumType.STRING) @Column(nullable = false) Category category;
        int priceInCents;
        protected Product() {}
        Product(String sku, Category category, int priceInCents) { this.sku = sku; this.category = category; this.priceInCents = priceInCents; }
        public String getSku() { return sku; }
        public int getPriceInCents() { return priceInCents; }
        @Override public String toString() { return sku + "@" + priceInCents; }
    }

    public record ProductView(String sku, int priceInCents) {}

    public interface ProductRepository extends JpaRepository {
        Slice findByCategory(Category category, Pageable pageable);                     // no count query

        @Query(value = "select p from Product p where p.priceInCents > :min",
               countQuery = "select count(p) from Product p where p.priceInCents > :min")
        Page findExpensive(@Param("min") int min, Pageable pageable);

        Window findFirst5ByCategoryOrderBySkuAsc(Category category, ScrollPosition position);   // scrolling API

        List findByCategory(Category category, Limit limit, Sort sort);
    }

    static String skus(Iterable ps) {
        StringBuilder sb = new StringBuilder("[");
        for (Product p : ps) sb.append(sb.length() > 1 ? ", " : "").append(p.getSku());
        return sb.append("]").toString();
    }

    @Bean CommandLineRunner demo(ProductRepository repo) {
        return args -> {
            Category[] cats = Category.values();
            for (int i = 1; i <= 23; i++) {
                repo.save(new Product(String.format("SKU-%02d", i), cats[i % 3], (i * 37) % 100 * 10));
            }

            System.out.println("-- A: Page with a two-level sort --");
            Pageable first = PageRequest.of(0, 5, Sort.by("priceInCents").descending().and(Sort.by("sku")));
            Page page = repo.findAll(first);
            System.out.println("content = " + skus(page));
            System.out.println("totalElements = " + page.getTotalElements() + ", totalPages = " + page.getTotalPages()
                    + ", number = " + page.getNumber() + ", hasNext = " + page.hasNext());

            System.out.println("-- B: the last page --");
            Page last = repo.findAll(PageRequest.of(page.getTotalPages() - 1, 5, first.getSort()));
            System.out.println("content = " + skus(last) + ", numberOfElements = " + last.getNumberOfElements() + ", hasNext = " + last.hasNext());

            System.out.println("-- C: Slice, no count --");
            Slice slice = repo.findByCategory(Category.FASTENER, PageRequest.of(0, 3, Sort.by("sku")));
            System.out.println("content = " + skus(slice) + ", hasNext = " + slice.hasNext());

            System.out.println("-- D: @Query with its own countQuery --");
            Page dear = repo.findExpensive(600, PageRequest.of(0, 4, Sort.by("sku")));
            System.out.println("content = " + skus(dear) + ", total = " + dear.getTotalElements());

            System.out.println("-- E: Page.map to a DTO --");
            Page views = page.map(p -> new ProductView(p.getSku(), p.getPriceInCents()));
            System.out.println(views.getContent().get(0) + " of " + views.getTotalElements());

            System.out.println("-- F: keyset scrolling --");
            Window w1 = repo.findFirst5ByCategoryOrderBySkuAsc(Category.STRUCTURAL, ScrollPosition.keyset());
            System.out.println("window 1 = " + skus(w1) + ", hasNext = " + w1.hasNext());
            Window w2 = repo.findFirst5ByCategoryOrderBySkuAsc(Category.STRUCTURAL, w1.positionAt(w1.size() - 1));
            System.out.println("window 2 = " + skus(w2) + ", hasNext = " + w2.hasNext());

            System.out.println("-- G: Limit + Sort on a derived query --");
            System.out.println(skus(repo.findByCategory(Category.TOOLING, Limit.of(3), Sort.by("priceInCents").descending())));

            System.out.println("-- H: unpaged --");
            System.out.println("all = " + repo.findAll(Pageable.unpaged()).getTotalElements());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Paging.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:paging;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

What each phase paid for:

  • A — two statements. The order by price_in_cents desc, sku comes straight from the Sort; offset ? rows fetch first ? rows only is H2's (and SQL:2008's) pagination syntax, which Hibernate picks per dialect. Then select count(p1_0.id) runs so the Page can answer getTotalElements() and getTotalPages(). Every page request pays that count.
  • B — one statement. Spring Data skips the count when it can derive the total: the last page returned 3 rows at offset 20, so the total must be 23. An optimisation, not a promise — do not design around it.
  • C — one statement, size + 1. A Slice asks for fetch first 4 when you wanted 3; if a fourth row comes back, hasNext() is true and the row is dropped. No count, so "page 1 of 937" cannot be shown, but infinite-scroll screens never needed it.
  • D — your own count. A @Query that returns Page needs a countQuery whenever Spring Data cannot derive one (joins, distinct, native SQL — anything beyond a simple select). Without it you get a runtime error on the first call, not at startup.
  • E — no statement. Page.map converts the content and keeps the metadata. Return this from a service, not a page of entities: the DTO page is complete, serialisable, and cannot trigger a lazy load.
  • F — keyset. The first window has no position, so it is a plain order by sku, id fetch first 5 — note that Spring Data appended id to make the sort unique. The second window carries the last row's keys: where sku > ? or (sku = ? and id > ?). The database seeks to that key through the index and reads five rows; it never skips anything, so window 10,000 costs the same as window 1.
  • G — Limit. When you want "the top 3" and nothing else, a Limit parameter plus a Sort is clearer than a Pageable you then ignore.
  • H — Pageable.unpaged(). Accepted everywhere a Pageable is, returns everything, no count query. Useful for the "export all" path of a method that otherwise pages.

Offset versus keyset, by the numbers

Sorting, safely

Sort.by("priceInCents").descending().and(Sort.by("sku"))     // property paths, validated against the entity
Sort.by(Sort.Direction.DESC, "category", "sku")
Sort.by(Sort.Order.asc("sku").ignoreCase())

Sort.TypedSort<Product> p = Sort.sort(Product.class);       // refactoring-safe
p.by(Product::getPriceInCents).descending().and(p.by(Product::getSku));

JpaSort.unsafe("length(sku)")                               // raw JPQL expression; never from user input

// a @Query honours the Pageable's sort by appending it, so the query must not have its own order by
@Query("select p from Product p where p.category = :c")
Page<Product> byCategory(@Param("c") Category c, Pageable pageable);

A Sort built from property names is checked against the entity metamodel at query time; a typo throws PropertyReferenceException rather than producing bad SQL. That check is what makes it safe to build a Sort from a request parameter after validating the property against an allow-list. JpaSort.unsafe skips the check and interpolates the expression, which is why its name says so.

Pagination gotchas
  • Paging a fetch join pages in memory. @Query("select o from Order o join fetch o.lines") with a Pageable cannot apply fetch first in SQL — the join multiplies rows per order — so Hibernate loads everything and pages the list, logging HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory. Page the parent ids first, then fetch the collections for that page (§6).
  • Offset pages drift under writes. If a row is inserted before page 3 while a user reads page 2, page 3 repeats a row and the one after it is skipped. Keyset positions are stable because they remember a key, not a count.
  • An unstable sort makes keyset wrong and offset random. Sorting by a non-unique column only (price) means equal rows have no defined order between queries. Spring Data appends id to keyset sorts (F shows it); for offset paging, add the tiebreaker yourself.
  • The count query is the slow one. On a large table with a filter the count(*) is a full scan the page query avoided through its index. If the UI only needs "next", return a Slice; if it needs totals, cache or estimate them.
  • Do not return Page<Entity> from an API. Serialising a page of entities walks lazy associations and ships internal fields; Page.map to a DTO, then (Spring Data 3.3+) wrap in PagedModel for a stable JSON shape. spring.data.web.pageable.* properties (default size, max size, one-indexed pages) configure the web binding — the web starter is not on this class path, so they are only mentioned.

Check yourself

1.A method returns Page<Product> for PageRequest.of(2, 20, Sort.by("sku")) on a 1,000-row table. How many SQL statements run, and what do they do?

B. Phase A, exactly: a Page promises totals, and totals need a count. The count is skipped only when the returned rows settle it (a short last page, or a first page smaller than its size — phase B).

A cannot know the total from 20 rows. C adds a statement nothing issues; hasNext is computed from the total. D is the Slice technique, which does not produce a total at all.

2.An infinite-scroll feed shows 50,000 events newest-first and users routinely scroll a thousand items deep. Which repository method shape is right?

C. Deep offset is the problem: item 1,000 means offset 1000, which reads and discards a thousand rows per request, and an insert at the top shifts every later page by one. A keyset window on (createdAt, id) uses the index and is immune to inserts above the cursor.

A pays a count of 50,000 rows on every scroll and still has the offset cost. B drops the count — better — but keeps offset, so it still degrades with depth and drifts under inserts. D loads 50,000 entities per request.

3.Which statements about this method are true? Select all that apply.

@Query("select o from Order o join fetch o.lines where o.status = :s")
Page<Order> open(@Param("s") Status s, Pageable pageable);

A and C. Two separate problems. The count: Spring Data rewrites simple queries into counts but refuses a fetch join, so you supply countQuery = "select count(o) from Order o where o.status = :s". The paging: a fetch join returns one row per line, so fetch first 20 rows would cut an order's lines in half; Hibernate therefore fetches all rows and pages the entities in memory, logging the warning. The fix is two queries — page the order ids, then fetch lines for those ids.

B is the misconception the warning exists for. D: a Slice still uses fetch first with a fetch join, so the same in-memory fallback applies.
