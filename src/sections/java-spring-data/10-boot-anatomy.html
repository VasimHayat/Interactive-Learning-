Section 1

A Spring Boot data application, dissected

The JPA module ended with a program that built a PersistenceConfiguration, opened an EntityManagerFactory, began a transaction, persisted a product and committed. Fifteen lines of plumbing around three lines of intent. Spring Boot's promise is that the plumbing is inferred: put spring-boot-starter-data-jpa and a JDBC driver on the class path, and the pool, the EntityManagerFactory, the transaction manager and a working repository all exist before your first line of code runs. The promise is kept, and the cost is that the plumbing is now invisible — which is fine right up to the moment it does something you did not expect. This section makes it visible once, so that every later section can refer back to a specific piece.

The mechanism is autoconfiguration. A starter is an empty jar whose only purpose is to bring other jars in; spring-boot-starter-data-jpa pulls Spring Data JPA, Hibernate, Spring's JDBC and transaction support and HikariCP. Spring Boot then evaluates a long list of @AutoConfiguration classes, each guarded by conditions — @ConditionalOnClass (is Hibernate on the class path?), @ConditionalOnMissingBean (did the user already declare a DataSource?), @ConditionalOnProperty — and registers beans for the ones whose conditions hold. Your own @Bean always wins over an autoconfigured one of the same type, because the autoconfiguration runs after your configuration and checks for a missing bean first.

Worked example: ask the context what it built

This is the shape every program in this module follows: one @SpringBootApplication class, nested entities and repository interfaces, a CommandLineRunner bean for the demonstration, and the property map explained in "How to use this module". The runner here injects the infrastructure beans and prints facts about them, then performs one save and one query so the SQL can be read.

package lm.anatomy;

import jakarta.persistence.*;
import jakarta.persistence.metamodel.EntityType;
import org.springframework.aop.support.AopUtils;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.core.env.Environment;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.transaction.PlatformTransactionManager;
import javax.sql.DataSource;
import java.util.Arrays;
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)   // the repositories below are nested interfaces
public class BootAnatomy {

    @Entity(name = "Product")                                // nested entities need an explicit JPQL name
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        int priceInCents;                                    // becomes price_in_cents — read on
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        @Override public String toString() { return "Product[" + id + ", " + sku + ", " + priceInCents + "c]"; }
    }

    public interface ProductRepository extends JpaRepository {
        List findBySkuStartingWithOrderBySku(String prefix);   // no body: derived from the name (§3)
    }

    @Bean
    CommandLineRunner demo(DataSource dataSource, PlatformTransactionManager txManager,
                           EntityManagerFactory emf, ProductRepository repo, Environment env) {
        return args -> {
            System.out.println("-- what the starter configured --");
            System.out.println("DataSource          = " + dataSource.getClass().getSimpleName());
            System.out.println("TransactionManager  = " + txManager.getClass().getSimpleName());
            System.out.println("repository is proxy = " + AopUtils.isAopProxy(repo));
            System.out.println("proxy interfaces    = " + Arrays.stream(repo.getClass().getInterfaces())
                    .map(Class::getSimpleName).filter(n -> n.contains("Repository")).sorted().toList());
            System.out.println("entities            = " + emf.getMetamodel().getEntities().stream()
                    .map(EntityType::getName).sorted().toList());
            System.out.println("naming strategy     = " + String.valueOf(emf.getProperties().get("hibernate.physical_naming_strategy"))
                    .replaceAll(".*\\.", ""));
            System.out.println("ddl-auto            = " + env.getProperty("spring.jpa.hibernate.ddl-auto"));
            System.out.println("open-in-view        = " + env.getProperty("spring.jpa.open-in-view"));

            System.out.println("-- one save, one derived query --");
            repo.save(new Product("BOLT-7", 80));
            repo.save(new Product("NUT-3", 25));
            repo.save(new Product("BOLT-9", 95));
            System.out.println("count = " + repo.count());
            System.out.println("bolts = " + repo.findBySkuStartingWithOrderBySku("BOLT"));
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(BootAnatomy.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:anatomy;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

Read it top to bottom; every line is evidence of a decision Spring Boot made without being asked:

  • The DDL ran before the runner. Five Hibernate: lines precede the first -- heading: the schema is generated while the EntityManagerFactory is being built, which happens during context refresh, before any runner. The HTE_product temporary table is Hibernate 7's scratch table for bulk HQL on H2 (JPA §1); it will appear in every output here.
  • price_in_cents, not priceInCents. Plain Hibernate kept the Java name. Spring Boot sets Hibernate's hibernate.physical_naming_strategy to the snake-case strategy — the program read the resolved property back from the factory and printed its class, PhysicalNamingStrategySnakeCaseImpl. The sequence is product_seq for the same reason. If you ever port an application from plain Hibernate to Boot, this is the first thing that breaks against an existing schema.
  • HikariDataSource. Hibernate's built-in pool (the one JPA §1 warned about) is never used: Boot's DataSourceAutoConfiguration saw HikariCP on the class path and built a pooled data source from spring.datasource.*. The embedded H2 URL was supplied explicitly; without it, Boot would have invented a random in-memory database name.
  • JpaTransactionManager. The @Transactional machinery of §5 is already wired to the EntityManagerFactory. Nothing in the program mentioned transactions, and yet each repo.save ran in one.
  • The repository is a proxy implementing ProductRepository and Spring Data's marker Repository. There is no class called ProductRepositoryImpl anywhere; §2 opens the proxy up.
  • ddl-auto = create-drop and open-in-view = false are the values from the property map. Leave both unset and Boot would choose create-drop here too — because H2 is an embedded database — but none against PostgreSQL, and it would leave open-in-view on and print a warning about it. Those three defaults (naming, ddl-auto, open-in-view) are the whole difference between "plain Hibernate" and "Hibernate inside Boot".
  • Two sequence calls for three inserts. product_seq increments by 50, so one call should cover fifty ids. The pooled optimiser makes an extra call the first time to establish the low end of its block; after that it is one call per fifty rows (JPA §2, §9).
  • The derived query. findBySkuStartingWithOrderBySku has no body. Spring Data parsed the method name into sku like ? escape '\' order by sku — the escape clause is there because a prefix containing % or _ must not become a wildcard. Section 3 is about that grammar.

Where does a property come from?

Every program here calls setDefaultProperties, which is the lowest-priority source Spring Boot has: anything else that sets the same key wins. That is deliberate — a reader who runs these programs with --spring.jpa.show-sql=false gets what they asked for. The order itself is long and worth having internalised, because "why is this setting not taking effect?" is the most common configuration question there is.

The pieces, named

@SpringBootApplication is three annotations: @SpringBootConfiguration (a @Configuration), @ComponentScan rooted at the class's package, and @EnableAutoConfiguration. It implies nothing about JPA — @EnableJpaRepositories and @EnableTransactionManagement arrive through autoconfiguration, conditionally, and only because the starter is present. Put the class at the top of your package tree; everything below it is scanned, everything beside it is not.

The programs here add @EnableJpaRepositories(considerNestedRepositories = true) explicitly. Repositories are normally top-level interfaces and Spring Data skips nested ones by default; one file per program forces them to be nested. Writing the annotation yourself replaces Boot's — the attributes you omit (base packages) fall back to the application package, as before.

Two ways to make a bean. Stereotype scanning: annotate a class @Component, @Service or @Repository and let the scan find it — the usual choice for your own classes, and the only way @Transactional proxies (§5) get created. @Bean methods in a configuration class: you construct the object; the usual choice for third-party types and for small runners like demo() above. Both end up as singletons in the same container; both can inject anything by constructor or method parameter.

@Service                                       // found by scanning; proxied if it has @Transactional methods
public class InventoryService {
    private final ProductRepository products;  // constructor injection: final, testable, no @Autowired needed
    InventoryService(ProductRepository products) { this.products = products; }
}

@Bean CommandLineRunner demo(ProductRepository repo) { return args -> { ... }; }   // runs once, after refresh

CommandLineRunner receives the raw String[]; ApplicationRunner receives parsed ApplicationArguments. Several runners execute in @Order. A runner is ordinary code: no transaction, no persistence context — every repository call it makes is its own unit of work, which is the behaviour the SQL above shows.

Spring Data JDBC, briefly

Spring Data JPA is not the only Spring Data module that talks to a relational database. Spring Data JDBC offers the same repository interfaces over plain JDBC with no persistence context, no lazy loading, no dirty checking and no caching: an aggregate is loaded whole and saved whole. It is simpler to reason about and has none of the N+1 and LazyInitializationException failure modes of §6 — and, by the same token, none of the first-level cache, the automatic update-on-commit or the mapping flexibility of JPA. If your domain is a set of small aggregates and you are tired of ORM surprises, it is worth a look. This module stays with JPA because the warehouse's associations, locking and batching are exactly the territory where JPA earns its complexity.

Autoconfiguration gotchas
  • The application class's package is the scan root. Entities and repositories in a sibling package are invisible — the symptom is "Not a managed type" for an entity, or a NoSuchBeanDefinitionException for a repository. Fix with @EntityScan / @EnableJpaRepositories(basePackages), or move the class.
  • ddl-auto changes meaning with the database. The embedded-database default silently becomes none the day you point at PostgreSQL. Set it explicitly in every profile (§12).
  • Declaring a bean replaces the autoconfigured one — entirely. A hand-written DataSource bean means spring.datasource.* is now ignored, including the Hikari tuning you set in properties.
  • Runners run with no transaction. Each repository call commits on its own. A LazyInitializationException in a runner is this, not a mapping bug.
  • Boot's naming strategy is not Hibernate's default. Against an existing schema with camel-case columns, either set the standard physical strategy or add @Column(name) everywhere.

Check yourself

1.An entity field int priceInCents produced the column price_in_cents above, while the same entity in the JPA module produced priceInCents. What changed?

B. The program printed the resolved property: hibernate.physical_naming_strategy is PhysicalNamingStrategySnakeCaseImpl, set by HibernateJpaAutoConfiguration. Hibernate on its own uses the standard strategy, which keeps the Java name.

A is wrong: Hibernate's default has not changed between patch releases, and the JPA module's 7.4.1 output is the proof that the default keeps camel case. C describes H2's case folding of unquoted identifiers, which would give PRICEINCENTS, not add underscores. D confuses two unrelated mechanisms: method-name derivation (§3) reads entity property names and never influences the schema.

2.You remove spring.jpa.hibernate.ddl-auto from a project that works against H2 and point spring.datasource.url at PostgreSQL. The first query fails with "relation product does not exist". Why?

C. The default is computed from the data source: embedded (H2, HSQLDB, Derby in memory) gets create-drop, everything else gets none. It is the single most common "works locally, fails in staging" cause, and the fix is to set the property explicitly per profile — validate in production with a migration tool owning the schema.

A is wrong: both spellings reach Hibernate; spring.jpa.hibernate.ddl-auto is the documented one. B is invented — there is no such misdetection. D is wrong: the snake-case strategy emits lower case, and the error says the relation does not exist at all, which is a missing table rather than a case mismatch.

3.Which of these does @SpringBootApplication itself imply, without any starter on the class path? Select all that apply.

A, B and D. Those three are the annotation's definition. Everything JPA-specific — repositories, transaction management, the entity manager — is added by autoconfiguration, conditionally, when the starter's classes are present.

C is the trap: @EnableJpaRepositories is applied for you by JpaRepositoriesAutoConfiguration, which is why removing the starter silently removes your repositories rather than failing to compile. The programs here write it explicitly only to set considerNestedRepositories.

4.Every program in this module calls setDefaultProperties rather than shipping an application.properties. A reader runs one with --spring.jpa.show-sql=false. What happens?

D. Command-line arguments sit near the top of the precedence order; setDefaultProperties sits at the very bottom, below application.properties and even below @PropertySource. That is why the programs use it: anything the reader sets, anywhere, overrides it.

A inverts the order — "programmatic" is not "specific"; the method's name says what it is. B is wrong: multiple sources for one key are the normal case, resolved by precedence, never an error. C is wrong because a property has exactly one effective value for the lifetime of the environment.
