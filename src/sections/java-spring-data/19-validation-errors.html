Section 10

Validation and exception translation

Bad data reaches a data layer by two roads. Sometimes your own code produced it: a negative price, a blank SKU, a malformed e-mail. Sometimes the database refuses something that looked fine in Java: a duplicate key, a stale version, a foreign key to a row that has gone. Both deserve a clear, specific exception at the right place — and in a raw JPA application they arrive as an assortment of Hibernate, JDBC and driver types whose names change with the database you happen to run.

Spring addresses each road separately. Bean Validation (Jakarta Validation, implemented by Hibernate Validator) puts the rules on the fields — @NotBlank, @Positive, @Email or your own — and checks them both on entities when Hibernate flushes and on method parameters of any @Validated bean. Exception translation catches whatever the persistence provider throws as it leaves a repository proxy and rethrows it as one of Spring's DataAccessException subclasses, a hierarchy that means the same thing on H2, PostgreSQL and Oracle. This section provokes one of each and prints what arrives.

Worked example: five ways to be rejected

A Product with field constraints, including a custom @Sku; a @Validated service; a unique SKU column; and a @Version for the stale-update case. Every failure is caught and reported as "outer exception <- root cause". SQL echo is off for this program so the exceptions are not buried in DDL, and Hibernate's own SQL-error log category is switched off because H2's messages embed generated constraint names.

package lm.validation;

import jakarta.persistence.*;
import jakarta.validation.*;
import jakarta.validation.constraints.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.dao.DataAccessException;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.stereotype.Service;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;
import org.springframework.validation.annotation.Validated;

import java.lang.annotation.*;
import java.util.Map;
import java.util.TreeSet;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class Validation {

    /* A custom constraint: an annotation plus a validator. */
    @Documented
    @Constraint(validatedBy = SkuValidator.class)
    @Target({ElementType.FIELD, ElementType.PARAMETER})
    @Retention(RetentionPolicy.RUNTIME)
    public @interface Sku {
        String message() default "must look like ABC-123";
        Class<?>[] groups() default {};
        Class<? extends Payload>[] payload() default {};
    }
    public static class SkuValidator implements ConstraintValidator<Sku, String> {
        @Override public boolean isValid(String value, ConstraintValidatorContext ctx) {
            return value == null || value.matches("[A-Z]+-\\d+");      // null is @NotBlank's job, not ours
        }
    }

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @NotBlank @Size(max = 16) @Sku
        @Column(nullable = false, unique = true, length = 16) String sku;
        @Positive int priceInCents;
        @Email String supplierContact;
        @Version long version;
        protected Product() {}
        Product(String sku, int priceInCents, String supplierContact) {
            this.sku = sku; this.priceInCents = priceInCents; this.supplierContact = supplierContact;
        }
        @Override public String toString() { return sku + "=" + priceInCents + "c v" + version; }
    }

    public interface ProductRepository extends JpaRepository<Product, Long> {}

    public static class ProductNotFound extends RuntimeException {
        ProductNotFound(long id) { super("no product with id " + id); }
    }

    /* A service with method validation: @Validated on the class, @Valid / constraints on parameters. */
    @Service
    @Validated
    public static class CatalogService {
        private final ProductRepository repo;
        CatalogService(ProductRepository repo) { this.repo = repo; }

        public Product reprice(@Positive long id, @Min(1) @Max(1_000_000) int newPrice) {
            Product p = repo.findById(id).orElseThrow(() -> new ProductNotFound(id));
            p.priceInCents = newPrice;
            return repo.save(p);
        }
        public Product register(@Valid Product p) { return repo.save(p); }
    }

    static String rootOf(Throwable t) {
        while (t.getCause() != null && t.getCause() != t) t = t.getCause();
        return t.getClass().getSimpleName();
    }
    static void report(String label, Throwable t) {
        System.out.println(label + ": " + t.getClass().getSimpleName() + " <- root " + rootOf(t));
    }
    static void violations(Throwable t) {
        while (t != null && !(t instanceof ConstraintViolationException)) t = t.getCause();
        if (t == null) { System.out.println("  (no ConstraintViolationException in the chain)"); return; }
        TreeSet<String> lines = new TreeSet<>();
        for (ConstraintViolation<?> v : ((ConstraintViolationException) t).getConstraintViolations()) {
            lines.add("  " + v.getPropertyPath() + ": " + v.getMessage());
        }
        lines.forEach(System.out::println);
    }

    @Bean CommandLineRunner demo(ProductRepository repo, CatalogService catalog, PlatformTransactionManager txm) {
        return args -> {
            System.out.println("-- 1. entity constraints are checked at flush --");
            try {
                repo.save(new Product("bolt 7", -5, "not-an-email"));
            } catch (RuntimeException e) {
                report("save", e);
                violations(e);
            }

            System.out.println("-- 2. method validation on a service --");
            try {
                catalog.reprice(-1, 0);
            } catch (RuntimeException e) {
                report("reprice", e);
                violations(e);
            }
            try {
                catalog.register(new Product("", 10, null));
            } catch (RuntimeException e) {
                report("register", e);
                violations(e);
            }

            System.out.println("-- 3. a valid product, then a duplicate --");
            Product ok = repo.save(new Product("BOLT-7", 80, "sales@acme.example"));
            System.out.println("saved " + ok);
            try {
                repo.saveAndFlush(new Product("BOLT-7", 90, null));
            } catch (DataAccessException e) {
                System.out.println("duplicate: " + e.getClass().getSimpleName()
                        + " <- most specific " + e.getMostSpecificCause().getClass().getSimpleName());
            }

            System.out.println("-- 4. missing rows --");
            try {
                catalog.reprice(999, 100);
            } catch (ProductNotFound e) {
                System.out.println("lookup: " + e.getClass().getSimpleName() + " (" + e.getMessage() + ")");
            }
            repo.deleteById(999L);
            System.out.println("deleteById(999) threw: false");

            System.out.println("-- 5. a stale update is translated --");
            TransactionTemplate tx = new TransactionTemplate(txm);
            Product stale = tx.execute(s -> repo.findById(ok.id).orElseThrow());       // detached copy, version 0
            tx.executeWithoutResult(s -> repo.findById(ok.id).orElseThrow().priceInCents = 85);  // someone else commits first
            try {
                stale.priceInCents = 70;
                repo.save(stale);                                                        // merge + flush → stale version
            } catch (RuntimeException e) {
                report("stale save", e);
            }
            System.out.println("db now " + repo.findById(ok.id).orElseThrow());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Validation.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:validation;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "false",
            "spring.jpa.open-in-view", "false",
            "logging.level.org.hibernate.orm.jdbc.error", "OFF"));   // H2 names its constraints; keep them out of stdout
        app.run(args).close();
    }
}

Five lessons, one per block:

  1. Entity constraints run at flush, so they surface at commit. Hibernate Validator hooks into Hibernate's pre-insert and pre-update events. repo.save only queued the insert; the flush happened as the repository's transaction committed, the validator threw ConstraintViolationException there, and Spring's transaction manager reported the failed commit as TransactionSystemException. If you catch only the inner type, you miss it. The three violations are printed sorted: @Sku, @Positive and @Email all failed, and they are reported together, not one at a time.
  2. Method validation runs before the method body. @Validated on the class makes Spring wrap the bean in a proxy that validates parameters on every call, so reprice(-1, 0) never reached findById. The violation paths read reprice.arg0: the build compiles without -parameters, so the real names are not in the bytecode. Spring Boot's Maven and Gradle plugins add that flag, and you would then see reprice.id. @Valid on register's parameter cascaded into the Product, which is why its field rules fired — two of them for the blank SKU.
  3. A duplicate key is translated. saveAndFlush forced the insert inside the repository call, H2 refused it, and what came out of the repository proxy was DataIntegrityViolationException — a Spring type you can catch on any database. getMostSpecificCause() still reaches the driver's own exception when you need the detail.
  4. Missing rows are your decision. findById returns an Optional; turning absence into a domain exception (ProductNotFound) is the service's job. deleteById of a missing id is silently ignored since Spring Data 3 — earlier versions threw EmptyResultDataAccessException, and code that relied on that now quietly succeeds.
  5. A stale update is translated too. The detached copy still had version 0; another transaction had already moved the row to version 1. save merged and flushed, Hibernate's where id=? and version=? matched no row, and Hibernate's StaleObjectStateException came out of the proxy as ObjectOptimisticLockingFailureException, a subclass of OptimisticLockingFailureException. The first writer's 85 cents survived.

Match the failure to what you catch

Each situation reaches your service code through a repository or a transactional method. What arrives?

All four correct. Constraint breaches from the database are DataIntegrityViolationException; version conflicts are ObjectOptimisticLockingFailureException; misuse of the API (here, a bulk update with no transaction to run in, which JPA reports as TransactionRequiredException) is InvalidDataAccessApiUsageException; and a validation failure that only happens at flush-on-commit is reported by the transaction manager as TransactionSystemException, with the ConstraintViolationException as its cause.

Validate at the boundary first. The request DTO a controller receives is where a user's mistake should be caught and reported field by field, before any transaction opens. Validate entities as the last line. Constraints on the entity catch bugs inside your own code — a service that computes a negative price — but they fire at flush, possibly at commit, far from the code that caused them.

  • @Valid (Jakarta) cascades into an object's fields; @Validated (Spring) on a class turns on method validation and can select groups, such as OnCreate versus OnUpdate.
  • Messages are interpolated from ValidationMessages.properties, so {jakarta.validation.constraints.Positive.message} can be translated without touching code.
  • Keep the database constraint too. Bean Validation cannot see other rows, so uniqueness is only ever enforced reliably by a unique index — a @Unique-style validator that runs a query has a race between the check and the insert.

Spring Data repositories are translated automatically: their proxies include a PersistenceExceptionTranslationInterceptor. Your own classes opt in by carrying @Repository, which PersistenceExceptionTranslationPostProcessor (registered by Spring Boot) wraps the same way.

The interceptor asks each PersistenceExceptionTranslator in the context — for JPA, the EntityManagerFactory bean, which delegates to Hibernate's dialect-aware SQL state mapping — to convert the exception. That is why a raw entityManager.flush() in a plain @Component throws Hibernate's own ConstraintViolationException, while the same failure through repo.saveAndFlush arrives as DataIntegrityViolationException (§11 shows exactly this).

Note the name clash: org.hibernate.exception.ConstraintViolationException (a database constraint) and jakarta.validation.ConstraintViolationException (a Bean Validation rule) are unrelated types with the same simple name. Import carefully.

  • Translate at the service edge. Catch DataIntegrityViolationException where you know what it means — registering a product — and throw SkuAlreadyExists. Callers should not have to know about constraints.
  • Retry only what can succeed on a retry. Optimistic and pessimistic locking failures can; integrity violations and API misuse cannot. A retry must start a new transaction, so it wraps the transactional method from outside (spring-retry's @Retryable, or a loop around a REQUIRES_NEW call as in §5), and the operation must be safe to repeat.
  • In a web layer a @ControllerAdvice maps domain exceptions to HTTP statuses — 409 for conflicts, 400 for validation, 404 for not found — so controllers stay free of try/catch. Spring MVC is out of scope here, but the mapping is only possible because the data layer threw specific types.
Validation and translation gotchas
  • The exception arrives at commit, wrapped. Entity validation fires at flush; if the flush is the commit, you get TransactionSystemException. Catching ConstraintViolationException around save alone catches nothing.
  • Method validation needs the proxy. @Validated constraints are ignored on self-invocation and on private methods, for the same reason @Transactional is (§5).
  • arg0 in messages means no -parameters. Builds outside Spring Boot's plugins often omit the flag; violation paths, @PathVariable without a name and @Param-less queries all depend on it.
  • A transaction that saw an exception is finished. After a DataIntegrityViolationException inside a @Transactional method, the transaction is marked rollback-only even if you catch the exception. Further work in it is wasted, and the commit raises UnexpectedRollbackException.
  • Do not log and rethrow at every layer. One stack trace per failure, at the edge that handles it; the translated exception keeps the original as its cause.

Check yourself

1.Outside any transaction, you call repo.save(new Product("BOLT-7", -5)) on an entity whose price is @Positive and whose id is SEQUENCE-generated. What do you catch?

C. Step 1 of the worked example printed exactly this. The repository opened its own transaction; persist only queued the insert; validation ran at flush, which happened during commit; the transaction manager wrapped the failed commit.

A would be true if validation ran at persist, but Hibernate validates on the pre-insert event at flush. B: the validator runs in the pre-insert event and stops the insert before the database ever sees the row, so no database constraint gets the chance to fire. D: Hibernate Validator is on the class path, so entity validation is on automatically.

2.A plain @Component (not @Repository) injects an EntityManager, persists a duplicate SKU and calls em.flush(). What reaches its caller?

B. Translation happens in an interceptor on repository proxies and on @Repository beans. A @Component has none, so Hibernate's exception passes through as-is. §11's harness hit exactly this until it switched to repo.saveAndFlush.

A overstates translation; it is opt-in by stereotype. C is the Bean Validation type with the same simple name — a different thing entirely. D: Hibernate already wrapped the JDBC exception in its own type before it left flush.

3.Which failures is it reasonable to retry automatically in a fresh transaction? Select all that apply.

A and C. Both are contention: another transaction got there first, and a fresh attempt that re-reads current state can succeed. The retry must wrap the transaction from outside and the operation must be safe to repeat.

B will fail identically every time — the SKU still exists — so it belongs in a domain error. D is a bug in the code; retrying only repeats it.
