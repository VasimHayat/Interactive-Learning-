Section 8

Auditing, lifecycle and domain events

Two questions every warehouse eventually asks of its database: who changed this row and when, and what else should happen when it changes. Both are cross-cutting — they apply to dozens of entities and belong to none of them — and both have a tempting wrong answer: setting updatedAt = Instant.now() by hand in every service method, and calling the e-mail sender from inside the one that saves the order. Spring Data gives each question a declarative answer that sits next to the entity and runs at exactly the right moment in the transaction.

For the first, auditing: four annotations on four fields, an AuditorAware that says who the current user is, and a JPA entity listener that fills them in before every insert and update. For the second, domain events: an aggregate root records that something happened, the repository publishes it when the aggregate is saved, and listeners choose whether to run inside the transaction or only after it has committed — which is the difference between an e-mail about an order that exists and one about an order that was rolled back.

Worked example: stamps and events

The DateTimeProvider bean is the one unusual thing here. Auditing normally calls Instant.now(); this program replaces it with a clock that ticks one second per call so the printed stamps are reproducible. That is not a trick for the page — it is exactly what you do in tests, and it is why the stamps below can be read rather than merely asserted non-null.

package lm.auditing;

import jakarta.persistence.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.annotation.Bean;
import org.springframework.context.event.EventListener;
import org.springframework.data.annotation.CreatedBy;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedBy;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.auditing.DateTimeProvider;
import org.springframework.data.domain.AbstractAggregateRoot;
import org.springframework.data.domain.AuditorAware;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaAuditing;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;
import java.time.Instant;
import java.time.temporal.TemporalAccessor;
import java.util.*;
import java.util.concurrent.atomic.AtomicInteger;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
@EnableJpaAuditing(auditorAwareRef = "auditor", dateTimeProviderRef = "clock")
public class Auditing {

    // who: in a real application this reads the security context
    @Bean AuditorAware auditor() { return () -> Optional.of("picker-42"); }

    // when: a fixed, ticking clock so the stamps are reproducible (tests do the same)
    @Bean DateTimeProvider clock() {
        AtomicInteger tick = new AtomicInteger();
        return () -> Optional.of(Instant.parse("2026-10-15T09:00:00Z").plusSeconds(tick.getAndIncrement()));
    }

    @MappedSuperclass
    @EntityListeners(AuditingEntityListener.class)
    public static abstract class Auditable {
        @CreatedDate Instant createdAt;
        @LastModifiedDate Instant updatedAt;
        @CreatedBy String createdBy;
        @LastModifiedBy String updatedBy;
    }

    static final AtomicInteger prePersist = new AtomicInteger(), postLoad = new AtomicInteger();

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product extends Auditable {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true, length = 16) String sku;
        int priceInCents;
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        @PrePersist void beforeInsert() { prePersist.incrementAndGet(); }      // JPA callback, independent of Spring
        @PostLoad void afterLoad() { postLoad.incrementAndGet(); }
        void setPriceInCents(int p) { priceInCents = p; }
    }

    public record OrderPlaced(String reference) {}

    @Entity(name = "Order")
    @Table(name = "orders")
    public static class Order extends AbstractAggregateRoot {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Column(nullable = false, unique = true) String reference;
        protected Order() {}
        Order(String reference) { this.reference = reference; }
        Order place() { registerEvent(new OrderPlaced(reference)); return this; }   // collected, published by save()
    }

    public interface ProductRepository extends JpaRepository {}
    public interface OrderRepository extends JpaRepository {}

    @Component
    public static class Listeners {
        final List log = Collections.synchronizedList(new ArrayList<>());
        @EventListener
        void inTransaction(OrderPlaced e) { log.add("inside tx: " + e.reference()); }
        @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
        void afterCommit(OrderPlaced e) { log.add("after commit: " + e.reference()); }
        List drain() { List out = new ArrayList<>(log); Collections.sort(out); log.clear(); return out; }
    }

    @Service
    public static class OrderService {
        private final OrderRepository orders;
        OrderService(OrderRepository orders) { this.orders = orders; }
        @Transactional public void place(String ref) { orders.save(new Order(ref).place()); }
        @Transactional public void placeAndFail(String ref) {
            orders.save(new Order(ref).place());
            throw new IllegalStateException("payment declined");                 // RuntimeException → rollback
        }
    }

    @Bean CommandLineRunner demo(ProductRepository products, OrderService service, Listeners listeners, ApplicationEventPublisher publisher) {
        return args -> {
            System.out.println("-- A: auditing stamps on insert --");
            Product p = products.save(new Product("BOLT-7", 80));
            Product loaded = products.findById(p.id).orElseThrow();
            System.out.println("createdBy = " + loaded.createdBy + ", createdAt = " + loaded.createdAt);
            System.out.println("updatedAt == createdAt: " + loaded.updatedAt.equals(loaded.createdAt));

            System.out.println("-- B: stamps on update --");
            loaded.setPriceInCents(95);
            Product after = products.findById(products.save(loaded).id).orElseThrow();
            System.out.println("updatedBy = " + after.updatedBy + ", updatedAt = " + after.updatedAt);
            System.out.println("updatedAt after createdAt: " + after.updatedAt.isAfter(after.createdAt));
            System.out.println("callbacks: prePersist = " + prePersist.get() + ", postLoad = " + postLoad.get());

            System.out.println("-- C: a domain event, committed --");
            service.place("ORD-1");
            System.out.println(listeners.drain());

            System.out.println("-- D: a domain event, rolled back --");
            try { service.placeAndFail("ORD-2"); } catch (IllegalStateException e) { System.out.println("caught " + e.getMessage()); }
            System.out.println(listeners.drain());

            System.out.println("-- E: published directly, outside any transaction --");
            publisher.publishEvent(new OrderPlaced("ORD-3"));
            System.out.println(listeners.drain());
        };
    }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Auditing.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:auditing;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

  • A. One save on a new entity: the AuditingEntityListener's @PrePersist callback filled all four fields before the insert ran — look at the insert's column list. The clock was asked once, so createdAt and updatedAt are the same instant: a new row is "last modified" at creation.
  • B. save on an existing entity is a merge (§2): the select loads the current row, the listener's @PreUpdate stamps updatedAt/updatedBy only, and the update writes every column because Hibernate updates all columns by default. The clock ticked once more, so updatedAt is one second later. The counters show plain JPA callbacks running alongside: one @PrePersist, three @PostLoads for the three selects.
  • C. place() only records the event; orders.save() publishes it. The @EventListener ran immediately, inside the still-open transaction; the @TransactionalEventListener(AFTER_COMMIT) ran after the commit. The output is sorted, because listener order is not a contract.
  • D. Same save, then an exception: the transaction rolled back. Notice there is no insert at all — the flush never happened — yet the in-transaction listener had already run on a row that would never exist. The after-commit listener, correctly, did not. That asymmetry is the whole reason the second phase exists.
  • E. Published by hand with no transaction. The plain listener runs; the transactional one does not, because there is no transaction to attach to. That is the default and it surprises people in batch jobs and tests — see fallbackExecution below.

When does each one run?

Drag each annotation onto the moment it fires, or click one then the other

All four. The two auditing stamps are JPA callbacks under the hood (AuditingEntityListener implements @PrePersist and @PreUpdate), so they fire at flush time, inside the transaction. The two event listeners differ only in when: one during publication, the other at a transaction phase. Choose the phase by asking "must this only happen if the data is really there?"

Event and auditing gotchas
  • An AFTER_COMMIT listener cannot write in the committed transaction. It runs with the transaction's resources still bound but the transaction finished; a repository call inside it joins a transaction that will never commit again, and the write is silently lost. Annotate the listener @Transactional(propagation = Propagation.REQUIRES_NEW), or hand the work to a queue.
  • Phase D is the e-mail bug. An @EventListener that sends "your order is confirmed" has sent it for ORD-2, which was rolled back. Anything with an external side effect belongs in AFTER_COMMIT — or, if it must not be lost when the process dies between commit and send, in an outbox row written inside the transaction and delivered by a separate poller. Spring Modulith's @ApplicationModuleListener packages that pattern.
  • @Async plus @TransactionalEventListener loses the context twice. The listener runs on another thread with no transaction and no security context; AuditorAware returns empty and lazy loading fails. Pass ids in the event, not entities.
  • Events only fire through save. Dirty checking at commit writes the aggregate's changes without calling the repository, so a method that mutates an aggregate and registers an event but never calls save publishes nothing. Call save explicitly when you register events.
  • @CreatedBy is null when nobody is logged in. Batch jobs and startup runners have no principal; either an AuditorAware that falls back to "system", or a nullable column with that meaning. Decide, then write it down.
  • Auditing columns are not history. They say who touched the row last; for what changed and the previous values you need Hibernate Envers (@Audited, shadow _aud tables) or an explicit event log. Envers is not on this class path and is out of scope, but it is the right next tool.

Check yourself

1.In phase D the transaction rolls back after save, yet the output shows inside tx: ORD-2 and no insert statement. Why both?

B. Two JPA facts combine: persist only schedules the insert (JPA §3, write-behind), and the sequence value was fetched eagerly for the id — which is why select next value appears and insert does not. Meanwhile the event was published the moment save returned, inside the transaction, and the plain listener acted on it.

A: show-sql prints every statement Hibernate executes, committed or not; none ran. C: publication happens after the delegate save, in the repository proxy. D: listeners are synchronous on the calling thread unless annotated @Async.

2.An @TransactionalEventListener(phase = AFTER_COMMIT) receives OrderPlaced and calls auditLog.save(new AuditEntry(…)). No exception is thrown, but the audit table stays empty. What is wrong?

C. The documented trap: at AFTER_COMMIT the synchronization still runs within the scope of the completed transaction, so a plain @Transactional (REQUIRED) joins it and its work is discarded. REQUIRES_NEW opens a real second transaction.

A: they can, with a new transaction. B: clearing the aggregate's list does not affect an event already handed to the publisher. D: AbstractAggregateRoot is about publishing events, not about being saveable.

3.Which of the following are true of Spring Data auditing as configured in the worked example? Select all that apply.

A and D. Bulk JPQL updates bypass the persistence context and its callbacks (JPA §6), so audited columns must be set in the statement itself. And the provider bean is precisely the hook this program uses — the printed stamps are proof.

B: the timestamp comes from the application's DateTimeProvider (JVM clock by default), which is why clock skew between instances is a real concern and why some teams use a database default instead. C: the save would join the finished transaction and be lost, the trap in question 2 — with REQUIRES_NEW it would stamp correctly.
