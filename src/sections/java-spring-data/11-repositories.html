Section 2

Repositories: from CrudRepository to JpaRepository

In §1 the repository was an interface with no implementation, and yet repo.save inserted a row. Somebody wrote that body. At startup Spring Data finds every interface that extends Repository, and for each one builds a JDK proxy whose method calls are routed to one of three places: a base implementation (SimpleJpaRepository, which holds an EntityManager and implements save, findById, delete and the rest), a query method generated from the method's name or annotation (§3, §4), or a fragment you implement by hand. Knowing which of the three is behind a call is most of what there is to know about repositories — because the base implementation is ordinary JPA code, and every one of its decisions is something the JPA module already taught.

The interfaces form a ladder. You pick the rung whose methods you want to expose, not the most powerful one available:

Spring Data repository interfaces and what each adds
InterfaceAddsUse it when
Repository<T, ID>nothing — a markeryou want to expose only the query methods you declare, e.g. a read-only reference-data repository
CrudRepository / ListCrudRepositorysave, findById, findAll, count, delete*, existsById (the List variant returns List instead of Iterable)the usual aggregate root
PagingAndSortingRepository / List…findAll(Sort), findAll(Pageable)you page or sort the whole table (§7)
JpaRepositoryflush, saveAndFlush, saveAllAndFlush, getReferenceById, deleteAllInBatch, deleteAllByIdInBatch, plus Query by Exampleyou need JPA-specific operations — which in practice is most of the time

Every method you inherit is a method a caller can use. A repository for an append-only audit log that extends JpaRepository has a deleteAllInBatch() on it, whether you meant to offer one or not. Narrowing the interface is cheap API design.

Worked example: what each method actually sends

One application, two entities, and a runner that calls the repository methods people most often misjudge. Product has a generated id and a @Version; Tag has an assigned String id and implements Persistable. The runner is not transactional, so unless a TransactionTemplate wraps a block, every repository call is its own transaction — a detail that explains several lines of the output.

package lm.repos;

import jakarta.persistence.*;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.data.domain.Persistable;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.data.repository.NoRepositoryBean;
import org.springframework.transaction.support.TransactionTemplate;
import java.util.Arrays;
import java.util.List;
import java.util.Map;

@SpringBootApplication
@EnableJpaRepositories(considerNestedRepositories = true)
public class Repositories {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;
        @Version Long version;                                   // save() looks at this first
        @Column(nullable = false, unique = true, length = 16) String sku;
        int priceInCents;
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        static Product detached(Long id, Long version, String sku, int price) {   // a row we hold without a context
            Product p = new Product(sku, price); p.id = id; p.version = version; return p;
        }
        String sku() { return sku; }
        @Override public String toString() { return "Product[" + id + ", v" + version + ", " + sku + ", " + priceInCents + "c]"; }
    }

    /* An assigned id gives save() nothing to go on: id is never null, there is
       no @Version. Persistable lets the entity say whether it is new. */
    @Entity(name = "Tag")
    @Table(name = "tag")
    public static class Tag implements Persistable {
        @Id String code;
        String label;
        @Transient private boolean isNew = true;
        protected Tag() {}
        Tag(String code, String label) { this.code = code; this.label = label; }
        @Override public String getId() { return code; }
        @Override public boolean isNew() { return isNew; }
        @PostPersist @PostLoad void markNotNew() { isNew = false; }
    }

    @NoRepositoryBean
    public interface BaseRepository extends JpaRepository {   // shared signatures, no bean of its own
        List findAllSortedById();
    }

    public interface ProductRepositoryCustom { List cheaperThan(int cents); }

    public static class ProductRepositoryCustomImpl implements ProductRepositoryCustom {   // a fragment: hand-written body
        @PersistenceContext EntityManager em;
        @Override public List cheaperThan(int cents) {
            return em.createQuery("select p from Product p where p.priceInCents < :c order by p.sku", Product.class)
                     .setParameter("c", cents).getResultList();
        }
    }

    public interface ProductRepository extends JpaRepository, ProductRepositoryCustom {}
    public interface TagRepository extends JpaRepository {}

    @Bean
    CommandLineRunner demo(ProductRepository products, TagRepository tags, TransactionTemplate tx) {
        return args -> {
            System.out.println("-- the hierarchy --");
            System.out.println("JpaRepository extends " + Arrays.stream(JpaRepository.class.getInterfaces())
                    .map(Class::getSimpleName).sorted().toList());

            System.out.println("-- save: new entity (id null) --");
            Product bolt = products.save(new Product("BOLT-7", 80));
            System.out.println("saved " + bolt);

            System.out.println("-- save: detached entity (id and version set) --");
            Product copy = Product.detached(bolt.id, bolt.version, "BOLT-7", 85);
            Product merged = products.save(copy);
            System.out.println("merged == copy: " + (merged == copy) + ", merged = " + merged);

            System.out.println("-- save: looks detached, but the row does not exist --");
            try {
                products.save(Product.detached(404L, 0L, "GHOST-1", 1));
            } catch (RuntimeException e) {
                System.out.println("threw " + e.getClass().getSimpleName() + " caused by " + rootCause(e).getClass().getSimpleName());
            }

            System.out.println("-- save: Persistable decides --");
            Tag fast = tags.save(new Tag("FAST", "fast mover"));
            fast.label = "fast-moving";
            tags.save(fast);
            System.out.println("tags = " + tags.count());

            System.out.println("-- reads --");
            System.out.println("findById       = " + products.findById(bolt.id).map(Product::toString).orElse("none"));
            System.out.println("findById(404)  = " + products.findById(404L).isPresent());
            tx.executeWithoutResult(status -> {
                Product ref = products.getReferenceById(bolt.id);
                System.out.println("reference type = " + (ref.getClass() == Product.class ? "Product" : "a Hibernate proxy") + " (no select yet)");
                System.out.println("field read     = " + ref.sku + " (a field read bypasses the proxy)");
                System.out.println("getter read    = " + ref.sku());
            });
            System.out.println("existsById     = " + products.existsById(bolt.id));

            System.out.println("-- saveAndFlush inside a transaction --");
            tx.executeWithoutResult(status -> {
                products.save(new Product("NUT-3", 25));
                System.out.println("after save: nothing sent yet");
                products.saveAndFlush(new Product("CAM-9", 2300));
                System.out.println("after saveAndFlush: both inserts sent");
            });

            System.out.println("-- the custom fragment --");
            System.out.println("cheaperThan(100) = " + products.cheaperThan(100));

            System.out.println("-- deletes --");
            products.deleteById(bolt.id);
            System.out.println("remaining = " + products.count());
            products.deleteAllInBatch();
            System.out.println("remaining = " + products.count());
        };
    }

    static Throwable rootCause(Throwable t) { while (t.getCause() != null) t = t.getCause(); return t; }

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(Repositories.class);
        app.setDefaultProperties(Map.of(
            "spring.main.web-application-type", "none",
            "spring.main.banner-mode", "off",
            "spring.main.log-startup-info", "false",
            "logging.level.root", "WARN",
            "logging.pattern.console", "%level %logger{0}: %msg%n",
            "spring.datasource.url", "jdbc:h2:mem:repos;DB_CLOSE_DELAY=-1",
            "spring.jpa.hibernate.ddl-auto", "create-drop",
            "spring.jpa.show-sql", "true",
            "spring.jpa.open-in-view", "false"));
        app.run(args).close();
    }
}

Read it block by block:

  
    
    
  • The hierarchy. JpaRepository extends ListCrudRepository, ListPagingAndSortingRepository and QueryByExampleExecutor (§9) — the table above, read off the class itself.
    • 
    
  • A new entity: sequence call, insert, no select. save asked "is this entity new?", decided yes, and called em.persist. The insert appears straight away rather than at some later flush because the call was its own transaction, and the transaction committed as save returned. The returned object is the same instance you passed in, now with id = 1 and version = 0.
    • 
    
  • A detached copy: select, then update. The copy carried an id and a version, so save decided it was not new and called em.merge — which loads the row (the select), copies your state onto the managed instance, and the commit's dirty check writes it (the update, guarded by and version=?). Note merged == copy: false: merge returns a different, managed instance, exactly as JPA §3 showed. The version is now 1 on the returned object; the copy you still hold says 0.
    • 
    
  • A copy whose row does not exist. Same decision — id and version set, so merge — but the select finds nothing. Because the entity is versioned, Hibernate does not treat the missing row as "insert it": it concludes another transaction deleted it and throws StaleObjectStateException, which Spring translates into its own ObjectOptimisticLockingFailureException (§10 covers the translation). Without @Version, the same call would have inserted a new row with whatever id the copy carried — usually not what anybody wanted.
    • 
    
  • Persistable decides for Tag. An assigned id is never null, and Tag has no version, so neither of the usual signals can tell a new tag from an existing one. Implementing Persistable hands the decision to the entity: isNew() starts true, so the first save is a plain insert with no select. A @PostPersist/@PostLoad callback flips the flag, so the second save merges — select, then update.
    • 
    
  • findById always selects, and returns Optional; a missing id is an empty Optional, not an exception. Each call ran in a separate transaction with a fresh persistence context, so the second read of the same id hit the database again.
    • 
    
  • getReferenceById sent nothing. It returned a Hibernate proxy — a generated subclass of Product — without touching the database. Then the surprise: reading the field ref.sku printed null. The proxy is a subclass instance whose own fields are never populated; only method calls are intercepted and forwarded to the real, lazily loaded entity. The getter ref.sku() triggered the select and returned BOLT-7. The block needed a TransactionTemplate: outside a transaction the persistence context would be gone before the getter ran (JPA §5).
    • 
    
  • existsById is a count(*), never a full row load.
    • 
    
  • save inside a transaction defers the insert. Within the template, save(NUT-3) fetched an id (the sequence call) but sent no insert — persist only queues the action. saveAndFlush(CAM-9) then flushed the whole persistence context, and both inserts went out. CAM-9 needed no sequence call of its own: the block of fifty fetched for NUT-3 covered it.
    • 
    
  • The fragment. cheaperThan is a method no naming convention could produce. ProductRepositoryCustomImpl holds its body; Spring Data found it by the interface name plus the Impl postfix and wired it into the proxy, so callers see one repository.
    • 
    
  • Two deletes, two shapes. deleteById loads the entity (select) and removes it through the persistence context, so the delete carries and version=? and any cascades, orphan removal and @PreRemove callbacks run. deleteAllInBatch is a single bulk delete from product: no select, no version check, no cascades, no callbacks.

Proxies, transactions and fragments


  
Every repository method is transactional. SimpleJpaRepository is annotated @Transactional(readOnly = true) at class level and plain @Transactional on its write methods. Called from code that has no transaction, each call opens and commits its own — which is why every save in the worked example produced SQL at once. Called from inside a @Transactional service (§5), the repository joins the caller's transaction and the SQL waits for that transaction's flush. Same call, different timing, and the difference is entirely in the caller. Your own query methods inherit the read-only default; a @Modifying query method needs its own @Transactional (§4).


  
Fragments compose. A repository interface may extend any number of fragment interfaces; for each, Spring Data looks for a class named after the fragment interface plus Impl (the postfix is configurable) and routes those methods to it. Fragments are ordinary beans, so they can inject an EntityManager, a JdbcClient or anything else. A fragment method with the same signature as a base method overrides it — which is how you replace, say, save for one aggregate without touching the others.


  
Shared signatures without a bean. BaseRepository in the example is marked @NoRepositoryBean: it is a building block that other repository interfaces extend, and Spring Data must not try to create a repository for it on its own (it has no concrete entity type). Nothing in this program extends it; it is there to show the shape. @RepositoryDefinition(domainClass = …, idClass = …) is the opposite tool: it makes a plain interface a repository without extending anything, so it exposes exactly the methods you write.


  
Return types. Single results come back as Optional<T> or as T (then null for "no row"); collections as List, Iterable, Streamable or Stream (the last one must be consumed inside a transaction and closed — §4). Prefer Optional for anything a caller might look up by user input. An application with two databases declares two @EnableJpaRepositories blocks, each with its own basePackages, entityManagerFactoryRef and transactionManagerRef; that is the only time the repository infrastructure needs configuring by hand.


  
Why flush is on the interface. Most code never needs it: the commit flushes. You need it when the database must see the change before the transaction ends — to trip a unique constraint now rather than at commit, so the exception surfaces where you can handle it, or before a native query that reads the same table. saveAndFlush is save followed by flush; as the output showed, it flushes everything pending, not just the entity you passed.

Repository gotchas

      
    
        
  • Use the object save returns. For a new entity it is the same instance; for anything merged it is a different one. Code that ignores the return value works for inserts and silently keeps a stale, detached object for updates.
    • 
        
  • Calling save on a managed entity is redundant. Inside a transaction, a loaded entity is already tracked; changing a field is enough and the commit's dirty check writes it. The extra save is harmless but suggests the author thinks it is required — and in a long loop with detached entities it turns into a select per row.
    • 
        
  • Assigned ids need Persistable or a @Version. Otherwise every save of a new entity is a merge: one extra select per insert, and a batch import twice as chatty as it needs to be.
    • 
        
  • A proxy's fields are empty. Code that reads entity fields directly — from equals, from a mapper, from a test — sees null on a reference or a lazy association. Access state through methods; it is one more reason entity equals should use getters (§11 of the JPA module).
    • 
        
  • deleteAllInBatch and deleteAllByIdInBatch skip the domain model. No cascades, no orphan removal, no @PreRemove, no auditing — and managed instances of the deleted rows stay in any open persistence context, stale. Fast, and only correct when nothing depends on those hooks.
