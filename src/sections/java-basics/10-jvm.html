Section 1

How Java runs your code

Java is neither purely compiled nor purely interpreted, and almost every confusing thing about the toolchain follows from that. Your source is compiled ahead of time into bytecode — a portable instruction set for a machine that does not exist — and then a real machine, the JVM, loads that bytecode, starts interpreting it, and progressively compiles the hot parts to native code while the program runs.

That two-stage design is why a .class file built on your laptop runs unmodified on a Linux server, and why a long-running Java service is often faster after a few minutes than it was at startup.

The mental model

JDK, JRE, JVM — which is which

These three names get used interchangeably in conversation and they are not interchangeable at all. Each one contains the next.

Java Development Kit — everything needed to build Java, which includes everything needed to run it.

  • javac, the compiler that turns .java into .class
  • jar, javadoc, jshell, jlink, and the diagnostic tools (jstack, jmap, jcmd)
  • a complete JRE inside it

Install this one. Since Java 11 there is no separate JRE download from most vendors, and a JDK is what every build tool expects.

Java Runtime Environment — everything needed to run a compiled program, and nothing needed to build one.

  • the JVM itself
  • the standard class library: java.lang, java.util, java.io, and the rest
  • no javac

If java -version works but javac -version says "command not found", you have a JRE. That is the single most common setup problem for people new to Java.

Java Virtual Machine — the specification, and the process that implements it. This is the part that actually executes bytecode.

  • loads and verifies classes, then interprets their bytecode
  • manages the heap and runs the garbage collector
  • JIT-compiles hot methods to native instructions

The JVM is not Java-specific. Kotlin, Scala, Clojure and Groovy all compile to the same bytecode and run on the same machine.

Worked example

The whole cycle, with the smallest program that touches both a reference type and a primitive. Save it as InventoryStart.java — the file name must match the public class name exactly, including case.

public class InventoryStart {
    public static void main(String[] args) {
        String sku = "BOLT-7";
        int onHand = 42;
        System.out.println("SKU " + sku + " has " + onHand + " units on hand.");
        System.out.println("Running on Java " + System.getProperty("java.specification.version"));
    }
}
  
javac InventoryStart.java   # produces InventoryStart.class
java InventoryStart         # note: no .class extension
  
SKU BOLT-7 has 42 units on hand.
Running on Java 21

That second line is not decoration. This module's build compiled and ran this exact program on the JDK it documents, and captured what it printed — which is how you know the "Java 21" claim on this page is true.

Gotchas that cost beginners an afternoon
  • java InventoryStart.class fails. The launcher takes a class name, not a file name. You will get ClassNotFoundException: InventoryStart.class because it looks for a class literally called class in a package called InventoryStart.
  • The file name must match the public class. class InventoryStart in Start.java is a compile error: class InventoryStart is public, should be declared in a file named InventoryStart.java.
  • main must be exactly that signature. Drop static, or take String instead of String[], and the class compiles fine but the launcher fails at runtime with Main method not found in class InventoryStart. The compiler has no idea you intended that method to be an entry point.
  • "Compiles" and "runs" are separate failures. A missing semicolon is a javac error. A missing class at runtime is a NoClassDefFoundError. Knowing which stage failed halves your debugging time.

Check yourself

Your colleague can run java -version but javac is not found. What do they have, and what should they install?

They have a JRE, not a JDK — the compiler ships only with the JDK. They should install a JDK 21 (or newer) and make sure its bin directory comes first on PATH. On a machine with several Javas installed, java -version and javac -version can even report different versions; if they disagree, PATH is picking the two binaries from different installations.

Why can the same .class file run on Windows, Linux and macOS, when a compiled C program cannot?

Because javac does not target any real CPU. It emits bytecode for the abstract JVM instruction set, and the portability problem is then solved once per platform by shipping a native JVM for each. A C compiler emits instructions for a specific CPU and calls into a specific operating system's ABI, so the binary is bound to both. The cost of Java's approach is that a JVM must be present, and that the first execution of any method is interpreted rather than native.

A service is benchmarked immediately after startup and looks slow, then benchmarked again ten minutes later and looks fast. Nothing was redeployed. Why?

JIT compilation. Every method starts out interpreted. Once a method or loop crosses an invocation threshold the JIT compiles it to optimised native code, using profiling data gathered during interpretation to inline calls and eliminate branches that never fire in practice. This is why JVM benchmarks need a warm-up phase before measurement, and why the first few requests to a freshly deployed service are routinely the slowest ones it will ever serve.
