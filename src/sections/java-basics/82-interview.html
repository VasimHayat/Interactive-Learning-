Rehearsal

Interview questions

Twelve questions that actually get asked, with the answer a strong candidate gives. Say your answer out loud before opening the reveal — recognising an answer and being able to produce one are different skills.

Easy  1. What is the difference between the JDK, the JRE and the JVM?

The JVM executes bytecode; it is the specification and the process implementing it. The JRE is the JVM plus the standard class library — enough to run a program. The JDK is the JRE plus development tools, notably javac. Each contains the previous. Practically: install a JDK, since Java 11 there is no separate JRE download from most vendors, and if java works but javac does not, that is what has happened.

Easy  2. Why should you never compare strings with ==?

== compares references, not characters. It appears to work for literals because identical compile-time literals share one pooled instance — which is exactly what makes the bug dangerous, since it passes every test written with literals and fails the moment a string arrives from a file, socket, database or Scanner. Use equals, or Objects.equals when a side may be null.

Easy  3. Is Java pass-by-value or pass-by-reference?

Always pass-by-value. For reference types the reference is what gets copied, so the method can mutate the object you handed it, but reassigning the parameter has no effect on the caller's variable. That is why you cannot write a working swap(a, b) in Java. People call this "pass-by-reference" loosely; being precise about it is a good signal.

Medium  4. What happens if you override equals but not hashCode?

Every hash-based collection breaks. Two equal objects get different identity-derived hash codes and land in different buckets, so a HashSet stores both and contains with an equal instance returns false. Nothing throws — the JDK cannot detect the violation. The contract is that equal objects must return equal hash codes; the converse is not required, since collisions are unavoidable. Follow-up they often add: is a constant hashCode legal? Yes, and it is correct but degrades every lookup to a single bucket.

Medium  5. Checked versus unchecked exceptions — when do you use each?

Checked extends Exception and must be caught or declared; use it for conditions a correct program can still meet and should decide about — a missing file, a rejected payment, an out-of-stock item. Unchecked extends RuntimeException; use it for programming errors where the fix is to change the code — a null that should have been guarded, an argument violating a documented precondition. Error is a third category for JVM-level failures you should not catch at all.

Medium  6. ArrayList or LinkedList?

ArrayList, essentially always. The textbook claim that LinkedList inserts in O(1) ignores that you must first walk to the index, which is O(n) — so the total is the same, while ArrayList's shift is one System.arraycopy over contiguous, cache-friendly memory. LinkedList also pays an object header and two references per element. It wins only when inserting through an Iterator you already hold. For a queue or stack use ArrayDeque, not LinkedList.

Medium  7. Explain String immutability and why it was chosen.

A String's characters never change; every "modifying" method returns a new instance. The reasons: pooling is only safe if instances cannot change; hash codes can be cached, which makes String an excellent map key; instances are automatically thread-safe; and security-sensitive values such as file paths and class names cannot be mutated between a check and its use. The cost is allocation, which is why concatenating in a loop is O(n²) and StringBuilder exists.

Medium  8. What is autoboxing, and where does it bite?

Automatic conversion between primitives and their wrappers. Three traps: unboxing a null throws NullPointerException at an assignment that looks harmless; == on wrappers compares references, so it is true for values in the −128…127 cache and false outside it; and boxing in a loop allocates an object per iteration. Also overload resolution — list.remove(1) removes an index, list.remove(Integer.valueOf(1)) removes a value.

Hard  9. Give the full initialization order for a subclass instance.

On first active use of the class: superclass static fields and static blocks, then this class's. Then on every new: superclass instance fields and initializer blocks, superclass constructor body, this class's instance fields and initializer blocks, this class's constructor body. Within a level, source order. Two consequences worth volunteering: statics run once and lazily, not at JVM start; and because the superclass constructor runs before the subclass's fields are initialised, calling an overridable method from a constructor lets the override observe null and 0.

Hard  10. What is type erasure and what does it prevent?

Generic type arguments exist only at compile time and are erased from the bytecode, so a List<String> is a plain List at runtime. It was done for backward compatibility with pre-generics code. Consequences: no new T(), no new T[], no instanceof List<String>, no overloads differing only by type argument, and no primitive type arguments. It is also why a raw type can smuggle a wrong element in and the ClassCastException surfaces later, at the read, far from the cause.

Hard  11. Overloading versus overriding — and when is each resolved?

Overloading is same name, different parameter types, resolved by the compiler from the static types of the arguments, in three phases: exact and widening first, then boxing, then varargs. Overriding is a subclass replacing a superclass method with the same signature, resolved by the JVM from the object's runtime class. So one call site can be picked at compile time and dispatched at runtime, and mixing them up produces genuinely surprising behaviour — a common test is a method overloaded on Object and String called with a null, or with a variable declared Object holding a String.

Hard  12. What does try-with-resources do that finally does not?

Three things. It closes resources in reverse acquisition order automatically. It closes only what was successfully acquired, so if the second resource's constructor throws, the first is still closed and the second is not touched. And it suppresses rather than discards: if the body throws and close() also throws, the body's exception propagates and the close exception is attached, retrievable via getSuppressed(). The hand-written finally { in.close(); } pattern gets the last one backwards, replacing the real failure with the close failure — which is how the actual cause of an outage disappears.
