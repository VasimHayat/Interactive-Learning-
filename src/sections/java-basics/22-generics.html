Section 13

Generics basics

Generics move a whole class of errors from runtime to compile time. List<Product> tells the compiler what goes in, so it can reject anything else and insert the casts on the way out for you. Before Java 5 every collection held Object and every read needed a hand-written cast that might fail.

The one thing to internalise now is erasure: generics exist for the compiler and are erased from the bytecode. At runtime a List<String> is just a List. That is why the guarantees are only as good as your willingness to keep the compiler informed.

What a raw type costs you

import java.util.ArrayList;
import java.util.List;

public class RawTypes {
    @SuppressWarnings({ "rawtypes", "unchecked" })
    public static void main(String[] args) {
        List raw = new ArrayList();     // raw type: the compiler stops helping
        raw.add("BOLT-7");
        raw.add(42);                    // accepted without complaint

        for (Object o : raw) System.out.println("element: " + o);

        List skus = raw;        // unchecked assignment, only a warning
        System.out.println("first : " + skus.get(0));
        System.out.println("second: " + skus.get(1));
    }
}
  
element: BOLT-7
element: 42
first : BOLT-7
  
Exception in thread "main" java.lang.ClassCastException:
        class java.lang.Integer cannot be cast to class java.lang.String
        at RawTypes.main(RawTypes.java:15)

The failure lands on line 15 — a println that looks entirely innocent — while the actual mistake was on line 9, possibly in a different class written months earlier. skus.get(1) is declared to return String, so the compiler inserted a cast there; the cast is the first moment anyone checks. This distance between cause and symptom is what generics exist to remove. Declare List<String> from the start and line 9 fails to compile.

Treat unchecked warnings as errors

Every step above was legal Java and every step produced a warning. Compile with -Xlint:all -Werror and this code stops building. Reach for @SuppressWarnings("unchecked") only on the narrowest possible scope, and only when you have personally proved the cast is safe.

Writing a generic type

interface Repository {                 // T is a type parameter
    void save(T item);
    T findBySku(String sku);
}

class ProductRepository implements Repository {
    @Override public void save(Product item) { /* … */ }
    @Override public Product findBySku(String sku) { /* … */ return null; }
}

// A generic METHOD declares its own parameter, before the return type:
static > T max(List items) {
    T best = items.get(0);
    for (T item : items) if (item.compareTo(best) > 0) best = item;
    return best;
}

<T extends Comparable<T>> is a bounded parameter: it accepts any type that can be compared to itself, which is what lets the body call compareTo. By convention T is a type, E an element, K and V a key and value. Wildcards (? extends, ? super) and the PECS rule belong to Java Intermediate.

Consequences of erasure
  • No primitives. List<int> does not compile — use List<Integer> and accept the boxing, or a primitive-specialised library if it is hot.
  • new T() is impossible. The type is gone by runtime. Pass a factory or a Class<T> if you must construct one.
  • o instanceof List<String> does not compile. Only instanceof List<?> — there is nothing left to test against.
  • Overloads that differ only by type argument clash. f(List<String>) and f(List<Integer>) erase to the same signature.
  • Generic arrays are not allowed. new T[10] is a compile error; arrays know their element type at runtime and generics do not, so the two cannot be reconciled. Use an ArrayList.

Check yourself

1.In the worked example, why does the exception point at line 15 rather than at line 9, where the wrong element was added?

B. At runtime the list is a plain List holding Objects, so add(42) is a perfectly ordinary operation. Because skus.get(1) is declared to yield a String, javac emits a checkcast at the call site — and that is where reality and the declaration finally meet.

A and C describe validation and laziness that ArrayList does not have; it stores references immediately and checks nothing. D is wrong — the loop reads elements as Object, which needs no cast, so it prints 42 quite happily.

2.Which of these compiles?

C. Nested type arguments are fine, and the diamond <> infers them from the declaration.

A fails because a type argument must be a reference type — Integer, not int. B fails because the type argument is erased, so there is nothing to test; instanceof List<?> is the legal form. D fails on new T[] — an array stores its element type at runtime, which erasure has already thrown away, so the array could not enforce anything.
