Section 12

Collections: choosing the right one

Three interfaces cover almost everything. List is an ordered sequence that allows duplicates and is addressable by index. Set holds distinct elements. Map associates keys with values. Pick the interface from what your data is, then pick the implementation from how you will use it.

LinkedList is almost never the answer

The table says O(1) insertion, which sounds decisive — but to insert at index i you must first walk i nodes, so the real cost is O(n) anyway. Meanwhile ArrayList's O(n) shift is a single System.arraycopy over contiguous memory, which the CPU cache handles roughly an order of magnitude faster than chasing scattered node pointers, and each node costs an extra object header plus two references. LinkedList wins only when you insert through an Iterator you already hold. If you want a queue or a stack, use ArrayDeque.

Worked example

import java.util.ArrayList;
import java.util.HashMap;
import java.util.HashSet;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeSet;

public class CollectionTour {
    public static void main(String[] args) {
        List picks = new ArrayList<>(List.of("NUT-3", "BOLT-7", "NUT-3"));
        System.out.println("list, dupes kept     = " + picks);

        Set unique = new HashSet<>(picks);
        System.out.println("hashset size         = " + unique.size());
        System.out.println("linkedhashset        = " + new LinkedHashSet<>(picks));
        System.out.println("treeset, sorted      = " + new TreeSet<>(picks));

        Map onHand = new HashMap<>();
        onHand.put("BOLT-7", 12);
        onHand.put("NUT-3", 0);
        System.out.println("get missing key      = " + onHand.get("NOPE"));
        System.out.println("getOrDefault         = " + onHand.getOrDefault("NOPE", 0));
        System.out.println("containsKey NUT-3    = " + onHand.containsKey("NUT-3"));

        onHand.put("BOLT-7", onHand.get("BOLT-7") + 5);
        System.out.println("after restock        = " + onHand.get("BOLT-7"));

        try {
            List.of("A", "B").add("C");
        } catch (UnsupportedOperationException e) {
            System.out.println("List.of is immutable = true");
        }
    }
}

Note what is not printed: the HashSet's contents. Its iteration order is unspecified and may differ between JVM versions, so printing it in a test is how you get a suite that passes locally and fails in CI. Only the size is meaningful. LinkedHashSet preserves insertion order; TreeSet sorts.

Gotchas
  • map.get() returning null is ambiguous. It means either "no such key" or "the key maps to null". Use containsKey to distinguish, or getOrDefault to stop caring.
  • Unboxing a missing value throws. int n = onHand.get("NOPE"); compiles and throws NullPointerException. getOrDefault(key, 0) is the fix.
  • List.of and Map.of are immutable and reject nulls. Great as constants, wrong as a starting point for something you will mutate — wrap in new ArrayList<>(…) for that.
  • Keys must have correct equals/hashCode, and should be immutable. See section 10 for what breaks otherwise.
  • Declare the interface, construct the implementation. List<String> picks = new ArrayList<>() lets you swap the implementation without touching callers.
  • Size the collection if you know the count. new ArrayList<>(10_000) avoids a dozen grow-and-copy cycles.

Check yourself

1.You need to record which SKUs a picker has already visited on this run, and ask "seen this one?" tens of thousands of times. Order never matters. What do you use?

C. Membership testing is exactly what a hash set is for: O(1) contains and free deduplication.

A and D both scan the whole list — O(n) per check, so O(n²) overall, which is the classic reason a nightly job that was fine with 100 SKUs takes hours with 100,000. B works and is O(log n), but you are paying for sorted order you explicitly do not need.

2.A test asserts set.toString() equals "[BOLT-7, NUT-3]". It passes locally and fails on the build server. The set is a HashSet. Why, and what is the right fix?

B. Nothing guarantees HashSet iteration order — it falls out of hash values and table size, and can differ across JVM versions and vendors. The assertion was testing an implementation detail. Assert what you actually care about: that the set contains those two elements and has size 2.

A is a real cause of other cross-machine failures — date and case formatting — but not this one. C would more likely give a ConcurrentModificationException or corruption, not a stable-but-different order. D cannot be done to a HashSet in place; copying to a sorted structure just to satisfy an assertion is the tail wagging the dog — if order matters, choose an ordered type in the production code.
