Section 2

Primitives, wrappers, and autoboxing

Java has two kinds of values and the split runs through everything else in the language. A primitive is a raw value of fixed width — int, double, boolean and five others. An object is something on the heap that you reach through a reference. Primitives are not objects, cannot be null, and cannot go into a collection.

That last restriction is why every primitive has a matching wrapper class — Integer for int, Double for double, and so on. Since Java 5 the compiler converts between the two automatically, which is convenient right up to the moment it silently changes what your code means.

What happens past the top of the range

Worked example

Three behaviours that surprise people, in one program: silent integer overflow, the Integer cache, and binary floating point.

public class Primitives {
    public static void main(String[] args) {
        int max = Integer.MAX_VALUE;
        System.out.println("MAX_VALUE     = " + max);
        System.out.println("MAX_VALUE + 1 = " + (max + 1));

        Integer a = 127, b = 127;
        Integer c = 128, d = 128;
        System.out.println("127 == 127    -> " + (a == b));
        System.out.println("128 == 128    -> " + (c == d));
        System.out.println("128 .equals   -> " + c.equals(d));

        System.out.println("0.1 + 0.2     = " + (0.1 + 0.2));
        System.out.println("as BigDecimal = " + new java.math.BigDecimal("0.1").add(new java.math.BigDecimal("0.2")));
    }
}
  
MAX_VALUE     = 2147483647
MAX_VALUE + 1 = -2147483648
127 == 127    -> true
128 == 128    -> false
128 .equals   -> true
0.1 + 0.2     = 0.30000000000000004
as BigDecimal = 0.3

Every one of those lines is a bug source in real code:

  • max + 1 wraps to the most negative int. No exception, no warning. A quantity counter that overflows just starts reporting negative stock. Use Math.addExact when overflow would be a correctness problem — it throws ArithmeticException instead.
  • 127 == 127 is true but 128 == 128 is false. Integer.valueOf caches boxed values from −128 to 127 and returns the identical object for those; outside that range it allocates a new one each time. == on wrappers compares references, so the answer changes with the magnitude of the number. This is the single most notorious autoboxing trap.
  • 0.1 + 0.2 is not 0.3. Neither operand is exactly representable in binary floating point, so the sum lands slightly high. Never use double for money — use BigDecimal constructed from a String, or count in integer minor units (cents).
Autoboxing gotchas
  • Unboxing null throws. Map<String,Integer> stock; int n = stock.get("MISSING"); compiles fine and throws NullPointerException at runtime, because get returned null and the compiler inserted .intValue() on it. The stack trace points at the assignment, not at the map.
  • Boxing in a hot loop allocates. Integer total = 0; for (int i = 0; i < 1_000_000; i++) total += i; creates a million Integer objects, because each += unboxes, adds, and reboxes. Declaring total as int makes it roughly an order of magnitude faster and allocation-free.
  • Overload resolution changes. Given both remove(int) and remove(Object) on List<Integer>, list.remove(1) removes the element at index 1, while list.remove(Integer.valueOf(1)) removes the value 1. The compiler prefers the primitive overload without widening or boxing.

Check yourself

1.What does this print?

Integer x = 1000;
Integer y = 1000;
System.out.println(x == y);
System.out.println(x.equals(y));

B. 1000 is outside the Integer cache range of −128…127, so each boxing allocates a separate object and == compares two different references — false. equals compares the wrapped values, so it is true.

A would be right if the value were ≤ 127 — that inconsistency is exactly the trap. C inverts the two operators. D is wrong because the code is perfectly legal; that is the problem with it.

2.An inventory counter is declared int onHand and reaches 2,147,483,647. One more unit arrives and onHand++ runs. What happens?

C. Java uses two's-complement arithmetic that wraps around. Adding 1 to the largest int gives the smallest one, with no diagnostic of any kind.

A is what Math.addExact(onHand, 1) would do, and is what you want here. B is saturating arithmetic, which Java does not do. D never happens implicitly on assignment back into an int — the arithmetic is performed in 32 bits and the result truncated.
