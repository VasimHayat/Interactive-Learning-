Section 5

Control flow

The shapes here will be familiar from any C-family language. What is worth your attention is the enhanced for loop, the difference between break and continue when both appear in one loop, and the switch expression — a Java 14+ form that removes the fall-through bug the old statement was famous for.

The five loop forms

Loop forms and when to use each
FormUse when
for (int i = 0; i < n; i++)you need the index, or you are stepping by something other than 1
for (T item : collection)you just need each element — the default choice, and the one that cannot go out of bounds
while (cond)the number of iterations is unknown up front
do { … } while (cond)the body must run at least once (menus, retry loops)
Iterator<T> it = …; while (it.hasNext())you need to remove() while iterating — see the gotcha below

Worked example

A picking routine that skips out-of-stock lines and stops once it has enough. Both continue and break appear, and the order in which they are tested changes the result.

public class ControlFlow {
    public static void main(String[] args) {
        String[] skus   = { "BOLT-7", "NUT-3", "CAM-9", "ROD-4", "PIN-2" };
        int[]    onHand = {       12,       0,       7,       0,      31 };
        int      needed = 2;
        int      picked = 0;

        for (int i = 0; i < skus.length; i++) {
            if (onHand[i] == 0) {
                System.out.println("skip  " + skus[i] + " (out of stock)");
                continue;
            }
            if (picked == needed) {
                System.out.println("stop  - picked enough");
                break;
            }
            System.out.println("pick  " + skus[i]);
            picked++;
        }
        System.out.println("picked = " + picked);

        for (String sku : new String[] { "BOLT-7", "CAM-9", "ZZZ-1" }) {
            String bin = switch (sku.substring(0, 3)) {
                case "BOL" -> "A1";
                case "CAM" -> "B2";
                default    -> "UNSORTED";
            };
            System.out.println(sku + " -> bin " + bin);
        }
    }
}
  
pick  BOLT-7
skip  NUT-3 (out of stock)
pick  CAM-9
skip  ROD-4 (out of stock)
stop  - picked enough
picked = 2
BOLT-7 -> bin A1
CAM-9 -> bin B2
ZZZ-1 -> bin UNSORTED

Notice ROD-4: it is skipped rather than triggering the stop, because the continue on line 11 fires before control ever reaches the break test. Swap the two if blocks and the loop stops one iteration earlier and prints something different. continue jumps to the next iteration; break leaves the loop entirely — and when both are present, the order you test them in is part of the logic.

Switch: statement versus expression

String bin;
switch (prefix) {
    case "BOL": bin = "A1";
    case "CAM": bin = "B2"; break;
    default:    bin = "UNSORTED";
}

The missing break on the "BOL" case means it falls through and bin ends up "B2". The compiler is happy. Every case needing an explicit break, with fall-through as the default, is a design that produces this bug reliably.

String bin = switch (prefix) {
    case "BOL" -> "A1";
    case "CAM" -> "B2";
    default    -> "UNSORTED";
};

Arrow cases do not fall through, the whole thing is an expression that yields a value, and bin can be final. When switching over an enum the compiler also checks exhaustiveness, so adding a new constant turns every unhandled switch into a compile error rather than a silent default. Prefer this form.

Removing while iterating throws
for (OrderLine line : order.lines()) {
    if (line.qty() == 0) order.lines().remove(line);   // ConcurrentModificationException
}

The enhanced for is an Iterator underneath, and the iterator notices the collection changed beneath it. Despite the name, no concurrency is involved — a single thread does this to itself. Use Iterator.remove(), or list.removeIf(line -> line.qty() == 0), which is clearer and does the same thing safely.

Check yourself

1.In the worked example, what changes if the break block is moved above the continue block?

B. On the fourth iteration picked already equals needed. If the break test comes first it fires immediately, so the loop exits at ROD-4 and the out-of-stock message for it is never reached.

A misses that continue skips the rest of the body. C is impossible — picked is only incremented after both guards pass, and stopping earlier cannot increase it. D invents a rule; break may appear anywhere in a loop body.

2.Which of these safely remove zero-quantity lines while walking the list? Select all that apply.

A and C. removeIf is purpose-built and the clearest option. Iterator.remove() is the low-level equivalent — it updates the iterator's own bookkeeping so no modification is detected.

B throws ConcurrentModificationException — the enhanced for hides an iterator that the direct remove invalidates. D does not throw, which makes it worse: removing at index i shifts everything left, the loop then increments i, and the element that moved into that slot is never examined. Two adjacent zero-quantity lines and it silently keeps one. Iterating backwards would fix it, but removeIf is better.
