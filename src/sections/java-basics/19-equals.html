Section 10

equals, hashCode, toString

Every class inherits these three from Object, and the inherited versions are almost never what you want. equals defaults to reference identity, hashCode to a value derived from the object's identity, and toString to a class name and a hex hash.

The critical rule is that equals and hashCode are one contract, not two methods: if two objects are equals, they must return the same hashCode. Override one without the other and every hash-based collection in the JDK starts giving wrong answers — quietly, with no exception.

A HashSet receiving two equal parts and one different one

Worked example

BadPart below overrides both methods — but derives the hash from a per-instance id that equals never looks at. That is a contract violation, and it fails deterministically.

import java.util.HashSet;
import java.util.Set;

public class EqualsContract {

    static final class BadPart {
        private static int counter = 0;
        private final String sku;
        private final int id = ++counter;

        BadPart(String sku) { this.sku = sku; }

        @Override public int hashCode() { return id; }   // NOT derived from sku
        @Override public boolean equals(Object o) {
            return o instanceof BadPart other && sku.equals(other.sku);
        }
    }

    static final class GoodPart {
        private final String sku;

        GoodPart(String sku) { this.sku = sku; }

        @Override public int hashCode() { return sku.hashCode(); }
        @Override public boolean equals(Object o) {
            if (this == o) return true;
            if (!(o instanceof GoodPart other)) return false;
            return sku.equals(other.sku);
        }
        @Override public String toString() { return "GoodPart[sku=" + sku + "]"; }
    }

    public static void main(String[] args) {
        Set bad = new HashSet<>();
        bad.add(new BadPart("BOLT-7"));
        bad.add(new BadPart("BOLT-7"));
        System.out.println("bad  equals    -> " + new BadPart("X").equals(new BadPart("X")));
        System.out.println("bad  set size  -> " + bad.size());
        System.out.println("bad  contains  -> " + bad.contains(new BadPart("BOLT-7")));

        Set good = new HashSet<>();
        good.add(new GoodPart("BOLT-7"));
        good.add(new GoodPart("BOLT-7"));
        System.out.println("good equals    -> " + new GoodPart("X").equals(new GoodPart("X")));
        System.out.println("good set size  -> " + good.size());
        System.out.println("good contains  -> " + good.contains(new GoodPart("BOLT-7")));
        System.out.println("good toString  -> " + new GoodPart("BOLT-7"));
    }
}
  
bad  equals    -> true
bad  set size  -> 2
bad  contains  -> false
good equals    -> true
good set size  -> 1
good contains  -> true
good toString  -> GoodPart[sku=BOLT-7]

Read the first three lines together: the two BadParts are equal, the set still holds both, and looking one up fails. A hash collection computes the hash first and only compares with equals inside the matching bucket — so unequal hashes mean equals is never even called. Omitting hashCode entirely produces the same failure, just non-deterministically, since identity hashes occasionally collide by luck.

The equals contract

For non-null x, y, z: reflexive — x.equals(x); symmetric — x.equals(y) implies y.equals(x); transitive; consistent across repeated calls; and x.equals(null) is always false. Symmetry is the one subclassing breaks: if equals uses getClass() != o.getClass(), a subclass instance is never equal to a base instance; if it uses instanceof, a base instance can be equal to a subclass instance but not the reverse. Declaring value classes final — as above — sidesteps the whole problem.

  5. 5 if (!(o instanceof GoodPart other)) return false;

Correct. The identity check first because it is a single pointer comparison and is often true for repeated lookups. Then the instanceof pattern, which handles the wrong type and null in one test — null instanceof Anything is false — and binds other so no cast is needed. Only then the field comparison, which is the expensive part.

Gotchas
  • Wrong parameter type silently overloads. public boolean equals(GoodPart o) does not override anything — Object.equals still wins when a collection calls it. @Override catches this instantly.
  • Never hash on a mutable field. Mutate a key after inserting it into a HashMap and it moves to a bucket nobody will look in. The entry is lost, and it still holds memory.
  • Objects.equals and Objects.hash handle null. Objects.hash(sku, price) is the readable default; for a hot path with one field, sku.hashCode() avoids the varargs array allocation.
  • Write toString for humans, and never put secrets in it. It ends up in logs and exception messages. Tokens, passwords and full card numbers must not.
  • A record gives you all three, correctly, for free. If the class is a transparent carrier of data, use one — Java Intermediate covers them.

Check yourself

1.A Product overrides equals on sku but not hashCode. Two products with the same SKU go into a HashSet. What is most likely observed?

C. Different identity hashes almost always mean different buckets, so equals is never consulted and the duplicate is stored. A lookup with a third equal instance hashes somewhere else again and finds nothing.

A is what you would get if hashCode were also overridden. B never happens — the JDK cannot detect the violation, which is the whole problem. D is self-contradictory: the same hash mismatch that allowed the duplicate also breaks the lookup. Note "most likely" — with luck the two identity hashes land in the same bucket and you get size 1, which is worse still, because the bug then appears only intermittently.

2.Is hashCode() { return 1; } — the same value for every instance — a violation of the contract?

A. The contract only requires that equal objects share a hash code. A constant satisfies that trivially and is therefore correct — just pathologically slow, since a hash map degenerates to a single bucket. (Modern HashMap treeifies large buckets, softening it to O(log n) for comparable keys, but it is still the wrong thing to ship.)

B states the converse, which is not required and cannot be — there are more possible objects than int values, so collisions are unavoidable. C is excellent advice and the practical way to satisfy the contract, but it is not itself the rule. D gets the verdict right and the reasoning wrong: equals is only reached for entries already in the same bucket, so the collisions are precisely what costs you.
