Section 7

Methods, overloading, and varargs

Java dispatches on the compile-time types of the arguments. Which overload runs is decided entirely by javac before your program starts, using a three-phase algorithm. Knowing those phases turns overload puzzles from guesswork into a lookup.

How the compiler picks

Worked example

public class Overloads {
    static String f(int x)     { return "int"; }
    static String f(long x)    { return "long"; }
    static String f(Integer x) { return "Integer"; }
    static String f(Object x)  { return "Object"; }
    static String f(int... x)  { return "varargs"; }

    public static void main(String[] args) {
        byte b = 1;
        System.out.println("f(1)           -> " + f(1));
        System.out.println("f(b)  byte     -> " + f(b));
        System.out.println("f(1L)          -> " + f(1L));
        System.out.println("f((Integer) 1) -> " + f((Integer) 1));
        System.out.println("f(1, 2)        -> " + f(1, 2));
        System.out.println("f(\"x\")         -> " + f("x"));
    }
}
  
f(1)           -> int
f(b)  byte     -> int
f(1L)          -> long
f((Integer) 1) -> Integer
f(1, 2)        -> varargs
f("x")         -> Object

Reading those in phase order:

  • f(1) — phase 1 finds f(int) exactly. f(Integer) would need boxing, which phase 1 forbids.
  • f(b) with a byte — no f(byte) exists, but widening byte→int is allowed in phase 1. int is more specific than long, so f(int) wins.
  • f((Integer) 1) — the argument's compile-time type is now Integer, matching f(Integer) exactly in phase 1. The cast changed the answer without changing the value.
  • f(1, 2) — nothing takes two arguments, so phases 1 and 2 find nothing and phase 3 reaches the varargs form.
  • f("x") — only f(Object) accepts a String.
Overloading gotchas
  • Java is pass-by-value, always. For a reference type the reference is copied, so a method can mutate the object you passed but cannot make your variable point somewhere else. Reassigning the parameter inside the method is invisible to the caller.
  • list.remove(1) vs list.remove(Integer.valueOf(1)). On a List<Integer> the first removes index 1 and the second removes the value 1, because phase 1 finds remove(int) before boxing is ever considered.
  • Return type is not part of the signature. Two methods differing only in return type do not compile.
  • Varargs must be last, and one per method. f(String... a, int b) is a compile error. Calling f() with no arguments gives an empty array, not null — but f(null) passes null as the array, so a length check throws.
  • Overloading is compile-time; overriding is runtime. They are unrelated mechanisms that beginners routinely conflate. Section 8 covers the runtime half.

Check yourself

1.What does this print?

static void swap(String a, String b) { String t = a; a = b; b = t; }

String x = "BOLT-7", y = "NUT-3";
swap(x, y);
System.out.println(x + " " + y);

B. Unchanged. a and b are copies of the references; reassigning them rebinds only the local parameters. The caller's variables still point where they always did. Java has no way to write a working swap for two variables.

A assumes pass-by-reference, which Java does not have for variables. C and D have no basis — the code is valid and nothing becomes null. Note the distinction: had the method called a mutator on the object rather than reassigning the parameter, the caller would see that change.

2.Given f(int), f(Integer) and f(int...), which runs for the call f(7), and why?

A. The literal 7 has compile-time type int, so phase 1 finds f(int) and resolution stops there.

B would require boxing, which phase 1 excludes — it is only reached in phase 2, and phase 2 never runs because phase 1 succeeded. C is true of varargs in general but it is the phase 3 candidate, evaluated last. D is wrong precisely because the phase ordering exists to break these ties deterministically; ambiguity errors happen between two candidates in the same phase.
