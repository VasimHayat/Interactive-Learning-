Section 4

Operators and precedence

Most of Java's operators do what you would guess. The handful that do not are responsible for a disproportionate share of quiet, wrong-answer bugs: integer division that truncates, % that returns negatives, and + that changes meaning as soon as a String enters the expression.

You do not need to memorise this. You need to recognise the three rows that bite — tier 3 above tier 4, tier 7 below tier 6, and && above || — and reach for parentheses everywhere else.

Worked example

public class Operators {
    public static void main(String[] args) {
        System.out.println("7 / 2        = " + (7 / 2));
        System.out.println("-7 / 2       = " + (-7 / 2));
        System.out.println("-7 % 2       = " + (-7 % 2));
        System.out.println("floorMod     = " + Math.floorMod(-7, 2));
        System.out.println("7 / 2.0      = " + (7 / 2.0));

        System.out.println("2 + 3 + \"!\"  = " + (2 + 3 + "!"));
        System.out.println("\"!\" + 2 + 3  = " + ("!" + 2 + 3));

        int i = 2;
        System.out.println("i++ + ++i    = " + (i++ + ++i));
        System.out.println("i is now     = " + i);

        int total = 0, count = 0;
        System.out.println("avg guarded  = " + (count > 0 && total / count > 5));
    }
}

  • 7 / 2 is 3, not 3.5. When both operands are integers, the result is an integer and the fraction is discarded. To get a real quotient, make one side floating point: 7 / 2.0, or (double) total / count. Writing (double)(total / count) is too late — the truncation already happened.
  • -7 / 2 is -3, not -4. Java truncates toward zero rather than flooring. -7 % 2 is -1, because the sign of % follows the dividend. If you are using % to wrap an array index, a negative input produces a negative index and an ArrayIndexOutOfBoundsException — use Math.floorMod, which always returns a non-negative result for a positive modulus.
  • 2 + 3 + "!" is 5! but "!" + 2 + 3 is !23. + is left-associative and switches from addition to concatenation the moment one operand is a String. This is why log messages sometimes show id: 12 when you meant id: 3.
  • && short-circuits, and that is load-bearing. The last line never divides by zero, because count > 0 is false and the right operand is not evaluated at all. Swap in & and the same line throws ArithmeticException. The same pattern guards null: if (o != null && o.isPaid()).

All four correct. The consequences: a + b * c multiplies first; a < b == c parses as (a < b) == c; a || b && c parses as a || (b && c); and -x++ parses as -(x++).

Two that the compiler will not save you from
  • Compound assignment hides a cast. byte b = 10; b += 300; compiles, because += performs an implicit narrowing cast. b = b + 300; does not compile. The convenient form is the one that silently truncates.
  • x == y on double is unreliable. Rounding means 0.1 + 0.2 == 0.3 is false. Compare with a tolerance — Math.abs(x - y) < 1e-9 — or avoid floating point for the value entirely.

Check yourself

1.An average is computed as int avg = total / count; with total = 7 and count = 2, and reports 3. Which fix produces 3.5?

D. The cast must apply to an operand before the division, so the division is performed in floating point. Casting one side promotes the other automatically.

A still divides two ints — the truncation to 3 happens first, and widening 3 to 3.0 afterwards cannot recover the lost fraction. B is the same mistake made explicit: the parentheses cast the result, not the operand. C does the division correctly but then fails to compile, because double cannot be assigned to int without an explicit narrowing cast.

2.A ring buffer indexes with items[i % items.length]. It works for months, then throws ArrayIndexOutOfBoundsException: Index -3. What happened, and what is the fix?

B. The message names index -3, so the modulo returned a negative value, which only happens when i is negative. A monotonically increasing int counter that overflows past Integer.MAX_VALUE wraps to a large negative number — which is exactly why this appears after months of uptime rather than in testing. Math.floorMod returns a non-negative result for a positive modulus.

A would give ArithmeticException: / by zero, not a negative index. C is false — the expression inside [] is delimited by the brackets, so precedence is not involved. D is simply not a Java rule.
