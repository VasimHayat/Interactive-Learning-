Self-assessment quiz

Sixteen questions covering all nine learning objectives. Answer every one, then submit — nothing is marked until you do, and the explanations stay hidden until then. Your answers are saved locally, so you can leave and come back.

1.A colleague can run java -version but not javac. What do they have?

C. The JRE runs programs; the JDK adds the tools to build them. B is impossible — a JRE contains the JVM, so having the JVM means having at least a JRE. A and D invent causes for what is simply the normal JRE layout.

2.int qty = Integer.MAX_VALUE; qty++; — what is qty?

B. Two's-complement wraparound, with no diagnostic. C is what Math.incrementExact would do and is what you want when overflow matters. A is saturating arithmetic, which Java does not have. D never happens on assignment back into an int.

3.Integer a = 1000, b = 1000; — what are a == b and a.equals(b)?

C. 1000 is outside the −128…127 Integer cache, so two distinct objects are allocated and == compares references. equals compares values. With 100 instead of 1000, A would be correct — that inconsistency is the whole trap.

4.What is -7 % 2 in Java?

A. Java's % takes its sign from the left operand, so it can be negative. B is Math.floorMod(-7, 2), which is what you want when wrapping an array index. C is -7 / 2.

5.String s = "BOLT"; s.concat("-7"); System.out.println(s);

D. Strings are immutable; concat returns a new string that nothing captured. A assumes mutation in place. C is at most a warning, never an error — which is why this slips through.

6.A SKU read from a socket fails an == comparison against the literal "BOLT-7", though both print identically. Why?

B. == compares references, and the pooled literal is not the same object as the one built from bytes. C is wrong — == is perfectly well defined, just not what you meant. A and D invent mechanisms; Java strings carry no terminator.

7.Building a 10,000-line CSV with report += line + "," inside a loop is slow. Why?

C. Use a StringBuilder. Note the boundary: a + chain in a single expression compiles to one efficient concatenation and needs no rewriting — the problem is specifically re-concatenating across iterations. A, B and D are invented mechanisms.

8.You must test membership tens of thousands of times, order irrelevant. Which collection?

B. O(1) contains. A and C scan linearly, giving O(n²) overall — the classic reason a job fine at 100 items crawls at 100,000. D works at O(log n) but charges you for sorted order you do not need.

9.A test asserting hashSet.toString() passes locally and fails in CI. The correct fix is…

A. The assertion was testing an implementation detail. B hides it rather than fixing it, and order can change between versions of one vendor anyway. C addresses concurrency, which is not what is happening. D is a real cause of other cross-machine failures — date and case formatting — but not this one.

10.Product overrides equals on sku only. Two same-SKU products go into a HashSet. Most likely result?

D. Without hashCode, equal objects hash to different buckets, so equals is never consulted. A needs hashCode overridden too. B never happens — the JDK cannot detect the violation. C is self-contradictory: the same mismatch that stored the duplicate also breaks lookup.

11.Running out of stock is a normal business outcome the caller must decide about. What kind of exception?

B. A correct program can hit it and must handle it, which is exactly the case checked exceptions model. A suits programming errors such as a negative quantity. C is reserved for JVM-level failures. D pushes the problem to a NullPointerException somewhere less informative.

12.try (A a = new A(); B b = new B()) — A constructs, then B's constructor throws. What is closed?

C. Only successfully acquired resources are closed, in reverse order. A would leak A. B would call close() on a never-assigned reference. This is exactly the case hand-written finally blocks get wrong.

13.Given f(int), f(Integer) and f(int...), which runs for f(7)?

A. Phase 1 allows only exact and widening matches, finds f(int), and stops. B needs boxing (phase 2) and C needs varargs (phase 3), neither of which is reached. D would require two candidates in the same phase.

14.A raw List got an Integer added, was assigned to List<String>, and throws ClassCastException at a get. Why there and not at the add?

C. At runtime it is a plain List of Object. Because get is declared to return String, javac emits a checkcast there. D is close but wrong in attribution — the JVM knows nothing about generics; the compiler inserted the cast. A and B describe behaviour that does not exist.

15.A field declared int qty; with no modifier is visible to…

B. That is package-private, the level you get by writing nothing. A requires an explicit private — the most common wrong answer. D describes protected, which is strictly wider.

16.Which safely remove elements while walking a list? Select all that apply.

A and C. B throws ConcurrentModificationException. D is worse than throwing: removing at i shifts everything left, the loop increments i, and the element that slid into that slot is skipped — so two adjacent matches silently leave one behind.
