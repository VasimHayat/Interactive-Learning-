Section 8

Classes, inheritance, and polymorphism

A class bundles state with the operations allowed on it. Encapsulation means the state is private and the operations enforce the rules, so an object cannot be put into an invalid condition from outside. Everything else in object-oriented Java rests on that.

Polymorphism is the payoff: code written against a supertype runs against any subtype, and the method that actually executes is chosen at runtime from the object's real class — not from the type of the variable holding it. That runtime choice is dynamic dispatch, and it is the exact opposite of the compile-time overload resolution in the previous section.

Worked example

public class Dispatch {

    static abstract class Product {
        private final String sku;               // private: nobody outside can corrupt it
        private int priceInCents;

        Product(String sku, int priceInCents) {
            if (sku == null || sku.isBlank()) throw new IllegalArgumentException("sku required");
            if (priceInCents < 0) throw new IllegalArgumentException("price must not be negative");
            this.sku = sku;
            this.priceInCents = priceInCents;
        }

        String sku() { return sku; }
        int priceInCents() { return priceInCents; }

        abstract int shippingInCents();          // no body: every subclass must decide

        int totalInCents() { return priceInCents + shippingInCents(); }
    }

    static class Bolt extends Product {
        Bolt(int priceInCents) { super("BOLT-7", priceInCents); }
        @Override int shippingInCents() { return 150; }
    }

    static class Girder extends Product {
        Girder(int priceInCents) { super("GIRD-1", priceInCents); }
        @Override int shippingInCents() { return 9_500; }
        @Override int totalInCents() { return super.totalInCents() + 250; }  // crane surcharge
    }

    public static void main(String[] args) {
        Product[] cart = { new Bolt(80), new Girder(120_000) };
        for (Product p : cart) {
            System.out.printf("%-8s price=%6d ship=%5d total=%6d%n",
                    p.sku(), p.priceInCents(), p.shippingInCents(), p.totalInCents());
        }

        Product p = new Girder(100);
        System.out.println("static type is Product, runtime type is " + p.getClass().getSimpleName());
    }
}
  
BOLT-7   price=    80 ship=  150 total=   230
GIRD-1   price=120000 ship= 9500 total=129750
static type is Product, runtime type is Girder

The loop variable is declared Product, yet each iteration runs a different shippingInCents. The compiler only verified that some shippingInCents() exists on Product; the JVM picked the implementation from the object's actual class. Girder also overrides totalInCents and calls super.totalInCents() to reuse the base calculation before adding its surcharge.

Abstract class or interface?

abstract class Product {
    private final String sku;           // state
    Product(String sku) { this.sku = sku; }
    String sku() { return sku; }        // shared implementation
    abstract int shippingInCents();     // subclass must supply
}
  • May hold instance fields and constructors
  • May have private and protected members
  • A class extends exactly one
interface Shippable {
    int shippingInCents();                                  // implicitly public abstract
    default boolean isFreeShipping() {                      // Java 8+
        return shippingInCents() == 0;
    }
    static Shippable free() { return () -> 0; }
}
  • No instance state — fields are implicitly public static final
  • A class may implement many
  • default methods allow adding behaviour without breaking implementers

Default to an interface. It describes a capability, permits multiple inheritance of type, and keeps implementations free to sit anywhere in the hierarchy.

Reach for an abstract class only when subclasses must share state or constructor logic — as Product does with its validated sku and priceInCents. A common pattern is both: a public interface for the contract, plus an AbstractProduct that implements the tedious parts for subclasses that want them.

Inheritance gotchas
  • Always write @Override. It is optional to the compiler but it turns a typo into a compile error. Without it, shippingInCent() silently becomes a brand-new method and the base implementation keeps running.
  • static methods are hidden, not overridden. They are bound at compile time from the declared type, so a static "override" is dispatched the opposite way to what you expect.
  • Never call an overridable method from a constructor. The subclass override runs before the subclass's own fields are initialised, so it sees them as null or 0.
  • Fields are not polymorphic. Accessing a field through a superclass-typed reference gets the superclass's field. Only methods dispatch dynamically — another reason to keep fields private.
  • Prefer composition to inheritance. extends couples you to the superclass's implementation, and a change there can break you silently. Inherit to be substitutable for a supertype, not merely to reuse code.

Check yourself

1.A subclass declares int shippingInCent() { return 0; } — note the missing s — without @Override. What happens?

C. A differently named method is simply a different method. With an abstract parent you get a clear error about not implementing the abstract member. With a concrete parent you get no diagnostic at all — the inherited body keeps running and your new method is dead code. That silent case is exactly what @Override exists to catch.

A only happens if you wrote @Override. B is wrong: nothing fails at runtime, which is what makes it insidious. D is invented — dispatch matches on exact name and erased parameter types.

2.You need a type shared by Product, GiftCard and ServicePlan — three classes with no common ancestor and no shared fields — expressing only "this can be priced". What should it be?

B. There is no shared state and the three are otherwise unrelated, so this is a capability, not a family. An interface adds the type without constraining anyone's inheritance.

A burns each class's single extends slot on a type carrying no state — and would be impossible if any of them already extends something. C gives up polymorphism entirely: every new type means editing the utility, and dispatch happens at compile time from the declared type, so a Priceable-typed variable would not resolve correctly. D forces an artificial "is-a" between a physical product and a service plan purely to share one method — the classic inheritance-for-reuse mistake.
