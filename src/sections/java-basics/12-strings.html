Section 3

Strings, immutability, and the pool

String is a normal class, not a primitive — but it gets three privileges no other class has: a literal syntax, the + operator, and a JVM-managed pool of shared instances. Understanding all three is the difference between writing correct string code and writing string code that works by accident.

The foundation is immutability. A String's contents can never change after construction. Every method that looks like it modifies a string — toUpperCase, trim, replace, concat — returns a new string and leaves the original untouched.

The mental model

Worked example

public class Strings {
    public static void main(String[] args) {
        String a = "BOLT-7";
        String b = "BOLT-7";
        String c = new String("BOLT-7");
        String d = c.intern();

        System.out.println("a == b        -> " + (a == b));
        System.out.println("a == c        -> " + (a == c));
        System.out.println("a.equals(c)   -> " + a.equals(c));
        System.out.println("a == d        -> " + (a == d));

        String s = "BOLT";
        s.concat("-7");
        System.out.println("after concat  : " + s);
        System.out.println("reassigned    : " + s.concat("-7"));
    }
}
  
a == b        -> true
a == c        -> false
a.equals(c)   -> true
a == d        -> true
after concat  : BOLT
reassigned    : BOLT-7

Lines 12–13 are the immutability trap in its purest form. s.concat("-7") computes a new string and throws it away, because nothing captured the return value. s still refers to "BOLT". Every string method behaves this way.

Never compare strings with ==

== asks "are these the same object?". For strings you almost always want "do these hold the same characters?", which is equals. Literal comparison happens to work because of pooling, which makes the bug invisible in tests and fatal in production — a string read from a file, a socket, a database or Scanner is never pooled, so == returns false for characters that are plainly identical. Use a.equals(b), or Objects.equals(a, b) when either side may be null.

Building strings efficiently

Because strings are immutable, concatenating in a loop allocates a new object on every iteration and copies everything so far. For n appends that is O(n²) work. StringBuilder keeps a mutable char buffer and appends in amortised O(1).

String report = "";
for (OrderLine line : order.lines()) {
    report += line.sku() + ",";   // allocates a new String every iteration
}

With 10,000 lines this copies roughly 50 million characters. It is the classic reason a report endpoint that was fine in testing falls over on a large order.

StringBuilder report = new StringBuilder();
for (OrderLine line : order.lines()) {
    report.append(line.sku()).append(',');
}
String result = report.toString();

One buffer, grown geometrically, converted to a String exactly once at the end.

String label = "SKU " + sku + " x" + qty;

Leave this alone. A + chain in a single expression is compiled into one efficient concatenation, so hand-rolling a StringBuilder here makes the code worse and no faster. The rule is about loops, not about +.

More string gotchas
  • split takes a regex, not a literal. "1.2.3".split(".") returns an empty array, because . matches any character. You need split("\\.") or split(Pattern.quote(".")).
  • trim() and strip() differ. trim() removes characters ≤ U+0020 only; strip() (Java 11+) is Unicode-aware and removes things like non-breaking space. Prefer strip() for user input.
  • equalsIgnoreCase beats toLowerCase().equals(…). The latter allocates and, in a Turkish locale, lowercases I to a dotless ı — a real internationalisation bug. If you must change case for comparison, pass Locale.ROOT.
  • length() counts UTF-16 code units, not characters. An emoji outside the Basic Multilingual Plane counts as 2. Use codePointCount when you mean user-visible characters.

Check yourself

1.A SKU read from a CSV file is compared to a literal with == and the comparison fails, even though printing both shows BOLT-7. Why?

C. Only compile-time literals and explicitly interned strings live in the pool. Anything constructed at runtime — from I/O, concatenation of non-constants, substring, or new String — is a fresh object, so == compares two different references and returns false.

A is a plausible separate bug, but it would also make equals fail, and the printed output would usually reveal it. B is invented — length is irrelevant. D is wrong: a String in memory has no encoding you can observe; encoding applies when converting to and from bytes.

2.What is printed?

String sku = "BOLT-7";
sku.toLowerCase();
sku.replace('-', '_');
System.out.println(sku);

B. Both method calls return new strings that are immediately discarded. sku is never reassigned, and the object it points to cannot change, so it still holds the original characters.

A assumes both calls mutate in place. C and D each assume one of them does. To get bolt_7 you must capture the results: sku = sku.toLowerCase().replace('-', '_');. Modern compilers will warn about ignoring the return value of a pure method — pay attention to that warning.
