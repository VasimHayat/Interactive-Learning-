Section 9

static and initialization order

static means "belongs to the class, not to any instance". A static field exists once no matter how many objects you create; a static method has no this and cannot touch instance state. That single concept explains counters, constants, factory methods, and main itself.

The part worth memorising is when each piece of initialization runs, because the order is fixed, non-obvious, and shows up in interviews and in real "why is this field null?" bugs.

Worked example

public class InitOrder {

    static class Base {
        static { System.out.println("1. Base   static block"); }
        {        System.out.println("3. Base   instance initializer"); }
        Base()  { System.out.println("4. Base   constructor"); }
    }

    static class Derived extends Base {
        static { System.out.println("2. Derived static block"); }
        {        System.out.println("5. Derived instance initializer"); }
        Derived() { System.out.println("6. Derived constructor"); }
    }

    public static void main(String[] args) {
        System.out.println("-- before any instance exists --");
        new Derived();
        System.out.println("-- second instance --");
        new Derived();
    }
}
  
-- before any instance exists --
1. Base   static block
2. Derived static block
3. Base   instance initializer
4. Base   constructor
5. Derived instance initializer
6. Derived constructor
-- second instance --
3. Base   instance initializer
4. Base   constructor
5. Derived instance initializer
6. Derived constructor

Four things that output tells you:

  • Static initialization is lazy. The static blocks did not run at program start — they ran at the first new Derived(), after the first println. A class is initialized on first active use, not when the JVM boots.
  • The superclass goes first, at both levels. Base's static block before Derived's; Base's instance work before Derived's.
  • Instance initializers run before the constructor body — and after the implicit super() call.
  • Statics run exactly once. The second instance printed only steps 3–6.

Order of initialization, as a rule

Initialization steps in order, with when each runs
#StepRuns
1Superclass static fields and static blocksOnce, on first active use of the class
2This class's static fields and static blocks
3Superclass instance fields and instance initializersEvery new
4Superclass constructor body
5This class's instance fields and instance initializers
6This class's constructor body

Within a level, fields and initializer blocks run in the order they appear in the source. A field declared below an initializer that reads it will still hold its default value at that point.

Where this bites
  • A constructor calling an overridable method. Step 4 runs the superclass constructor, which may call an overridden method — and that override belongs to a subclass whose fields are not initialised until step 5. The override sees null and 0. Make such methods final or private.
  • static mutable state is shared by everything. A static SimpleDateFormat or a static collection is a data race waiting for a second thread, and a memory leak that never gets collected because the class holds it for the JVM's lifetime.
  • static final primitives and Strings are inlined at compile time. A constant is copied into every calling class's bytecode, so changing it and recompiling only that one class leaves the old value baked into the others.
  • You cannot use this in a static context. "Non-static variable cannot be referenced from a static context" almost always means you tried to touch instance state from main.

Check yourself

1.What does this print?

class Config {
    private final String name = describe();
    private final String type = "PRODUCT";
    private String describe() { return "type is " + type; }
    public static void main(String[] a) { System.out.println(new Config().name); }
}

B. Instance fields initialise top to bottom. When name is computed, type has not been assigned yet and still holds its default of null. Concatenating null into a string yields the four characters null rather than failing.

A assumes declaration order does not matter — swapping the two lines really would produce it. C is the intuitive guess but string concatenation is null-safe; you would only get an NPE if describe called a method on type. D describes the illegal-forward-reference rule, which applies to direct reads in an initialiser, not to reads inside a method the initialiser calls — which is exactly why this compiles and misbehaves.

2.InventoryService keeps private static int totalPicks, incremented in an instance method. Two services are constructed and each picks 3 items. What is totalPicks?

C. A static field belongs to the class. Both instances increment the same storage, so the counts add up to 6.

A describes an instance field — drop static and it would be 3 each. B inverts the real rule: an instance method may freely read and write statics; it is the other direction, static code touching instance state, that is forbidden. D is wrong single-threaded — though with two threads and no synchronisation the count really would become unreliable, since ++ is not atomic. That is a genuine hazard of mutable static state, covered in Java Intermediate.
