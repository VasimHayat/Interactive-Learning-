Section 11

Exceptions and try-with-resources

An exception unwinds the stack looking for a handler. If none is found the thread dies and the trace is printed. Java splits exceptions into two kinds, and the split is enforced by the compiler rather than by convention.

Checked exceptions must be caught or declared with throws; the compiler will not let you ignore them. They model conditions a correct program can still hit — a file is missing, a socket drops. Unchecked exceptions (RuntimeException and its subclasses) need no declaration and model bugs — a null you should have guarded, an argument that violates a documented precondition.

Worked example

public class Exceptions {

    static class Resource implements AutoCloseable {
        private final String name;
        Resource(String name) { this.name = name; System.out.println("open  " + name); }
        void use() { System.out.println("use   " + name); }
        @Override public void close() { System.out.println("close " + name); }
    }

    static int sneaky() {
        try {
            return 1;
        } finally {
            System.out.println("finally runs before the caller sees the value");
        }
    }

    static int stockFor(String sku) {
        if (sku == null) throw new IllegalArgumentException("sku must not be null");
        return 42;
    }

    public static void main(String[] args) {
        try (Resource a = new Resource("A"); Resource b = new Resource("B")) {
            a.use();
            b.use();
        }

        System.out.println("sneaky() = " + sneaky());

        try {
            stockFor(null);
        } catch (IllegalArgumentException e) {
            System.out.println("caught: " + e.getMessage());
        } finally {
            System.out.println("finally always runs");
        }
    }
}

Two details in that output earn their place:

  • Resources close in reverse order — B then A. They are released like a stack, which is what you need when a later resource depends on an earlier one (a statement opened from a connection, say). This happens whether the block exits normally or by exception, with no finally written by you.
  • finally runs before the caller sees the return value. The return value is computed and set aside, then the finally block runs, then control returns. If a finally block itself returns, it replaces the pending return and discards any in-flight exception — which is why returning from finally is a bug rather than a technique.

Checked or unchecked?

Place each situation on the exception type it should use

The distinction is who is at fault. A missing file is the environment's doing and a correct program must cope — checked. A bad argument, an uninitialised field, and an operation invalid for the current state are all programming errors: the fix is to change the code, not to catch anything. Note the pair IllegalArgument versus IllegalState — the first says "this input is wrong", the second says "this input might be fine later, but not now".

Never swallow an exception
try {
    inventory.reserve(sku, qty);
} catch (Exception e) { }        // the outage you will spend a day finding

An empty catch destroys the only evidence that anything went wrong. If a failure is genuinely expected and ignorable, say so in a comment and log at debug. Otherwise handle it, or wrap it with context and rethrow: throw new InventoryException("reserving " + sku, e) — passing the original as the cause keeps the underlying trace attached.

Gotchas
  • Catch the specific type, and order subclasses first. catch (Exception e) before catch (IOException e) is a compile error — the second is unreachable.
  • The old finally { in.close(); } pattern loses exceptions. If the body threw and close() also throws, the close exception replaces the real one. Try-with-resources instead suppresses the secondary exception and attaches it, retrievable via getSuppressed().
  • Java 14+ gives helpful NPE messages. Instead of a bare line number you get Cannot invoke "Product.sku()" because "<local3>" is null — read it, it names the exact expression.
  • Exceptions are not control flow. Building a stack trace is expensive; using one to exit a loop is slow and obscures intent.
  • Do not catch Error. OutOfMemoryError and StackOverflowError mean the JVM is in no state to continue.

Check yourself

1.In the worked example, Resource A is opened, then B's constructor throws. What is closed?

B. Try-with-resources tracks what it has successfully acquired. A exists, so it is closed; B never came into being, so there is nothing to close. This is precisely the case hand-written finally blocks get wrong.

A would leak A. C would call close() on a reference that was never assigned — an NPE. D inverts it.

2.A REST handler wraps its whole body in catch (Exception e) { return 200; } to stop 500s appearing in the dashboard. What is the real consequence?

C. The dashboard turns green because the failures stopped being reported, not because they stopped happening. A caller told "200 OK" will not retry, so a reservation that never persisted is simply gone. The metric got healthier and the system got worse.

A mistakes suppressing the signal for handling the problem. B is factually wrong — RuntimeException is a subclass of Exception, so this catches everything except Error. D is closer, and logging is strictly better than not, but the response code is still a lie; the status must reflect what actually happened.
