Section 1

Why an ORM, and what it costs

A relational database stores rows in tables and relates them by values in columns. A Java program holds objects on a heap and relates them by references. Neither model is wrong, but they disagree about almost everything that matters, and the disagreement has a name: the object–relational impedance mismatch. An object-relational mapper exists to translate across it — and like every translator, it is only trustworthy once you know what it says on your behalf.

Worked example, part 1: the baseline without an ORM

Before reading a line of Hibernate, see what it replaces. This is plain JDBC against the same in-memory H2 database every other program in this module uses. Note everything you have to write yourself: the table, the parameter indices, the column names repeated in the select and again in the ResultSet reads, the row-to-object code, and the update statement for a change to one field.

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;
import java.util.ArrayList;
import java.util.List;

public class JdbcBaseline {

    record Product(long id, String sku, int priceInCents) {}

    public static void main(String[] args) throws SQLException {
        String url = "jdbc:h2:mem:JdbcBaseline;DB_CLOSE_DELAY=-1";
        try (Connection c = DriverManager.getConnection(url, "sa", "")) {
            c.setAutoCommit(false);                         // a transaction starts here

            try (Statement s = c.createStatement()) {
                s.execute("create table product (" +
                          "id bigint generated always as identity primary key, " +
                          "sku varchar(16) not null unique, " +
                          "price_in_cents int not null)");
            }

            try (PreparedStatement ps = c.prepareStatement(
                    "insert into product (sku, price_in_cents) values (?, ?)")) {
                ps.setString(1, "BOLT-7"); ps.setInt(2, 80); ps.executeUpdate();
                ps.setString(1, "NUT-3");  ps.setInt(2, 25); ps.executeUpdate();
            }
            c.commit();

            List cheap = new ArrayList<>();
            try (PreparedStatement ps = c.prepareStatement(
                    "select id, sku, price_in_cents from product where price_in_cents < ? order by sku")) {
                ps.setInt(1, 100);
                try (ResultSet rs = ps.executeQuery()) {
                    while (rs.next()) {                      // row -> object, by hand, column by column
                        cheap.add(new Product(rs.getLong("id"), rs.getString("sku"), rs.getInt("price_in_cents")));
                    }
                }
            }
            System.out.println("mapped by hand = " + cheap);

            try (PreparedStatement ps = c.prepareStatement(
                    "update product set price_in_cents = ? where sku = ?")) {
                ps.setInt(1, 90); ps.setString(2, "BOLT-7");
                System.out.println("rows updated   = " + ps.executeUpdate());
            }
            c.commit();
        }
    }
}
  
mapped by hand = [Product[id=1, sku=BOLT-7, priceInCents=80], Product[id=2, sku=NUT-3, priceInCents=25]]
rows updated   = 1

Nothing here is wrong. JDBC is explicit, fast, and every statement is one you wrote. The cost is repetition that must agree: the column list appears in the DDL, the insert, the select and the mapping loop, and a renamed column breaks all four at runtime, not at compile time. Multiply by forty tables and two hundred queries and the mapping code is the largest, dullest, most bug-prone part of the application. That is the problem an ORM solves — not "writing SQL", which it cannot spare you from reading, but writing the same SQL and the same mapping over and over.

Worked example, part 2: the same thing as an entity

Now the ORM version. The class is annotated instead of mapped by hand; the table is generated from it; the insert, the select and the update are all written by Hibernate. Read the program, then read the SQL it produced — every Hibernate: line below was captured from the real run.

import jakarta.persistence.*;
import java.util.List;

public class FirstEntity {

    @Entity(name = "Product")              // the name JPQL uses; for a nested class it would otherwise be FirstEntity$Product
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;
        private int priceInCents;

        protected Product() {}             // JPA instantiates entities reflectively
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }

        Long id() { return id; }
        String sku() { return sku; }
        int priceInCents() { return priceInCents; }
        void reprice(int cents) { this.priceInCents = cents; }
        @Override public String toString() { return "Product[" + id + ", " + sku + ", " + priceInCents + "c]"; }
    }

    static EntityManagerFactory emf(Class... entities) {
        var cfg = new PersistenceConfiguration("warehouse")
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:FirstEntity;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true");
        for (Class c : entities) cfg.managedClass(c);
        return cfg.createEntityManagerFactory();
    }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf(Product.class)) {

            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                em.persist(new Product("BOLT-7", 80));
                em.persist(new Product("NUT-3", 25));
                em.getTransaction().commit();           // the inserts happen here, not at persist()
            }

            try (EntityManager em = emf.createEntityManager()) {
                List all = em.createQuery(
                        "select p from Product p order by p.sku", Product.class).getResultList();
                System.out.println("loaded " + all);
            }

            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product bolt = em.find(Product.class, 1L);
                bolt.reprice(90);                        // no SQL written by you: dirty checking does it
                em.getTransaction().commit();
                System.out.println("after reprice " + bolt);
            }
        }
    }
}

Read the output as a transcript of what Hibernate did on your behalf, in order:

  1. create global temporary table HTE_product … — a scratch table Hibernate 7 prepares on H2 for bulk JPQL update and delete statements that touch several tables (§6). It appears at the top of every program in this module; it is harmless, and from here on the text will not mention it again.
  2. drop … / create sequence / create table — schema generation, because the configuration asked for drop-and-create. The column list came from the fields of Product: @Column supplied not null unique and varchar(16); the primitive int became not null on its own, because a primitive cannot hold null. Hibernate orders columns its own way; you did not write this DDL and should not rely on its shape (§10).
  3. create sequence product_SEQ start with 1 increment by 50 — the default for GenerationType.SEQUENCE is an allocation size of 50: Hibernate asks the database for one value and hands out fifty ids from it before asking again. That is why two persist calls produced only two select next value lines here — and why a thousand would produce twenty, not a thousand. §2 compares this with the other strategies.
  4. Two inserts, after both persist calls — persist does not write. It assigns the id, registers the object with the persistence context, and queues the insert; the queue is flushed at commit. §3 is entirely about that gap, and almost every surprise in Hibernate lives in it.
  5. select p1_0.id, … from product p1_0 order by p1_0.sku — the JPQL select p from Product p became SQL with Hibernate's own aliases. JPQL names entities and fields; the SQL names tables and columns. That translation is the whole job (§6).
  6. select … where p1_0.id=? then update product set priceInCents=?,sku=? where id=? — find loaded the row; reprice changed a field in memory; nothing in the program said "update". At commit Hibernate compared the entity's current state with a snapshot taken at load, found a difference, and wrote the row back. That is dirty checking. Note that it updated every column, not only the changed one — the default, and tunable (§9, §11).

What JPA specifies, what Hibernate adds

Jakarta Persistence (JPA) is a specification: the annotations (@Entity, @Id, @OneToMany …), the EntityManager API, the query language JPQL, the Criteria API, the lifecycle rules and the exception hierarchy. Hibernate is the implementation almost everyone uses, and it has existed longer than the specification it implements; JPA was largely written by standardising what Hibernate already did. In practice you program against the JPA API and reach into Hibernate's own API when you need something the spec does not offer:

The JPA standard versus Hibernate-specific capabilities
Standard JPAHibernate-only (unwrap or annotate)
EntityManagerFactory, EntityManagerSessionFactory, Session — the same objects; em.unwrap(Session.class) gets the richer one
JPQLHQL — a superset: more functions, insert … select, with clauses, window functions
@GeneratedValue strategies@UuidGenerator styles, custom generators, @NaturalId with its own cache
@Version, LockModeType@OptimisticLocking(type = ALL), @DynamicUpdate, @SQLDelete, @SQLRestriction (§7, §11)
Entity graphs, FetchType@BatchSize, @Fetch(SUBSELECT), the Statistics API that counts statements (§5, §9)
Schema generation propertiesJDBC batching, ordered inserts/updates, StatelessSession, second-level cache integration (§9)

This module uses the JPA API wherever it exists and names every Hibernate-specific feature as such, so you know which parts would survive a switch to another provider — and which parts you would miss.

The architecture, in three objects

  • One EntityManagerFactory per application. Expensive to build (the stepper above), thread-safe, holds the metamodel, the dialect, the connection pool and the second-level cache. In a Spring application it is the bean behind every repository.
  • One EntityManager per unit of work. Cheap, not thread-safe, and the owner of a persistence context: the set of entities it currently manages. A web request, a message handler, a batch chunk — each gets its own, and closes it.
  • One transaction per unit of work, usually. Begun and committed explicitly here with EntityTransaction; in a container, declared with @Transactional and begun for you. Reads outside a transaction are allowed; writes without one are silently never flushed (§7).

When not to use an ORM

Hibernate is a tool for an object model that is persisted: a domain with identity, invariants and associations, where the same objects are loaded, changed and saved many times. It is the wrong tool when there is no such model:

  • Reporting and analytics. A query that joins six tables and groups by three columns does not want to become entities. Use a projection (§6), or skip the ORM and use a query builder such as jOOQ, which gives you type-safe SQL without pretending the result is an object graph.
  • Bulk operations. Updating a million rows through managed entities loads a million objects. Use a JPQL or native bulk statement (§6), or a StatelessSession (§9).
  • Very small applications. Three tables and ten queries are less code with Spring's JdbcClient than with an entity model, and far easier to reason about.

Most applications are a mixture: an ORM for the transactional core, plain SQL for the reports. Knowing where the line falls is a large part of what this module teaches.

The cost model: what you pay for not writing the SQL
  • SQL you did not write still runs. The update above wrote every column. A lazy collection you touched in a loop ran a query per iteration. Nothing is free because it is implicit; it is merely hidden. Keep show_sql on in development and read it, every time (§12).
  • The N+1 problem is the default outcome, not an edge case. Loading twenty orders and printing each one's lines is twenty-one queries unless you say otherwise (§5).
  • Flushes happen when Hibernate decides. Before a query that might see stale data, and at commit. An unexpected update in the middle of a read is usually a flush you did not plan for (§3).
  • The factory is slow to build and the first query is slow to run — metamodel, dialect probing, schema checks, query plan compilation. Measure a warm application, never the first request.
  • The database still has the last word. Constraints, indexes, isolation levels and locks are database facts. An ORM that lets you forget them has not made them go away.

Check yourself

1.In FirstEntity, two persist calls produced two insert statements — but only after both calls, at commit. Why?

C. This is the persistence context's write-behind behaviour: operations are collected in an action queue and flushed as late as possible so they can be ordered and batched. §3 shows exactly when a flush happens.

A confuses the database transaction with Hibernate's queue; the database executes each statement as it arrives. B is backwards — the sequence was consulted at each persist (two select next value lines appear before the inserts). D is invented: show_sql prints at execution time, which is exactly how you can tell that execution was deferred.

2.The program never contains the word update, yet an update product set … statement ran. Which mechanism produced it?

B. The snapshot comparison is why a managed entity needs no "save" call — and why it is dangerous to hand managed entities to code that mutates them casually: every change is a pending update.

A would mean a round trip per field assignment; nothing in the output shows that. C: Hibernate uses proxies for lazy loading, not for intercepting setters on an entity you constructed with new. D is false — unchanged entities produce no SQL at all, which is what makes loading a thousand products for a read cheap.

3.Which of these are good reasons to bypass the ORM for a particular piece of code? Select all that apply.

A and D. A read-only aggregate has no object model to manage, and a bulk move has no business passing through two million managed entities; both are SQL jobs (or a projection / bulk JPQL statement, §6).

B is the ORM's home ground: load, mutate, let dirty checking write the change, with optimistic locking for free (§7). C is far too broad — JPQL and the Criteria API join entities perfectly well, and join fetch is the standard fix for N+1 (§5).
