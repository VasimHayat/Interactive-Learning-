Section 6

JPQL, the Criteria API and native SQL

find() gets you one row by primary key. Everything else — a filtered list, a report, a page of results, a bulk price change — needs a query, and JPA gives you three ways to write one. JPQL is a query language over entities and their attributes: you name Product and p.priceInCents, never the table or the column, and Hibernate translates to the SQL of whatever database it is talking to. The Criteria API builds the same query from Java objects, which is the right tool when the shape of the query depends on which filters a user filled in. Native SQL is the escape hatch for the one query per project that genuinely needs a database-specific feature.

The mental model that keeps JPQL from feeling like "SQL with the keywords moved": a JPQL query walks the object graph. l.product.sku is a path through a @ManyToOne, and Hibernate turns the path into a join for you. o.lines is empty is a predicate on a collection, and Hibernate turns it into a not exists subquery. You describe what you want in terms of the model from §2 and §4; the SQL below each query in the worked example is what that description became.

Worked example

One factory, three entities, eleven queries. The order with no lines (initech) is there on purpose: it is what makes left join and is empty show their difference from their inner-join cousins. Every Hibernate: line is the SQL this program actually sent to H2.

import jakarta.persistence.*;
import jakarta.persistence.criteria.*;
import java.util.ArrayList;
import java.util.List;

public class Queries {

    public enum Category { FASTENER, STRUCTURAL, MOTION }

    @Entity(name = "Product")
    @Table(name = "product")
    @NamedQuery(name = "Product.bySku", query = "select p from Product p where p.sku = :sku")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;
        @Enumerated(EnumType.STRING) @Column(nullable = false, length = 16)
        private Category category;
        private int priceInCents;

        protected Product() {}
        Product(String sku, Category category, int priceInCents) {
            this.sku = sku; this.category = category; this.priceInCents = priceInCents;
        }
        String sku() { return sku; }
        int priceInCents() { return priceInCents; }
        @Override public String toString() { return sku + "@" + priceInCents + "c"; }
    }

    @Entity(name = "PurchaseOrder")                 // "Order" is an SQL keyword; name the entity and table safely
    @Table(name = "purchase_order")
    public static class PurchaseOrder {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, length = 32)
        private String customer;
        @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
        private List lines = new ArrayList<>();

        protected PurchaseOrder() {}
        PurchaseOrder(String customer) { this.customer = customer; }
        PurchaseOrder add(Product p, int qty) { lines.add(new OrderLine(this, p, qty)); return this; }
        String customer() { return customer; }
    }

    @Entity(name = "OrderLine")
    @Table(name = "order_line")
    public static class OrderLine {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @ManyToOne(fetch = FetchType.LAZY, optional = false) @JoinColumn(name = "order_id")
        private PurchaseOrder order;
        @ManyToOne(fetch = FetchType.LAZY, optional = false) @JoinColumn(name = "product_id")
        private Product product;
        private int qty;

        protected OrderLine() {}
        OrderLine(PurchaseOrder order, Product product, int qty) { this.order = order; this.product = product; this.qty = qty; }
    }

    /** A DTO for projections: the query instantiates it directly, no entity is hydrated. */
    public record SkuRevenue(String sku, long cents) {}

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Product.class).managedClass(PurchaseOrder.class).managedClass(OrderLine.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:Queries;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();
    }

    static void seed(EntityManagerFactory emf) {
        try (EntityManager em = emf.createEntityManager()) {
            em.getTransaction().begin();
            Product bolt = new Product("BOLT-7", Category.FASTENER, 80);
            Product nut  = new Product("NUT-3",  Category.FASTENER, 25);
            Product gird = new Product("GIRD-1", Category.STRUCTURAL, 120_000);
            Product cam  = new Product("CAM-9",  Category.MOTION, 2_300);
            for (Product p : List.of(bolt, nut, gird, cam)) em.persist(p);
            em.persist(new PurchaseOrder("acme").add(bolt, 100).add(nut, 400));
            em.persist(new PurchaseOrder("globex").add(bolt, 50).add(gird, 1));
            em.persist(new PurchaseOrder("initech"));                       // an order with no lines
            em.getTransaction().commit();
        }
    }

    static void section(String title) { System.out.println("-- " + title + " --"); }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {
            seed(emf);
            try (EntityManager em = emf.createEntityManager()) {

                section("named parameter");
                List dear = em.createQuery(
                        "select p from Product p where p.priceInCents > :min order by p.sku", Product.class)
                    .setParameter("min", 1_000).getResultList();
                System.out.println(dear);

                section("join + aggregate + having + DTO projection");
                List revenue = em.createQuery(
                        "select new Queries$SkuRevenue(p.sku, sum(l.qty * p.priceInCents)) " +
                        "from OrderLine l join l.product p " +
                        "group by p.sku having sum(l.qty) >= :minQty order by p.sku", SkuRevenue.class)
                    .setParameter("minQty", 100L).getResultList();
                System.out.println(revenue);

                section("left join: products that were never ordered still appear");
                List counts = em.createQuery(
                        "select p.sku, count(l) from Product p left join OrderLine l on l.product = p " +
                        "group by p.sku order by p.sku", Object[].class).getResultList();
                for (Object[] row : counts) System.out.println(row[0] + " ordered on " + row[1] + " line(s)");

                section("pagination");
                List page2 = em.createQuery("select p from Product p order by p.sku", Product.class)
                    .setFirstResult(2).setMaxResults(2).getResultList();
                System.out.println(page2);

                section("in with a list parameter");
                System.out.println(em.createQuery(
                        "select p from Product p where p.sku in :skus order by p.sku", Product.class)
                    .setParameter("skus", List.of("NUT-3", "CAM-9")).getResultList());

                section("collection predicates: is empty, size()");
                System.out.println(em.createQuery(
                        "select o.customer from PurchaseOrder o where o.lines is empty", String.class).getResultList());
                System.out.println(em.createQuery(
                        "select o.customer from PurchaseOrder o where size(o.lines) = 2 order by o.customer", String.class).getResultList());

                section("named query, single result, result stream");
                Product bolt = em.createNamedQuery("Product.bySku", Product.class)
                    .setParameter("sku", "BOLT-7").getSingleResult();
                System.out.println("single = " + bolt);
                long cheap = em.createQuery("select p from Product p", Product.class)
                    .getResultStream().filter(p -> p.priceInCents() < 100).count();
                System.out.println("cheap via stream = " + cheap);

                section("bulk update bypasses the persistence context");
                em.getTransaction().begin();
                int changed = em.createQuery(
                        "update Product p set p.priceInCents = p.priceInCents + 5 where p.category = :c")
                    .setParameter("c", Category.FASTENER).executeUpdate();
                System.out.println("rows updated = " + changed);
                System.out.println("managed copy still says " + bolt.priceInCents() + "c");
                em.refresh(bolt);
                System.out.println("after refresh " + bolt.priceInCents() + "c");
                em.getTransaction().commit();

                section("native SQL");
                List raw = em.createNativeQuery(
                        "select sku, priceInCents from product where category = 'FASTENER' order by sku", Object[].class)
                    .getResultList();
                for (Object[] row : raw) System.out.println(row[0] + " " + row[1]);

                section("Criteria API: a dynamic filter");
                System.out.println(find(em, Category.FASTENER, null));
                System.out.println(find(em, null, 2_000));

                section("Criteria API: construct projection");
                CriteriaBuilder cb = em.getCriteriaBuilder();
                CriteriaQuery cq = cb.createQuery(SkuRevenue.class);
                Root l = cq.from(OrderLine.class);
                Join p = l.join("product");
                cq.select(cb.construct(SkuRevenue.class, p.get("sku"), cb.sum(cb.prod(l.get("qty"), p.get("priceInCents")))))
                  .groupBy(p.get("sku"))
                  .orderBy(cb.asc(p.get("sku")));
                System.out.println(em.createQuery(cq).getResultList());
            }
        }
    }

    /** Predicates are added only for the filters the caller supplied — no string concatenation. */
    static List find(EntityManager em, Category category, Integer minPrice) {
        CriteriaBuilder cb = em.getCriteriaBuilder();
        CriteriaQuery cq = cb.createQuery(Product.class);
        Root p = cq.from(Product.class);
        List where = new ArrayList<>();
        if (category != null) where.add(cb.equal(p.get("category"), category));
        if (minPrice != null) where.add(cb.ge(p.get("priceInCents"), minPrice));
        cq.select(p).where(where.toArray(new Predicate[0])).orderBy(cb.asc(p.get("sku")));
        return em.createQuery(cq).getResultList();
    }
}

Reading the SQL, query by query

  • Named parameter. :min became a JDBC ?. The value travels separately from the SQL text, so the database can cache one plan for every price, and a value that happens to contain a quote cannot change the query. Never build a JPQL string with + sku + "'"; that is the SQL-injection bug with an extra layer of paint.
  • Join, aggregate, having, DTO. join l.product p became join product p1_0 on p1_0.id=ol1_0.product_id — Hibernate knew the foreign key from the @ManyToOne mapping. select new Queries$SkuRevenue(…) handed each row straight to the record's constructor: no Product entity was loaded, nothing became managed, and the result is a plain immutable value you can return from a service without a lazy-loading worry. The class name in select new is the binary name, hence the $ for a nested record.
  • Left join with on. count(l) became count(ol1_0.id), which counts 0 for CAM-9 because its joined columns are all null. An inner join would have dropped the row; a path like p.lines would have required a mapped collection. The explicit on clause (JPA 2.1) lets you join two entities that have no mapped association between them.
  • Pagination. setFirstResult(2).setMaxResults(2) became offset ? rows fetch first ? rows only — the SQL:2008 form, chosen by the H2 dialect; MySQL would get limit ?,?. Pagination without an order by is a bug: the database is free to return pages in any order, and the same row can appear on two pages.
  • in :skus. The list was expanded to in (?,?) — one placeholder per element, bound in order. A list of a different length is a different SQL string, which matters for the database's plan cache when callers pass lists of wildly varying sizes.
  • Collection predicates. o.lines is empty became not exists(select 1 …) and size(o.lines) = 2 became a correlated (select count(*) …) = 2. Neither loaded a single OrderLine; the database answered the question about the collection.
  • Named query, single result, stream. @NamedQuery is parsed and validated once, at factory start-up, so a typo fails at boot rather than at 3 a.m. getSingleResult() throws NoResultException on zero rows and NonUniqueResultException on two; for a lookup that may miss, prefer getResultList() or Hibernate's uniqueResultOptional(). The stream example is a trap shown deliberately: filter(p -> p.priceInCents() < 100) ran in Java after every product had been loaded — look at the SQL, it has no where. Filter in the query, not in the stream.
  • Bulk update. One update product … where category=? changed two rows without loading either. The price is the point of the next three lines: bolt was loaded earlier in this same persistence context, and it still says 80c, because a bulk statement talks to the database directly and the first-level cache (§3) is never told. refresh() re-reads the row. In the Criteria filter further down, NUT-3 prints as 25c for the same reason: the query returned the row, but the identity guarantee handed back the already-managed instance with its stale field. Bulk operations belong at the start of a transaction, or in one of their own.
  • Native SQL. Tables and columns, verbatim, sent as written. The default column name for priceInCents is priceInCents — Hibernate's default naming strategy copies the field name; a CamelCaseToUnderscoresNamingStrategy would make it price_in_cents, and a native query is the first thing that breaks when someone changes the strategy.
  • Criteria, dynamic filter. find(em, FASTENER, null) and find(em, null, 2_000) produced two different where clauses from one method and zero string concatenation. That is what the Criteria API is for. The second query, construct(…), is the typed twin of select new; note Hibernate aliased the columns c0, c1 and ordered by position.

Hibernate 6+ also instantiates a record or a class with a matching constructor when you pass it as the result type without select new: createQuery("select p.sku, p.priceInCents from Product p", SkuPrice.class). It is convenient and non-standard; select new is the portable spelling.

setFirstResult / setMaxResults become the dialect's offset and limit syntax, and they are the only correct way to page: loading everything and calling subList is a memory bomb with a delay fuse.

The trap is paginating a fetch join. select o from PurchaseOrder o join fetch o.lines returns one SQL row per line, so a database-side limit of 10 rows is not 10 orders. Hibernate refuses to guess: it loads the whole result set and pages in memory, logging HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory. Page the parent ids first, then fetch the collections for that page in a second query, or use @BatchSize (§5).

Keyset pagination — where (placedOn, id) > (:lastDate, :lastId) order by placedOn, id — is what large tables need; offset pagination re-reads every skipped row.

A native query is sent verbatim, so it can use anything the database has: window functions, jsonb operators, recursive CTEs, vendor hints. The cost is portability and the fact that Hibernate cannot validate it at start-up.

  .setParameter("c", "FASTENER").getResultList();

// entities: Hibernate maps the columns by name onto the entity — they ARE managed
em.createNativeQuery("select * from product where priceInCents > 1000", Product.class).getResultList();

// a DTO via @SqlResultSetMapping(name = "skuRevenue",
//     classes = @ConstructorResult(targetClass = SkuRevenue.class,
//               columns = { @ColumnResult(name = "sku"), @ColumnResult(name = "cents", type = Long.class) }))
em.createNativeQuery("select p.sku as sku, sum(l.qty * p.priceInCents) as cents from order_line l " +
                     "join product p on p.id = l.product_id group by p.sku", "skuRevenue").getResultList();

Parameters work exactly as in JPQL; never concatenate. A native update bypasses the persistence context just like a JPQL bulk update, with the same staleness consequence.

  • setHint("org.hibernate.readOnly", true) — Hibernate skips the dirty-checking snapshot for the loaded entities: less memory, no accidental UPDATE. §9 uses it for reports.
  • setHint("org.hibernate.fetchSize", 500) — the JDBC fetch size for getResultStream(), so a million-row export does not load a million rows at once (driver-dependent; PostgreSQL also needs a transaction).
  • setHint("jakarta.persistence.query.timeout", 5000) — milliseconds before the driver cancels the statement.
  • setHint("jakarta.persistence.fetchgraph", graph) — an entity graph (§5) decides what to fetch eagerly for this one query.

The static metamodel (Product_.sku, Product_.priceInCents), generated at compile time by hibernate-jpamodelgen, replaces the string p.get("sku") in Criteria queries with a typed, refactoring-safe reference. Any Criteria query longer than a few lines should use it; this module's examples use strings only because they must compile from a single file.

Query mistakes that pass code review
  • Filtering in Java. getResultList().stream().filter(…) loads every row to throw most away. If the predicate can be said in JPQL, say it there.
  • Implicit joins in the where clause. where l.product.category = :c is fine; select l.product from OrderLine l is an implicit inner join that silently drops lines whose product is null. Write the join you mean.
  • Bulk update, then trusting managed entities. Shown above: the entities are stale until refresh() or clear(). Hibernate's Statistics will not warn you.
  • Pagination without order by. Pages overlap and skip. Order by something unique — add the id as a tiebreaker.
  • Building JPQL with string concatenation for optional filters. It works until the day two filters are both null and you ship where and. The Criteria API exists for exactly this.
  • getSingleResult() for a lookup that may miss. NoResultException is an unchecked exception that also marks the transaction for rollback in a container. Use getResultList() and check isEmpty(), or getResultStream().findFirst().

Check yourself

1.A colleague writes em.createQuery("select p from Product p where p.sku = '" + sku + "'"). What is wrong with it?

B. JPQL is translated to SQL and sent to the database, so a value containing ' or '1'='1 rewrites the query exactly as it would in raw SQL. Even with trusted input, each distinct string is a distinct statement that must be parsed and planned; a :sku parameter gives one plan for every value.

A is the dangerous belief that makes this bug common. C is false: literals are legal, which is why the code compiles and runs. D misses that a quote, not a space, is the problem — and that the plan-cache cost applies to every value.

2.Inside a transaction, bolt is a managed Product at 80c. You run em.createQuery("update Product p set p.priceInCents = p.priceInCents + 5").executeUpdate(). What does bolt.priceInCents() return immediately afterwards?

B. The worked example printed exactly this: managed copy still says 80c. A bulk JPQL or native update is executed as one SQL statement; Hibernate does not know which managed objects it touched and does not try to find out. refresh(bolt) or clear() is on you.

A describes what people expect and is why the bug is subtle. C is wrong: nothing throws, which is the whole problem. D is wrong too: commit flushes dirty entities to the database, it never pulls database changes into entities — and if bolt were dirty, its stale 80 would overwrite the 85.

3.Which of these produce no managed entities? Select all that apply.

A and C. A constructor projection and a scalar projection both return values that are not entities; the persistence context is neither consulted nor populated, and nothing will be dirty-checked at flush.

B returns entities, which are managed. D is the one people miss: a native query whose result type is an entity class maps the columns onto managed entities exactly like a JPQL query would — it is only the text that bypasses Hibernate, not the result handling.
