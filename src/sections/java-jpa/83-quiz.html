Self-assessment quiz

Sixteen questions covering all twelve learning objectives. Answer every one, then submit — nothing is marked until you do, and the explanations stay hidden until then. Your answers are saved locally, so you can leave and come back. Each question about runtime behaviour was checked against this module's verified programs on Hibernate 7.4 and H2.

1.An entity uses GenerationType.SEQUENCE with the default allocation size. Inside a transaction you call em.persist(product) and stop there. Which SQL has executed so far?

B. The identity map needs a key, so the sequence is consulted at persist (once per block of fifty); the insert waits for the flush. FirstEntity printed two sequence calls, then two inserts at commit. A and D describe IDENTITY, where the row must be inserted to obtain the key. C is contradicted by the id being printable before commit.

2.Product has SEQUENCE ids, Warehouse has IDENTITY ids. In one transaction the code persists a product, then a warehouse, then prints a line, then commits. Which inserts have run when the line is printed?

C. The Mapping program's output shows the product insert, then insert into warehouse … values (?,default), and only then the printed line. A ignores that an identity column is assigned by the database during the insert. B misses the ordering rule: Hibernate does not let a later insert overtake an earlier queued one. D has the forced insert on the wrong entity.

3.sku has a unique constraint. One transaction calls em.remove(oldBolt), then persists a new product with the same SKU, then commits. Result?

B. The action queue is sorted at flush: inserts, updates, collection changes, deletes. An explicit flush() between the two calls fixes it. A is the assumption behind the bug. C concerns a duplicate id in the context; the new entity has a fresh one. D: two different entities are never folded into one statement.

4.Order.lines is @OneToMany(mappedBy = "order", cascade = ALL, orphanRemoval = true) and OrderLine.order is the @ManyToOne with the @JoinColumn. Which are true? Select all that apply.

A and C. Both were printed by the Relationships program: a line with order_id null in block 1, and a delete from order_line after removeLine in block 3. B is reversed — the side holding the foreign key owns the association, and mappedBy marks Order.lines as inverse. D: cascade = ALL includes REMOVE, so the lines are deleted before the order.

5.Fifty orders with a lazy lines collection are loaded with select o from Order o, and a loop reads getLines().size() on each. Statement count with the default mapping, and with @BatchSize(size = 25) on the collection?

C. One query for the orders plus one per collection: 51. Batch fetching groups the collection loads into in (…) chunks: 1 + ⌈50 / 25⌉ = 3, the same arithmetic as phase D of NPlusOne. A would need join fetch or an entity graph. B drops the orders query. D halves the loads instead of chunking them.

6.A template reads order.getLines() after the service's EntityManager closed and gets LazyInitializationException. Which fix removes both the exception and the hidden extra queries?

D. The exception means the entity outlived its context; deciding what the view needs inside the service fixes the cause in one statement. A is open-session-in-view: the lazy loads now succeed from the template, one query each, with a connection held for the whole request. B changes every load forever and, for JPQL, still issues the extra selects. C renders wrong data.

7.What SQL shape does select o.customer from PurchaseOrder o where o.lines is empty become?

B. The Queries program printed exactly that not exists subquery; size(o.lines) = 2 likewise became a correlated count(*) subquery. A is a valid hand-written alternative but not what Hibernate emits. C describes lazy loading, which a predicate never triggers. D: collection predicates are part of JPQL.

8.bolt is a managed Product at 80 cents. The same transaction runs the bulk statement update Product p set p.priceInCents = p.priceInCents + 5 where p.category = :c, which affects that row. What does bolt.priceInCents() return right after executeUpdate()?

C. The output reads managed copy still says 80c and then after refresh 85c. Bulk statements go straight to the database; managed copies keep their snapshot, and a later flush could even overwrite the bulk change with stale values. A and B invent synchronisation that does not exist. D: versions are checked when this context writes, not when it reads.

9.In an empty table, inside one transaction, the code persists a product and then runs select count(p) from Product p. What is the count with the default flush mode, and with FlushModeType.COMMIT?

A. FlushModeType.AUTO flushes the pending insert before a query that could see it, so the count is 1; COMMIT defers the insert to commit and the query counts 0. Both numbers are printed by Flushing. B and C deny that the mode changes anything. D has the two modes swapped.

10.Which statements about committing are true on Hibernate 7.4 with default settings? Select all that apply.

B and D. OptimisticLock printed RollbackException caused by OptimisticLockException; Flushing printed that commit() returned normally after setRollbackOnly() and no row was written. A forgets the wrapping at commit time. C is the JPA-specified behaviour, which Hibernate adopts only with hibernate.jpa.compliance.transaction=true.

11.CardPayment extends Payment must store last4 as NOT NULL, and Payment ids come from an identity column. Which strategy satisfies both?

B. A subclass table of its own can carry last4 varchar(4) not null, as the InheritanceMapping DDL showed, and identity ids are fine because the parent row is inserted first. A forces subclass columns to be nullable. C cannot use identity ids — keys must be unique across tables, so a sequence is required. D makes Payment unqueryable and gives no polymorphism.

12.A loop persists 100 products with hibernate.jdbc.batch_size=20 and order_inserts=true. Prepared-statement count with IDENTITY ids, and with SEQUENCE ids (default allocation) plus flush()/clear() every 20?

C. These are the numbers Batching measured: every IDENTITY insert is its own statement, while SEQUENCE lets the inserts queue and batch — five batches of twenty plus the sequence round trips. A gives IDENTITY a batching ability it does not have. B is false; inserts batch when deferred. D: an identity insert cannot be grouped at all.

13.Production configuration sets jakarta.persistence.schema-generation.database.action=none and hibernate.hbm2ddl.auto=validate. A migration was forgotten and a mapped column is missing. What happens at startup?

C. The §10 worked example hit this: with the JPA key set, validate is ignored. Set only hibernate.hbm2ddl.auto=validate to get A, which is the behaviour you want. B is what update would do, and why update is not a deployment strategy. D is invented; Hibernate never silently drops a mapped column.

14.An entity's equals and hashCode use its generated id. The code adds a new instance to a HashSet, persists it, then calls set.contains(instance). Result?

B. EntityDesign printed id-based hashCode : id=1, set.contains = false; a business-key hash or a constant hash with an id-based equals printed true. A confuses identity with hashing — HashSet finds the bucket first. C needs iteration during modification, which did not happen. D: flushing writes the row; it does not move the object between buckets.

15.An entity carries @SQLDelete(sql = "update soft_product set deleted = true where id = ?") and @SQLRestriction("deleted = false"). After em.remove(p) and commit, what do select count(p) from SoftProduct p (JPQL) and select count(*) from soft_product (native) return for a table that held only that row?

C. remove became an update … set deleted = true, the restriction hides the row from JPQL and find, and native SQL still sees it — JPQL count = 0, native count = 1 in the worked example. A would need a real delete. B ignores the restriction. D reverses which API sees the filter.

16.Which of these were demonstrated by this module's verified programs? Select all that apply.

A, B and D. A is why Batching switched the echo off and counted with statistics. B was visible in Relationships block 4: find(Product) also selected product_details, because Hibernate cannot proxy a field that may be null. D is the JPQL in Queries. C is false: for JPQL an eager collection is loaded by secondary selects after the query — the statement count does not drop, which is one more reason to keep every mapping lazy.
