Section 10

Schema generation, validation and migrations

Every program in this module has started with drop-and-create: Hibernate reads the mappings, derives DDL, and builds a fresh schema in an empty in-memory database. That is exactly right for a learning page and a test, and exactly wrong for a database with data in it. The question this section answers is who owns the schema once the data matters — and the answer is never "the application at startup".

Two vocabularies describe the same switch. JPA's is jakarta.persistence.schema-generation.database.action with the values none, create, drop, drop-and-create; Hibernate's older hibernate.hbm2ddl.auto adds the two values JPA does not have, update and validate. When both are set, the JPA property wins and the Hibernate one is ignored — a detail that bit the worked example below on its first draft.

Worked example: generate, export, validate, and refuse

One in-memory database, three bootstraps. The first generates the schema from the v1 mapping and also writes the DDL to a script file. The second starts with validate against the same mapping and is allowed through. The third validates a v2 mapping that gained a field nobody migrated — and the program ends there, in the exception the build expects.

import jakarta.persistence.*;

import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;

public class SchemaValidate {

    /* Version 1 of the mapping: what the database was created from. */
    @Entity(name = "StockLevel")
    @Table(name = "stock_level")
    public static class StockLevel {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
        @Column(nullable = false, unique = true, length = 16) private String sku;
        private int onHand;
        protected StockLevel() {}
        StockLevel(String sku, int onHand) { this.sku = sku; this.onHand = onHand; }
    }

    /* Version 2 of the mapping: a developer added a field — but nobody migrated the table. */
    @Entity(name = "StockLevelV2")
    @Table(name = "stock_level")
    public static class StockLevelV2 {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
        @Column(nullable = false, unique = true, length = 16) private String sku;
        private int onHand;
        private int reorderPoint;          // new column, never added to the schema
        protected StockLevelV2() {}
    }

    static PersistenceConfiguration base(Class entity) {
        return new PersistenceConfiguration("warehouse")
            .managedClass(entity)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:SchemaValidate;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property("hibernate.show_sql", "true");
    }

    public static void main(String[] args) throws Exception {
        System.out.println("-- 1. generate the schema from the v1 mapping, and export the DDL to a script --");
        Path script = Path.of("schema.sql");
        Files.deleteIfExists(script);
        var create = base(StockLevel.class)
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property(PersistenceConfiguration.SCHEMAGEN_SCRIPTS_ACTION, "create")
            .property("jakarta.persistence.schema-generation.scripts.create-target", script.toString());
        try (EntityManagerFactory emf = create.createEntityManagerFactory();
             EntityManager em = emf.createEntityManager()) {
            em.getTransaction().begin();
            em.persist(new StockLevel("BOLT-7", 120));
            em.getTransaction().commit();
        }
        System.out.println("- schema.sql, the starting point for a hand-written migration -");
        for (String line : Files.readAllLines(script)) System.out.println("  " + line);
        Files.delete(script);

        System.out.println("-- 2. start again with 'none' + validate against the v1 mapping: fine --");
        var validateV1 = base(StockLevel.class)
            .property("hibernate.hbm2ddl.auto", "validate");
        try (EntityManagerFactory emf = validateV1.createEntityManagerFactory();
             EntityManager em = emf.createEntityManager()) {
            List rows = em.createQuery("select s.sku from StockLevel s").getResultList();
            System.out.println("validated, rows = " + rows);
        }

        System.out.println("-- 3. the v2 mapping against the unmigrated table: bootstrap refuses --");
        var validateV2 = base(StockLevelV2.class)
            .property("hibernate.hbm2ddl.auto", "validate");
        EntityManagerFactory never = validateV2.createEntityManagerFactory();   // throws SchemaManagementException
        never.close();
        System.out.println("unreachable");
    }
}

Three things to take from the output. The schema.sql that step 1 wrote is almost the DDL that ran, and it is the right starting point for a migration: copy it into a versioned script, read every line, fix the names you do not like, add the index the mapping cannot express, and commit it. Step 2 shows validate costing one metadata query at startup and nothing else. Step 3 is the payoff: the deploy fails at bootstrap with the exact column named, instead of succeeding and then failing on the first request that touches reorderPoint. Notice also that validate left the HTE_stock_level temporary table alone in step 2 but recreated it in step 3 with the new column: that table is not part of your schema at all. Hibernate 7 declares it at every bootstrap for bulk-mutation queries, which is why it appears even under none, and why validate never complains about it.

Is this setting safe here?

Schema setting versus environment

Why update is not a migration

update looks like the grown-up option: it keeps the data and adds what is missing. The trouble is everything it cannot know. Rename a field from onHand to quantityOnHand and update adds a new nullable column and leaves the old one full of data, forever. Remove a field and the column stays. Narrow a String from 255 to 16 characters and nothing happens, because shrinking might fail. Add a nullable = false column to a populated table and the ALTER fails, or on some databases succeeds and leaves nulls in a not-null column. Add a unique constraint that existing data violates and startup fails in production at the worst possible moment. And in every case the DDL ran unreviewed, under the application's credentials, at the instant the pod started, possibly holding a table lock while traffic waited.

A migration tool fixes all of that by making schema change a versioned, reviewed, ordered artefact that runs once per environment and records that it ran.

src/main/resources/db/migration/
  V1__create_product_and_stock.sql      <- the hand-edited output of schema.sql
  V2__add_reorder_point.sql             <- alter table stock_level add column reorder_point integer not null default 0;
  V3__backfill_reorder_point.sql        <- update stock_level set reorder_point = 10 where ...;
  R__product_view.sql                   <- repeatable: re-run whenever its checksum changes
      
# Flyway and Liquibase are not on this page's class path — these are shown, not run
flyway -url=jdbc:postgresql://db/warehouse -user=deploy migrate     # applies V2, V3 in order, records each in flyway_schema_history
flyway info                                                          # which versions are applied, pending, or failed
flyway validate                                                      # checksums of applied scripts still match the files
flyway baseline -baselineVersion=1                                   # adopt an existing database without re-running V1

Plain SQL, one file per change, a version in the name, a checksum recorded on apply so an edited historical script is detected. Simple enough that the review is of the SQL itself, which is the point.

Liquibase describes changes in a database-neutral form (YAML, XML, JSON or SQL) and renders them per dialect, tracks them in DATABASECHANGELOG, and supports declared rollbacks and preconditions. More machinery than Flyway; worth it when the same migrations must run on several database products.

  1. Change the mapping in the entity.
  2. Generate the DDL difference locally — schema-generation.scripts.action=create for a new table, or simply read what update would have done against a scratch database.
  3. Write the migration by hand from that output: real names, the index, the default value, the backfill, the constraint added after the backfill.
  4. Review it like code. Ask what happens to a 50-million-row table while this runs, and whether the previous version of the application can still run against the new schema during a rolling deploy.
  5. Run it in CI against a real database engine (Testcontainers), then run the tests with validate.
  6. Deploy with the migration step before the application starts, and the application on validate.

What validate checks, and what it does not

Validation compares, for every mapped entity: that the table exists, that each mapped column exists, and that each column's type is compatible with the mapping. It does not check indexes, foreign-key or unique-constraint names, column nullability, defaults, or column length on most dialects. So validate catches the missing column and the wrong type — the two failures that break at runtime — and ignores the ones that only affect performance or integrity. Those still need a migration review; validate is a tripwire, not an audit.

Naming is the other half. By default Hibernate derives column names from field names as written (priceInCents becomes a column called priceInCents, as every echoed statement in this module shows); most teams install a physical naming strategy that produces price_in_cents instead (hibernate.physical_naming_strategy, or the CamelCaseToUnderscoresNamingStrategy that Spring Boot applies by default). Whichever you choose, choose it before the first migration is written, because renaming later is exactly the change update cannot make.

Schema gotchas
  • The JPA property silently wins. With schema-generation.database.action=none set, hbm2ddl.auto=validate is ignored and no validation happens. The first draft of the worked example printed "unreachable". Set one or the other.
  • H2 in tests, PostgreSQL in production. Types differ (timestamp(6) with time zone is not the same object in both), sequences differ, for update and on conflict differ, case-sensitivity of identifiers differs. A migration that passed on H2 can fail on PostgreSQL. Test on the engine you deploy to; Testcontainers makes that a one-line annotation.
  • create drops tables it does not own. Anything mapped is dropped, including a table another service shares with you.
  • Sequences are schema too. product_SEQ in the echoed DDL must exist in production with the same increment, or ids collide. A migration that creates the table but not the sequence passes validate (which does not check sequences) and fails on the first insert.
  • Rolling deploys need backward-compatible schemas. Add the column, deploy code that writes both, backfill, deploy code that reads the new column, drop the old one — five steps, two releases. A rename in one migration breaks the old pods still running.

Check yourself

1.A team renames the entity field onHand to quantity and deploys with hbm2ddl.auto=update. What happens to the production table?

C. update only adds. It cannot know a rename from an add-plus-remove, so it adds the new column and never drops anything. Every stock level now reads as null or zero, and nothing failed to tell you.

A would require intent the tool cannot infer. B is what validate does, not update. D is wrong because update never drops — which is sometimes presented as its safety feature, and is really why drift accumulates.

2.Production runs Flyway migrations in a deploy step and starts the application with hbm2ddl.auto=validate. A migration added a product table but forgot the product_SEQ sequence the mapping uses. When does this fail?

B. Validation checks tables and columns, not sequences. Startup passes; the first insert asks the sequence for a value and the database answers that it does not exist. This is the gap between a tripwire and an audit.

A overstates what validate checks. C is false under validate and none; only the generation modes create sequences. D is false: Flyway knows nothing about JPA mappings; it runs the SQL you wrote.

3.Which are sound reasons to run integration tests against the production database engine rather than H2? Select all that apply.

A, C and D. Each is a class of bug that only the real engine reveals: DDL and types, concurrency semantics, and dialect-specific native SQL. Testcontainers makes the real engine as convenient as H2 was.

B is false — every program in this module ran on H2. H2 is a fine learning and unit-test database; the argument is about fidelity, not capability.
