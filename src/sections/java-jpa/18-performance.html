Section 9

Batching, projections and caching

Everything Hibernate does ends as a round trip to the database, and round trips are what you pay for. A persistence layer that is "slow" is almost never slow because Hibernate is slow; it is slow because it makes ten thousand trips where twenty would do, hydrates ten thousand entities to read two columns, or drags a persistence context the size of the table through a loop. This section is about seeing those trips — with Statistics, not guesswork — and removing them.

The tool matters, because show_sql misleads here: it prints one line per logical statement, so a hundred batched inserts and a hundred unbatched ones look identical on the console. Only the statistics tell you how many statements were actually prepared and sent.

Worked example: counting the trips

Three phases on one in-memory database. Phases A and B insert a hundred products each with the SQL echo off and the statistics on, so the numbers are the whole story; phase C turns the echo back on for the read paths, where the SQL itself is the lesson.

import jakarta.persistence.*;
import org.hibernate.Session;
import org.hibernate.SessionFactory;
import org.hibernate.StatelessSession;
import org.hibernate.stat.Statistics;

import java.util.List;

public class Batching {

    /* Phase A: IDENTITY ids — the database assigns the id when the row is inserted,
       so Hibernate must execute every INSERT immediately to learn it. */
    @Entity(name = "IdProduct")
    @Table(name = "id_product")
    public static class IdProduct {
        @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
        @Column(nullable = false, unique = true, length = 16) private String sku;
        private int priceInCents;
        protected IdProduct() {}
        IdProduct(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
    }

    /* Phase B: SEQUENCE ids — the id is known before the INSERT, so inserts can be
       queued and sent in batches. */
    @Entity(name = "SeqProduct")
    @Table(name = "seq_product")
    public static class SeqProduct {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
        @Column(nullable = false, unique = true, length = 16) private String sku;
        private int priceInCents;
        protected SeqProduct() {}
        SeqProduct(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
    }

    /* Phase C: the read paths, on a tiny table, with the SQL echoed. */
    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
        @Column(nullable = false, unique = true, length = 16) private String sku;
        private int priceInCents;
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        String sku() { return sku; }
        int priceInCents() { return priceInCents; }
        void setPriceInCents(int p) { this.priceInCents = p; }
        @Override public String toString() { return sku + "=" + priceInCents + "c"; }
    }

    /* A projection: no identity, no dirty checking, no persistence context entry. */
    public record ProductView(String sku, int priceInCents) {}

    static EntityManagerFactory emf(boolean showSql, boolean batching, Class... entities) {
        var cfg = new PersistenceConfiguration("warehouse")
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:Batching;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", String.valueOf(showSql))
            .property("hibernate.generate_statistics", "true");
        if (batching) {
            cfg.property("hibernate.jdbc.batch_size", "20")
               .property("hibernate.order_inserts", "true")
               .property("hibernate.order_updates", "true");
        }
        for (Class c : entities) cfg.managedClass(c);
        return cfg.createEntityManagerFactory();
    }

    static Statistics stats(EntityManagerFactory emf) {
        return emf.unwrap(SessionFactory.class).getStatistics();
    }

    public static void main(String[] args) {
        System.out.println("-- phase A: 100 inserts, IDENTITY ids, batch_size=20 --");
        try (EntityManagerFactory emf = emf(false, true, IdProduct.class)) {
            Statistics st = stats(emf);
            st.clear();
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                for (int i = 1; i <= 100; i++) em.persist(new IdProduct("ID-" + i, i));
                em.getTransaction().commit();
            }
            System.out.println("statements prepared = " + st.getPrepareStatementCount());
            System.out.println("entities inserted   = " + st.getEntityInsertCount());
        }

        System.out.println("-- phase B: 100 inserts, SEQUENCE ids, batch_size=20, flush+clear every 20 --");
        try (EntityManagerFactory emf = emf(false, true, SeqProduct.class)) {
            Statistics st = stats(emf);
            st.clear();
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                for (int i = 1; i <= 100; i++) {
                    em.persist(new SeqProduct("SEQ-" + i, i));
                    if (i % 20 == 0) { em.flush(); em.clear(); }   // bound the persistence context
                }
                em.getTransaction().commit();
            }
            System.out.println("statements prepared = " + st.getPrepareStatementCount());
            System.out.println("entities inserted   = " + st.getEntityInsertCount());
        }

        System.out.println("-- phase C: read paths --");
        try (EntityManagerFactory emf = emf(true, false, Product.class)) {
            Statistics st = stats(emf);
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                em.persist(new Product("BOLT-7", 80));
                em.persist(new Product("NUT-3", 25));
                em.persist(new Product("CAM-9", 2300));
                em.getTransaction().commit();
            }

            System.out.println("- entity query -");
            st.clear();
            try (EntityManager em = emf.createEntityManager()) {
                List all = em.createQuery("select p from Product p order by p.sku", Product.class).getResultList();
                System.out.println("rows = " + all + ", entities hydrated = " + st.getEntityLoadCount());
            }

            System.out.println("- DTO projection -");
            st.clear();
            try (EntityManager em = emf.createEntityManager()) {
                List views = em.createQuery(
                        "select p.sku, p.priceInCents from Product p order by p.sku", ProductView.class).getResultList();
                System.out.println("rows = " + views + ", entities hydrated = " + st.getEntityLoadCount());
            }

            System.out.println("- read-only session: a change is not written -");
            st.clear();
            try (EntityManager em = emf.createEntityManager()) {
                em.unwrap(Session.class).setDefaultReadOnly(true);
                em.getTransaction().begin();
                Product bolt = em.createQuery("select p from Product p where p.sku = 'BOLT-7'", Product.class).getSingleResult();
                bolt.setPriceInCents(999);
                em.getTransaction().commit();
            }
            System.out.println("entity updates = " + st.getEntityUpdateCount());

            System.out.println("- StatelessSession: no persistence context at all -");
            try (StatelessSession ss = emf.unwrap(SessionFactory.class).openStatelessSession()) {
                ss.getTransaction().begin();
                ss.insert(new Product("PIN-2", 15));
                ss.getTransaction().commit();
            }

            System.out.println("- bulk update in one statement -");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                int changed = em.createQuery("update Product p set p.priceInCents = p.priceInCents + 5").executeUpdate();
                em.getTransaction().commit();
                System.out.println("rows changed = " + changed);
            }
            try (EntityManager em = emf.createEntityManager()) {
                System.out.println("after = " + em.createQuery("select p from Product p order by p.sku", Product.class).getResultList());
            }
        }
    }
}

Read the two counts first. Phase A prepared 100 statements for 100 rows even though batch_size was set: with IDENTITY the database invents the id during the INSERT, and Hibernate must have an id for every managed entity, so each persist runs immediately and there is never anything to batch. Phase B prepared 8: three round trips to the sequence (the pooled optimiser fetches a value per block of 50, plus one call to establish its first block) and five batched INSERT executions carrying 20 rows each. Same rows, same table shape, twelve times fewer trips — and the flush(); clear() every twenty rows means the persistence context never holds more than twenty entities and their snapshots.

Phase C is about what a read costs after the SQL returns. The entity query hydrated three managed objects — each with a snapshot for dirty checking, a place in the identity map, and the obligation to be scanned at flush. The projection into ProductView selected only the two columns it needed and hydrated zero entities: Hibernate 6 and later build a record straight from the row when you pass the record class as the result type. The read-only session proves the other half: the price was changed to 999 and committed, and entity updates = 0 — no snapshot, no dirty check, no UPDATE. The StatelessSession skips the persistence context entirely (one INSERT, nothing cached, no cascades, no lazy loading), and the bulk update changed four rows in one statement instead of loading four entities to change them one by one.

The write side: rules that decide the trip count

Settings that affect batching and what each does
LeverEffectWatch out
hibernate.jdbc.batch_sizeQueues up to N inserts/updates/deletes for the same table and sends them as one JDBC batch at flush.Off by default. Pointless with IDENTITY ids.
hibernate.order_inserts / order_updatesSorts queued statements by entity type so a batch is not broken every time the loop alternates between Order and OrderLine.Without it, interleaved types yield batches of size 1.
hibernate.jdbc.batch_versioned_dataAllows batching of UPDATEs on @Versioned entities (§7); on by default since 5.x for drivers that report correct update counts.An old driver that returns SUCCESS_NO_INFO silently disables optimistic-lock checks in batches.
SEQUENCE allocation sizeOne sequence call per block of ids (50 by default). The id is known before the insert, which is what makes batching possible.Ids have gaps after a restart. That is fine; ids are identifiers, not counters.
flush() + clear()Sends the queued batch and empties the context, so memory stays flat and each flush scans only the current chunk.After clear() every previously loaded entity is detached; keep nothing from before the clear.
StatelessSessionDirect JDBC-ish operations: insert, update, delete, get. No context, no dirty checking, no cascades, no lazy loading, no first-level cache.Callbacks and listeners do not fire. Batches still apply if batch_size is set.
Bulk JPQL update / deleteOne statement for the whole set. The persistence context is not updated: entities already loaded keep their old values.Clear or refresh after a bulk statement if you continue in the same context.

The read side: fetch what the screen needs

// 1. a record, instantiated by Hibernate from the selected columns
record StockRow(String sku, int onHand) {}
List rows = em.createQuery(
    "select p.sku, s.onHand from Product p join p.stock s where s.onHand < 10", StockRow.class)
    .getResultList();

// 2. the JPA-standard spelling, any class with a matching constructor
List rows2 = em.createQuery(
    "select new com.acme.StockRow(p.sku, s.onHand) from Product p join p.stock s", StockRow.class)
    .getResultList();

// 3. untyped columns when the shape is ad hoc
List t = em.createQuery("select p.sku as sku, count(l) as lines from Product p join p.lines l group by p.sku", Tuple.class)
    .getResultList();
long lines = t.get(0).get("lines", Long.class);

A projection is the single biggest read optimisation available: fewer columns over the wire, no entity hydration, no snapshot, no dirty-check scan at flush, and nothing to accidentally lazy-load later. Report screens, lists and exports should almost never load entities.

// whole session: no snapshots are taken, flush has nothing to compare
em.unwrap(Session.class).setDefaultReadOnly(true);

// one query: the entities it returns are read-only
em.createQuery("select o from Order o", Order.class)
  .setHint("org.hibernate.readOnly", true)
  .getResultList();

// one entity, after the fact
em.unwrap(Session.class).setReadOnly(order, true);

Read-only entities are still managed — identity map, lazy loading, the lot — they just cannot be dirty. Hibernate skips the snapshot copy on load and the comparison on flush, which for a page that loads a thousand entities to render them is most of the flush cost. Changes you make are silently discarded; that is the contract, not a bug.

List page = em.createQuery("select o from Order o order by o.placed desc, o.id", Order.class)
    .setFirstResult(40)        // OFFSET
    .setMaxResults(20)         // LIMIT — Hibernate renders the dialect's syntax
    .getResultList();

// streaming a large result instead of materialising it
try (Stream s = em.createQuery("select o from Order o", Order.class)
        .setHint("org.hibernate.fetchSize", 500)
        .getResultStream()) {
    s.forEach(this::export);
}

Always order a paged query by something unique, or pages overlap. Offset paging degrades as the offset grows (the database still walks the skipped rows); keyset paging — where o.placed < :lastSeen — does not. fetchSize is a JDBC hint for how many rows the driver pulls per network read; PostgreSQL ignores it unless the connection is in a transaction with auto-commit off.

Caching: what it can and cannot do

Hibernate has three caches and they are routinely confused. The first-level cache is the persistence context itself (§3): per EntityManager, always on, guarantees one object per row and is the reason the same find twice in one context hits the database once. The second-level cache is shared across the whole EntityManagerFactory and caches entity rows by id (and collections by owner id) — not query results, and not the object graph. The query cache caches the ids returned by a particular query with particular parameters, and is invalidated the moment any table the query touches is written.

// configuration shape only — no cache provider is on this page's class path, so this block is not verified
.property("hibernate.cache.use_second_level_cache", "true")
.property("hibernate.cache.region.factory_class", "jcache")       // hibernate-jcache + a provider such as Ehcache or Caffeine
.property("hibernate.javax.cache.uri", "classpath:ehcache.xml")
.property("hibernate.cache.use_query_cache", "true")              // only if you also set the hint per query

@Entity @Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Product { ... }

@Entity @Immutable @Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_ONLY)   // the ideal cache citizen
public class Currency { ... }

em.createQuery("select p from Product p where p.category = :c", Product.class)
  .setHint("org.hibernate.cacheable", true)                         // opt in, per query
  .setParameter("c", Category.FASTENER).getResultList();
When a second-level cache is a win, and when it is a trap
  • Win: reference data read constantly and written rarely — categories, currencies, tax rates — especially @Immutable entities under READ_ONLY, which need no locking at all.
  • Win: find by id and the @NaturalId lookup (§11), which consult the cache before the database. JPQL never does, unless the query cache is on for that query.
  • Trap: entities written by anything other than this application. The cache does not know, and serves stale rows until the entry expires.
  • Trap: the query cache on a busy table. Every write to the table invalidates every cached query touching it, so the hit rate collapses while the bookkeeping cost stays.
  • Trap: caching to fix an N+1 problem. The queries are still issued; they are just served from memory. Fix the fetch plan (§5) first.

Measuring, and the pool underneath

Turn on hibernate.generate_statistics in any environment where you are investigating — it is cheap — and read getPrepareStatementCount, getEntityLoadCount, getCollectionFetchCount and getQueryExecutionCount around the operation you care about. getQueryExecutionMaxTime is also there; it was deliberately never printed in this module because a wall-clock number is not reproducible, and that is also why it is a poor thing to assert on in a test. For a running service, hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS=50 logs every statement that exceeds the threshold, with its SQL, which is usually how a slow page is first located.

Beneath all of it sits the connection pool. The warning you have seen on every run in this module — Using built-in connection pool (not intended for production use) — is Hibernate telling you its bundled pool is a toy. Production uses HikariCP (hibernate-hikaricp, hibernate.hikari.maximumPoolSize), sized small: a pool of ten connections outperforms a pool of a hundred on most databases, because connections beyond the core count mostly queue inside the database instead of outside it. A transaction that holds a connection while it calls a remote service is the classic way to exhaust even a well-sized pool.

Performance gotchas
  • show_sql cannot show batching. It logs each logical statement. Only Statistics or the driver's own logging (p6spy, datasource-proxy) reveal what was actually sent.
  • A bulk JPQL statement bypasses the context. Entities already loaded keep stale values and a later flush can overwrite the bulk change with them. Clear first, or run the bulk statement in its own transaction.
  • @DynamicUpdate is not free. It writes only changed columns, but Hibernate must then build and prepare a different statement per combination of changed columns, which defeats statement caching. Use it for wide tables with hot contention, not by default.
  • Loading to count. findAll().size() hydrates the table; select count(p) from Product p moves one number.
  • The pool is the real ceiling. Ten slow queries with a pool of ten freeze every other request. Measure pool wait time before adding threads.

Check yourself

1.You set hibernate.jdbc.batch_size=50, insert 1,000 Order entities in one transaction, and Statistics still reports 1,000 prepared statements. Which is the most likely cause?

C. Exactly phase A of the worked example. An IDENTITY id exists only after the row is inserted, Hibernate needs the id to manage the entity, so persist cannot be deferred and there is never a queue to batch. Switch to SEQUENCE.

A is false: inserts, updates and deletes all batch. B is false: commit flushes, and the queued statements are batched then. D is false: H2 supports batching, and phase B proved it on this very database.

2.A report page lists 5,000 products with their SKU and price. It runs select p from Product p and maps each entity to a row. The query takes 40 ms; the page takes 900 ms. What is the first change to make?

B. The database is not the problem (40 ms); hydrating 5,000 managed entities, snapshotting each one and scanning them all at flush is. A projection hydrates nothing — the worked example showed entities hydrated = 0 — and the mapping step disappears too.

A and C keep the 5,000-entity hydration; they only skip the 40 ms query. D affects writes, and this page writes nothing.

3.Which statements about Hibernate's caches are true? Select all that apply.

A and D. The second-level cache is a map from id to row state; a query has to run to discover which ids match. The query cache keys on the query and its parameters and is dropped whenever a touched table changes, which is why it rarely pays on busy tables.

B describes the second-level cache; the first-level cache is the persistence context, one per EntityManager. C is wrong: the query cache stores ids (and scalar values) and then looks each entity up in the second-level cache, or in the database if it is not there — which can turn one cached query into N lookups.
