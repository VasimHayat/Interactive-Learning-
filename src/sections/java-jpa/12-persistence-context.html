Section 3

The persistence context and the entity lifecycle

Everything surprising about JPA — the update you never wrote, the second find that hits no database, the change that silently vanished — comes from one object: the persistence context. An EntityManager owns one. It is two things at once: an identity map (for each primary key, at most one Java instance) and a snapshot store (a copy of every managed entity's state as it was loaded). Hibernate uses the first to answer loads from memory and the second to work out, at flush time, which rows changed and what SQL to emit for them. That second mechanism is called dirty checking, and it is why you never call an update method: there is none.

An entity instance is always in exactly one of four states relative to a context. Transient: a plain Java object the context has never seen, no row behind it. Managed: tracked by a context; changes to it will be written at flush. Detached: it has a row, but no context is watching it any more — the context was closed or the instance was evicted. Removed: scheduled for deletion at flush. Every EntityManager method you call is a transition between those states, and the worked example walks all of them.

Worked example: one entity, nine transitions

Read the Hibernate: lines as closely as the prose. Where SQL appears, and where it does not, is the lesson.

import jakarta.persistence.*;

public class Lifecycle {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;
        private int priceInCents;

        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        Long id() { return id; }
        String sku() { return sku; }
        int priceInCents() { return priceInCents; }
        void setPriceInCents(int p) { this.priceInCents = p; }
        @Override public String toString() { return "Product[" + id + ", " + sku + ", " + priceInCents + "c]"; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Product.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:Lifecycle;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();
    }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {

            System.out.println("-- 1. persist: transient -> managed, insert deferred to commit --");
            Long id;
            try (EntityManager em = emf.createEntityManager()) {
                Product bolt = new Product("BOLT-7", 80);
                System.out.println("managed before persist: " + em.contains(bolt));
                em.getTransaction().begin();
                em.persist(bolt);
                System.out.println("managed after persist:  " + em.contains(bolt) + ", id already assigned: " + (bolt.id() != null));
                em.getTransaction().commit();
                id = bolt.id();
            }

            System.out.println("-- 2. find twice in one context: one select, one instance --");
            try (EntityManager em = emf.createEntityManager()) {
                Product a = em.find(Product.class, id);
                Product b = em.find(Product.class, id);
                System.out.println("same instance: " + (a == b));
            }

            System.out.println("-- 3. dirty checking: a plain setter becomes an update at commit --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product p = em.find(Product.class, id);
                p.setPriceInCents(85);
                System.out.println("no SQL yet; committing...");
                em.getTransaction().commit();
            }

            System.out.println("-- 4. detach, then modify: nothing is written --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product p = em.find(Product.class, id);
                em.detach(p);
                p.setPriceInCents(999);
                em.getTransaction().commit();
                System.out.println("managed after detach: " + em.contains(p));
            }

            System.out.println("-- 5. merge a detached copy: select, then update; a different instance comes back --");
            Product detached;
            try (EntityManager em = emf.createEntityManager()) {
                detached = em.find(Product.class, id);     // loaded, then the context closes
            }
            detached.setPriceInCents(90);                       // modified outside any context
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product merged = em.merge(detached);
                System.out.println("merged == detached: " + (merged == detached)
                        + ", detached managed: " + em.contains(detached) + ", merged managed: " + em.contains(merged));
                em.getTransaction().commit();
            }

            System.out.println("-- 6. refresh discards an in-memory change --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product p = em.find(Product.class, id);
                p.setPriceInCents(1);
                em.refresh(p);
                System.out.println("after refresh: " + p.priceInCents() + "c");
                em.getTransaction().commit();
            }

            System.out.println("-- 7. flush: SQL now, visible inside the same transaction --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                em.persist(new Product("NUT-3", 25));
                em.flush();
                Number rows = (Number) em.createNativeQuery("select count(*) from product").getSingleResult();
                System.out.println("rows visible after flush: " + rows);
                em.getTransaction().commit();
            }

            System.out.println("-- 8. getReference: a proxy, no select until a field is read --");
            try (EntityManager em = emf.createEntityManager()) {
                Product ref = em.getReference(Product.class, id);
                System.out.println("is a proxy subclass: " + (ref.getClass() != Product.class));
                System.out.println("reading sku forces the load...");
                System.out.println("sku = " + ref.sku());
            }

            System.out.println("-- 9. remove: delete at commit --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product p = em.find(Product.class, id);
                em.remove(p);
                System.out.println("still managed? " + em.contains(p));
                em.getTransaction().commit();
                System.out.println("find after remove: " + em.find(Product.class, id));
            }
        }
    }
}

Nine blocks, nine lessons:

  1. persist is not insert. The only SQL at persist time is select next value for product_SEQ — Hibernate must know the id to register the instance in the identity map, and a SEQUENCE strategy lets it get one without inserting. The insert itself waits for the flush at commit. (With IDENTITY the insert would have to happen immediately — §2 explains why that disables batching.)
  2. The identity map answers the second find. One select, two calls, a == b. Inside one context an entity is loaded at most once; this is the first-level cache, and it is scoped to the EntityManager, not the application.
  3. Dirty checking. A plain setter on a managed instance, no further API call, and an update appears at commit. Hibernate compared the instance against the snapshot it took at load time. Note that the update sets every column (priceInCents=?,sku=?), not just the changed one — §9 shows @DynamicUpdate for the cases where that matters.
  4. Detached means invisible. After detach, the setter runs on a plain object as far as the context is concerned. Commit writes nothing. This is the state every entity is in once its EntityManager closes — which is most of the time in a web application.
  5. merge copies, it does not adopt. Hibernate loads the current row (the first select; the second comes from find inside the previous block), copies the detached object's state onto the managed instance, and returns that managed instance. The object you passed in is still detached: merged == detached: false. Keep using the return value, never the argument.
  6. refresh is the opposite of flush. It overwrites the in-memory state from the database; the 1c is gone and 90c is back.
  7. flush forces the SQL now, but not the commit. The native count(*) runs in the same transaction and sees the new row. Hibernate would in fact have flushed automatically before that query: in FlushModeType.AUTO any JPQL or native query triggers a flush first, so queries never miss pending writes. The explicit call just makes the order visible.
  8. getReference returns a proxy. No select runs until sku() is called. Use it to set an association (line.setOrder(em.getReference(Order.class, id))) without loading the target. The class is a runtime subclass generated by ByteBuddy — which is why entity classes and their accessors must not be final.
  9. remove is deferred too. The instance leaves the context immediately (still managed? false) but the delete runs at commit. The find afterwards goes to the database — the context no longer holds the instance — and returns null.

All six correct. The two that trip people up are merge, which never changes the state of its argument, and remove, which takes the instance out of the context immediately even though the delete waits for the flush. clear() is detach for every managed instance at once — and it also discards the action queue, so un-flushed changes are lost.

Flushing: when the SQL actually runs

The context is write-behind: operations are queued and run together at flush. A flush happens at commit, when you call flush(), and — in the default FlushModeType.AUTO — just before any JPQL, Criteria or native query that might otherwise read stale data. (Hibernate is clever about JPQL: it flushes only if the query touches a table with pending changes. For native SQL it cannot know, so it flushes every time.) FlushModeType.COMMIT switches the automatic pre-query flush off; a query can then return rows that your own pending writes contradict, which is occasionally what a bulk job wants and usually a bug.

At flush, Hibernate does not replay your calls in order. It sorts the queue: all inserts, then updates, then collection removals and additions, then deletes. That order keeps foreign keys satisfied in the common cases, and it is why "I removed the old row and persisted a new one with the same unique key" fails with a constraint violation — the insert runs first. The fix is flush() between the two, or a different key design.

  • Takes a transient instance and makes that instance managed. Returns void; keep using your reference.
  • Passing a detached instance throws: PersistentObjectException: detached entity passed to persist. Hibernate knows it is detached because the id is already set (or, with @Version, the version is).
  • Passing an instance whose id already exists in the context throws EntityExistsException; if the row exists only in the database, the duplicate surfaces at flush as a constraint violation.
  • Cascades along CascadeType.PERSIST associations (§4).
  • Takes a detached (or transient) instance, loads the current row if it is not already in the context, copies the state across, and returns the managed copy. Your argument is untouched.
  • Because it copies every field, a detached object with a stale or missing field overwrites the database with that stale value. A form that binds only three columns of a ten-column entity and merges it is the classic data-loss bug. Load, then set the three fields, instead.
  • With a transient instance (no id) it behaves like persist but still returns a copy.
  • Cascades along CascadeType.MERGE.

Persistence-context gotchas
  • The context grows until you clear it. A loop that persists a million rows keeps a million managed instances and a million snapshots in memory, and every auto-flush dirty-checks all of them. Batch jobs flush() then clear() every few hundred rows (§9).
  • An EntityManager is not thread-safe. It is a unit-of-work object, not a connection pool. Share the EntityManagerFactory; create an EntityManager per request or job and close it.
  • The first-level cache can lie to you — within a transaction. If another transaction updates a row after you loaded it, your find keeps returning the old state. That is correct repeatable-read behaviour, and refresh is the way out when you need the latest.
  • "No SQL ran" is not "nothing happened". Changes sit in the queue. A test that asserts on a native query without flushing first reads stale data — or, with native SQL, triggers a flush you did not expect.
  • Modifying an entity outside a transaction on a managed instance in an open context queues an update that may never run (no commit) — or runs at the next transaction's flush, long after the line that caused it. Keep modifications inside transaction boundaries.

1.Inside one transaction you call em.find(Product.class, 1L), then em.find(Product.class, 1L) again. Meanwhile another transaction committed a price change to that row. What does the second find return?

C. The identity map already holds key 1, so find returns that instance without touching the database. The context gives you repeatable reads for free, and it has no idea the row changed.

A and B would both need a select, which the first-level cache exists to avoid; refresh is how you ask for it. D only happens at write time, and only with a @Version column (§7) — a read never checks versions.

2.A controller receives a detached Product from a form, calls Product m = em.merge(product);, then product.setPriceInCents(200); and commits. What is in the database?

B. merge copies state onto a managed instance and returns it; the argument stays detached (merged == detached: false in the worked example). The setter on product is invisible to the context, so the merged state — the form's price — is what gets flushed.

A is the mistake the question is about: use m. C is backwards — merge does queue an update of the copied state. D is what persist would throw for a detached instance; merge accepts them by design.

3.Which of these cause SQL to be sent before commit(), in the default FlushModeType.AUTO? Select all that apply.

A and D. flush() runs the queue on demand, and a JPQL query over a table with pending changes triggers an automatic flush so the query cannot miss them.

B: with SEQUENCE only select next value runs at persist; the insert waits (it would run immediately with IDENTITY, which is one reason to avoid that strategy). C: a setter changes a Java field; the context notices at flush, not at the call.
