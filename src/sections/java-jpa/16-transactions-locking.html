Section 7

Transactions, flushing and locking

§3 said that a managed entity's changes reach the database "at flush". This section is about when that is, what a transaction has to do with it, and what happens when two users change the same row. The short version: a transaction is a unit of work — a set of changes that either all become visible to other users or none do — and the persistence context queues your writes until the latest safe moment inside it. Locking is how you decide what "safe" means when a second transaction is editing the same stock level at the same time.

Worked example 1: when SQL is actually sent

Four small transactions. Read the SQL interleaved with the printed lines: the position of each insert and update relative to the println around it is the point.

import jakarta.persistence.*;

public class Flushing {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;
        private int priceInCents;
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        Long id() { return id; }
        void setPriceInCents(int c) { priceInCents = c; }
        @Override public String toString() { return "Product[" + id + ", " + sku + ", " + priceInCents + "c]"; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Product.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:Flushing;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();
    }

    static long rowsInDatabase(EntityManagerFactory emf) {
        try (EntityManager em = emf.createEntityManager()) {          // a fresh context: sees only committed rows
            return ((Number) em.createNativeQuery("select count(*) from product").getSingleResult()).longValue();
        }
    }

    static void section(String title) { System.out.println("-- " + title + " --"); }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {

            section("1. a query flushes pending writes first, then rollback undoes them");
            try (EntityManager em = emf.createEntityManager()) {
                EntityTransaction tx = em.getTransaction();
                tx.begin();
                Product bolt = new Product("BOLT-7", 80);
                em.persist(bolt);                                            // no SQL yet: only scheduled
                System.out.println("persisted, id already assigned = " + bolt.id());
                long seen = em.createQuery("select count(p) from Product p", Long.class).getSingleResult();
                System.out.println("count inside the transaction = " + seen);
                tx.rollback();
                System.out.println("after rollback, em.contains(bolt) = " + em.contains(bolt));
            }
            System.out.println("rows committed = " + rowsInDatabase(emf));

            section("2. FlushModeType.COMMIT: the query does NOT see the pending insert");
            try (EntityManager em = emf.createEntityManager()) {
                em.setFlushMode(FlushModeType.COMMIT);
                EntityTransaction tx = em.getTransaction();
                tx.begin();
                em.persist(new Product("NUT-3", 25));
                long seen = em.createQuery("select count(p) from Product p", Long.class).getSingleResult();
                System.out.println("count inside the transaction = " + seen);
                tx.commit();                                                 // the insert happens here
            }
            System.out.println("rows committed = " + rowsInDatabase(emf));

            section("3. dirty checking: a changed field becomes an UPDATE at flush");
            try (EntityManager em = emf.createEntityManager()) {
                EntityTransaction tx = em.getTransaction();
                tx.begin();
                Product nut = em.createQuery("select p from Product p where p.sku = 'NUT-3'", Product.class).getSingleResult();
                nut.setPriceInCents(30);                                     // no em call at all
                System.out.println("field changed, nothing written yet");
                tx.commit();                                                 // flush compares snapshot → UPDATE
                System.out.println("committed " + nut);
            }

            section("4. a failure marks the transaction rollback-only");
            try (EntityManager em = emf.createEntityManager()) {
                EntityTransaction tx = em.getTransaction();
                tx.begin();
                em.persist(new Product("CAM-9", 2_300));
                try {
                    if (true) throw new IllegalStateException("price feed unavailable");
                } catch (IllegalStateException e) {
                    tx.setRollbackOnly();
                    System.out.println("caught '" + e.getMessage() + "', rollbackOnly = " + tx.getRollbackOnly());
                }
                try {
                    tx.commit();
                    System.out.println("commit() returned normally: Hibernate rolled back instead of committing");
                } catch (RollbackException e) {
                    System.out.println("commit refused: " + e.getClass().getSimpleName());
                }
                System.out.println("tx.isActive() = " + tx.isActive());
            }
            System.out.println("rows committed = " + rowsInDatabase(emf));
        }
    }
}

  1. A query flushes first. persist() obtained an id from the sequence immediately (ids are assigned at persist, not at flush) but sent no insert. The count query did: Hibernate's default FlushModeType.AUTO flushes pending changes before any query that might see them, so your own transaction never reads a stale answer. Then rollback() undid the insert at the database and evicted bolt from the context — a rolled-back entity is detached, and reusing it is a bug.
  2. FlushModeType.COMMIT defers everything. The same query now counts 0: the insert waited for commit(). Use this mode for a transaction that does many reads and one write at the end, when you can prove the reads do not depend on the write; it saves flush-time dirty checks on every query.
  3. Dirty checking. No em call touched nut, yet an update went out at commit. Hibernate kept a snapshot of the row when it loaded it and compared field by field at flush. Notice the SQL: set priceInCents=?,sku=? — every column, not just the changed one, because Hibernate caches one UPDATE statement per entity. @DynamicUpdate changes that at the cost of a statement per distinct change set.
  4. Rollback-only. After setRollbackOnly(), commit() did not commit — CAM-9 never reached the database — but it also did not throw. That is Hibernate's historical behaviour; the JPA specification says commit() on a rollback-only transaction throws RollbackException, and you get that by setting hibernate.jpa.compliance.transaction=true. In a container (Spring, Jakarta EE) the container does the equivalent and throws. Either way, never assume a returned commit() means "written" without checking the flag.

Flush order and the transaction boundary

At flush, Hibernate does not replay your calls in order. It sorts: all inserts (in persist order, respecting foreign-key dependencies), then all updates, then collection changes, then all deletes. This is why a remove() followed by a persist() of a row with the same unique key can fail with a constraint violation — the insert runs first. hibernate.order_inserts and hibernate.order_updates go further and group statements by entity type, which §9 needs for JDBC batching.

The boundary matters as much as the order. Code that runs after commit() but still uses the entities — sending an email with order.getLines(), say — works until the first lazy association, which throws LazyInitializationException because the context is closed (§5). And code that does side effects inside the transaction — calling a payment gateway before commit — can charge the card and then roll back the order. Do external calls after a successful commit, driven by what was committed.

Worked example 2: two pickers, one row

The classic lost update: two users read stock of 10, one picks 1 and writes 9, the other picks 2 and writes 8. The first pick has vanished. @Version is the JPA cure, and the SQL shows exactly how it works.

import jakarta.persistence.*;

public class OptimisticLock {

    @Entity(name = "StockLevel")
    @Table(name = "stock_level")
    public static class StockLevel {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;
        private int onHand;
        @Version
        private long version;                    // Hibernate owns this field: never set it yourself

        protected StockLevel() {}
        StockLevel(String sku, int onHand) { this.sku = sku; this.onHand = onHand; }
        Long id() { return id; }
        int onHand() { return onHand; }
        long version() { return version; }
        void pick(int qty) { onHand -= qty; }
        @Override public String toString() { return sku + " onHand=" + onHand + " v" + version; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(StockLevel.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:OptimisticLock;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();
    }

    static void section(String title) { System.out.println("-- " + title + " --"); }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {
            Long id;
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                StockLevel s = new StockLevel("BOLT-7", 10);
                em.persist(s);
                em.getTransaction().commit();
                id = s.id();
                System.out.println("seeded " + s);
            }

            section("two pickers load the same row");
            EntityManager picker1 = emf.createEntityManager();
            EntityManager picker2 = emf.createEntityManager();
            picker1.getTransaction().begin();
            picker2.getTransaction().begin();
            StockLevel copy1 = picker1.find(StockLevel.class, id);
            StockLevel copy2 = picker2.find(StockLevel.class, id);
            System.out.println("picker1 sees " + copy1);
            System.out.println("picker2 sees " + copy2);

            section("picker1 commits first: UPDATE ... where id=? and version=?");
            copy1.pick(1);
            picker1.getTransaction().commit();
            System.out.println("picker1 committed " + copy1);

            section("picker2 commits on a stale version");
            copy2.pick(2);
            try {
                picker2.getTransaction().commit();
                System.out.println("(unreachable)");
            } catch (RollbackException e) {
                System.out.println("commit failed: " + e.getClass().getSimpleName()
                    + " caused by " + e.getCause().getClass().getSimpleName());
            }
            picker1.close();
            picker2.close();

            try (EntityManager em = emf.createEntityManager()) {
                System.out.println("database row is " + em.find(StockLevel.class, id)
                    + " (picker1's write survived, picker2's was refused, nothing was lost)");
            }

            section("OPTIMISTIC_FORCE_INCREMENT: bump the version on a read");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                StockLevel s = em.find(StockLevel.class, id, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
                em.getTransaction().commit();
                System.out.println("after commit " + s);
            }

            section("PESSIMISTIC_WRITE: the database locks the row until commit");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                StockLevel s = em.find(StockLevel.class, id, LockModeType.PESSIMISTIC_WRITE);
                s.pick(3);
                em.getTransaction().commit();
                System.out.println("after commit " + s);
            }
        }
    }
}

  • The version column is just a column (version bigint not null) that Hibernate includes in every UPDATE's where: where id=? and version=?, with set version=? incrementing it. Picker 1's update matched 1 row (version 0 → 1). Picker 2's update, sent with the stale version=0, matched 0 rows, and Hibernate turned "0 rows updated" into OptimisticLockException, wrapped in RollbackException because it happened during commit. The database row shows picker 1's write; no update was silently overwritten.
  • What to do with the exception is a business decision, not a technical one. Re-read the row and retry the pick (stock is now 9, so picking 2 still works), or tell the user "someone else just changed this". What you cannot do is catch it and carry on with the same EntityManager: after the exception the context is in an undefined state and must be closed.
  • OPTIMISTIC_FORCE_INCREMENT bumped the version with an update … set version=? even though nothing else changed. Use it when reading a parent while editing its children, so that two users editing different lines of the same order still conflict — the version on the parent becomes the version of the aggregate.
  • PESSIMISTIC_WRITE appended for update to the select: the database locked the row until commit, so a second transaction's find with the same lock would wait instead of fail. This program could not show the waiting (a blocked second transaction would stall the build); the behaviour is that jakarta.persistence.lock.timeout milliseconds later the waiter gets PessimisticLockException (or LockTimeoutException, which does not roll back the transaction).

Choosing a locking strategy

  • The field may be int, long, their wrappers, or a timestamp (Instant, LocalDateTime). Prefer an integer: timestamps have clock resolution and clock-skew problems.
  • Never set, increment or expose a setter for it. Hibernate manages it; a mapped version that your code changes defeats the check.
  • Cost: one extra column and an extra predicate on each update. No locks, no waiting, no deadlocks — conflicts are detected, not prevented. Right for web applications where conflicts are rare and users can retry.
  • Hibernate-only alternative for legacy tables without a version column: @OptimisticLocking(type = OptimisticLockType.DIRTY) with @DynamicUpdate puts every changed column's old value in the where clause.
  • OPTIMISTIC lock mode (without FORCE_INCREMENT) re-checks the version at commit even if you did not modify the entity — for reads that must not have been overtaken.
  • PESSIMISTIC_WRITE → select … for update: exclusive row lock until commit. Readers using plain selects are not blocked on MVCC databases (PostgreSQL, Oracle, MySQL/InnoDB), only other lockers.
  • PESSIMISTIC_READ → for share where the dialect has it: others may read and share-lock, none may write.
  • PESSIMISTIC_FORCE_INCREMENT → locks and bumps @Version, for combining both schemes.
  • Set jakarta.persistence.lock.timeout (ms) as a hint or property; 0 means nowait on databases that support it. Without a timeout, a forgotten lock holder stalls everyone.
  • Lock rows in a consistent order (by id, by SKU — Advanced §3's rule in SQL clothing) or the database will detect a deadlock and kill one transaction with an exception you must handle.
  • Right for short, high-contention operations where a retry would be worse than a short wait: decrementing stock at checkout, allocating the next invoice number.

A user opens an edit form, goes to lunch, and saves at 2 p.m. No database transaction can span that — a connection held open for an hour is a connection the pool has lost. The pattern is detached entities with versions: load the entity in one short transaction, close the context, let the user edit the detached object (or a DTO carrying the version), and in a second short transaction merge() it back. Because the detached object still carries version=0, the merge's UPDATE … where version=0 fails if anyone else saved in between — the lost update is caught across an hour and two transactions. Hidden form fields carrying the version are not a hack; they are the mechanism.

What does not work: an EntityManager kept open across requests ("extended persistence context") outside a very controlled container-managed setup, and copying the version into a fresh entity by hand.

Transaction mistakes that cost real money
  • Side effects before commit. Charging a card, sending an email, calling another service inside the transaction: if the commit then fails, the side effect is already done. Do them after commit, from a record of what committed.
  • Catching an exception and continuing with the same context. Any exception from flush, commit or a query leaves the persistence context undefined. Roll back, close it, start again.
  • Reading the entity after rollback(). It is detached; its ids may refer to rows that were never committed.
  • Assuming commit() throws. Shown above: with Hibernate's defaults a rollback-only transaction rolls back quietly. Check getRollbackOnly() or turn on hibernate.jpa.compliance.transaction.
  • Pessimistic locks without timeouts, or in inconsistent order. A hung request becomes a hung system.
  • A @Version field with a setter. The first "helpful" refactoring that copies all fields from a DTO will write it and silently disable the check.

Check yourself

1.In worked example 1, why does an insert appear before the select count SQL in the first transaction, when the code called persist and then ran the query?

A. FlushModeType.AUTO (the default) flushes before executing a query whose result could be affected by pending changes. Section 2 of the same program proves the other half: with FlushModeType.COMMIT the same query counted 0 and the insert moved to commit().

B is false for SEQUENCE ids — the program printed the assigned id with no insert yet; only IDENTITY ids force an immediate insert (§2). C confuses the database with the ORM; H2 counts whatever is there. D is wrong: the transaction stayed open and was rolled back afterwards, undoing the insert.

2.Two transactions load the same StockLevel (version 3). The first changes it and commits. The second changes it and commits. With @Version mapped, what happens to the second commit?

B. That is the mechanism in worked example 2: the second session's where id=? and version=? carries the stale version, matches nothing, and Hibernate converts the unexpected row count into an exception. Nothing is overwritten.

A is what happens without @Version at the common isolation levels. C describes pessimistic locking (for update), which was not requested. D does not exist: Hibernate has no idea which of two conflicting values is right, and does not guess.

3.Which of these prevent the lost-update problem on a stock row? Select all that apply.

A and B. Optimistic locking detects the conflict at commit; pessimistic locking prevents it by making the second reader wait for the first writer. They solve the same problem with opposite trade-offs — retries versus waiting.

C only changes when within the transaction the write is sent; both transactions still write unconditionally. D concerns id generation and has nothing to do with concurrent updates of an existing row.
