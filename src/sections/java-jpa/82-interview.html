Rehearsal

Interview questions

Twelve questions that actually get asked about JPA and Hibernate, with the answer a strong candidate gives. Say your answer out loud before opening the reveal — recognising an answer and being able to produce one are different skills.

Easy  1. What is the persistence context?

It is the set of entities an EntityManager currently manages, implemented as two things: an identity map and a snapshot store. The identity map guarantees one Java instance per primary key inside one context — a second find for the same id returns the same object without touching the database, which is why it is also called the first-level cache. The snapshot store holds each managed entity's state as loaded; at flush time Hibernate compares the current state with the snapshot and emits an update for every row that differs. That is dirty checking, and it is why there is no update method on the API. The context is write-behind: operations are queued and flushed at commit, before a query that could see them, or on an explicit flush(). It is scoped to one EntityManager, which is cheap, single-threaded and meant to live for one unit of work.

Easy  2. What is the difference between persist and merge?

persist takes a transient object and makes that instance managed; it returns nothing, and passing a detached instance throws PersistentObjectException ("detached entity passed to persist"). With a SEQUENCE id it only asks the sequence for a value and queues the insert; with IDENTITY it must insert at once to learn the id. merge takes a detached (or transient) object, loads the current row if it is not already in the context, copies the argument's state onto the managed instance and returns that instance — the argument stays detached, so a setter called on it afterwards is lost. Because it copies every field, merging a half-populated object overwrites the columns it did not carry. The habit to recommend: load, modify the managed instance, commit; reach for merge only for a genuinely detached object, and always use its return value.

Easy  3. What does "owning side" mean, and what does mappedBy do?

A relational database stores a relationship in one place — a foreign-key column or a join-table row — while an object graph can hold it on both ends. JPA resolves that by declaring one side the owner: the side whose field maps to the column. For @ManyToOne/@OneToMany that is always the many side, because the foreign key lives in its table; for @ManyToMany it is the side that declares @JoinTable; for @OneToOne it is the side with @JoinColumn or @MapsId. mappedBy marks the other side as the inverse: Hibernate loads it, iterates it and cascades through it, but ignores it when deciding what to write. Add a line to order.getLines() without setting line.setOrder(order) and the row is inserted with a null foreign key. The fix is a sync helper that sets both sides, and the rule is that only the owning side's state reaches the database.

Easy  4. What causes the N+1 problem and how do you fix it?

Lazy associations load on first access, one query per instance. Query fifty orders and loop over order.getLines() and you run one query for the orders and fifty more for the lines — fifty-one round trips for a page that needed one. It is invisible in the code and in local tests because each query is tiny; it shows up as latency under network round-trip cost. You detect it by counting statements, with hibernate.generate_statistics or a proxy driver, never by reading the code. Three fixes, chosen per query: join fetch (or an entity graph) to bring the collection in the same statement; @BatchSize to load collections for several parents at once with an in (…) list; or a DTO projection that reads only the columns the screen needs and hydrates no entities. The non-fix is fetch = EAGER: it changes every load forever and does not even reduce the statement count for JPQL queries.

Medium  5. What is LazyInitializationException, and is open-session-in-view the answer?

It is thrown when a lazy proxy or collection is touched after the persistence context that owned it has closed — typically an entity returned from a service method and then rendered in a view, or serialised to JSON. The message names the collection role and the key: "no session". Open-session-in-view keeps the EntityManager open until the response is written, so the lazy loads succeed; I argue against it. It hides the exception while leaving every lazy load in place, now running N+1 from the template; it pins a database connection for the whole request including the rendering time; and it moves data access out of the layer that is supposed to own transactions. The right answers are to fetch what the view needs inside the service — join fetch, an entity graph, batch fetching — or to return a DTO that already contains it. Spring Boot's spring.jpa.open-in-view defaults to true, which is why so many teams meet this question late.

Medium  6. How does @Version work, and what exactly fails?

It is optimistic locking: a numeric (or timestamp) column that Hibernate includes in every update's where clause and increments in its set clause — update … set …, version=? where id=? and version=?. Two transactions read the row at version 0; the first commits and the row becomes version 1; the second's update still says where version=0, matches zero rows, and Hibernate turns that unexpected count into OptimisticLockException, wrapped in RollbackException because it happened at commit. Nothing was overwritten — the lost update was detected rather than prevented. The caller must close that context, re-read and retry, or report the conflict; the context after the exception is undefined. The field belongs to Hibernate: no setter, never copied from a DTO. The same version carried through a detached entity or a hidden form field makes the check work across an hour and two transactions, which is how long edit forms stay correct without holding a connection.

Medium  7. Why does GenerationType.IDENTITY hurt insert performance?

With an identity column the database assigns the key during the insert, and Hibernate must know the key to register the entity in the persistence context. So persist cannot queue the insert; it executes it immediately, reads the generated id back, and — to keep statement order — flushes any earlier queued inserts first. Write-behind is gone for that entity, and with it JDBC batching: a hundred persists are a hundred round trips whatever hibernate.jdbc.batch_size says, and the statistics prove it. With SEQUENCE the id comes from a select next value call, one per allocation block of fifty by default, the inserts wait for the flush, and with batching and ordered inserts a hundred rows become a handful of statements. IDENTITY is the right choice only when the database offers nothing else or writes are rare; on MySQL be aware that SEQUENCE falls back to a table generator.

Medium  8. What goes wrong when you paginate a query that uses join fetch?

A fetched collection multiplies the result rows: an order with three lines is three rows in the joined result. A SQL LIMIT 10 would therefore cut through the middle of some order's lines and return a partially initialised collection, which Hibernate refuses to do. Instead it drops the limit from the SQL, loads the whole result, and applies setFirstResult/setMaxResults in memory, logging HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory. For a large table that is the full table through the network on every page. The fix is two steps: page the parent entities with a plain query, then load their collections for that page with batch fetching or a second join fetch query restricted to those ids, or project a DTO. Related traps: two List collections cannot be join-fetched together (MultipleBagFetchException), and two Sets can, but produce a cartesian product.

Medium  9. SINGLE_TABLE or JOINED — how do you choose?

SINGLE_TABLE puts the whole hierarchy in one table with a discriminator column: a polymorphic query is one select, a subtype query is the same select with a discriminator predicate, inserts touch one table. The cost is that every subclass-specific column must be nullable, because rows of other subtypes have nothing to put there, so the database cannot enforce "a card payment always has a last-four". JOINED gives each subclass its own table sharing the parent's primary key: subclass columns can be NOT NULL, the schema is normalised, but a polymorphic query left-joins every subclass table and uses a case expression to decide the type, and inserts write two rows. My default is SINGLE_TABLE while the subclass-specific fields are few; I move to JOINED when they are many or must be constrained. TABLE_PER_CLASS — a union over every concrete table and no identity ids — almost never. A @MappedSuperclass is not inheritance mapping at all: it copies shared columns into each table and cannot be queried.

Hard  10. Why is hbm2ddl.auto=update not a migration strategy?

Because it only adds. It compares the mapping to the schema and creates missing tables and columns; it cannot rename a column, narrow a type, drop anything, move data between columns or add the not-null constraint to a column that already has nulls. Rename a field and you get a new empty column beside the old full one, silently. Nothing is reviewed, nothing is versioned, nothing can be rolled back, and the DDL it runs differs by dialect, so what worked on H2 in tests is not what runs on PostgreSQL. The alternative is boring and right: generate the DDL from the entities once as a starting point, hand-edit it into a versioned script, let Flyway or Liquibase apply scripts in order with checksums, and run validate at startup so the application refuses to boot against a schema it does not match. Two details people miss: validate checks tables and columns but not sequences or indexes, and setting the JPA property schema-generation.database.action=none alongside it silently disables the validation.

Hard  11. How should an entity implement equals and hashCode?

The constraint is that hashCode must not change while the object is in a hash-based collection, and a generated id does not exist until persist. So the obvious implementation — equals and hashCode on the id — breaks: add the entity to a HashSet, persist it, and contains returns false because it now hashes to a different bucket; the worked example prints exactly that. Three correct options. If there is an immutable business key, such as a SKU, use it for both. Otherwise use the id for equals (null-safe, so two transient instances are never equal) and return a constant from hashCode; every entity of that type shares a bucket, which is fine for the small sets entities live in, and the hash never moves. Or do not override at all and compare only within one context, where the identity map makes == correct. Never include a lazy @ManyToOne in either method, and never let Lombok's @Data generate them for an entity.

Hard  12. What does the second-level cache cache, and what does it not?

It caches entity state by primary key, shared across persistence contexts and backed by a provider such as JCache or Infinispan, for entities marked @Cacheable. A find or a lazy proxy resolution for a cached id skips the database; natural-id lookups and collections can be cached too if asked. It does not cache queries: select p from Product p where … still hits the database, and if you enable the separate query cache it stores only the matching ids, with a timestamp region that invalidates every cached result the moment any table in the query is written — which in a system that writes regularly makes it a cost, not a saving. Concurrency strategies matter: READ_ONLY for reference data, READ_WRITE or TRANSACTIONAL for data that changes, and any write outside Hibernate (a bulk JPQL statement, a migration, another service) leaves the cache stale. My rule: cache immutable reference entities, measure with statistics, and treat the query cache as a last resort.
