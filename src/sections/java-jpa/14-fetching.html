Section 5

Fetching: lazy, eager and the N+1 problem

When Hibernate loads an Order, what happens to its lines? The mapping says LAZY for collections by default, so Hibernate puts a proxy collection in the field: an object that knows which order it belongs to and nothing else. The first time you call size(), iterator() or get(0) on it, it runs a select … where order_id = ? and fills itself. That is exactly right for one order. For a list of five hundred orders in a loop it is one query for the list and five hundred more for the lines — the N+1 problem, the single most common performance bug in JPA applications, and one you cannot see in the code because every line of it looks innocent.

The cure is never "make it eager". fetch = EAGER on the mapping changes how every load behaves, forever, including the loads that did not need the lines, and (as the sandbox shows) does not even remove the extra statements for JPQL queries. The cure is to decide per query what the query needs and fetch that in one or two statements: join fetch, an entity graph, or batch fetching. This section measures all three against the problem with Hibernate's own statistics, so the numbers are facts rather than folklore.

Worked example: counting statements

Five orders, three lines each. The report in totalQty is the same every time; only the fetch plan changes. hibernate.generate_statistics lets the program count prepared statements, and the Hibernate: lines show what they were.

import jakarta.persistence.*;
import org.hibernate.Session;
import org.hibernate.SessionFactory;
import org.hibernate.stat.Statistics;
import java.util.ArrayList;
import java.util.List;

public class NPlusOne {

    @Entity(name = "Order")
    @Table(name = "orders")
    public static class Order {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        private String reference;
        @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)   // lazy by default
        private List lines = new ArrayList<>();
        protected Order() {}
        Order(String reference) { this.reference = reference; }
        List lines() { return lines; }
        void addLine(OrderLine l) { lines.add(l); l.order = this; }
    }

    @Entity(name = "OrderLine")
    @Table(name = "order_line")
    public static class OrderLine {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "order_id")
        private Order order;
        private String sku;
        private int qty;
        protected OrderLine() {}
        OrderLine(String sku, int qty) { this.sku = sku; this.qty = qty; }
        int qty() { return qty; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Order.class).managedClass(OrderLine.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:NPlusOne;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .property("hibernate.generate_statistics", "true")
            .createEntityManagerFactory();
    }

    // the "report": walks every order's lines — touching lines() initialises the collection
    static int totalQty(List orders) {
        int total = 0;
        for (Order o : orders) for (OrderLine l : o.lines()) total += l.qty();
        return total;
    }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {
            Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();

            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                for (int i = 1; i <= 5; i++) {
                    Order o = new Order("ORD-" + i);
                    o.addLine(new OrderLine("BOLT-7", i));
                    o.addLine(new OrderLine("NUT-3", i * 2));
                    o.addLine(new OrderLine("CAM-9", 1));
                    em.persist(o);
                }
                em.getTransaction().commit();
            }

            System.out.println("-- A. lazy default: 1 query for the orders, then 1 per order for its lines --");
            stats.clear();
            try (EntityManager em = emf.createEntityManager()) {
                List orders = em.createQuery("select o from Order o order by o.id", Order.class).getResultList();
                System.out.println("total qty: " + totalQty(orders) + ", statements: " + stats.getPrepareStatementCount());
            }

            System.out.println("-- B. join fetch: one query, lines arrive with their orders --");
            stats.clear();
            try (EntityManager em = emf.createEntityManager()) {
                List orders = em.createQuery(
                        "select o from Order o join fetch o.lines order by o.id", Order.class).getResultList();
                System.out.println("orders: " + orders.size() + " (no duplicates: Hibernate 6+ de-duplicates root entities)");
                System.out.println("total qty: " + totalQty(orders) + ", statements: " + stats.getPrepareStatementCount());
            }

            System.out.println("-- C. entity graph: the same plan, declared instead of written into the query --");
            stats.clear();
            try (EntityManager em = emf.createEntityManager()) {
                EntityGraph graph = em.createEntityGraph(Order.class);
                graph.addAttributeNodes("lines");
                List orders = em.createQuery("select o from Order o order by o.id", Order.class)
                                       .setHint("jakarta.persistence.fetchgraph", graph)
                                       .getResultList();
                System.out.println("total qty: " + totalQty(orders) + ", statements: " + stats.getPrepareStatementCount());
            }

            System.out.println("-- D. batch fetching (size 10): 1 + ceil(5/10) queries --");
            stats.clear();
            try (EntityManager em = emf.createEntityManager()) {
                em.unwrap(Session.class).setFetchBatchSize(10);   // same effect as @BatchSize(size = 10) on the mapping
                List orders = em.createQuery("select o from Order o order by o.id", Order.class).getResultList();
                System.out.println("total qty: " + totalQty(orders) + ", statements: " + stats.getPrepareStatementCount());
            }
        }
    }
}

Before the four phases, notice the seeding: fifteen separate insert statements, each its own round trip. §9 turns those into two batched statements. Now the phases, same report, same answer of 50 every time:

  • A — six statements. One for the orders, then the loop touches o.lines() five times and the proxy collection runs its select … where order_id=? each time. With 500 orders it would be 501. The cost is round trips, not rows: each query is tiny, and that is what makes N+1 invisible in a local test and ruinous over a network.
  • B — one statement. join fetch o.lines tells Hibernate to pull the lines in the same query. Fifteen result rows come back (each order repeated per line) and Hibernate assembles five Order objects with their collections already initialised. Since Hibernate 6 the duplicates are removed automatically; the old select distinct idiom is unnecessary and would only push a pointless DISTINCT to the database.
  • C — one statement, as a plan rather than a query. An entity graph says "when you run this query, also fetch lines". The query text stays reusable and the SQL is the same join — a left join this time, because a fetch graph must not drop orders that have no lines, whereas join fetch is an inner join unless you write left join fetch.
  • D — two statements. Batch fetching leaves the collection lazy but, when the first one is touched, loads it for up to ten orders at once with where order_id in (?, …). For 500 orders that is 1 + 50 statements, no cartesian product, and no change to the query. The ten placeholders are padded (Hibernate rounds the batch to a fixed size so the database can cache the plan) even though only five ids exist.

The exception you will meet first

A lazy collection needs its context to load itself. Close the EntityManager, keep the entity, touch the collection:

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

public class LazyInit {

    @Entity(name = "Order")
    @Table(name = "orders")
    public static class Order {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        private String reference;
        @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
        private List lines = new ArrayList<>();
        protected Order() {}
        Order(String reference) { this.reference = reference; }
        Long id() { return id; }
        List lines() { return lines; }
        void addLine(OrderLine l) { lines.add(l); l.order = this; }
    }

    @Entity(name = "OrderLine")
    @Table(name = "order_line")
    public static class OrderLine {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @ManyToOne(fetch = FetchType.LAZY, optional = false)
        @JoinColumn(name = "order_id")
        private Order order;
        private String sku;
        protected OrderLine() {}
        OrderLine(String sku) { this.sku = sku; }
    }

    public static void main(String[] args) {
        EntityManagerFactory emf = new PersistenceConfiguration("warehouse")
            .managedClass(Order.class).managedClass(OrderLine.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:LazyInit;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();

        Long id;
        try (EntityManager em = emf.createEntityManager()) {
            em.getTransaction().begin();
            Order o = new Order("ORD-1");
            o.addLine(new OrderLine("BOLT-7"));
            em.persist(o);
            em.getTransaction().commit();
            id = o.id();
        }

        Order detached;
        try (EntityManager em = emf.createEntityManager()) {
            detached = em.find(Order.class, id);          // lines is an uninitialised proxy collection
        }                                                 // the context that owned it is now closed

        System.out.println("order loaded, context closed; touching lines() ...");
        System.out.println("lines: " + detached.lines().size());   // LazyInitializationException escapes here
        emf.close();
    }
}

Exception in thread "main" org.hibernate.LazyInitializationException: Cannot lazily initialize collection of role 'LazyInit$Order.lines' with key '1' (no session)

The message names the collection role and the key, and the cause is always the same: the entity outlived its context. In a web application that context is usually the service method's transaction, and the touch happens later, in the view. The tempting fix is open session in view — keep the EntityManager open until the response is written — and it is a trap: it hides the exception while leaving every one of those lazy loads in place, now running N+1 from the template with a database connection pinned for the whole request. The real fixes are to fetch what the view needs inside the service (join fetch, entity graph) or to return a DTO that already contains it (§6, §9).

Fetching gotchas
  • EAGER is a mapping-level decision you cannot undo per query. A @ManyToOne left at its EAGER default drags the parent into every load of the child, and a chain of them (line → order → customer → account) loads half the schema for a find. Mark every @ManyToOne and @OneToOne LAZY and fetch deliberately.
  • EAGER does not even help JPQL. Only em.find turns an eager association into a join; a JPQL query runs the extra selects immediately after the main query instead — the same N+1, just without the loop.
  • A proxy is not the entity. ref.getClass() is a generated subclass, instanceof works but a pattern match on the concrete class fails, and Hibernate.unproxy(ref) or Hibernate.isInitialized(ref) are the tools when you must know. Also: accessing the proxy's id does not trigger a load — Hibernate knows the key — but any other getter does.
  • Pagination plus join fetch = in-memory paging. Hibernate cannot apply LIMIT to a joined result without truncating a collection, so it fetches everything and pages in Java, logging HHH90003004. Page the parents first, then batch-fetch the collections.
  • Lazy loading in toString, equals or a JSON serialiser is how N+1 and LazyInitializationException arrive from code you did not write. Keep associations out of toString, and never hand an entity to a serialiser; serialise a DTO.

Check yourself

1.A page lists 200 orders and shows each order's line count. The service runs select o from Order o and the template calls order.getLines().size() inside a transaction. How many SQL statements run?

C. The textbook N+1: size() initialises the proxy collection, which selects the lines for that one order. The worked example's phase A is this at N = 5.

A would need join fetch or an entity graph. B is what batch fetching with a size ≥ 200, or @Fetch(SUBSELECT), would give. D: size() loads the whole collection, not a count (Hibernate's @LazyCollection(EXTRA) once did a count and is deprecated); and the orders still cost one query.

2.You add fetch = FetchType.EAGER to Order.lines to fix that page. The page now runs select o from Order o again. What changed?

B. For a JPQL query, an eager collection is honoured by issuing the secondary selects immediately — the statement count does not drop. And because the setting lives on the mapping, a find(Order.class, id) on a checkout page that never shows lines now joins them in as well.

A is only what em.find does for eager associations. C: the query is legal. D: subselect fetching is an explicit Hibernate annotation, never a default.

3.An Order has List<OrderLine> lines and List<Note> notes, both lazy. A screen needs both for 50 orders. Which approaches work without an exception and without a cartesian product? Select all that apply.

B and D. Batch fetching loads each collection in in (…) chunks — three statements for 50 orders — with no joins to multiply. Two queries in one context also work: the second query's fetched notes attach to the Order instances the identity map already holds.

A throws MultipleBagFetchException: cannot simultaneously fetch multiple bags — two Lists cannot be joined in one result. C runs, but every order row is repeated lines × notes times: 50 orders with 10 of each is 5,000 rows for 1,050 useful ones, and it gets worse quadratically.
