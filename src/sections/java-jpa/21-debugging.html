Section 12

Reading the SQL and the exceptions

An ORM fails in two ways: slowly, by issuing more SQL than you imagined, and loudly, with an exception whose name is three wrappers away from the thing that went wrong. Both are diagnosable in minutes once you know where Hibernate reports what it does. This section is the toolkit: what to switch on, how to read what comes out, and a map from each common exception to its cause and its fix.

The first rule applies to both kinds of failure: look at the SQL. Hibernate never does anything to the database that it cannot show you. If a page is slow, the statement count explains it; if a commit fails, the statement that failed is in the log one line above the stack trace.

Worked example: nine failures, nine cause chains

Every exception below is provoked on purpose, caught, and printed as its cause chain — outermost first, following getCause() to the end. Read the chains before the prose: the outermost type is what your catch sees, the innermost is what Hibernate actually detected.

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;

public class Exceptions {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;
        private int priceInCents;
        @Version
        private int version;
        protected Product() {}
        Product(String sku, int priceInCents) { this.sku = sku; this.priceInCents = priceInCents; }
        Long id() { return id; }
        void setPriceInCents(int p) { this.priceInCents = p; }
        int priceInCents() { return priceInCents; }
    }

    @Entity(name = "Order")
    @Table(name = "orders")                          // ORDER is a reserved word in SQL
    public static class Order {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @ManyToOne(fetch = FetchType.LAZY)            // no cascade: the product must already be persistent
        private Product product;
        @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
        private List lines = new ArrayList<>();
        protected Order() {}
        Order(Product product) { this.product = product; }
        Long id() { return id; }
        List lines() { return lines; }
        void addLine(int qty) { OrderLine l = new OrderLine(this, qty); lines.add(l); }
    }

    @Entity(name = "OrderLine")
    @Table(name = "order_line")
    public static class OrderLine {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @ManyToOne(fetch = FetchType.LAZY)
        private Order order;
        private int qty;
        protected OrderLine() {}
        OrderLine(Order order, int qty) { this.order = order; this.qty = qty; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Product.class).managedClass(Order.class).managedClass(OrderLine.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:Exceptions;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "false")   // nine failure paths: the facts matter here, not the SQL
            .createEntityManagerFactory();
    }

    /* The exception you catch is rarely the one that explains the problem:
       JPA wraps Hibernate's, and commit wraps everything in RollbackException.
       Walk the cause chain and print every link, outermost first. */
    static String chain(Throwable t) {
        StringBuilder sb = new StringBuilder();
        for (Throwable c = t; c != null; c = c.getCause() == c ? null : c.getCause()) {
            if (sb.length() > 0) sb.append(" <- ");
            sb.append(c.getClass().getSimpleName());
        }
        return sb.toString();
    }

    interface Case { void run(EntityManager em) throws Exception; }

    static void attempt(EntityManagerFactory emf, String label, Case c) {
        EntityManager em = emf.createEntityManager();
        try {
            em.getTransaction().begin();
            c.run(em);
            em.getTransaction().commit();
            System.out.println(label + ": no exception");
        } catch (Exception e) {
            System.out.println(label + ": " + chain(e));
        } finally {
            if (em.isOpen()) {
                if (em.getTransaction().isActive()) em.getTransaction().rollback();
                em.close();
            }
        }
    }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {
            long boltId, orderId;
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product bolt = new Product("BOLT-7", 80);
                em.persist(bolt);
                em.persist(new Product("NUT-3", 25));
                Order o = new Order(bolt);
                o.addLine(2);
                o.addLine(5);
                em.persist(o);
                em.getTransaction().commit();
                boltId = bolt.id();
                orderId = o.id();
            }

            // 1. a lazy collection touched after the EntityManager is gone
            Order detachedOrder;
            try (EntityManager em = emf.createEntityManager()) {
                detachedOrder = em.find(Order.class, orderId);
            }
            try {
                System.out.println("1 lines on a closed context: " + detachedOrder.lines().size());
            } catch (RuntimeException e) {
                System.out.println("1 lines on a closed context: " + chain(e));
            }

            // 2. an association to an object that was never persisted
            attempt(emf, "2 order -> unsaved product", em -> {
                Order o = new Order(new Product("CAM-9", 2300));   // CAM-9 is transient
                em.persist(o);
            });

            // 3. persist() on an entity that already has an identity
            attempt(emf, "3 persist a detached entity", em -> {
                Product bolt = em.find(Product.class, boltId);
                em.detach(bolt);
                em.persist(bolt);
            });

            // 4 & 5. getSingleResult expects exactly one row
            attempt(emf, "4 single result, two rows", em ->
                em.createQuery("select p from Product p", Product.class).getSingleResult());
            attempt(emf, "5 single result, no rows", em ->
                em.createQuery("select p from Product p where p.sku = 'NOPE'", Product.class).getSingleResult());

            // 6. two contexts edit the same row; the second commit is stale
            EntityManager em1 = emf.createEntityManager();
            EntityManager em2 = emf.createEntityManager();
            try {
                em1.getTransaction().begin();
                em2.getTransaction().begin();
                Product first = em1.find(Product.class, boltId);
                Product second = em2.find(Product.class, boltId);
                first.setPriceInCents(81);
                em1.getTransaction().commit();                  // version 0 -> 1
                second.setPriceInCents(82);
                try {
                    em2.getTransaction().commit();              // expects version 0: refused
                    System.out.println("6 stale update: no exception");
                } catch (RuntimeException e) {
                    System.out.println("6 stale update: " + chain(e));
                }
            } finally {
                if (em2.getTransaction().isActive()) em2.getTransaction().rollback();
                em1.close(); em2.close();
            }

            // 7. a unique constraint, discovered only at flush
            attempt(emf, "7 duplicate sku", em -> em.persist(new Product("BOLT-7", 1)));

            // 8. a JPQL path that does not exist, discovered at query creation
            attempt(emf, "8 unknown attribute in JPQL", em ->
                em.createQuery("select p from Product p where p.colour = 'red'", Product.class).getResultList());

            // 9. a transaction marked rollback-only: commit() quietly becomes rollback()
            attempt(emf, "9 commit after setRollbackOnly", em -> {
                em.find(Product.class, boltId).setPriceInCents(999);
                em.getTransaction().setRollbackOnly();
            });
            try (EntityManager em = emf.createEntityManager()) {
                System.out.println("  price after that commit: " + em.find(Product.class, boltId).priceInCents());
            }

            // the context survived all of it: the data is intact
            try (EntityManager em = emf.createEntityManager()) {
                System.out.println("products still in the database: " +
                    em.createQuery("select count(p) from Product p", Long.class).getSingleResult());
            }
        }
    }
}

Nine lines, and each one teaches a rule about when Hibernate notices a problem:

  • 1 fails at access time, not at load time. The order loaded fine; the collection was left as a proxy, and the proxy's context was closed when it was first asked for its elements. Nothing in the stack trace points at the em.close() that caused it. §5 covers the fixes; the one that is not a fix is making the collection EAGER.
  • 2, 6 and 7 fail at flush, which happened inside commit(), which is why each chain starts with RollbackException. The real diagnosis is the innermost link: an unsaved reference, a stale version, a unique index. If you flushed explicitly you would see the inner exception directly and could still roll back on your own terms.
  • 3 fails immediately: persist refuses an object that already has an identifier. The JPA type is EntityExistsException; Hibernate's own message, one link in, is the famous detached entity passed to persist. The method you wanted was merge — or, more often, you wanted to keep the entity managed and never detach it.
  • 4 and 5 are query-contract failures. The doubled name in 4 is not a typo: Jakarta's NonUniqueResultException wraps Hibernate's class of the same simple name. Use getSingleResultOrNull() (JPA 3.2) or getResultStream().findFirst() when zero rows is a normal outcome.
  • 8 fails when the query is created, before any SQL exists: Hibernate parses JPQL against the mapped model, so a wrong attribute is caught as early as a compile error would be. Native SQL gives up that check.
  • 9 is the surprise: no exception at all. The JPA specification says commit() on a rollback-only transaction throws RollbackException; Hibernate, by default, silently rolls back instead and only throws if you set hibernate.jpa.compliance.transaction=true. The price check proves the write was discarded. If your code relies on commit failing to notice a problem, it never will.

What to switch on

.property("hibernate.show_sql", "true")        // print every statement to System.out — what this module uses
.property("hibernate.format_sql", "true")      // one clause per line; easier on a 40-join query, noisier on a page
.property("hibernate.highlight_sql", "true")   // ANSI colours; terminals only

show_sql writes to stdout, bypassing your logging framework entirely, which is why it is a development switch and not a production one. It also prints ? for every parameter; the bound values are a separate logging category (next tab). What it shows is exactly the statement text handed to JDBC, including Hibernate's generated aliases (p1_0) and column order.

Read a statement from its from clause outwards: which tables, joined how, then which columns, then the where. The things that should make you stop are a select inside a loop (the N+1 shape, §5), a select you did not expect before an update (a merge or a lazy load you forgot you triggered), and an update that writes every column when one changed (the default; @DynamicUpdate changes it, §9).

.property("hibernate.generate_statistics", "true")

Statistics st = emf.unwrap(SessionFactory.class).getStatistics();
st.clear();
// … the code you are measuring …
st.getPrepareStatementCount();     // how many SQL statements were prepared
st.getEntityLoadCount();           // entities materialised from rows
st.getEntityFetchCount();          // of those, how many were lazy loads triggered by a proxy  ← the N+1 counter
st.getCollectionFetchCount();      // lazy collections initialised
st.getFlushCount();                // auto flushes forced by queries
st.getSecondLevelCacheHitCount();  // zero until you configure a cache (§9)
st.getQueryExecutionMaxTimeQueryString();   // the slowest JPQL since clear()

Statistics are the tool for a test: assert that listing twenty orders prepares one statement, and the N+1 regression can never come back silently. They are cheap enough to leave on in production behind a metrics endpoint; logSummary() prints the whole set on shutdown.

# logging.properties (java.util.logging; the same category names work in Log4j and Logback)
org.hibernate.SQL.level = FINE                # every statement, through the logging framework (no show_sql needed)
org.hibernate.orm.jdbc.bind.level = FINER     # the parameter values bound to each ?
org.hibernate.orm.jdbc.extract.level = FINER  # the values read back from each ResultSet column
org.hibernate.stat.level = FINE               # per-query timing and row counts as they happen
org.hibernate.SQL_SLOW.level = INFO           # with hibernate.log_slow_query=250: statements slower than 250 ms

Prefer the logger to show_sql as soon as the application has a logging framework: it goes where every other log line goes, carries timestamps and thread names, and can be turned on for one category in a running JVM. The bind category is the one that answers why did this query return nothing? — it shows the actual value, and the actual type, that was sent.

Two tools sit between Hibernate and the driver and see everything, including statements Hibernate did not issue (a migration tool, a second ORM, hand-written JDBC):

  • datasource-proxy wraps a DataSource and can log, count, or assert on statements — its QueryCountHolder is the basis of the test-time N+1 detectors in several libraries.
  • p6spy is a JDBC driver wrapper that logs every statement with its parameters inlined, timings included, with no code change beyond the JDBC URL.

For the database's own view, EXPLAIN (or EXPLAIN ANALYZE) the statement text you copied out of the log, with the real parameter values from the bind category. Hibernate chose the statement; only the database can tell you whether it used an index.

A slow page: the six-step diagnosis

  1. Count the statements. Statistics or the proxy counter around the one request. A page that needs one query and runs sixty is not slow because of the database.
  2. Find the loop. Sixty near-identical select … where id=? lines are an N+1 (§5); getEntityFetchCount() names the entity being lazily loaded.
  3. Check the fetch plan. For each association the page touches: is it fetched by the query (join fetch, entity graph), batched (@BatchSize), or loaded one proxy at a time? Fix at the query, not the mapping.
  4. Check the flush count. A high getFlushCount() means queries kept forcing auto-flush of a dirty context — usually a long transaction that reads and writes alternately. Split it, or flush once at the end.
  5. Check the pool. If statements are few and fast but the request is slow, time is spent waiting for a connection: pool exhausted by long transactions, or a transaction held open across a remote call.
  6. EXPLAIN the worst statement. Only now is the database the suspect: a missing index, a cast that defeats an index (the bind category shows the type), or a select * of a table with a 4 MB blob column that a DTO projection would skip.

A word on Spring Data JPA, since most readers will meet Hibernate through it. It changes none of the above. @Transactional opens the transaction and the persistence context for you, and closes both when the method returns; JpaRepository methods such as findById and save are thin calls to find and persist-or-merge on an injected EntityManager; derived query methods are JPQL generated from the method name; @EntityGraph and @Query("… join fetch …") are how you fix N+1 there. The convenience hides the context's lifetime, which is exactly the thing this module has spent twelve sections making visible. When a Spring application misbehaves, the diagnosis is still the SQL and the statistics — and the exception map above is the same.

Debugging gotchas
  • The stack trace points at the commit, not the cause. A flush-time failure surfaces wherever the transaction ends. Flush explicitly in tests so the failing statement is next to the code that produced it.
  • An exception leaves the context unusable. After any PersistenceException the EntityManager may be inconsistent; roll back and discard it. Catching and carrying on inside the same context is how it fails only the second time bugs are born.
  • show_sql does not show parameter values. A query that returns nothing usually bound the wrong value or the wrong type; the bind log category shows both.
  • H2 is not your production database. It is excellent for this module and for fast tests, but it differs in locking, sequences, upsert syntax and type coercion. Run the integration suite against the real engine (Testcontainers makes that a one-line annotation).
  • Silence is not success. Case 9 above: Hibernate's default rollback-only behaviour never throws. A use case that ends without an exception has not necessarily written anything; read the outcome back when it matters.

Check yourself

1.A commit throws RollbackException. Where is the information that tells you what actually went wrong?

C. The worked example shows the shape: RollbackException <- ConstraintViolationException <- JdbcSQLIntegrityConstraintViolationException. The outer type only says commit failed; the inner ones say why.

A gives you a generic message. B is wrong — the chain is retained precisely so you can diagnose after rollback. D may also have it, but the JVM has it first and with the Java context.

2.A listing page runs 41 statements for 40 rows. Which statistic confirms the N+1 diagnosis most directly?

B. Fetch counts measure loads triggered by proxies — exactly the one-per-row pattern. Forty of them after one query is the fingerprint.

A measures auto-flushes forced by queries, a different problem. C is zero unless a cache is configured. D finds the slowest single query; an N+1 is forty fast queries.

3.Which of these are real consequences of putting Lombok's @Data on an entity with a bidirectional association? Select all that apply.

A, C and D. All-fields toString on both sides of a link is mutual recursion (A); walking an association to print or hash it initialises the proxy (C); and a hash that includes the generated id changes value when the id is assigned, so the Set looks in the wrong bucket (D, §11).

B is false: Hibernate maps the class happily, which is why the problems show up at runtime instead of at startup.

4.In the worked example, case 9 marks the transaction rollback-only and then calls commit(). Nothing is thrown. Why?

D. The specification mandates RollbackException; Hibernate chose leniency by default and gates the strict behaviour behind a compliance flag. The line price after that commit: 81 shows the work was indeed discarded.

A confuses the mechanism: a rollback discards the change whether or not it was flushed. B is wrong — attempt() prints any exception's chain, and would have. C is invented; rollback-only is a JPA-level flag, not a database feature.
