Section 8

Inheritance mapping

Tables do not inherit. A relational schema has no way to say "a CardPayment is a Payment with two extra columns", so when your Java model has a hierarchy — Intermediate §9's sealed Discount family, a Payment with card and bank-transfer variants — something has to decide how the hierarchy is laid out as rows. JPA offers three layouts, plus a fourth option that is not a layout at all. Each one is a real trade-off between normalisation, query cost and constraints, and the choice is visible in every statement Hibernate generates afterwards.

Worked example

Three small hierarchies, one per strategy, in a single factory so that the DDL for all of them appears together. Read the create table lines first, then the polymorphic queries.

import jakarta.persistence.*;
import java.time.LocalDate;
import java.util.List;

public class InheritanceMapping {

    /** Not an entity: its columns are copied into every entity table that extends it. */
    @MappedSuperclass
    public static abstract class Auditable {
        @Column(nullable = false)
        protected LocalDate createdOn = LocalDate.of(2026, 10, 15);
    }

    // ── SINGLE_TABLE: one table, a discriminator column, nullable subclass columns ──
    @Entity(name = "Discount")
    @Table(name = "discount")
    @Inheritance(strategy = InheritanceType.SINGLE_TABLE)
    @DiscriminatorColumn(name = "kind", length = 8)
    public static abstract class Discount extends Auditable {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        protected Long id;
        @Column(nullable = false, length = 16)
        protected String code;
        protected Discount() {}
        Discount(String code) { this.code = code; }
        abstract long apply(long cents);
        @Override public String toString() { return getClass().getSimpleName() + "(" + code + ")"; }
    }

    @Entity(name = "PercentOff") @DiscriminatorValue("PCT")
    public static class PercentOff extends Discount {
        private Integer percent;                 // Integer, not int: the column must be nullable for other kinds
        protected PercentOff() {}
        PercentOff(String code, int percent) { super(code); this.percent = percent; }
        int percent() { return percent; }
        @Override long apply(long cents) { return cents - cents * percent / 100; }
    }

    @Entity(name = "FixedOff") @DiscriminatorValue("FIX")
    public static class FixedOff extends Discount {
        private Integer offCents;
        protected FixedOff() {}
        FixedOff(String code, int offCents) { super(code); this.offCents = offCents; }
        @Override long apply(long cents) { return Math.max(0, cents - offCents); }
    }

    // ── JOINED: one table per class, subclass tables share the parent's primary key ──
    @Entity(name = "Payment")
    @Table(name = "payment")
    @Inheritance(strategy = InheritanceType.JOINED)
    public static abstract class Payment {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        protected Long id;
        protected long amountCents;
        protected Payment() {}
        Payment(long amountCents) { this.amountCents = amountCents; }
        @Override public String toString() { return getClass().getSimpleName() + "(" + amountCents + "c)"; }
    }

    @Entity(name = "CardPayment") @Table(name = "card_payment")
    public static class CardPayment extends Payment {
        @Column(nullable = false, length = 4)
        private String last4;                    // NOT NULL is possible: the column lives in its own table
        protected CardPayment() {}
        CardPayment(long amountCents, String last4) { super(amountCents); this.last4 = last4; }
    }

    @Entity(name = "BankTransfer") @Table(name = "bank_transfer")
    public static class BankTransfer extends Payment {
        @Column(nullable = false, length = 34)
        private String iban;
        protected BankTransfer() {}
        BankTransfer(long amountCents, String iban) { super(amountCents); this.iban = iban; }
    }

    // ── TABLE_PER_CLASS: one complete table per concrete class, polymorphic reads are a UNION ──
    @Entity(name = "Shipment")
    @Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
    public static abstract class Shipment {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)   // IDENTITY is impossible here: ids must be unique ACROSS tables
        protected Long id;
        protected int weightKg;
        protected Shipment() {}
        Shipment(int weightKg) { this.weightKg = weightKg; }
        @Override public String toString() { return getClass().getSimpleName() + "(" + weightKg + "kg)"; }
    }

    @Entity(name = "ParcelShipment") @Table(name = "parcel_shipment")
    public static class ParcelShipment extends Shipment {
        private String carrier;
        protected ParcelShipment() {}
        ParcelShipment(int weightKg, String carrier) { super(weightKg); this.carrier = carrier; }
    }

    @Entity(name = "FreightShipment") @Table(name = "freight_shipment")
    public static class FreightShipment extends Shipment {
        private int pallets;
        protected FreightShipment() {}
        FreightShipment(int weightKg, int pallets) { super(weightKg); this.pallets = pallets; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Discount.class).managedClass(PercentOff.class).managedClass(FixedOff.class)
            .managedClass(Payment.class).managedClass(CardPayment.class).managedClass(BankTransfer.class)
            .managedClass(Shipment.class).managedClass(ParcelShipment.class).managedClass(FreightShipment.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:InheritanceMapping;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();
    }

    static void section(String title) { System.out.println("-- " + title + " --"); }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {
            section("insert one of each");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                em.persist(new PercentOff("SPRING10", 10));
                em.persist(new FixedOff("WELCOME5", 500));
                em.persist(new CardPayment(12_000, "4242"));
                em.persist(new BankTransfer(250_000, "GB33BUKB20201555555555"));
                em.persist(new ParcelShipment(2, "DHL"));
                em.persist(new FreightShipment(900, 3));
                em.getTransaction().commit();
            }

            try (EntityManager em = emf.createEntityManager()) {
                section("SINGLE_TABLE polymorphic query: one select, filtered by the discriminator");
                List discounts = em.createQuery("select d from Discount d order by d.id", Discount.class).getResultList();
                for (Discount d : discounts) System.out.println(d + " applied to 10000c = " + d.apply(10_000));

                section("type() and treat(): asking for one subtype");
                System.out.println(em.createQuery("select d from Discount d where type(d) = PercentOff", Discount.class).getResultList());
                System.out.println(em.createQuery("select treat(d as PercentOff).percent from Discount d where type(d) = PercentOff", Integer.class).getResultList());

                section("JOINED polymorphic query: the parent table left-joins every subclass table");
                System.out.println(em.createQuery("select p from Payment p order by p.id", Payment.class).getResultList());

                section("JOINED subtype query: an inner join to the parent");
                System.out.println(em.createQuery("select c from CardPayment c", CardPayment.class).getResultList());

                section("TABLE_PER_CLASS polymorphic query: a UNION of every concrete table");
                System.out.println(em.createQuery("select s from Shipment s order by s.id", Shipment.class).getResultList());

                section("find() by id works for every strategy");
                System.out.println(em.find(Payment.class, 1L) + ", " + em.find(Shipment.class, 2L));
            }
        }
    }
}

Reading the schema

  • SINGLE_TABLE — discount. One table holds both subtypes; kind is the discriminator, with a check constraint Hibernate derived from the two @DiscriminatorValues. percent and offCents are nullable, and must be: a FIX row has no percent. That is the strategy's defining weakness — a subclass field can never be NOT NULL at the database level. It is also the fastest: a polymorphic read is one select … from discount, a subtype read is the same with where kind='PCT', and an insert is one row.
  • JOINED — payment, card_payment, bank_transfer. The parent table has the shared columns; each subclass table has its own columns plus the same primary key, enforced by a foreign key back to payment. last4 and iban are NOT NULL, because each lives in a table where every row has it. The price is in the queries: a polymorphic read is the parent left joined to every subclass table with a case when … then 1 … then 2 expression deciding the type per row, a subtype read is an inner join, and an insert is two statements.
  • TABLE_PER_CLASS — parcel_shipment, freight_shipment. No shipment table exists; each concrete class gets a complete table with the inherited columns copied in. A polymorphic read is a union all over every concrete table with a synthetic clazz_ column, which no index can help. Ids must be unique across the tables — hence one shared Shipment_SEQ — so IDENTITY generation is impossible here. Subtype reads and inserts are as cheap as they get, which is the only argument for it.
  • @MappedSuperclass — Auditable. Not an entity: no table, no discriminator, no polymorphic query. Its createdOn column simply appears in the discount table because Discount extends it. It is the right tool for "every entity has these audit columns" and the wrong tool for "I want to query all Auditable things".
  • type() and treat(). where type(d) = PercentOff became where d1_0.kind='PCT'; treat(d as PercentOff).percent let the query reach a subclass attribute. Under JOINED the same predicate becomes a test on which subclass table has a matching row.
  • The last line printed no SQL. Both find() calls were served from the persistence context — the earlier polymorphic queries had already loaded those rows. §3's first-level cache applies to subclasses exactly as it does to any entity.

Two rules cover most decisions. Start with SINGLE_TABLE; move to JOINED when the nullable columns become embarrassing or the subclass-specific columns outnumber the shared ones. And model the hierarchy for the data, not for code reuse: if two kinds of thing share behaviour but no identity — a Product and a ServicePlan are both priced — give them an interface in Java and separate tables, not a Priceable entity hierarchy.

Polymorphic associations follow the strategy: @ManyToOne Discount applied on an Order works for any of the three, and loads whichever subtype the row is. Only the root carries @Inheritance; writing it on a subclass is ignored. Hibernate 6+ also allows @ManyToOne to an interface implemented by several unrelated entities via @Any, which is a different, discriminator-plus-id mapping and best left for when nothing else fits.

Where hierarchies go wrong
  • Discriminator values are data. Rename the class PercentOff and nothing changes; rename the value PCT and every existing row is unreadable. Set @DiscriminatorValue explicitly rather than relying on the default (the entity name), and never change it without a migration.
  • SINGLE_TABLE plus a NOT NULL requirement. The column cannot be NOT NULL; add @Check(constraints = "kind <> 'PCT' or percent is not null") on the root so the database still refuses a broken row.
  • JOINED with a deep hierarchy. Each level is another join on every read and another insert on every write. Three levels is the practical ceiling.
  • TABLE_PER_CLASS with IDENTITY. Fails at start-up: ids must be unique across the union, so a sequence or table generator is mandatory.
  • Associations to a @MappedSuperclass. @ManyToOne Auditable x is a mapping error; the target of an association must be an entity.
  • Querying the root when you meant a subtype. select p from Payment p under JOINED left-joins every subclass table even if your code immediately checks instanceof CardPayment. Ask for CardPayment.

Check yourself

1.In the worked example, PercentOff.percent is declared Integer and the column is created nullable, while CardPayment.last4 is NOT NULL. Why the difference?

C. The strategy decides it. A single shared table must tolerate every subtype's absent fields, which is the one hard limitation of SINGLE_TABLE; the @Check constraint in the gotcha callout is the workaround. In JOINED (and TABLE_PER_CLASS) the subclass column lives where every row has a value, so the constraint is honest.

A is false — nullable is set by annotation, not by Java type, and a primitive int percent would have produced not null and then failed on the first FixedOff insert. B misses that adding nullable = false to percent would make the program fail. D is invented; the discriminator column itself carries a check constraint in the DDL.

2.Which strategy cannot use GenerationType.IDENTITY, and why?

B. A polymorphic read is a union all over the concrete tables, and find(Shipment.class, 2L) only makes sense if id 2 exists in exactly one of them. Identity columns are per table, so two tables would both hand out 2. The worked example therefore shares one Shipment_SEQ sequence, and Hibernate rejects IDENTITY here at start-up.

A is backwards: under JOINED the parent row is inserted first and its generated id is reused for the subclass row — IDENTITY works fine. C is invented. D is the belief that fails at boot.

3.Which statements about a @MappedSuperclass are true? Select all that apply.

A and C. A mapped superclass contributes mappings, not identity: its fields are copied into each subclass's table as if declared there, and no table or discriminator exists for it. That is exactly why audit columns and shared id fields are its natural use.

B fails — it is not an entity, so it has no name in JPQL and no polymorphic query. D is a mapping error for the same reason: associations target entities, and a foreign key needs a table to point at.
