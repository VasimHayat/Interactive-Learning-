Section 4

Relationships and the owning side

A relational database stores a relationship in exactly one place: a foreign-key column, or a row in a join table. An object graph stores it in two — order.getLines() and line.getOrder() are both references, and nothing forces them to agree. JPA bridges that gap with a rule that explains most relationship bugs: one side owns the column, and only writes to the owning side reach the database. The other side, marked mappedBy, is the inverse side: Hibernate loads it, iterates it, cascades through it, but never consults it when deciding what to write.

For @ManyToOne / @OneToMany the owning side is always the many side, because that is the table holding the foreign key — an order_line row has one order_id; an orders row has nowhere to put a list. For @ManyToMany neither table has the key; the side that declares @JoinTable owns the join table. For @OneToOne you choose: the side with @JoinColumn owns the key, and @MapsId lets the dependent row reuse the parent's primary key instead of adding a second column.

Worked example: five associations, and the bug in block 1

Block 1 does what every beginner does — adds the line to the order's list and persists both — and the database quietly stores a line that belongs to nobody. Block 2 fixes it with a two-line helper. The rest of the program maps a many-to-many, a shared-key one-to-one, orphan removal and cascading delete, and shows the SQL each one costs.

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

public class Relationships {

    @Entity(name = "Product")
    @Table(name = "product")
    public static class Product {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true, length = 16)
        private String sku;

        // many-to-many: THIS side owns the join table because it declares @JoinTable
        @ManyToMany
        @JoinTable(name = "product_supplier",
                   joinColumns = @JoinColumn(name = "product_id"),
                   inverseJoinColumns = @JoinColumn(name = "supplier_id"))
        private Set suppliers = new HashSet<>();

        // one-to-one, inverse side: the FK (shared primary key) lives in product_details
        @OneToOne(mappedBy = "product", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
        private ProductDetails details;

        protected Product() {}
        Product(String sku) { this.sku = sku; }
        Long id() { return id; }
        String sku() { return sku; }
        Set suppliers() { return suppliers; }
        void addSupplier(Supplier s) { suppliers.add(s); s.products.add(this); }
        void setDetails(ProductDetails d) { this.details = d; d.product = this; }
    }

    @Entity(name = "Supplier")
    @Table(name = "supplier")
    public static class Supplier {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @Column(nullable = false, unique = true)
        private String name;
        @ManyToMany(mappedBy = "suppliers")                // inverse: never written from here
        private Set products = new HashSet<>();
        protected Supplier() {}
        Supplier(String name) { this.name = name; }
        String name() { return name; }
    }

    @Entity(name = "ProductDetails")
    @Table(name = "product_details")
    public static class ProductDetails {
        @Id
        private Long id;                                   // no @GeneratedValue: copied from product
        @OneToOne(fetch = FetchType.LAZY)
        @MapsId                                            // "my primary key IS the product's primary key"
        @JoinColumn(name = "product_id")
        private Product product;
        private String description;
        protected ProductDetails() {}
        ProductDetails(String description) { this.description = description; }
        Long id() { return id; }
        String description() { return description; }
    }

    @Entity(name = "Order")
    @Table(name = "orders")                                // ORDER is a reserved word in SQL
    public static class Order {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        private String reference;

        // inverse side: the FK order_id lives in order_line, so this side is mappedBy
        @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
        private List lines = new ArrayList<>();

        protected Order() {}
        Order(String reference) { this.reference = reference; }
        Long id() { return id; }
        List lines() { return lines; }

        // the sync helper: sets BOTH sides, so the owning side gets written
        void addLine(OrderLine line) { lines.add(line); line.order = this; }
        void removeLine(OrderLine line) { lines.remove(line); line.order = null; }
    }

    @Entity(name = "OrderLine")
    @Table(name = "order_line")
    public static class OrderLine {
        @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
        private Long id;
        @ManyToOne(fetch = FetchType.LAZY)                 // optional by default, so a line CAN exist with no order
        @JoinColumn(name = "order_id")                     // owning side: this column IS the relationship
        private Order order;
        private String sku;
        private int qty;
        protected OrderLine() {}
        OrderLine(String sku, int qty) { this.sku = sku; this.qty = qty; }
        Long id() { return id; }
        String sku() { return sku; }
    }

    static EntityManagerFactory emf() {
        return new PersistenceConfiguration("warehouse")
            .managedClass(Product.class).managedClass(Supplier.class).managedClass(ProductDetails.class)
            .managedClass(Order.class).managedClass(OrderLine.class)
            .property(PersistenceConfiguration.JDBC_URL, "jdbc:h2:mem:Relationships;DB_CLOSE_DELAY=-1")
            .property(PersistenceConfiguration.JDBC_USER, "sa")
            .property(PersistenceConfiguration.JDBC_PASSWORD, "")
            .property(PersistenceConfiguration.SCHEMAGEN_DATABASE_ACTION, "drop-and-create")
            .property("hibernate.show_sql", "true")
            .createEntityManagerFactory();
    }

    static long count(EntityManager em, String sql) {
        return ((Number) em.createNativeQuery(sql).getSingleResult()).longValue();
    }

    public static void main(String[] args) {
        try (EntityManagerFactory emf = emf()) {

            System.out.println("-- 1. setting only the inverse side: the FK is never written --");
            Long orphanOrderId;
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Order o = new Order("WRONG-1");
                OrderLine line = new OrderLine("BOLT-7", 10);
                o.lines().add(line);                       // inverse side only: line.order stays null
                em.persist(o);
                em.persist(line);
                em.getTransaction().commit();
                orphanOrderId = o.id();
            }
            try (EntityManager em = emf.createEntityManager()) {
                System.out.println("order_line rows with order_id null: " + count(em, "select count(*) from order_line where order_id is null"));
            }

            System.out.println("-- 2. the sync helper sets the owning side: FK written, lines cascaded --");
            Long orderId;
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Order o = new Order("ORD-1");
                o.addLine(new OrderLine("BOLT-7", 10));
                o.addLine(new OrderLine("NUT-3", 40));
                o.addLine(new OrderLine("CAM-9", 1));
                em.persist(o);                             // cascade = ALL persists the lines too
                em.getTransaction().commit();
                orderId = o.id();
            }
            try (EntityManager em = emf.createEntityManager()) {
                System.out.println("order_line rows for ORD-1: " + count(em, "select count(*) from order_line where order_id = " + orderId));
            }

            System.out.println("-- 3. orphanRemoval: dropping a line from the collection deletes the row --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Order o = em.find(Order.class, orderId);
                OrderLine cam = o.lines().stream().filter(l -> l.sku().equals("CAM-9")).findFirst().orElseThrow();
                o.removeLine(cam);
                em.getTransaction().commit();
                System.out.println("lines left: " + count(em, "select count(*) from order_line where order_id = " + orderId));
            }

            System.out.println("-- 4. many-to-many: the @JoinTable side writes the join rows --");
            Long boltId;
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Supplier acme = new Supplier("Acme Fasteners");
                Supplier zeta = new Supplier("Zeta Metals");
                Product bolt = new Product("BOLT-7");
                bolt.addSupplier(acme);
                bolt.addSupplier(zeta);
                em.persist(acme); em.persist(zeta); em.persist(bolt);   // no cascade on many-to-many
                em.getTransaction().commit();
                boltId = bolt.id();
            }
            try (EntityManager em = emf.createEntityManager()) {
                Product bolt = em.find(Product.class, boltId);
                Set names = new TreeSet<>();
                for (Supplier s : bolt.suppliers()) names.add(s.name());
                System.out.println("suppliers of BOLT-7: " + names);
                System.out.println("join rows: " + count(em, "select count(*) from product_supplier"));
            }

            System.out.println("-- 5. one-to-one with @MapsId: the details row reuses the product's id --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                Product bolt = em.find(Product.class, boltId);
                bolt.setDetails(new ProductDetails("M8 hex bolt, zinc plated"));
                em.getTransaction().commit();              // cascade ALL on the one-to-one persists it
            }
            try (EntityManager em = emf.createEntityManager()) {
                ProductDetails d = em.find(ProductDetails.class, boltId);
                System.out.println("details id == product id: " + d.id().equals(boltId) + ", " + d.description());
            }

            System.out.println("-- 6. cascade REMOVE: deleting the order deletes its lines first --");
            try (EntityManager em = emf.createEntityManager()) {
                em.getTransaction().begin();
                em.remove(em.find(Order.class, orderId));
                em.getTransaction().commit();
                System.out.println("order_line rows left: " + count(em, "select count(*) from order_line"));
            }
        }
    }
}

Reading the schema first: order_line.order_id is nullable because the @ManyToOne is optional by default — that is what lets block 1 store an orphan instead of failing. Add optional = false and the column becomes not null, block 1 fails at flush with PropertyValueException, and every join Hibernate generates for the association becomes an inner join instead of a left join. Prefer that whenever the business rule really is "a line always belongs to an order". Then the six blocks:

  1. The inverse side is ignored for writes. o.lines().add(line) changes the Java object only. Hibernate inserts the line from its state — and line.order is null — so the foreign key is null. No error, no warning: a row that no order will ever find.
  2. The helper sets both sides. addLine writes line.order = this, the owning side, and the FK is populated. cascade = ALL also means em.persist(o) reaches the three lines; the three inserts follow the order's. Note order_id = 2: block 1's order took id 1.
  3. orphanRemoval turns "no longer in the collection" into delete. Removing CAM-9 from the list produces exactly one delete from order_line where id=?. Without orphanRemoval, the same code would leave the row in place with order_id nulled — because a List element disappearing is not, by itself, a deletion.
  4. Many-to-many rows come from the @JoinTable side. addSupplier adds to Product.suppliers (owning) and Supplier.products (inverse); only the first matters for the two product_supplier inserts. Look at the find(Product) afterwards: it also runs a select … from product_details. That lazy @OneToOne(mappedBy) on the inverse side cannot be lazy — Hibernate must know whether to put null or a proxy in the field, and the only way to know is to query. The gotcha callout covers the fix.
  5. @MapsId shares the primary key. product_details has no id of its own; its product_id is both primary key and foreign key, so d.id().equals(boltId). Hibernate copied the parent's id when it persisted the dependent entity through the cascade.
  6. Cascade REMOVE orders the deletes correctly. Lines first, then the order, so the foreign key constraint never complains. The surviving row is block 1's orphan — the database kept it because nothing references it.

A List without @OrderColumn is what Hibernate calls a bag: unordered, duplicates allowed, and — because the database cannot tell two equal rows apart — some changes are implemented by deleting every row and re-inserting the survivors. Removing one element from a 500-element bag on the owning side of a @ManyToMany is 1 delete-all plus 499 inserts. A Set can address rows individually and emits one delete. Two bags also cannot be join fetched together (§5).

  • Set for @ManyToMany and for any collection you will join fetch alongside another.
  • List + @OrderColumn(name = "position") when order is part of the data (steps in a recipe). Hibernate maintains the column — at the cost of updating every later row on an insert in the middle.
  • List with @OrderBy("sku") only sorts on load; it is still a bag for writes. Fine for a mappedBy side with cascaded children, which is the case in the worked example.

A @OneToMany with no @ManyToOne on the other side and no @JoinColumn has nowhere to put the foreign key, so Hibernate invents a join table (orders_order_line) and maintains it with extra inserts and deletes — a surprise in the DDL and a tax on every write. Add @JoinColumn(name = "order_id") to the collection to put the key where you expected it; better, make the association bidirectional and let the many side own it, which is the mapping the database actually wants.

Relationship gotchas
  • The inverse @OneToOne is eager whatever you write. Block 4 proves it: find(Product) also selected product_details. Hibernate cannot create a proxy for a field that might legitimately be null without querying. Fixes: map the association only from the dependent side (drop Product.details), use @MapsId on the owning side so the parent's id is the key (then Hibernate can proxy), or enable bytecode enhancement.
  • Never put a @ManyToOne entity in equals/hashCode of the child — a lazy proxy's class is not the entity's class, and comparing it loads it. And never add an entity to a HashSet before its id is generated if hashCode uses the id: the hash changes after persist and the set can no longer find it (§11).
  • Cascading REMOVE through a @ManyToMany deletes the supplier when you delete the product. Nothing in the mapping warns you.
  • Bidirectional sync is your job. Forgetting the inverse side will not corrupt the database (only the owning side is written) but it will give you an in-memory order that does not list its own lines until reloaded — and a test that passes against the database while the object graph is wrong.
  • @JoinColumn names default to field_referencedId. Without it the column is order_id only because the field is order; rename the field and the schema changes. Always name the column.

Check yourself

1.In a bidirectional Order – OrderLine mapping, which side is the owning side, and why?

B. The owning side is the side that maps the physical column. A one-row-per-line foreign key can only live in order_line, so OrderLine.order owns the relationship and Order.lines must be mappedBy.

A and D confuse ownership with cascade — cascade decides which operations propagate, not which side is written. C is invented; ownership is fixed in the mapping, not by call order.

2.Product has @ManyToMany(cascade = CascadeType.ALL) Set<Supplier> suppliers. You call em.remove(product). What happens to Acme Fasteners, a supplier that also supplies forty other products?

C. REMOVE cascades to the entity on the other side, not to the join rows. Hibernate queues delete from supplier; whether that succeeds depends only on the database's constraints. Either outcome is wrong, which is why cascade REMOVE (and therefore ALL) has no place on a many-to-many.

A is what happens without cascade — Hibernate always cleans this product's join rows. B: Hibernate does not check for other references; the database might. D: cascade applies to every association type.

3.Which statements about orphanRemoval = true on Order.lines are correct? Select all that apply.

A and C. Orphan removal watches the collection: an element that leaves it is deleted. That is also why re-parenting is risky — the removal schedules a delete even though another order now references the line.

B: REMOVE cascades a remove call on the parent; it does nothing when an element merely leaves the collection. The two are complementary, not equal. D: without orphan removal, and with the many side owning the key, removing from the inverse collection changes nothing in the database — the line's own order field still points at the order. Only the sync helper's line.order = null would null the column.
