Cheat sheet

Everything worth having in front of you while a persistence layer is misbehaving. This section is laid out to print cleanly — controls and navigation are hidden, and tables are kept whole across page breaks. Each block names the section it condenses. Where a fact is specific to the pinned stack (Hibernate 7.4, JPA 3.2, H2), it says so.

Cascade and orphan removal §4

When to cascade and when not to
SituationUseNever
Parent owns children that cannot exist alone (order → lines)cascade = ALL, orphanRemoval = true on the parent's collection—
Reference to a shared entity (line → product, product ↔ supplier)no cascade; persist the target yourself or getReference itREMOVE on @ManyToOne or @ManyToMany — deletes the shared row
Remove a child from the parent's collection and delete its roworphanRemoval = truerelying on cascade = REMOVE (that only fires when the parent is removed)
Keep both sides of a bidirectional pair consistenta sync helper: lines.add(l); l.order = this;setting only the inverse side — the FK is written as null
 
// Bidirectional one-to-many, done the way that writes the foreign key
@Entity(name = "Order") @Table(name = "orders")
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List lines = new ArrayList<>();

    public void addLine(OrderLine line)    { lines.add(line);    line.setOrder(this); }   // both sides, always
    public void removeLine(OrderLine line) { lines.remove(line); line.setOrder(null); }   // orphanRemoval deletes the row
}

@Entity(name = "OrderLine") @Table(name = "order_line")
public class OrderLine {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) private Long id;
    @ManyToOne(fetch = FetchType.LAZY, optional = false)      // LAZY: never let a line drag its order in
    @JoinColumn(name = "order_id")                            // name the column; the default follows the field name
    private Order order;
    void setOrder(Order order) { this.order = order; }
}

Isolation is the connection's default (READ_COMMITTED on PostgreSQL, Oracle, SQL Server, H2; REPEATABLE_READ on MySQL/InnoDB); JPA sets none. Inside one context you have repeatable reads anyway, via the identity map.

// Optimistic retry: re-read and re-apply, never reuse the failed EntityManager
int attempts = 0;
while (true) {
    attempts++;
    try (EntityManager em = emf.createEntityManager()) {
        em.getTransaction().begin();
        StockLevel s = em.find(StockLevel.class, id);     // fresh copy, current version
        s.pick(qty);                                      // the business change
        em.getTransaction().commit();                     // update … where id=? and version=?
        return attempts;
    } catch (RollbackException e) {
        if (!(e.getCause() instanceof OptimisticLockException) || attempts >= 3) throw e;
        // someone else committed first: loop, with a fresh context
    }
}

Never put a lazy @ManyToOne in equals or toString. Lombok @Data on an entity generates all of the above wrongly at once. Callbacks: @PrePersist/@PreUpdate (and @EntityListeners) for audit fields; @SQLDelete + @SQLRestriction for soft delete — JPQL and find no longer see the row, native SQL still does; @Immutable for reference data (changes are silently ignored).
